# 設計レビュー（受け渡しの仕組み）

CLI とプラグインを繋ぐ仕組み（[受け渡しの作法](protocol.md)・`cli/internal/spool`・
[プラグインの設計](plugin/README.md)）を、拡張性・保守性・堅牢性の観点で見直した結果と、
各項目の扱いです。対象は protocol 3 の時点（`943b6e4`）の文書とコードです。

**反映したら、該当のページへ書き込み、この表の「扱い」を「済み」にします。** すべて済んだら
このページを消します（決めごとの真実は各ページに置き、ここには残さない）。

## 総評

ファイルとロックによる受け渡し、ロックだけによる生死の判定、「読む → 消す → 実行」による
二重実行の防止、`.tmp` からの rename による公開、受け付けの手順（`core::serve`）の SDK からの
分離は、いずれも妥当です。

残っている穴は、**呼ぶ側が待つのをやめた・異常終了したときの要求の扱い**に集中しています。
読む道具だけなら実害は小さいものの、書く道具（[未決 1](plugin/open-questions.md)）を足す前に
作法として決めておく必要があります。

## 1. 取り下げの成否を確かめていない

**現状**: `spool.Call` は締切を過ぎると `_ = os.Remove(requestPath)` で要求を消し、結果を見ずに
`ErrTimeout`（終了コード 4。「要求を取り下げた」）を返す。

**問題**: プラグインが要求を既に消して実行していれば、CLI の削除は失敗する。Windows では、
プラグインが要求を開いている間は共有違反で削除が失敗しうる（MSVC の `ifstream` は既定で
`FILE_SHARE_DELETE` を付けない）。どちらの場合も CLI は「取り下げた」と報告するが、要求は実行
される。呼ぶ側は「実行されていない」と「実行されたが応答を受け取れなかった」を区別できず、
書く道具では図面への二重の操作につながる。

**反映**:

- 削除できた → 確実に実行されていない。終了コード 4 のまま。
- 削除できなかった（無い・消せない） → プラグインが受け取ったものとみなす。応答は受け付けの
  同じ回の中で書かれるので、短い猶予だけ追加で待つ。それでも届かなければ、別の終了コード
  （案: 8「受け取られたが応答が無い」）で終える。
- 作法の「応答」の節と、`vw2026` の終了コードの一覧（`main.go` の `cli.Help()`）に書く。

**その後**: 2 の待つ印を入れたので、要求を消す取り下げはやめた。呼ぶ側は待つ印を放して消してから
要求が残っているかを見て、残っていれば 4、無ければ猶予のあと 8 とする（[作法「待つのをやめる」](protocol.md#待つのをやめる)）。
Windows で要求を消せない問題も起きなくなった。

## 2. 待つ者の居なくなった要求が実行される

**現状**: 呼ぶ側が強制終了（Ctrl-C・kill）されると、要求はスプールに残る。CLI は SIGINT を
受けても取り下げない。

**問題**: 受け付けが長く見送られた（ダイアログが長時間開いていた）あと、誰も待っていない要求が
まとめて実行される。書く道具では危険。

**検討した案**:

| 案 | 判断 |
| --- | --- |
| 要求に期限（`expires_at`）を載せる | 採らない。長い `--timeout` で生きて待っている呼ぶ側の要求まで捨ててしまう。狙いは「待つ者が居ないこと」で、時刻はその代わりにすぎない |
| 要求に呼ぶ側の pid を載せ、死んでいれば消す | 採らない。pid は再利用される（Windows は早く、macOS も 99999 で一巡する）。防ぐには開始時刻との組で照合する必要があり、取り方が OS ごとに違う。また、作法の「生死はロックで決め、pid で推し量らない」と食い違う |
| **呼ぶ側も待つ間ロックを掴む** | **採る** |

**反映**（`bridge.lock` と同じ仕組みを、要求 1 件ごとに逆向きに使う）:

- 呼ぶ側:
  1. `<id>.wait` を作って掴む（POSIX は `flock(LOCK_EX)`、Windows は共有なしで開く）。
  2. そのあとで `<id>.req.json` を公開する。
  3. 応答を受け取るか取り下げたら、`<id>.wait` を放して消す。
- プラグイン: 要求を消した直後、実行する前に `<id>.wait` を掴めるか試す。
  - 掴めた → 呼ぶ側は死んでいる（異常終了でも OS が放す）。`.wait` を消し、実行も応答もしない。
  - 掴めない → 呼ぶ側は待っている。実行する。
  - `.wait` が無い → いまどおり実行する（`flock` を使いにくいシェルのスクリプトなどでも作法を
    守れるように、`.wait` は省略できる）。→ その後、`.wait` を必須にした。無い要求は実行せず、
    `no_wait` で応答する（消えても見送りに倒れ、呼ぶ側は待つのをやめるときに `.wait` を消せる。
    シェルからは `vw2026 call` を使う）。
- ロックを取ったときの掃除（`sweep`）の対象に `*.wait` を加える。
- CLI は SIGINT・SIGTERM を受けたら要求を取り下げる（死の判定は要求を取り出す回まで行われない
  ので、その前に消しておく方がスプールに残るものが減る）。→ やめた。強制終了でも OS が待つ印を
  放すので、残った要求は実行されない。
- Go 側は標準の `syscall` だけで書ける（Windows の共有なしは `syscall.CreateFile`。cgo は不要）。
- 1 とは独立に必要（1 は呼ぶ側が生きている場合の曖昧さ）。

## 3. ロックが子プロセスに受け継がれうる

**現状**: 作法の表では、プラグインは `open(O_RDWR|O_CREAT, 0600)` のあと `flock` でロックを
掴む。`O_CLOEXEC` が無い。

**問題**: `flock` は開いたファイルの記述単位で効くため、Vectorworks が fork/exec した子プロセス
（レンダリングや補助のプロセスなど）が記述子を受け継ぐと、Vectorworks が終わってもロックが
放されない。`status` は `running` のまま、`wait --down` は終わらず、`install` は終了コード 7 で
拒み続ける。

**反映**:

- 作法の「ロック」の表に `O_CLOEXEC` を明記する。
- Windows は「`CreateFile` のハンドルを継承させない（`lpSecurityAttributes` に null を渡す）」
  と明記する。
- 2 の `<id>.wait` にも同じことを書く。CLI 側は Go が既定で `O_CLOEXEC` を付けるので変更は不要。

## 4. 互換性の決まりが無い

**現状**: 「形を変えたら版を上げる」だけで、フィールドを 1 つ足すだけでも版が上がる。作法は
「作法を守る任意のプログラム」や、将来のほかのプラグインにも公開する想定である。

**反映**（実行時に版を照合しない方針は保つ）:

- 読み手は、要求と応答の知らないフィールドを無視する（must-ignore）。プラグインが要求の知らない
  トップレベルのキーをどう扱うかも、これで決まる。
- 省略できるフィールドを足すことは互換の変更とし、版を上げない。
- 意味を変える・必須のフィールドを足す・ファイルの形を変えるときだけ版を上げる。
- 13（未知の値はエラー）との境界を書く: 無視するのは**作法の封筒の知らないフィールド**、
  エラーにするのは**知っているフィールドの未知の値**と**道具の知らない引数**。

## 5. 失敗に機械が読む種別が無い

**現状**: 失敗の応答は `{"ok":false,"error":"知らない道具です: nope"}` のように自由文だけで、
日本語である。CLAUDE.md の「機械が読む出力は英語」の趣旨とも合わない。

**反映**:

- 応答に固定の綴りの `code` を足す。案: `unknown_tool` / `invalid_args` / `no_document` /
  `internal`。2 で実行しなかった要求には応答しないので、そのための綴りは要らない。
  → `no_document` は、図面を開かずに実行できる道具もあり道具ごとの理由なので、`internal` に
  含めた。壊れた要求のための `invalid_request` と、待つ印が無いときの `no_wait` を足した。
- `error` は人向けの文として残す。
- `vw2026 call` は `--raw` で `code` を出す。終了コードは 1 のまま（道具ごとに解釈しない）。

## 6. 受け付け 1 回の上限が件数だけ

**現状**: 1 回の受け付けで処理するのは 16 件まで（[ブリッジ](plugin/bridge.md)）。

**問題**: 重い読む道具が 16 件溜まると、その間 Vectorworks の UI が止まる。

**反映**: 時間の上限を併せて設ける（案: 経過が 50〜100 ms を超えたら新しい要求を取り出さない）。
1 件目は必ず処理する（どれほど重い道具でも進むように）。作法の「プラグイン側の義務」と
[ブリッジ「受け付け 1 回」](plugin/bridge.md#受け付け-1-回coreserve)に書く。

## 7. 壊れた応答を締切まで待ち続ける

**現状**: CLI は壊れた応答を「まだ無い」とみなして締切まで読み直し、最後に
「a dialog may be open」で終了コード 4 を返す。

**問題**: rename で公開する作法なので、壊れた `.res.json` が見えるのはプラグインの不具合の
ときだけである。理由も終了コードも誤っている。

**反映**: 応答のファイルが存在し、一定時間（案: 1 秒）壊れたままなら、終了コード 6 と
「malformed response」で終える。応答のファイルは消す。作法の「ファイル」の節の「読み直す」に、
この上限を書き足す。

## 8. 偽のプラグインが作法より緩い

**現状**: `cli/internal/fakeplugin` は、id の検査・16 件の上限・1 MiB の上限・ロックを取った
ときの掃除・壊れた要求への応答を真似ていない。`AppDirName` と `PLUGIN_APP_DIR` などの定数は
Go と C++ に二重に書かれる。

**扱い**: プラグインの実装（段 1）と併せて検討する。案は、予定している `protocol/fixtures/` に
定数と受け付けの入出力の見本を置き、C++ のテストと `fakeplugin` の両方がそれに従うこと。

## 9. JSON の解析が Vectorworks を落としうる

**現状**: 元のプラグインから移す `core/Json` に、入れ子の深さの上限があるかは確かめていない。

**問題**: 1 MiB の `[[[[…` を読ませるとスタックが溢れ、Vectorworks ごと落ちる。利用者の未保存の
作業が失われる。

**反映**: 段 1 で、入れ子の深さに上限を設け（超えたら「読めない要求」）、CI に `core/Json` の
ファジングを足す（ASan・UBSan の上に載せる）。[実装の順序](plugin/plan.md)の段 1 に書く。

## 10. 起動直後の掃除が新しい要求を消しうる

**現状**: プラグインはロックを取った直後に、残骸（要求・応答・書きかけ）を消す。

**問題**: ロックを取ってから掃除するまでのごく短い間に、`wait` がロックを見て `call` が要求を
置くと、その要求が消える。呼ぶ側は終了コード 4 を受け取る。確率は低い。

**反映**: 掃除の対象を「更新時刻がロックを取った時刻より前のファイル」に限る（rename は更新時刻を
変えず、`.tmp` は公開の直前に書かれるので、更新時刻は置いた時刻とほぼ同じになる）。

## 11. 送った順の保証を言い過ぎている

**現状**: 作法の「id」の節は「別々のプロセスからの要求も送った順に並びます」と書く。

**問題**: 時計が調整されると時刻は前後する。id を付ける時刻と rename で公開する時刻もずれるので、
遅れて公開された要求は次の回に回る。

**反映**: 「同じプロセスから続けて送った要求は送った順に処理される。別々のプロセスからの要求の
順序は保証しない（順序が要るなら呼ぶ側が揃える）」と書き直す。[設計「CLI はプリミティブに
保つ」](design.md#cli-はプリミティブに保つ)の方針と合う。

## 12. CLI のスプールの求め方が文書と食い違う

**現状**: 作法は「環境変数で決まる一時ディレクトリは使わない」とし、プラグインは
`SHGetKnownFolderPath` を使う。CLI の `spool.DefaultDir` は環境変数（`HOME`・`LOCALAPPDATA`）を
読む。

**反映**: Windows では CLI も `SHGetKnownFolderPath(FOLDERID_LocalAppData)` を `syscall` 経由で
呼ぶ（cgo は不要）。macOS は `HOME` のままでよいが、その理由（ssh でも GUI と同じ値になる）を
作法に書く。

## 13. 未知の値の扱い

**現状**: `kind` に知らない値が来たとき、ユニバーサル名で呼ぶほかのプラグインの機能の `kind`
をどうするかが決まっていない。

**反映**（決定）: **可能な限り既定値を設け、未知の値が渡されたときはエラーを返す。**

- 道具の引数・作法のフィールドは、省略できるものに既定値を設ける。
- 知っているフィールドに未知の値が来たら、エラーで応える（4 の境界を参照）。
- `kind` は `read` / `write` / `app` の 3 つに限る。ほかのプラグインの機能は、図面を変えるかが
  分からないので既定で `write` とし、undo の作法を通す（[設計「他のプラグインの道具」](design.md#他のプラグインの道具)）。

## 14. 続けて呼ぶと遅い

1 回の呼び出しに、タイマーの間隔（250 ms）と CLI のプロセス起動の時間がかかり、続けて呼ぶと
1 秒に数件が限度になる。

**扱い**: 当面は扱わない。必要になったら、プラグインに予約の道具（例: `batch`）を足す。CLI を
プリミティブに保ったまま、あとから互換の変更として足せる（4）。
