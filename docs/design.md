# 設計

## 目的

**Vectorworks を外部から機械的に操作するための窓口を、独立したプラグインとして提供します。**

- プラグイン（C++・VW SDK）が Vectorworks の内部に**本番環境でも常駐する**ブリッジを有する
- 同梱の CLI（`vw2026`）・他のプラグイン・任意のスクリプトが、そのブリッジを介して
  Vectorworks を操作する
- 現在提供するのは、図面の読み取りツールと、図面の保存・終了のツール、Vectorworks を終了するツール
  （[ツール](plugin/tools.md)）。**図面の変更も CLI を介して機械的に行えるようにすることを目標とする**

今後作成するものと、未決定の事項は [GitHub の issue](https://github.com/min-nano/vectorworks-plugin-command-line-interface/issues) で扱います。

## 決定事項

| 項目 | 決定 | 理由・補足 |
| --- | --- | --- |
| CLI の性格 | **プリミティブ**。指示された通りに 1 回動作する | 再試行・占有の待機・ツールごとの解釈は保持しない。占有はプラグインが保持する（下記） |
| 複数の呼び出し元 | **呼び出し元の 1 つがブリッジを占有できる。** セッション ID はプラグインが 1 つの Vectorworks につき同時に 1 つのみ発行し、メモリに保持する。呼び出し元は `vw2026 session start` で受け取り、`call --session` で付与し、`session end` で終了する。図面か Vectorworks を変更するツール（種類 `write`・`app`。`quit` を含む）は占有の中でのみ呼び出せ、読み取りツールは占有と照合せずに誰に対しても実行する | 別々のエージェントの書き込みが同一の Vectorworks の中で混在しない。読み取りツールは図面を変更しないので混在しない。CLI の呼び出しは 1 回ごとに終了するので、セッション ID を受け取って付与する形式が使用方法に適合する。期限やタイマーでは解除せず、終了し忘れは Vectorworks の再起動で解除する（[通信規則「占有」](protocol.md#占有セッション)） |
| 対象の図面 | **図面（ファイル）の切り替えなどは、`call` で呼び出すプラグインのツールが行う** | CLI は図面を関知しない。占有の中では、呼び出し元がツールで対象の図面を決定すればよい（CLI を使用している間は GUI を操作しない前提）。ツール（開いている図面の一覧・前面の切り替えなど）に必要な SDK の挙動は判明した（[SDK の調査 3](sdk-research.md#3-開いている図面の一覧と前面の図面の切り替え判明)） |
| 他のプラグインのツール | **このプラグインが唯一の窓口**となり、他のプラグインの機能を**名前で呼び出す** | 手段は `CallPluginLibrary`（[下記](#他のプラグインのツール)） |
| 配置と更新 | **配置は全て CLI（`vw2026 install <name>@<tag>` / `uninstall <name>`）が行う。このプラグインも、他のプラグインも同一の手順でインストールされる。** 最初の 1 回は、CLI を取得して `install cli@<tag>` を実行するだけのスクリプトを使用する。更新も同じ `install` で行い、Vectorworks の終了を要求する（動作中であれば何もせず、そのための終了コードで終了する） | インストーラとアンインストーラが不要になる。インストールの手順（どのプラグインにも共通のもの）は Go の単体テストで、プラグインごとの配置方法（このプラグインなら PATH）はフックのテストで検証する。動作中の Vectorworks のファイルを置換する手順が不要になる。終了させるのは呼び出し元（[インストール](plugin/install-and-update.md)） |
| インストール対象の決定方法 | **レジストリ（名前 → マニフェストの場所の規則）とマニフェスト（リリースごとのタグ・資産・sha256・フック）の 2 段。** 既定のレジストリは CLI に埋め込み、`--registry` で追加したものより先に参照する（既定のレジストリの名前は上書きできず、`cli` は常に本リポジトリを指す）。タグは必ず指定し、再利用しない。最新を指す名前（`latest` など）は提供側が配置場所で用意する | 名前とリリースの配置場所はほぼ変わらず本リポジトリが受け入れを決定し、資産とハッシュはリリースごとに提供側が保持する。GitHub の API にも GitHub そのものにも依存せず、ファイル共有などにも配置できる。認証は保持しない（[レジストリとマニフェスト](registry.md)） |
| プラグインごとの配置方法 | **プラグインのフォルダの外に配置するものは、そのプラグインのフック（`install` / `uninstall` のスクリプト）が配置する。** このプラグインの PATH も `cli` のフックが設定し、スクリプトのテストで検証する | Go の `install` はどのプラグインにも共通の手順のみを保持し、`cli` を特別に扱わない。配置方法の知識は、インストールされるビルド自身が保持する。利用者が使用しないコマンドを追加しない（[インストール「`cli` のフック」](plugin/install-and-update.md#cli-のフック)） |
| CLI とスプールの配置場所 | **`cli` のフォルダ（`<Plug-Ins>/cli/`）の中**（`bin/vw2026` と `spool/`）。`install` は、実行中の CLI がフォルダの中にあれば、差し替える前にフォルダの外（`<Work>/old/`）へ移動する | `cli` も他のプラグインと同様に、フォルダを差し替えるだけで置換され、削除するだけでアンインストールされる。CLI の複製を配置し直す手順が不要で、プラグインと CLI が食い違わない。Windows は開いているファイルを含むフォルダの名前を変更できないが、実行中の実行ファイルそのものは移動できる。Windows の移動プロファイル（`%APPDATA%`。ログオン・ログオフの際にのみ複製する）に含まれることは許容し、利用者フォルダをクラウドの同期やフォルダ リダイレクトの対象とした環境には対応しない（ロックが拒否されるため。[インストール「CLI とスプールの配置場所」](plugin/install-and-update.md#cli-とスプールの配置場所)） |
| フォルダ名 | **レジストリの名前**（`<Plug-Ins>/<name>/`）。内部にインストールの記録を格納し、記録の無い同名のフォルダにはインストールしない | 一見してどのプラグインか分かり、名前からフォルダが直接定まる。更新でパスが変わらないので「有効化」が保持される（Vectorworks はフルパスで記憶する） |
| 二重のインストール | **防止するのは利用者の責任。** CLI は同名のフォルダへの上書きのみを防止する | 何をもって衝突とみなすかは SDK リファレンスで確認されておらず、衝突しうる値（ユニバーサル名など）はコードが登録の際に渡すもので外部から読み取れない。確認されていない挙動に依存して、ファイル名などで中途半端に判別しない（[レジストリ「提供側への要件」](registry.md#提供側への要件)） |
| 既定以外のプラグインのフォルダ | **初回スクリプトに `--plugins-dir` で渡す。インストールされた `vw2026` は自身のインストール先の `<Plug-Ins>` を使用する**（インストールした場所を記録しない。インストールしたものの記録はプラグインのフォルダの中にのみ格納する。`--plugins-dir` はスクリプトが一時的な `vw2026` に渡す隠した指定で、環境変数を持たず、インストールされた `vw2026` は拒否する） | 記録ファイルと、その読み取り方法を 2 か所に持たずに済む。インストールされた `vw2026` が、実行中の `cli` と異なる `<Plug-Ins>` を扱わない（異なる場所のロックを参照しない） |
| プラグインのフォルダ | **`vw2026` の作業領域（`<Work>`。利用者ごとの一時フォルダの下）と同一のドライブにある前提** | 置換と実行中の CLI の移動を名前の変更のみで行い、ボリュームをまたぐ場合の扱いを持たない |
| `cli` を配置する `<Plug-Ins>` | **利用者ごとの `Plug-Ins` のみ**。ワークグループのフォルダ・アプリケーションのフォルダの `Plug-Ins` など、複数の利用者が読み込む場所には配置しない（利用者の責任。プラグインも CLI も場所を検証しない） | スプールはモジュールのある場所に付随するので、共有の場所に配置するとスプールとロックも共有され、別の利用者（ネットワーク共有なら別の計算機の利用者）の要求を自分の Vectorworks が実行しうる（[通信規則「スプールの場所」](protocol.md#スプールの場所)） |
| 他のプラグインのインストール先 | **`cli` がインストールされている `<Plug-Ins>` のみ**。`cli` の無い `<Plug-Ins>`（ワークグループのフォルダなど）へはインストールしない | Vectorworks が動作中かを、インストール先の `<Plug-Ins>/cli/spool/` のロックで判定するため（[インストール「処理の流れ」](plugin/install-and-update.md#処理の流れ)） |
| `vw2026` の永続領域 | **保持しない**。構築・退避・退避した CLI は利用者ごとの一時フォルダの下（`<Work>`）に配置し、フックが使用できる永続領域も用意しない | いずれも利用者のデータではなく、消失してもレジストリから再取得できる。`uninstall cli` の後に `vw2026` の領域が残存しない（[インストール「作業領域」](plugin/install-and-update.md#作業領域)） |
| CLI の言語 | **Go** | 単一の実行ファイルで、ランタイム不要。mac（arm64/amd64）と Windows を 1 つの CI から生成できる |
| 名前 | プラグイン `cli`・コマンド `vw2026`（Vectorworks 2025 用は `vw2025`） | コマンド名はプラグインのインストール先の Vectorworks の版。版ごとにプラグインをインストールするので、版の異なる Vectorworks が同居してもコマンドが衝突しない。配布後に変更するとスプールの場所・リンク・ユニバーサル名が変わる |
| 対象の版 | **2026 と 2025。** 同一のソースから版ごとに生成し（CLI は Go のビルドタグ、プラグインは各版の SDK）、同一のリリースに並べる | 2025 を使用する利用者にも同一の手順（初回スクリプト・`install`）で配布する。版ごとの名前と配置場所は[版](plugin/editions.md) |
| 生死の判定 | **ロックのみで決定する**。標識（状態のファイル）は保持しない。版は `ping` が返す | 標識を書き込む処理と「応答しない」状態が不要になる。応答するかは要求を配置して待機すれば分かる（[通信規則](protocol.md#生存の判定)） |
| 通信規則の版の照合 | **実行時に照合しない** | CLI とプラグインは同一の zip から同時にインストールされ、更新は Vectorworks の終了後にしか行わないので、両側は常に同一のビルド（[通信規則「版」](protocol.md#版)） |
| スプールの安全性 | **利用者の領域（`cli` のフォルダの中）に 0700 で作成するのみ**（Windows は親のフォルダの権限を継承する）。所有者と権限は検証しない | そこへ他の利用者が書き込めるなら、スプールに限らず利用者のファイル（プラグインのモジュールを含む）は保護できない。`cli` を利用者ごとの `Plug-Ins` に配置すること（上記）が、この「利用者の領域」の前提となる |
| 更新の取得 | **GitHub の API を使用せず**、マニフェストの絶対参照で zip を取得し、sha256 で照合する。新しいかはタグ（とターゲット）のみで比較し、同じなら zip を取得しない | トークン・回数制限・リリース本文の読み取りが不要になる。タグを再利用しないので、タグが同じならビルドも同じ（[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)） |
| 開発版 | **保持しない**（安定版と開発版を区別しない） | PR では変更後のコードでビルドしたものを push ごとに新しいタグでプレリリースし、同じプラグイン名で置換して検証する（`install cli@<そのタグ>`）。名前・スプール・CLI の配置場所が 1 組で足りる |

## 構成

```
   vw2026 / 他のプログラム
          │ <id>.req.json を配置／<id>.res.json を待機
          ▼
   スプール（<Plug-Ins>/cli/spool/。0700）
          ▲
          │ 取り出し／応答
          │
   ┌──────┴───────────── Vectorworks ────────────────────────────────────┐
   │  プラグイン（.vwlibrary / .vlb）… 起動時に読み込まれ、終了まで常駐  │
   │   ・OS タイマー（受付処理を 1 回ずつ呼び出す）                      │
   │   ・ブリッジ（ロックを終了まで保持）・ツール（読み取り／書き込み）  │
   │   ・拡張機能は登録しない（更新は vw2026 install が行う）            │
   │          │ 名前で呼び出す（CallPluginLibrary）                      │
   │          ▼                                                          │
   │  他のプラグイン                                                     │
   └─────────────────────────────────────────────────────────────────────┘
```

### プラグイン

設計の詳細は[プラグインの設計](plugin/README.md)にあります。

- Vectorworks の起動時に読み込まれ、終了まで常駐します。メニューなどの拡張機能は登録しません
  （[構成](plugin/architecture.md)）。
- **受付処理は OS タイマーが 1 回ずつ呼び出し、SDK 呼び出しはメインスレッドからのみ**行います
  （[構成「受付処理の流れ」](plugin/architecture.md#受付処理の流れ)）。
- 1 から記述し、SDK リファレンスで確認された挙動のみを根拠とします
  （[プラグインの設計「根拠」](plugin/README.md#根拠)）。

### ファイルで受け渡す理由

ソケットや名前付きパイプでも実現できますが、次の理由でファイルを採用しています。

- 実行はいずれにしてもタイマーの 1 回の中なので、経路を変更しても高速にならない
- **周期処理が届かない間（重い処理・一部のダイアログの最中）も要求が残存し、復帰すれば処理される**
  （ソケットは呼び出し元が接続を保持し続けるか、再接続と再送の手順が別途必要となる）
- mac のファイアウォールの確認が表示されない。Winsock と BSD ソケットで分岐しない

## CLI のプリミティブ性の維持

`vw2026` は**指示された通りに 1 回動作するのみ**のエントリポイントです。

- 保持するもの: スプールの探索・要求を配置して応答を待機すること・Vectorworks の起動・ブリッジが
  動作中かの判定（`vw2026 status`）・ツールの一覧（`vw2026 tools`）・占有のセッション ID の受け取り・付与・終了（`vw2026 session`）・
  **プラグインのインストールと更新・アンインストール**
  （`vw2026 install <name>@<tag>` / `uninstall <name>`。レジストリに掲載されたプラグインを、指定された
  タグの通りに 1 回インストールする。Vectorworks が動作中であれば何もしない。終了させて更新し
  再起動するのは、`session start`・`call quit`・`install`・`launch` と、その間でブリッジが
  停止する・動作を開始するのを待機することを呼び出し元が組み合わせる）
- 保持しないもの: 再試行・占有の待機・ブリッジの動作開始（停止）の待機（呼び出し元が
  `vw2026 status` を繰り返す。間隔と上限は呼び出し元の方針。記述方法は `vw2026 help status`）・
  ツールごとの解釈（引数の検証はプラグイン側の役割）
- 出力は標準出力へ JSON 1 行。成否は終了コード（使用方法は `vw2026 --help`。定義は [`cli/cmd/vw2026/`](../cli/cmd/vw2026/)）

排他はプラグインの占有のみです。CLI はセッション ID を受け取って要求に付与するのみで、占有を判定しません。
占有の間はそのセッション ID を付与した `vw2026 call` のみが実行され、他の呼び出し元は占有により拒否されたことを表す終了コードで拒否されます
（待機しない。待機するか断念するかは呼び出し元が決定する）。占有しない呼び出し元どうしが同時に書き込みツールを呼び出せば、
図面への操作は混在し、その順序も保証されません（受け渡し自体は破損しない。[通信規則「id」](protocol.md#id)）。**混在してはならない使用方法では、
占有するのは呼び出し元の責任です。**

## 他のプラグインのツール

このプラグインを**唯一の窓口**とし、他のプラグインが提供する機能を
**名前で呼び出す**形式を目標とします（未実装）。他のプラグインはこのプラグインを関知せずに済み、この
プラグインは名前で参照するのみとなります。CLI から見たツールの名前は `<提供者>.<名前>` とします。

**手段は `ISDK::CallPluginLibrary` です**（相手が登録したプラグインライブラリルーチンを名前で呼び出す。
[Findings「Plug-in Interop」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Interop.md)）。

他のプラグインの機能の種類（`kind`）は、**既定で `write`** とします。このプラグインからは
その機能が図面を変更するかが判別できないため、変更するものとして扱い、undo の手順に従います
（[本番環境で常駐させる前提](#本番環境で常駐させる前提安全性)）。種類 `write` なので、占有の中でのみ呼び出せます
（[通信規則「占有」](protocol.md#占有セッション)）。

- 提供者が種類を示さない機能は `write` として掲載します（既定値）。
- 提供者が `read` / `write` / `app` 以外の種類を示した機能は、ツールの一覧に掲載しません（`vw2026 tools` に
  表示されず、呼び出せば `unknown_tool`）。未知の値を既定値に読み替えない規則（[通信規則「互換性」](protocol.md#互換性)）に従います。

## 本番環境で常駐させる前提（安全性）

**利用者の Vectorworks で常に受け付けます。**
前提は次の通りで、これを崩す変更を行う場合はこの判断を再検討します。

- **相手は同一の計算機の同一の利用者のプロセスのみ**（スプールは利用者の領域に 0700。Windows は親のフォルダの権限を継承する。[通信規則「スプールの場所」](protocol.md#スプールの場所)）。
  その利用者の権限で動作するプログラムは、いずれにしても利用者のファイルを読み書きできる。
- **依頼されたときにしか動作しない。** 自動的に実行される処理（定期的な取り込みなど）は保持しない。
- **図面に書き込むツールは undo の手順に必ず従う**（[SDK リファレンス「Undo」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Undo.md)）。
  書き込みツールは自ら undo の記録を開始し、戻る前に必ず終了する（要求 1 件で undo 1 つ。
  [ブリッジ「ツールの一覧」](plugin/bridge.md#ツールの一覧)）。
- **利用者が開いた図面とダイアログも、呼び出し元が指定すれば操作の対象とする。** 保存せずに閉じることも、
  Vectorworks のダイアログのいずれのボタンを押すことも、呼び出し元が明示したときにのみ行い、プラグインと CLI が自発的には
  行わない（上記の「依頼されたときにしか動作しない」）。CLI から利用者の Vectorworks を操作するには、利用者の操作と
  区別せずに扱えるほうが分かりやすいため。図面のファイルは削除しない（削除処理の配置場所は CLAUDE.md の 9）。
- **受付処理を停止する手段は保持しない**（停止したい場合はアンインストールする）。代わりに、
  受付処理の入れ子と終了の依頼の最中は、要求を `busy` で拒否する
  （[構成「Vectorworks が処理中」](plugin/architecture.md#vectorworks-が処理中)）。
