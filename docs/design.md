# 設計

## 目的

**Vectorworks を外部から機械的に操作するための受け口を、独立したプラグインとして提供します。**

- プラグイン（C++・VW SDK）が Vectorworks の中で**本番でも常駐する**ブリッジを持つ
- 同梱の CLI（`vw2026`）・ほかのプラグイン・任意のスクリプトが、そのブリッジ越しに
  Vectorworks を操作する
- はじめは図面を読む道具だけ。**将来は図面の変更も CLI 越しに機械的に行えるようにする**
  ための布石

## 決めたこと

| 項目 | 決定 | 理由・補足 |
| --- | --- | --- |
| CLI の性格 | **プリミティブ**。指示されたとおりに 1 回動く | 再試行・占有を待つこと・道具ごとの解釈は持たない。占有はプラグインが持つ（下記） |
| 複数の呼ぶ側 | **呼ぶ側の 1 つがブリッジを占有できる。** 印（セッション ID）はプラグインが 1 つの Vectorworks につき同時に 1 つだけ発行し、メモリに持つ。呼ぶ側は `vw2026 session start` で受け取り、`call --session` で載せ、`session end` で終える。図面か Vectorworks を変える道具（種類 `write`・`app`。`quit` を含む）は占有の中でだけ呼べ、読む道具は占有に照らさずに誰にでも実行する | 別々のエージェントの書き込みが同じ Vectorworks の中で混ざらない。読む道具は図面を変えないので混ざらない。CLI の呼び出しは 1 回ごとに終わるので、印を受け取って載せる形が使い方に合う。期限やタイマーでは解かず、終え忘れは Vectorworks の再起動で解く（[通信規則「占有」](protocol.md#占有セッション)） |
| 対象の図面 | **図面（ファイル）の切り替えなどは、`call` で呼ぶプラグインの道具が行う** | CLI は図面を知らない。占有の中では、呼ぶ側が道具で対象の図面を決めればよい（CLI を使っている間は GUI を操作しない前提）。道具（開いている図面の一覧・前面の切り替えなど）に要る SDK の挙動はほぼ分かった（[SDK の調査 3](sdk-research.md#3-開いている図面の一覧と前面の図面の切り替えほぼ分かった)） |
| 他のプラグインの道具 | **このプラグインが唯一の受け口**になり、ほかのプラグインの機能を**名前で呼び出す** | 手段は `CallPluginLibrary`（下記）。呼び出しの形は未決 |
| 配置と更新 | **配置はすべて CLI（`vw2026 install <name>@<tag>` / `uninstall <name>`）が行う。このプラグインも、ほかのプラグインも同じ手順で入る。** 最初の 1 回は、CLI を取ってきて `install cli@<tag>` を走らせるだけのスクリプトを使う。更新も同じ `install` で、Vectorworks の終了を求める（動いていれば何もせず、そのための終了コードで終わる） | インストーラとアンインストーラを持たずに済み、入れる手順は Go の単体テストで確かめられる。動いている Vectorworks のファイルを入れ替える手順を持たずに済む。終了させるのは呼ぶ側（[インストール](plugin/install-and-update.md)） |
| 入れるものの決め方 | **レジストリ（名前 → マニフェストの場所の規則）とマニフェスト（リリースごとのタグ・資産・sha256・フック）の 2 段。** 既定のレジストリは CLI に埋め込み、`--registry` で足したものより先に引く（既定のレジストリの名前は上書きできず、`cli` はいつもこのリポジトリを指す）。タグは必ず指定し、使い回さない。最新を指す名前（`latest` など）は提供側が置き場所で用意する | 名前とリリースの置き場所はほとんど変わらずこのリポジトリが受け入れを決め、資産とハッシュはリリースごとに提供側が持つ。GitHub の API にも GitHub そのものにも依らず、ファイル共有などにも置ける。認証は持たない（[レジストリとマニフェスト](registry.md)） |
| プラグインごとの置き方 | **プラグインのフォルダの外に置くものは、そのプラグインのフック（`install` / `uninstall` のスクリプト）が置く。** このプラグインの CLI（`<CLI>/bin/`）と PATH も `cli` のフックが置き、スクリプトのテストで確かめる | Go の `install` はどのプラグインにも同じ手順だけを持ち、`cli` を特別に扱わない。置き方の知識は、入るビルド自身が持つ。利用者が使わないコマンドを足さない（[インストール「`cli` のフック」](plugin/install-and-update.md#cli-のフック)） |
| フォルダ名 | **レジストリの名前**（`<Plug-Ins>/<name>/`）。中に入れたときの記録を置き、記録の無い同じ名前のフォルダには入れない | 見れば何のプラグインか分かり、名前からフォルダが直接決まる。更新でパスが変わらないので「有効化」が残る（Vectorworks はフルパスで覚える） |
| 二重のインストール | **防ぐのは利用者の責任。** CLI は同じ名前のフォルダへの上書きだけを防ぐ | 何をもって衝突とみなすかは SDK リファレンスで確かめられておらず、衝突しうる値（ユニバーサル名など）はコードが登録のときに渡すもので外から読めない。確かめられていない挙動に頼って、ファイル名などで中途半端に見分けない（[レジストリ「提供側に求めること」](registry.md#提供側に求めること)） |
| 既定以外のプラグインのフォルダ | **`install` / `uninstall` に毎回 `--plugins-dir` で渡す**（入れた場所を記録しない。入れたものの記録はプラグインのフォルダの中にだけ置く） | 記録ファイルと、その読み方を 2 か所に持たずに済む |
| プラグインのフォルダ | **CLI の場所と同じドライブにある前提** | 入れ替えを名前の変更だけで行い、ボリュームをまたぐ場合の扱いを持たない |
| CLI の言語 | **Go** | 単一の実行ファイルで、ランタイム不要。mac（arm64/amd64）と Windows を 1 つの CI から作れる |
| 構造設計支援のブリッジ | **当面は並存**。移行はあとで決める | スプールの名前が違うので混ざらない（[通信規則](protocol.md)） |
| 名前 | プラグイン `cli`・コマンド `vw2026` | コマンド名はプラグインのインストール先の Vectorworks の版。版ごとにプラグインを入れるので、版の違う Vectorworks が同居してもコマンドが衝突しない。配布後に変えるとスプールの場所・リンク・ユニバーサル名が変わる |
| 生死の判定 | **ロックだけで決める**。印（状態のファイル）は持たない。版は `ping` が返す | 印を書く処理と「応えない」状態を持たずに済む。応えるかは要求を置いて待てば分かる（[通信規則](protocol.md#生存の判定)） |
| 通信規則の版の照合 | **実行時に照合しない** | CLI とプラグインは同じ zip から同時に入り、更新は Vectorworks の終了後にしか行わないので、両側は常に同じビルド（[通信規則「版」](protocol.md#版)） |
| スプールの安全 | **利用者のホームの下に 0700 で作るだけ**。持ち主と権限は確かめない | そこへほかの利用者が書けるなら、スプールに限らず利用者のファイルは守れない |
| 更新の取得 | **GitHub の API を使わず**、マニフェストの絶対の参照で zip を取り、sha256 で照らす。新しいかはタグ（とターゲット）だけで比べ、同じなら zip を取らない | トークン・回数制限・リリース本文の読み取りを持たずに済む。タグを使い回さないので、タグが同じならビルドも同じ（[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)） |
| 開発版 | **持たない**（安定版と開発版を区別しない） | PR では変更後のコードでビルドしたものを push ごとに新しいタグでプレリリースし、同じプラグイン名で入れ替えて確かめる（`install cli@<そのタグ>`）。名前・スプール・CLI の置き場所が 1 組で済む |

## 構成

```
   vw2026 / ほかのプログラム
          │ <id>.req.json を置く／<id>.res.json を待つ
          ▼
   スプール（<CLI>/spool/。0700）
          ▲
          │ 取り出す／応答する
          │
   ┌──────┴───────────── Vectorworks ─────────────────────────┐
   │  プラグイン（.vwlibrary / .vlb）… 起動時に読まれ、終了まで居る │
   │   ・OS タイマー（受け付けを 1 回ずつ呼ぶ）                    │
   │   ・ブリッジ（ロックを終了まで掴む）・道具（読む／書く）      │
   │   ・拡張機能は登録しない（更新は vw2026 install が行う）       │
   │          │ 名前で呼ぶ（CallPluginLibrary）                     │
   │          ▼                                                 │
   │  ほかのプラグイン（構造設計支援など）                          │
   └────────────────────────────────────────────────────────────┘
```

### プラグイン

1 から書きます。ほかのプラグインの作りは引き継がず、SDK リファレンスで確かめられた挙動を
根拠にします（[プラグインの設計「根拠」](plugin/README.md#根拠)）。

- Vectorworks の起動時に読まれ、終了まで居ます。新しい版は次の起動から効きます。
  メニューなどの拡張機能は登録しません。
- **配置と更新は CLI（`vw2026 install`）が行い、Vectorworks の終了を求めます**
  （[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)）。
- **受け付けは OS タイマーが 1 回ずつ呼びます。** ISDK に周期的に呼ばれる口は無く、OS の
  タイマーからは `gSDK` を読み書きできます（[Findings「Timers and Notifications」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Timers%20and%20Notifications.md)
  の 1・4）。受け付けの中にループを書きません（図面が操作できなくなる）。
- **SDK 呼び出しはメインスレッドからだけ**行います。受け付け用のスレッドは持ちません
  （SDK はメインスレッドからの呼び出ししか想定していない）。

### なぜファイルで受け渡すのか

ソケットや名前付きパイプでも作れますが、次の理由でファイルにしています。

- 実行はどのみちタイマーの 1 回の中なので、通り道を変えても速くならない
- **刻みが届かない間（重い処理・一部のダイアログの最中）も要求が残り、戻れば処理される**
  （ソケットは呼ぶ側が接続を保ち続けるか、再接続と再送の手順が別に要る）
- macOS のファイアウォールの確認が出ない。Winsock と BSD ソケットで分岐しない

## CLI はプリミティブに保つ

`vw2026` は**指示されたとおりに 1 回動くだけ**の入口です。

- 持つもの: スプールの探索・要求を置いて応答を待つ・Vectorworks の起動・ブリッジが
  動いているかの判定（`vw2026 status`）・占有の印を受け取る・載せる・終える（`vw2026 session`）・
  **プラグインのインストールと更新・アンインストール**
  （`vw2026 install <name>@<tag>` / `uninstall <name>`。レジストリに載ったプラグインを、指定された
  タグのとおりに 1 回入れる。Vectorworks が動いていれば何もしない。終了させて更新し
  起動し直すのは、`session start`・`call quit`・`install`・`launch` と、その間でブリッジが
  止まる・動き出すのを待つことを呼ぶ側が組み合わせる）
- 持たないもの: 再試行・占有を待つこと・ブリッジが動き出す（止まる）のを待つこと（呼ぶ側が
  `vw2026 status` を繰り返す。間隔と上限は呼ぶ側の方針。書き方は `vw2026 help status`）・
  道具ごとの解釈（引数の検証はプラグイン側の仕事）
- 出力は標準出力へ JSON 1 行。成否は終了コード（使い方は `vw2026 --help`。定義は [`cli/cmd/vw2026/`](../cli/cmd/vw2026/)）

排他はプラグインの占有だけです。CLI は印を受け取って要求に載せるだけで、占有を判定しません。
占有の間はその印を載せた `vw2026 call` だけが実行され、ほかの呼ぶ側は占有に断られたことを表す終了コードで断られます
（待たない。待つか諦めるかは呼ぶ側が決める）。占有しない呼ぶ側どうしが同時に書く道具を呼べば、
図面への操作は混ざり、その順序も保証されません（受け渡し自体は壊れない。[通信規則「id」](protocol.md#id)）。**混ざってはいけない使い方では、
占有するのは呼ぶ側の責任です。**

## 他のプラグインの道具

このプラグインを**唯一の受け口**にし、ほかのプラグイン（構造設計支援など）が提供する機能を
**名前で呼び出す**形を目指します。ほかのプラグインはこのプラグインを知らずに済み、この
プラグインは名前で引くだけになります。CLI から見た道具の名前は `<提供者>.<名前>` にする予定です。

**手段は `ISDK::CallPluginLibrary` です**（[Findings「Plug-in Interop」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Interop.md)。[SDK の調査 1](sdk-research.md#1-ほかのプラグインの機能を名前で呼び出す手段分かった)）。
相手が登録したプラグインライブラリルーチンを名前で呼び、最大 11 本の引数と結果を受け渡します。
OS タイマーの刻みの中からも呼べ、相手が居なければ `false` が返ります。

**呼び出しの形（道具の表への載せ方・引数の渡し方）はまだ決めていません**（[未決 3](plugin/open-questions.md#3-ほかのプラグインの機能の呼び出しの形)）。
決まるまでは、このプラグイン自身の道具だけを提供します。

ほかのプラグインの機能の種類（`kind`）は、**既定で `write`** とします。このプラグインからは
その機能が図面を変えるかが分からないため、変えるものとして扱い、undo の手順に従います
（[本番で常駐させる前提](#本番で常駐させる前提安全)）。種類 `write` なので、占有の中でだけ呼べます
（[通信規則「占有」](protocol.md#占有セッション)）。

- 提供者が種類を示さない機能は `write` として載せます（既定値）。
- 提供者が `read` / `write` / `app` 以外の種類を示した機能は、道具の表に載せません（`tools` に
  出ず、呼べば `unknown_tool`）。未知の値を既定値に読み替えない決まり（[通信規則「互換性」](protocol.md#互換性)）に従います。

## 本番で常駐させる前提（安全）

**利用者の Vectorworks で常に受け付けます。**
前提は次のとおりで、崩す変更をするならこの判断をやり直します。

- **相手は同じ計算機の同じ利用者のプロセスだけ**（スプールは利用者のホームの下で 0700）。
  その利用者の権限で動くプログラムは、どのみち利用者のファイルを読み書きできる。
- **頼まれたときにしか動かない。** 勝手に回る処理（定期的な取り込みなど）は持たない。
- **図面に書き込む道具は undo の手順に必ず従う**（[SDK リファレンス「Undo」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Undo.md)）。
  書く道具は自分で undo の記録を開き、戻る前に必ず閉じる（要求 1 件で undo 1 つ。
  [ブリッジ「道具の表」](plugin/bridge.md#道具の表)）。
- **利用者の図面を保存せずに閉じる・消す道具は持たない。**
- **受け付けを止める手段は持たない**（止めたければアンインストールする）。代わりに、
  受け付けの入れ子と終了の依頼の最中は、要求を `busy` で断る
  （[構成「Vectorworks が処理中」](plugin/architecture.md#vectorworks-が処理中)）。

## 配布と PATH

- 配布 zip の直下に、プラグイン・`bin/vw2026`（Windows は `bin\vw2026.exe`）・`cli` のフック
  （`hooks/`）を置きます。`vw2026 install` は zip の中身をそのままプラグインのフォルダへ置き、
  `cli` の `install` のフックが `bin/` の CLI を CLI の場所へ置きます。プラグインと CLI は常に
  1 つの zip から入るので、同じビルドになります。
- **最初の 1 回は、初回のスクリプト（`get-vw2026.sh` / `.ps1`）を curl などで取ってパイプで
  実行します。** スクリプトは zip から CLI を一時フォルダへ取り出して `install cli@<tag>` を
  走らせるだけで、配置の手順を持ちません（プラグインの配置は `install`、CLI と PATH は `cli` の
  フックの 1 か所）。
- **CLI はプラグインのフォルダの外（`<CLI>/bin/`）に置き、そこから動かします**。スプールもその隣の
  `spool/` です（場所は[名前と識別子「置き場所」](plugin/identifiers.md#置き場所)）。Windows では開いている
  ファイルを含むフォルダの名前を変えられないので、CLI がプラグインのフォルダの中で動いていると
  （`install` 自身を含む）、プラグインのフォルダを付け替えられなくなるためです。
- **PATH は `cli` の `install` のフックが通します**（走らせるたびに確かめ、足りなければ通す。
  プラグインの起動時には何もしない）。
  - macOS: `~/.local/bin/vw2026` → `<CLI>/bin/vw2026` のシンボリックリンク
    （sudo 不要）。`~/.local/bin` が PATH に無ければ、追加の方法を表示するだけでシェルの
    設定ファイルは書き換えない。
  - Windows: 利用者の PATH に `<CLI>\bin` を追加する。
- `vw2026 uninstall cli` は（`cli` の `uninstall` のフックが）**自分のフォルダを指すリンク・PATH の
  項目だけ**を取り除きます。
- 隔離属性の解除（mac）・`Unblock-File`（Windows）は持ちません。curl や Go の HTTP で取った
  ファイルには隔離属性も Web からの印も付かないためです。

## 進め方

プラグインの設計は [docs/plugin/](plugin/README.md)、実装の順序は
[plugin/plan.md](plugin/plan.md)、決まっていないことは
[plugin/open-questions.md](plugin/open-questions.md) にあります。

1. **通信規則と CLI**（済み）: `docs/protocol.md`・`cli/`。
2. **プラグイン**: plan.md の段 1〜6（共通部 → 骨格と配布 → インストール → 共通部の変更 → 読む道具と図面を扱う道具 → 終了の依頼）。
3. **他のプラグインの機能の呼び出し**（`CallPluginLibrary`。形は[未決 3](plugin/open-questions.md#3-ほかのプラグインの機能の呼び出しの形)）。
4. **書く道具**（undo の手順・人の操作との混在の扱いを決めてから）。
