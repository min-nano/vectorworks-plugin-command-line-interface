# 設計

## 目的

**Vectorworks を外部から機械的に操作するための受け口を、独立したプラグインとして提供します。**

- プラグイン（C++・VW SDK）が Vectorworks の中で**本番でも常駐する**ブリッジを持つ
- 同梱の CLI（`vw2026`）・ほかのプラグイン・任意のスクリプトが、そのブリッジ越しに
  Vectorworks を操作する
- はじめは図面を読む道具だけ。**将来は図面の変更も CLI 越しに機械的に行えるようにする**
  ための布石

## 決めたこと

| 項目 | 決定 | 理由・補足 |
| --- | --- | --- |
| CLI の性格 | **プリミティブ**。指示されたとおりに 1 回動く | 占有・セッション間のロック・再試行は持たない（下記） |
| 他のプラグインの道具 | **このプラグインが唯一の受け口**になり、ほかのプラグインの機能を**ユニバーサル名で呼び出す** | 呼び出しの手段は SDK の調査待ち（下記） |
| 配置と更新 | **配置はすべて CLI（`vw2026 install`）が行う。** 最初の 1 回は、CLI を取ってきて `install` を走らせるだけのスクリプトを使う。 更新も同じ `install` で、Vectorworks の終了を求める（動いていれば何もせず終了コード 7） | インストーラとアンインストーラのスクリプトを持たずに済み、配置は Go の単体テストで確かめられる。動いている Vectorworks のファイルを入れ替える手順を持たずに済む。終了させるのは呼ぶ側（[インストール](plugin/install-and-update.md)） |
| 既定以外のプラグインのフォルダ | **`install` / `uninstall` に毎回 `--plugins-dir` で渡す**（入れた場所を記録しない） | 記録ファイルと、その読み方を 2 か所に持たずに済む |
| プラグインのフォルダ | **CLI の場所と同じドライブにある前提** | 入れ替えを名前の変更だけで行い、ボリュームをまたぐ場合の扱いを持たない |
| CLI の言語 | **Go** | 単一の実行ファイルで、ランタイム不要。mac（arm64/amd64）と Windows を 1 つの CI から作れる |
| 構造設計支援のブリッジ | **当面は並存**。移行はあとで決める | スプールの名前が違うので混ざらない（[作法](protocol.md)） |
| 名前 | プラグイン `cli`・コマンド `vw2026` | コマンド名はプラグインのインストール先の Vectorworks の版。版ごとにプラグインを入れるので、版の違う Vectorworks が同居してもコマンドが衝突しない。配布後に変えるとスプールの場所・リンク・ユニバーサル名が変わる |
| 生死の判定 | **ロックだけで決める**。印（状態のファイル）は持たない。版は `ping` が返す | 印を書く処理と「応えない」状態を持たずに済む。応えるかは要求を置いて待てば分かる（[作法](protocol.md#生存の判定)） |
| 作法の版の照合 | **実行時に照合しない** | CLI とプラグインは同じ zip から同時に入り、更新は Vectorworks の終了後にしか行わないので、両側は常に同じビルド（[作法「版」](protocol.md#版)） |
| スプールの安全 | **利用者のホームの下に 0700 で作るだけ**。持ち主と権限は確かめない | そこへほかの利用者が書けるなら、スプールに限らず利用者のファイルは守れない |
| 更新の取得 | **GitHub の API を使わず**、タグと資産名から決まる URL で zip を取り、中の `build.json` で新しいかを判定する | トークン・回数制限・リリース本文の読み取りを持たずに済む（[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)） |
| 開発版 | **持たない**（安定版と開発版を区別しない） | PR では変更後のコードでビルドしたものをプレリリースし、同じプラグイン名で入れ替えて確かめる。名前・スプール・CLI の置き場所が 1 組で済む |

## 構成

```
   vw2026 / ほかのプログラム
          │ <id>.req.json を置く／<id>.res.json を待つ
          ▼
   スプール（<CLI>/spool/。0700）
          ▲
          │ 取り出す／応答する
          │
   ┌──────┴───────────── Vectorworks ─────────────────────────┐
   │  プラグイン（.vwlibrary / .vlb）… 起動時に読まれ、終了まで居る │
   │   ・OS タイマー（受け付けを 1 回ずつ呼ぶ）                    │
   │   ・ブリッジ（ロックを終了まで掴む）・道具（読む／書く）      │
   │   ・拡張機能は登録しない（更新は vw2026 install が行う）       │
   │          │ ユニバーサル名で呼ぶ（手段は SDK の調査待ち）       │
   │          ▼                                                 │
   │  ほかのプラグイン（構造設計支援など）                          │
   └────────────────────────────────────────────────────────────┘
```

### プラグイン

構造設計支援プラグインで実機で確かめた受け付けの作りを引き継ぎます（あちらの
`docs/development/mcp-bridge.md`・M41）。

- Vectorworks の起動時に読まれ、終了まで居ます。新しい版は次の起動から効きます。
  メニューなどの拡張機能は登録しません。
- **配置と更新は CLI（`vw2026 install`）が行い、Vectorworks の終了を求めます**
  （[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)）。
- **受け付けは OS タイマーが 1 回ずつ呼びます。** 受け付けの中にループを書きません
  （図面が操作できなくなる）。undo の記録が開いている間の呼び出しは見送ります。
- **SDK 呼び出しはメインスレッドからだけ**行います。受け付け用のスレッドは持ちません
  （SDK はメインスレッドからの呼び出ししか想定していない）。

### なぜファイルで受け渡すのか

ソケットや名前付きパイプでも作れますが、次の理由でファイルにしています。

- 実行はどのみちタイマーの 1 回の中なので、通り道を変えても速くならない
- **受け付けが見送られている間（ダイアログの最中など）も要求が残り、戻れば処理される**
  （ソケットは呼ぶ側が接続を保ち続けるか、再接続と再送の作法が別に要る）
- macOS のファイアウォールの確認が出ない。Winsock と BSD ソケットで分岐しない

## CLI はプリミティブに保つ

`vw2026` は**指示されたとおりに 1 回動くだけ**の入口です。

- 持つもの: スプールの探索・要求を置いて応答を待つ・Vectorworks の起動・ブリッジが
  動き出す（止まる）のを待つ・**プラグインのインストールと更新・アンインストール**
  （`vw2026 install` / `uninstall`。Vectorworks が動いていれば何もしない。終了させて更新し
  起動し直すのは、`call quit`・`wait --down`・`install`・`launch`・`wait` を呼ぶ側が組み合わせる）
- 持たないもの: **占有・セッション間のロック**・再試行・道具ごとの解釈（引数の検証は
  プラグイン側の仕事）
- 出力は標準出力へ JSON 1 行。成否は終了コード（使い方は [`cli/cmd/vw2026/doc.go`](../cli/cmd/vw2026/doc.go) の godoc）

占有を持たないので、2 つのプロセスが同時に書く道具を呼べば、図面への操作は送った順に
混ざります（受け渡し自体は壊れない）。**安全にセッションから使う責任は呼ぶ側に
あります。**

## 他のプラグインの道具

このプラグインを**唯一の受け口**にし、ほかのプラグイン（構造設計支援など）が提供する機能を
**ユニバーサル名で呼び出す**形を目指します。ほかのプラグインはこのプラグインを知らずに
済み、このプラグインは名前で引くだけになります。CLI から見た道具の名前は
`<提供者>.<名前>` にする予定です。

**呼び出しの手段は、SDK でできることが分かってから決めます**（リポジトリの決めごと
「SDK の調査はリファレンス側で行う」）。調査は
[SDK リファレンス #217](https://github.com/min-nano/vectorworks-developer-sdk-reference/issues/217)
で、候補と調べることは [SDK の調査](sdk-research.md) にまとめています。それまでは、この
プラグイン自身の道具だけを提供します。

## 本番で常駐させる前提（安全）

開発版だけの道具だった元のブリッジと違い、**利用者の Vectorworks で常に受け付けます。**
前提は次のとおりで、崩す変更をするならこの判断をやり直します。

- **相手は同じ計算機の同じ利用者のプロセスだけ**（スプールは利用者のホームの下で 0700）。
  その利用者の権限で動くプログラムは、どのみち利用者のファイルを読み書きできる。
- **頼まれたときにしか動かない。** 勝手に回る処理（定期的な取り込みなど）は持たない。
- **図面に書き込む道具は undo の作法を必ず通す**（[SDK リファレンス「Undo」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Undo.md)）。
  人が図面を操作している最中にも要求は届くので、人の操作と undo の記録が混ざらないかを
  先に確かめる。
- **利用者の図面を保存せずに閉じる・消す道具は持たない。**
- **受け付けを止める手段は持たない**（止めたければアンインストールする）。代わりに、
  Vectorworks の処理中（undo の記録が開いている間など）はその回の受け付けを見送る
  （[構成「受け付けを止めない・処理中は見送る」](plugin/architecture.md#受け付けを止めない処理中は見送る)）。

## 配布と PATH

- 配布 zip の直下に、プラグインと `bin/vw2026`（Windows は `bin\vw2026.exe`）を置きます。
  `vw2026 install` は「zip の直下の `bin/` は CLI の場所へ、それ以外はそのままプラグインの
  フォルダへ置く」。プラグインと CLI は常に 1 つの zip から入るので、同じビルドになります。
- **最初の 1 回は、初回のスクリプト（`get-vw2026.sh` / `.ps1`）を curl などで取ってパイプで
  実行します。** スクリプトは zip から CLI を一時フォルダへ取り出して `install` を走らせる
  だけで、配置の手順を持ちません（CLI・PATH・プラグインの配置は `install` の 1 か所）。
- **CLI はプラグインのフォルダの外（`<CLI>/bin/`）に置きます**。スプールもその隣の `spool/`
  です（場所は[名前と識別子「置き場所」](plugin/identifiers.md#置き場所)）。Windows では開いている
  ファイルを含むフォルダの名前を変えられないので、CLI がプラグインのフォルダの中で動いていると
  （`install` 自身を含む）、プラグインのフォルダを付け替えられなくなるためです。
- **PATH は `install` が通します**（走らせるたびに確かめ、足りなければ通す。プラグインの
  起動時には何もしない）。
  - macOS: `~/.local/bin/vw2026` → `<CLI>/bin/vw2026` のシンボリックリンク
    （sudo 不要）。`~/.local/bin` が PATH に無ければ、追加の方法を表示するだけでシェルの
    設定ファイルは書き換えない。
  - Windows: 利用者の PATH に `<CLI>\bin` を追加する。
- `vw2026 uninstall` は**自分のフォルダを指すリンク・PATH の項目だけ**を取り除きます。
- 隔離属性の解除（mac）・`Unblock-File`（Windows）は持ちません。curl や Go の HTTP で取った
  ファイルには隔離属性も Web からの印も付かないためです。

## 進め方

プラグインの設計は [docs/plugin/](plugin/README.md)、実装の順序は
[plugin/plan.md](plugin/plan.md)、決まっていないことは
[plugin/open-questions.md](plugin/open-questions.md) にあります。

1. **作法と CLI**（済み）: `docs/protocol.md`・`cli/`。
2. **プラグイン**: plan.md の段 1〜5（共通部 → 骨格 → 読む道具 → 配布 → 更新）。
3. **他のプラグインの機能の呼び出し**（SDK の調査の結果しだい）。
4. **書く道具**（undo の作法・人の操作との混在の扱いを決めてから）。
