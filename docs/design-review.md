## A. 段 2・5 の前に決めること

### A1. 種類 `app` と終了の依頼が同じ意味になっている

- `src/core/Serve.cpp` の `answer` は、種類 `app` の道具が成功すると必ず終了の依頼（`quit`）を
  返す。偽のプラグイン（`cli/internal/fakeplugin`）も「種類 `app` の道具は `quit` だけ」とみなす。
- 一方、[設計「決めたこと」](design.md#決めたこと)の「対象の図面」は、図面の切り替え・開くことを
  道具で行う前提である。これらは図面を変えないので `write` ではなく、`app`（Vectorworks そのもの
  に働く道具）に当たる。`app` として載せると、成功した時点で終了を頼むことになる。
- 案:
  - 終了の依頼を種類から切り離し、道具が返す印にする（`ToolError` と同じく出力の引数で返す）。
  - `app` の意味を「Vectorworks そのものに働き、占有の中でだけ呼べる」に限る。
- 道具が `quit` だけのいまなら、出した実装が無いので版を上げずに直せる
  （[通信規則「互換性」](protocol.md#互換性)の例外）。直すなら `src/core`・見本・偽のプラグイン・
  [ブリッジ「受け付け 1 回」](plugin/bridge.md#受け付け-1-回coreserverserve)を合わせて直す。

### A2. `quit`・`ping` が使う SDK 呼び出しが確かめられていない

- [SDK の調査 4](sdk-research.md#4-最初の道具が使う-sdk-呼び出し)では、次が未確認である。
  - OS タイマーの刻みから `CloseAllFilesAndQuitVectorworks(true, false)` を呼んでよいか
  - 保存の確認を取り消したときに呼び出しから戻るか
  - 図面が 1 枚も無いときの `GetCurrentLayer()` の戻り値
- [実装の順序](plugin/plan.md)の段 2（`ping`）・段 4（読む道具）・段 5（`quit`）には「使う SDK
  呼び出しが SDK リファレンスで確かめられてから」と書いた（CLAUDE.md の 7）。残っているのは調べる
  ことで、`GetCurrentLayer()` は段 2 の前、`quit` の 2 つは段 5 の前に、SDK リファレンスで issue を
  立てて確かめる。

### A3. 未決 2 が段 2 の作りを変える

- いまは `Clock` が `IsCurrentlyBuildingAnUndoEvent()` が真の間、受け付けの回ごと見送る
  （[構成「受け付けを止めない・処理中は見送る」](plugin/architecture.md#受け付けを止めない処理中は見送る)）。
  SDK リファレンスによれば、スクリプトエンジンが真を残すことがあり、受け付けが止まったままに
  なりうる（[未決 2](plugin/open-questions.md#2-undo-の記録が開いている間の見送り)）。
- 未決 2 を「書く道具と `quit` だけを見送る」に決めると、次が変わる。
  - 見送りの判定が `Clock` から `core::Server::serve` の中へ移る（取り出さずに残す要求ができる）。
  - [通信規則「生存の判定」](protocol.md#生存の判定)の「見送ります」の範囲。
  - 受け付けの見本（`protocol/fixtures/serve`）の表し方。
- `Clock` を作る段 2 の前に決めると手戻りが無い（段 2 には `quit` も書く道具も無いが、見送りの
  判定の置き場所が変わるため）。

### A4. 終了の依頼の最中に受け付けが入れ子になりうる

- `CloseAllFilesAndQuitVectorworks` は保存の確認（モーダル）を出し、その間もタイマーは刻む。
- 入れ子の見送りは「受け付けのコードがスタックに載っている」ことで判定するが、終了の依頼は
  受け付けの外（タイマーが `serve` から戻ったあと）で行うので、この判定に掛からない。
- A3 で読む道具を記録の開いている間も通すと、保存の確認の最中に受け付けが走り、2 つ目の
  `quit` で終了の依頼が重なりうる。入れ子の見送りの範囲をタイマーの呼び出し全体にする。

## B. 文書の誤りと、文書と実装の食い違い

### B1. 更新の手順の見本が占有を残す

- [インストール「流れ」](plugin/install-and-update.md#流れ)の見本は、`call quit` が失敗したとき
  （`|| exit`）と、保存の確認が取り消されたとき（`exit 3`）に `session end` を呼ばない。
  占有は Vectorworks を起動し直すまで残り、ほかの呼ぶ側はすべて `busy` で断られる。
- 見本は「この組み合わせの真実」なので、失敗の道筋で `session end` を呼ぶ形に直す。
  [実装の順序](plugin/plan.md)の段 5 の確かめ方には、取り消したあとの `session end` を入れてある。

### B2. Windows の PATH の書き換えが既存の項目を壊しうる

- [インストール「PATH」](plugin/install-and-update.md#path)は、PowerShell の
  `[Environment]::SetEnvironmentVariable('Path', …, 'User')` で書く。この手段は値を REG_SZ で
  書き戻し、読むときも展開した値を返すとされる。利用者の `Path` の `%USERPROFILE%\…` のような
  項目が、展開された固定の値に変わるおそれがある。
- 段 3 の実装の前に実機で確かめる。代わりの案は、`advapi32` の `RegQueryValueExW` /
  `RegSetValueExW` を `syscall` で呼んで型（REG_EXPAND_SZ）を保ち、`WM_SETTINGCHANGE` を送る形
  （外部の依存を足さない）。`uninstall` の PATH の後始末も同じ。

### B3. `VW2026_APP` が環境変数の名前の決まりに反する

- CLAUDE.md の決まりでは `VW2026_<コマンド>_<指定>` で、`launch --app` は `VW2026_LAUNCH_APP`
  になる（`cli/cmd/vw2026/launch.go`）。
- 例外として残すなら CLAUDE.md に書く。改めるなら、名前を変えられなくなる最初の配布の前に行う。
- **済。** 名前は残し、決まりのほうを改めた。名前は使うコマンドではなく値の通じる範囲で決める。
  Vectorworks の場所はどのコマンドからも同じものを指すので `VW2026_APP`、待つ上限はコマンドごとに
  違う値を与えうるので `VW2026_<コマンド>_TIMEOUT`（CLAUDE.md「Go」）。インストールのタグと
  プラグインのフォルダも同じ決まりで `VW2026_TAG`・`VW2026_PLUGINS_DIR` とした（段 3 で実装する）。

### B4. SDK の調査の古い参照

- [SDK の調査 2](sdk-research.md#2-汎用の実行口のちの検討)の「設計『進め方』の 6（書く道具）」は、
  いまの [設計「進め方」](design.md#進め方)では 4 である。
- **済。** 4 に直した。

### B5. 段 2〜4 では実機の確かめ方が成り立たない

（この節の見出しと本文の段の番号は、入れ替え前のもの）

- CLAUDE.md と [実装の順序「実機の確かめ方」](plugin/plan.md#実機の確かめ方)は「PR の
  プレリリースを入れ、`vw2026` で呼ぶ」とするが、`vw2026 install` は段 5、zip に `bin/vw2026` が
  入るのは段 4 である。
- 段 2〜4 では「zip を手で置き、`vw2026` は `go build` したものを使う」と明記する。スプールの
  場所は CLI の置き場所に依らないので、手でビルドした CLI でも同じスプールを使う。
- **済。** 段を入れ替え、梱包（`bin/vw2026`）を段 2、`install` を段 3 に置いた（ここは新しい
  番号）。`install` が無いのは段 2 だけで、段 2 は zip を手で置き、zip の `bin/` の
  CLI を使う。段 3 は初回のスクリプトに `--tag dev-<slug>` を渡して入れる
  （[実装の順序「実機の確かめ方」](plugin/plan.md#実機の確かめ方)）。

## C. 今後の段の仕様の穴

### C1. 読む道具の結果に決まっていない点がある

[最初に提供する道具](plugin/tools.md)で次が決まっていない。既定値はあとで変えると互換を崩すので、
段 4 の PR で決めて tools.md に書く（`ping` の `current_layer` は段 2 の PR で決める）。

- `layer_objects` の `type` が種別の番号か名前か
- `layers` の `scale` の形（数か比か）
- `bounds` の単位（図面の単位か、決まった単位か）
- `layers` の `objects` と `object_counts` の数え方（グループ・シンボルの中を数えるか、図面全体に
  シートレイヤを含むか）
- 図面が開かれていないときの `ping` の `current_layer`（`null` か、省くか）と、各道具の応答
  （`internal` とする想定）

`classes` が使う SDK 呼び出しは SDK リファレンスに無いので、issue を立てる
（[SDK の調査 4](sdk-research.md#4-最初の道具が使う-sdk-呼び出し)）。

### C2. ほかのプラグインの機能と書く道具の順序が矛盾する

- [設計「他のプラグインの道具」](design.md#他のプラグインの道具)は、ほかのプラグインの機能を
  既定で `write` として載せる。[ブリッジ「道具の表」](plugin/bridge.md#道具の表)は、`write` の
  道具を undo の手順に対応するまで表に載せない。
- そのため [設計「進め方」](design.md#進め方)の 3（他のプラグインの機能）は、4（書く道具。
  [未決 1](plugin/open-questions.md#1-図面に書く道具の振る舞い)）が決まるまで提供できない。
  順序を入れ替えるか、提供者が `read` と示した機能だけを先に載せるかを決める。
- ほかのプラグインのルーチンが undo の手順に従うことを、このプラグインがどう保証するか
  （このプラグインが記録を開いて包むか、提供者の義務とするか）を未決 1 か未決 3 の論点に足す。

### C3. そのほか

- **PR のプレリリースの版。** `pull_request` の `GITHUB_SHA` はマージのためのコミットで、
  ブランチの head と違う。`VW_BUILD_VERSION` と `build.json` にどちらの sha を載せるかを
  [ビルドとリリース](plugin/build-and-release.md)に書く（head の sha を想定）。
  **済。** ブランチの head の sha を載せ、ビルドも head で行う。ブランチを main に追いつかせることは
  求めず、main の変更が道具の振る舞い・描画に影響しうるときだけ取り込んで確かめる
  （[ビルドとリリース「リリースの形」](plugin/build-and-release.md#リリースの形)）。
- **終了の処理中のタイマー。** Vectorworks が終わる途中（図面を閉じたあと、プロセスが終わる
  まで）に刻みが届いたときの扱い（タイマーを止める入口があるか）を、段 5 の実機確認の項目に
  入れる。
