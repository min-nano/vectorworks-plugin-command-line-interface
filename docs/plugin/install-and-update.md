# インストール・更新・アンインストール

**配置はすべて `vw2026 install` / `uninstall` が行います。** このプラグイン（`cli`）も、ほかの
プラグインも同じ手順で入ります。何を・どこから取るかは[レジストリとマニフェスト](../registry.md)が
決め、プラグインのフォルダの外に置くもの（`cli` なら PATH）はそのプラグインのフックが
置きます。`cli` の CLI とスプールは `cli` のフォルダの中にあり（[CLI とスプールの置き場所](#cli-とスプールの置き場所)）、
外に置くのは PATH だけです。最初の 1 回だけは CLI がまだ無いので、取ってきて `install` を走らせるだけの短い
スクリプト（`get-vw2026.sh` / `.ps1`）を使います。

| 段 | 手段 | すること |
| --- | --- | --- |
| 初回 | `get-vw2026.sh` / `.ps1`（curl などで取ってパイプで実行） | 一時フォルダに CLI を取り出し、`vw2026 install cli@<tag>` を走らせる |
| インストール・更新 | `vw2026 install <name>@<tag>` | `<Plug-Ins>/<name>/` を付け替え、フックを走らせる。入っているものと同じタグなら、zip を取らず付け替えもせずに、フックだけを走らせる |
| アンインストール | `vw2026 uninstall <name>` | フックを走らせ、`<Plug-Ins>/<name>/` を取り除く |

```sh
# macOS
curl -fsSL https://github.com/min-nano/vectorworks-plugin-command-line-interface/releases/latest/download/get-vw2026.sh | sh
curl -fsSL …/get-vw2026.sh | sh -s -- --plugins-dir <Plug-Ins>   # 既定以外の場所へ
```

```powershell
# Windows
irm https://github.com/min-nano/vectorworks-plugin-command-line-interface/releases/latest/download/get-vw2026.ps1 | iex
& ([scriptblock]::Create((irm …/get-vw2026.ps1))) --plugins-dir <Plug-Ins>   # 既定以外の場所へ
```

## 前提

- **プラグインのフォルダ（`<Plug-Ins>`）と `vw2026` の作業の場所（`<Work>`。下記「[作業の場所](#作業の場所)」）は
  同じドライブ（ボリューム）にあるものとします。** 既定では同じボリュームにあります（下記「作業の場所」）。入れ替えは名前の変更だけで
  行い、ボリュームをまたぐ場合の扱い（コピーへの切り替え・その検出）は持ちません。名前の
  変更が失敗したら、何も変えずに失敗で終わります。
- **入れた場所を記録しません。** 既定以外の `<Plug-Ins>` を使う利用者は、`install` と
  `uninstall` に毎回 `--plugins-dir`（環境変数 `VW2026_PLUGINS_DIR`）を渡します（[設計「CLI はプリミティブに保つ」](../design.md#cli-はプリミティブに保つ)）。
  入れたものの記録は、プラグインのフォルダの中にだけ置きます（[レジストリ「入れたときの記録」](../registry.md#入れたときの記録)）。
- **安定版と開発版を区別しません。** PR のプレリリースを `cli@<そのタグ>` で入れると、プラグインも
  CLI もそのビルドのものに入れ替わります。
- **隔離属性の解除（mac）・`Unblock-File`（Windows）は行いません。** curl・`Invoke-RestMethod`・
  Go の HTTP で取ったファイルには、隔離属性も Web からの印（Mark of the Web）も付かないためです。
  署名はビルドがかけたアドホック署名で、zip から取り出したファイルにそのまま残ります。
- **同じプラグインを二重に入れないのは利用者の責任です**（[レジストリ「提供側に求めること」](../registry.md#提供側に求めること)）。

場所は[名前と識別子「置き場所」](identifiers.md#置き場所)にあります。

### 作業の場所

**`install` / `uninstall` の作業の場所（`<Work>`）は、利用者ごとの一時フォルダの下の `vectorworks2026-cli/` です。**
置くのは、組み立て（`staging/`）・退避（`old/<name>/` と `uninstall` の途中の印）・よけた CLI（`old/` の直下の
`vw2026.old-*` / `vw2026.exe.old-*`）だけで、どれも `install` / `uninstall` の中でしか要らないものです。
持続する `vw2026` の場所（設定・フックが使う場所など）は持ちません。

| OS | `<Work>` | 求め方 |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Temp\vectorworks2026-cli\` | `SHGetKnownFolderPath(FOLDERID_LocalAppData)` の下の `Temp`（`%TEMP%` の既定の場所）。環境変数 `TMP` / `TEMP` は読まない |
| mac | `/var/folders/…/T/vectorworks2026-cli/` | `/usr/bin/getconf DARWIN_USER_TEMP_DIR` の出力（`confstr(_CS_DARWIN_USER_TEMP_DIR)`。利用者ごとの一時フォルダ）。環境変数 `TMPDIR` は読まない（cgo を使わないので `getconf` を走らせる） |

- **環境変数を読まないのは、**走らせ方（端末・ssh・ほかのアプリ）で場所が変わると、前の `install` /
  `uninstall` が途中で止まって残した `old/` を、次の回が見つけられなくなるためです。mac で `TMPDIR` が
  無いときに Go の `os.TempDir()` が返す `/tmp` は利用者の間で共有され、ほかの利用者がシンボリックリンクを
  仕掛けられるので使いません。どちらの場所も利用者だけが書けるフォルダです。
- **OS が片付けて消えてもかまいません**（Windows のディスク クリーンアップ・ストレージ センサー、mac の
  しばらく使われていないファイルの片付け）。どれも利用者のデータではなく、プラグインはレジストリから
  取り直せるためです。
  - よけた CLI の残りは、この片付けで消えます（[`uninstall cli` のあとに残るもの](#uninstall-cli-のあとに残るもの)）。
  - 途中で止まった回の `old/<name>/` が消えたとき、`<Plug-Ins>/<name>/` があれば何も起きません。
    無ければ入っていない状態になり、`install` で入れ直します。
  - **片付けはファイルを 1 つずつ消すので、`old/<name>/` が一部だけ残ることがあります。** 退避した版を
    `<Plug-Ins>` へ戻すのは同じ回の中の失敗のときだけです。前の回が残した `old/<name>/` は、`install` では
    消すか断るだけ（[入れ替えの手順](#入れ替えの手順)の 1）、続きから走る `uninstall` では戻さずに消すか
    断るだけ（[アンインストール](#アンインストールvw2026-uninstall)の 4）で、`Plug-Ins` に戻しません。
  - **同じ回の中で戻すときも、その間に片付けが入る危うさは残ります（受け入れる）。** 退避してから戻すまでの
    間にはフックが走り、フックの時間に上限はありません（[レジストリ「書き方」](../registry.md#書き方)）。
    名前の変更ではファイルの時刻（更新・参照）が変わらないので、`<Work>` へ移した直後の旧版も、時刻の古さで
    選ぶ片付けの対象になりえます。片付けがこの間に当たると、一部だけ消えた版が `Plug-Ins` に戻ります。
    片付けが走るのは OS が決めた時機だけで、フックが走る間に当たる確率は低いので、歯止めを足さずに
    受け入れます。戻った版が壊れていたときの直し方は、何が消えたかで変わります。
    - 記録の `module` が消えていれば、同じタグの `install` が入れ直します（[流れ](#流れ)）。
    - 記録と `module` が残り、ほかのファイルだけが消えたとき（`cli` の `bin/vw2026` だけ・mac の `.vwlibrary`
      のバンドルの中身の一部など）は、同じタグの `install` では「同じタグのとき」の道に入り、フックだけが
      走って付け替えないので直りません。`uninstall` してから入れ直します。`cli` は、`bin/vw2026` が消えて
      いれば `vw2026` を走らせられないので、[初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)に
      `uninstall cli` を渡してから、初回のスクリプトで入れます。
  - 組み立ての途中のファイルが同じように選ばれないよう、zip を展開するときにファイルの時刻を zip の項目の
    ものに戻しません（[レジストリ「zip の形」](../registry.md#zip-の形)）。
  - `old/<name>/` は残り、印 `old/<name>.uninstalling` だけが消えたときは、`install` / `uninstall` が
    `old` の場所を `message` に載せて断るので（[入れ替えの手順](#入れ替えの手順)の 1・[アンインストール](#アンインストールvw2026-uninstall)の 2）、
    利用者が消します。
- **同じボリュームにあること**: Windows の `%LOCALAPPDATA%\Temp` と既定の `<Plug-Ins>`（`%APPDATA%` の下）は
  どちらも利用者のプロファイルの中です。mac の `/var/folders` とホームは、どちらもデータボリュームに
  あります（`/private/var` はデータボリュームへの firmlink）。mac で `/var/folders` から `~/Library/…` へ名前の
  変更で移せることは、段 3b の実機の確認で確かめます（[実装の順序](plan.md)の段 3b）。

## 初回のスクリプト（`get-vw2026.sh` / `.ps1`）

**CLI を取ってきて `install cli@<tag>` を走らせるだけ**です。配置の手順・PATH・判断は `install` と
`cli` のフックが持ち、スクリプトは持ちません。

1. 引数を見て、走らせるものを決める。
   - **最初の引数が `uninstall` なら**、受け付けるのは `uninstall cli`（と `--plugins-dir`）だけで、
     `cli@<tag>` は足さない。`latest` の CLI を取り出して `vw2026 uninstall cli …` を走らせる（`uninstall cli`
     がフックの途中で止まり、CLI が消えたときに抜け出すため。下記「アンインストール」）。
   - それ以外は、引数から `cli@<tag>` の形のものを探す（無ければ `cli@latest` を足す）。ほかの名前は
     受け付けない（このスクリプトは `cli` を入れるためのもの）。
2. ターゲット（mac は `sysctl -n hw.optional.arm64` が 1 なら `macos-arm64`、それ以外は `macos-x64`。
   Windows は `windows-x64`。[レジストリ「名前・タグ・ターゲット」](../registry.md#名前タグターゲット)）の zip を一時フォルダへ取ってきて、中の
   `bin/vw2026`（Windows は `bin\vw2026.exe`）だけを取り出す。zip の場所は既定のレジストリの `cli` の
   規則と同じ形で決める（`latest` なら `releases/latest/download/cli-<target>.zip`、それ以外は
   `releases/download/<tag>/cli-<target>.zip`）。JSON を読まずに済むように、マニフェストは読まない。
3. 取り出した CLI で `install`（または `uninstall`）を走らせる（スクリプトの引数をそのまま渡す）。
4. 一時フォルダを消し、走らせた `install` / `uninstall` の終了コードで終わる。「Vectorworks が動いている」終了コード
   （番号は `vw2026 --help`）なら「Vectorworks を終了してからもう一度走らせる」と表示する。

- CLI だけの資産は持ちません。zip から取り出します。
- 一時フォルダの CLI は、`install` の中でマニフェストと zip をもう一度取ります（スクリプトが取った
  zip は渡さない。指定を増やさないため。zip は小さい）。`install` は zip を sha256 で照らします。
- `latest` が、スクリプトが zip を取ってから `install` がマニフェストを取るまでの間に進むと、
  一時フォルダの CLI と入る CLI は別のビルドになります。入れる手順はどのプラグインにも同じ
  （ビルドに固有の置き方は、入るものの側のフックが持つ）なので、一時フォルダの CLI がその
  `manifest_version` を読めれば正しく入ります。
- PR のプレリリースを試すときは、そのリリースのスクリプトに `cli@<そのタグ>` を渡します
  （スクリプトが取る zip もそのタグのものになり、`install` へもそのまま渡る）。

## インストールと更新（`vw2026 install`）

**初回のインストールも更新も、同じ `install` で行います。**

```sh
vw2026 install cli@latest                         # main の最新（同じタグなら zip を取らず、フックだけを走らせる）
vw2026 install cli@dev-feature-x-61-a1b2c3d       # PR のプレリリース
vw2026 install cli@latest --check                 # 入れずに、新しいビルドがあるかだけ返す（動いていてもよい）
vw2026 install cli@latest --plugins-dir <Plug-Ins>
vw2026 install import-ifc-homeskz@latest
vw2026 install my-plugin@2026.3.1 --registry ./plugins.json
```

- **名前とタグは必須です**（`<name>@<tag>`。既定のタグは持たない）。1 回に 1 つだけ入れます
  （途中で失敗したときに、どこまで入ったかを持たないため）。
- `--check` は、新しいビルドがあるか（`available`）と最新か（`up_to_date`）を、終了コードでは
  なく出力の `outcome` で分けます（新しいビルドがあることは失敗ではないため。判定できなかった
  ときだけ失敗）。入っていなければ `available` です。
- **同じタグなら、zip を取らず、フォルダも付け替えずに、`install` のフックだけを走らせます**
  （`up_to_date`）。`cli` なら PATH を通し直します。フックは
  Vectorworks が止まっている間にしか走らせないので、同じタグでも Vectorworks が動いていれば
  `vectorworks_running` で終わります（新しいかだけを知りたいときは `--check`）。
- **フォルダの中身を入れ直す手段は持ちません。** 入れ直すには `uninstall` してから入れます。
  - ほかのプラグイン: `vw2026 uninstall <name>` のあと `vw2026 install <name>@<tag>`。
  - `cli`: `uninstall cli` は CLI そのもの（`<Plug-Ins>/cli/bin/vw2026` と PATH）も消すので、続けて
    `vw2026 install` は走らせられません。`uninstall cli` のあと、[初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)で入れます。
    `<Plug-Ins>/cli/bin/vw2026` が消えた（ウイルス対策が隔離した・`install` が付け替えの途中で止まった）
    ときも同じで、`vw2026` を走らせられないので、初回のスクリプトに `uninstall cli` を渡してから入れ直します。
  - どちらも同じパスに入るので、その間に Vectorworks を起動しなければ「有効化」は残ります（下記
    「入れる先のフォルダ」）。
- 指定・環境変数・終了コードの具体的な値は `vw2026 help install` が真実です（`CLAUDE.md`「Go」）。

### 流れ

```
vw2026 install <name>@<tag>
  1. 名前を引く                       既定のレジストリ → --registry の順（レジストリ「レジストリの順」）
  2. マニフェストを取る               合った規則の path（{tag} を置き換える）。tag を照らし、今のターゲットを選ぶ
                                     （合った規則の path に {tag} があり、@ の後ろが記録の tag と同じで、記録の
                                      target が今のターゲットと同じなら取らない。下記「同じタグのとき」）
  3. 入れる先を確かめる               <Plug-Ins>/<name>/ と中の記録（下記「入れる先のフォルダ」）。
                                     <name> が cli でなければ、<Plug-Ins>/cli/ に正しい記録があること
                                     （無ければ何も変えずに失敗。下記「cli と同じ <Plug-Ins> に入れる」）
                                     --check なら入れずに {"outcome":"up_to_date"} か {"outcome":"available"}
  4. Vectorworks が動いていないか     <Plug-Ins>/cli/spool/ のロックが掴まれていれば終わり
                                     {"outcome":"vectorworks_running"}（専用の終了コード）
     （同じタグのとき）              記録の tag と target が同じで、記録の module がフォルダの中に実在するなら、
                                     入っているフォルダで記録の hooks.install だけを
                                     走らせて終わり {"outcome":"up_to_date",…,"hook":{…}}（zip を取らず、付け替えない）
  5. zip を取って照らす               asset を <Work>/staging/<name>.zip へ。sha256 が合わなければ失敗
  6. 組み立てる                       <Work>/staging/<name>/ へ展開し、モジュールを確かめ、記録を書く
  7. プラグインのフォルダを付け替える  下記「入れ替えの手順」（直前にロックをもう一度見る。動いている CLI が
                                     その中にあれば先によける）
  8. install のフックを走らせる        失敗したら 7 を戻す（レジストリ「フック」）
  9. 後始末                           <Work>/staging/<name>/・<Work>/staging/<name>.zip・<Work>/old/<name>/ を消し、
                                     よけた CLI を消してみる
                                     {"outcome":"installed","name":…,"requested":…,"tag":…,"target":…,
                                      "registry":…,"plugins_dir":…,"hook":{…}}
```

- **GitHub の API を使いません。** レジストリの規則とマニフェストの絶対の参照で、取るものの場所が
  決まります。API の回数制限・トークンの扱い・リリース本文の読み取りが要りません。
- **新しいかは、タグとターゲットだけで比べます**（タグは使い回さないので、タグが同じならビルドも
  同じ）。マニフェストだけを取り、zip は取りません。
- **記録の `module` がフォルダの中に無いとき**（ウイルス対策が隔離した・手で消した）は、同じタグでも
  同じとみなさず、マニフェストを取って入れ直します（付け替えるので、Vectorworks が止まっている必要が
  ある）。`uninstall` は `module` が無いフォルダを消さない（安全弁）ので、壊れたフォルダは先にこの
  `install` で直してから `uninstall` します。
- **同じタグのとき**は、**記録に写した `hooks.install`** を走らせます（マニフェストのものは使わない。
  提供側が同じ場所のマニフェストを差し替えても、入れていないフックが走らないため）。
  `VW2026_HOOK_PREVIOUS_TAG` には同じタグを渡します。タグをそのまま指定し（`cli@<入っているタグ>`）、
  合った規則の `path` に `{tag}` があり、記録の `target` が今のターゲットと同じなら、マニフェストも
  取りません（ターゲットが違えば、入れ直すのでマニフェストを取る）。ネットワークにつながっていなくても、
  消えた PATH を置き直せます（CLI はフォルダの中にあるので、同じタグでは戻らない。消えたときは
  [初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)に `uninstall cli` を渡してから入れ直す）（`latest` のように決まった場所を指す規則では、今のタグを知るために
  マニフェストを取る）。入っているタグは `install` / `--check` の出力の `tag` と、記録で分かります。
- **プラグインと CLI は 1 つの zip から入り、同じフォルダと一緒に付け替わります**（`cli` の zip の
  `bin/` がそのまま `<Plug-Ins>/cli/bin/` になる）。動いているプラグインと入っている CLI は同じビルドです（[通信規則「版」](../protocol.md#版)の前提）。
- 初回でも Vectorworks が動いていれば何もせずに終わり、CLI も置きません（何も変えない）。
- **`cli` と同じ `<Plug-Ins>` に入れる**: Vectorworks が動いているかは、入れる先の `<Plug-Ins>/cli/spool/` の
  ロックで判定します。そのため、`cli` 以外のプラグインは、`cli` が入っている `<Plug-Ins>` にだけ入れます
  （`--plugins-dir` で別の `<Plug-Ins>` を渡したときも同じ）。`<Plug-Ins>/cli/` に正しい記録（`name` が `cli` で、
  `module` が実在する）が無ければ、何も変えずに失敗にします（`uninstall` も同じ）。`cli` の無い `<Plug-Ins>`
  では、Vectorworks が動いていても判定できず、付け替えとフックが走ってしまうためです。ワークグループの
  フォルダなど、`cli` の無い Plug-Ins へは入れられません（対応しない）。Go がここで `cli` の名前を使うのは、
  ロックの場所を決めるためだけです。
- **Vectorworks が動いているかはロックで判定します**（[通信規則「生存の判定」](../protocol.md#生存の判定)）。
  プロセス名は見ません。ロックを掴んでいない Vectorworks（`cli` が入っていない・起動の途中で
  最初の刻みの前・2 つ目の起動）が居るときは、Windows では読み込み中のフォルダの名前を変えられないので
  （[SDK の調査 6](../sdk-research.md#6-プラグインのフォルダの中のモジュール以外のものとモジュールの読み込み元分かった)）
  付け替えが失敗し、何も変わりません。mac では付け替えが成功し、その
  Vectorworks は古い版のまま動き、次の起動から新しい版になります。
- **ロックは手順 4 と付け替えの直前（[入れ替えの手順](#入れ替えの手順)の 2）の 2 度見ます。** 手順 4 は
  zip を取る前に断るため、直前の 2 度目は、zip を取って組み立てる間（ネットワーク次第で長い）に起動した
  Vectorworks を見落とさないためです。mac では付け替えが通るので、その間に起動してロックを掴んだ
  Vectorworks があると、次のことが起きます。
  - プラグインは `bridge.lock` を一度掴むと放さず（[通信規則「ロック」](../protocol.md#ロックbridgelock)）、
    POSIX では開いているファイルはフォルダの名前の変更に付いて動くので、掴まれたロックは付け替えで
    `<Work>/old/cli/spool/bridge.lock` へ移ります。プラグインはほかのファイルをスプールの場所の文字列から
    開き直す（`core::Bridge` はロックのハンドルとスプールのパスを持つ）ので、要求は付け替えたあとの
    `<Plug-Ins>/cli/spool/` で探します。
  - 新しい CLI は `<Plug-Ins>/cli/spool/` でロックを掴む者を見つけられず、Vectorworks が動いていても
    止まっていると判定し、`call` も断ります。
  - 手順 9 の後始末が、掴まれたままのロックごと `<Work>/old/cli/` を消します。それ以降の `install` /
    `uninstall` は、Vectorworks が動いているのに通ります。
- **フックが失敗して戻す前にも、ロックを見ます**（[入れ替えの手順](#入れ替えの手順)の 4）。フックの時間には
  上限が無く、その間に起動した Vectorworks が新しい版を読み込み、ロックを掴むことがあります。そのまま戻すと、
  mac では動いているプラグインのロックごと新しい版が消え、`Plug-Ins` には古い版が戻り、上と同じく止まって
  いると判定されます。Windows では読み込まれた新しい版の名前を変えられず、戻しの途中で止まります。
- 2 度目と戻しの前の確認のあとも見落とすのは、確かめてから名前を変えるまでのごく短い間に起動した
  Vectorworks と、起動の途中でまだ最初の刻みが来ていない Vectorworks だけで、どちらも上と同じくロックを
  掴んでいない Vectorworks です。
- **終了させるのは呼ぶ側です。** `install` は終了を頼まず、待ちもしません（[設計「CLI は
  プリミティブに保つ」](../design.md#cli-はプリミティブに保つ)）。終了から起動し直すまでを 1 度に
  行いたい呼ぶ側は、`session start` → `call quit` → 止まるのを待つ → `install` → `launch` →
  動き出すのを待つ、を組み合わせます。sh の見本は `vw2026 --help` にあります（CLI の使い方の真実は
  help。ほかのページは、組み合わせの決めごとをここで、見本を help で参照します）。見本が守る決めごとは
  次のとおりです。
  - `quit` は占有の中でだけ呼べ、図面を 1 枚も開いていないときだけ受け付けます。呼ぶ側が先に図面を
    保存して閉じます（[道具](tools.md#quit)。図面が開いているときの失敗は、標準出力の `detail` に一覧が出る）。
  - **失敗したら占有を解いてから抜けます。** 占有は Vectorworks を起動し直すまで残り、ほかの呼ぶ側は
    すべて `occupied` で断られるためです。`call quit` が失敗したとき、止まるのを待ちきれなかったとき、
    止まるのを待つ間に `status` が失敗したときに `session end` を呼びます。ただし `status` の失敗は
    スプールの場所が分からないとき（1）で、`session end` も同じ理由で失敗するので、占有は
    Vectorworks が終わるまで残ります。
  - 0 のまま上限を過ぎたのは、確かめてから頼むまでの間に利用者が図面を開いて保存の確認が開き、
    取り消された（または開いたままの）ときです。0 のまま抜けると成功に見えるので、待ちきれなかった
    ことを表す 3 で抜けます。
  - 動き出すのを待って 5 のまま上限を過ぎた・1 で失敗したら、その終了コードで抜けます。

  CLI は動き出す・止まるのを待つコマンドを持ちません（[設計](../design.md#cli-はプリミティブに保つ)）。
  `vw2026 status` を繰り返し、終了コードで分けます（PowerShell の書き方は `vw2026 help status`）。

  Vectorworks が終われば占有も消えるので、起動し直したあとに使うなら占有を取り直します。

  `quit` が入る（[実装の順序](plan.md)の段 6）までは、`call quit` と止まるのを待つところを、
  利用者が Vectorworks を手で終了することに置き換えます。

- 失敗したら（取れない・照らせない・展開できない・付け替えられない・フックが失敗した）、
  `<Plug-Ins>` を元のままにして理由を `message` に載せ、失敗の終了コードで終わります
  （フックがフォルダの外で変えたものは除く。よけた CLI も元の場所へ戻す）。

### 入れる先のフォルダ

**フォルダ名はレジストリの名前です**（`<Plug-Ins>/<name>/`。`cli` は `<Plug-Ins>/cli/`）。見れば何の
プラグインか分かり、名前からフォルダが直接決まります。

| `<Plug-Ins>/<name>/` | 振る舞い |
| --- | --- |
| 無い | 作って入れる |
| あり、記録の `name` が一致し、記録の `registry` が今回使ったレジストリと同じ | 更新として付け替える |
| あるが、記録が無い（手で入れたもの・ほかのインストーラで入れたもの） | **何も変えずに失敗にする。** `message` に場所を載せる（利用者のものを上書きしない） |
| あるが、記録の `name` がフォルダ名と違う（手で写したものなど）・記録が読めない（壊れている・知らない `record_version`） | **何も変えずに失敗にする。** `message` に場所を載せる（どう直すかは利用者が決める） |
| あるが、記録の `registry` が違う（後から既定のレジストリに同じ名前が載り、そちらが勝つようになったときなど） | **何も変えずに失敗にする。** 別のプラグインを黙って入れ替えないため。利用者が `uninstall` してから入れ直す（`cli` は既定のレジストリが先頭にあるので、この場合にならない） |

- **更新ではフォルダのパスが変わりません。** Vectorworks は署名の無いプラグインの「有効化」を
  モジュールのフルパスで覚えるので、モジュールのファイル名が変わらない限り、更新のあとも有効の
  まま読み込まれます（[Findings「Plug-in Modules」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)の「開発元不明のプラグイン」のダイアログ。SDK リファレンス #258）。
  `uninstall` してから入れ直しても同じパスなので、その間に Vectorworks を起動しなければ有効のままです
  （プラグインが居ない起動でダイアログを閉じると、有効化は消える）。
- 同じ名前のフォルダに記録が無ければ断るので、**同じ名前のフォルダへの上書きだけは CLI が防ぎます**。
  別の名前で同じプラグインが入っているか（手で入れたもの・別のレジストリの名前）は見ません。

### 入れ替えの手順

1. **組み立て**: zip を `<Work>/staging/<name>/` に展開し、直下のモジュールを確かめて、記録
   （`vw2026-install.json`）を書く。前回の残りの `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip` が
   あれば先に消す。
   **前回の残りの `<Work>/old/<name>/` があるとき**（前の `install` / `uninstall` が付け替えの途中で
   止まった）:
   - `<Plug-Ins>/<name>/` もあり、`old` の記録の `name` が一致して記録の `module` があるなら、退避の
     残りとみなして消す。
   - それ以外（`<Plug-Ins>/<name>/` が無い＝`old` が入っていた唯一の版かもしれない・`old` の記録が
     読めない）は、何も変えずに `old` の場所を `message` に載せて失敗にする（戻すか消すかは利用者が
     決める）。
2. **ロックをもう一度見て、動いている CLI をよける**: `<Plug-Ins>/cli/spool/` のロックが掴まれていれば、
   何も変えずに `vectorworks_running` で終わる（[流れ](#流れ)の 4 と同じ。2 度見る理由は[流れ](#流れ)の
   「ロックは手順 4 と付け替えの直前の 2 度見ます」）。このとき組み立てた `<Work>/staging/<name>/`・
   `<Work>/staging/<name>.zip` は消す。続けて、走らせている CLI の実行ファイルが `<Plug-Ins>/<name>/` の中にあれば、
   `<Work>/old/` へ名前の変更で移す（下記「[動いている CLI のよけ方](#動いている-cli-のよけ方)」）。
   失敗したら何もせずに終わる。
3. **付け替え**: `<Plug-Ins>/<name>` → `<Work>/old/<name>`、続けて `<Work>/staging/<name>` →
   `<Plug-Ins>/<name>`。1 つ目が失敗したら、2 でよけた CLI を戻して終わる。1 つ目が失敗するのは、
   Windows で次のどれかがフォルダの中のものを開いているときです。
   - エクスプローラーやウイルス対策がフォルダの中のファイルを開いている
   - Vectorworks が読み込んでいる
   - **端末などのプロセスのカレントディレクトリがフォルダの中にある**（`Path` は新しく開いた端末から効くので、
     開いたままの端末で `cd <Plug-Ins>\cli\bin` してから `.\vw2026.exe` を走らせたときなど。走らせた
     `vw2026` 自身もカレントディレクトリを受け継ぐので、CLI をよけても通らない）

   どれかを `vw2026` から見分けることはできないので、失敗の `message` には、名前を変えられなかった場所と
   ともに、これらを閉じる・カレントディレクトリをフォルダの外へ移すことを示します。2 つ目が
   失敗したら 1 つ目を戻し、よけた CLI を戻す。まだ入っていなければ 1 つ目は飛ばす。
4. **フック**: `install` のフックを走らせる。失敗したら、まず `<Plug-Ins>/cli/spool/` のロックを見る
   （[流れ](#流れ)の「フックが失敗して戻す前にも、ロックを見ます」）。掴まれていれば戻さない。戻しの
   1 の名前の変更が失敗したとき（Windows で、ロックを掴む前の Vectorworks が新しい版を読み込んでいる）も、
   その先へ進まない。どちらも新しい版を `<Plug-Ins>/<name>` に残し、`<Work>/old/<name>` とよけた CLI も
   残して（次の `install` の 1 と後始末が消す）、フックの失敗として失敗で終わる。`message` には、フックが
   失敗したことと、Vectorworks が起動したので新しい版を残したこと、Vectorworks を終了してから同じタグで
   `install` を走らせ直す（フックだけが走る）ことを載せる。ロックが掴まれていなければ、次の順に戻す。
   1. 新しい `<Plug-Ins>/<name>` を、名前の変更で `<Work>/staging/<name>` へよける（1 回で済み、元に
      戻せる。消すのはあとにする。ウイルス対策が新しいファイルを調べていると削除が途中で止まり、
      半分消えたプラグインが `Plug-Ins` に残るため）。
   2. `<Work>/old/<name>` を `<Plug-Ins>/<name>` へ戻す（最初に入れたときは無い）。
   3. 2 でよけた CLI を、戻したフォルダの元の場所へ戻す。
   4. よけた `<Work>/staging/<name>` を消す。
5. **後始末**: `<Work>/old/<name>/` などを消し（[流れ](#流れ)の 9）、中断した `uninstall` の印
   `<Work>/old/<name>.uninstalling` が残っていれば消し（付け替えに成功したので、もう中断した `uninstall` ではない。
   残すと、次の `install` が付け替えの途中で止まったときに、次の `uninstall` がそれを中断した `uninstall` と
   みなし、唯一残った `old/<name>/` を消してしまう）、2 でよけた CLI と前回までの残り
   （`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`）を消してみる。動いていて消せない
   ものは残し、次の `install` / `uninstall` で消す。

- 付け替えを名前の変更で行うのは、途中で失敗したときに元へ戻せるようにするためです（ファイル
  ごとに置き換えると、半端な版が残る）。
- 組み立てと退避の場所を `<Work>` に置くのは、`Plug-Ins` の外（Vectorworks に読まれない）で、
  前提により `<Plug-Ins>` と同じドライブにあるためです。
- **`install` と `uninstall` を同時に走らせないのは、呼ぶ側の責任です。** 同じ名前の 2 つの `install`
  は同じ `<Work>/staging/<name>/`・`<Work>/old/<name>/` を使い、片方の「前回の残りを消す」がもう片方の
  組み立ての途中のフォルダを消しうるので、「失敗したら `<Plug-Ins>` を変えない」が保てません。CLI は
  排他を持ちません（[設計「CLI はプリミティブに保つ」](../design.md#cli-はプリミティブに保つ)。
  排他はプラグインの占有だけで、`install` は Vectorworks が止まっている間に走るので占有も無い）。
  **名前が違っても同時に走らせません。** どの回も後始末で共通の `<Work>/old/vw2026.old-*` /
  `vw2026.exe.old-*` を消すので、mac では、`install cli@…` がよけた CLI を、同時に走る別の名前の
  `install` が消しえます（動いているファイルも消せる）。そのあと `cli` の付け替えかフックが失敗すると
  CLI を戻せず、`bin/vw2026` の無い `cli/` が残ります。
- フックが失敗して元に戻したとき、フックがフォルダの外で変えたもの（`cli` なら PATH）は
  戻りません。フックは何度走っても同じ結果になるように書くので、もう一度 `install` を走らせます。

### 動いている CLI のよけ方

**Windows では、開いているファイルを含むフォルダの名前を変えられません。** 動いている実行ファイルも
開いているファイルなので、`install cli@…` を走らせている CLI（`<Plug-Ins>/cli/bin/vw2026.exe`）が
`<Plug-Ins>/cli/` の中にある限り、付け替えの 1 つ目が失敗します。一方で、**動いている実行ファイルそのものの
名前は変えられ、同じボリュームの別のディレクトリへも移せます**（移すことも名前の変更）。そこで、
付け替えの前に CLI 自身をフォルダの外へ移します（[入れ替えの手順](#入れ替えの手順)の 2）。

- **条件は「走らせている CLI の実行ファイルが、付け替える `<Plug-Ins>/<name>/` の中にあること」だけ**です。
  実行ファイルの場所は `os.Executable()` を `filepath.EvalSymlinks` で解いたもの（mac の
  `~/.local/bin/vw2026` はリンクなので、解いた先で判定する）。Go のコードは名前で `cli` を見分けません
  （ほかの名前のフォルダに CLI が入ることはないので、実際に当たるのは `cli` だけ）。
- **中にあるかは、パスの文字列ではなくディレクトリの同一性で決めます。** 実行ファイルのあるディレクトリから
  親へ 1 つずつ上り、どれかが `<Plug-Ins>/<name>/` と `os.SameFile` で同じなら中にあるとします（根に着いたら
  外）。`<Plug-Ins>` は `--plugins-dir`・`VW2026_PLUGINS_DIR`・既定の場所のどれからでも来て、実行ファイルの
  パス（Windows では `Path` の項目のまま）と書き方が揃うとは限らないためです。文字列で比べると、Windows の
  大文字と小文字の違い・8.3 形式の短い名前・ジャンクションや `subst` を通したパス・末尾の区切りの有無で
  外と判定し、よけずに付け替えの 1 つ目が失敗します（何も変わらないが、入っている CLI では `install cli` /
  `uninstall cli` が通らなくなる）。`os.SameFile` は Windows ではボリュームとファイルの番号、mac では
  デバイスと inode で比べるので、どの書き方でも同じディレクトリなら一致します。
- 移す先は `<Work>/old/<実行ファイルの名前>.old-<時刻>`（`vw2026.old-…` / `vw2026.exe.old-…`）です。
  `<Work>` は前提により `<Plug-Ins>` と同じドライブにあるので、名前の変更で移せます。名前に `.` を
  含むので、`<Work>/old/<name>/`（名前は `.` を含まない）と重なりません。
- **mac でも同じ手順を踏みます。** mac は中で何が動いていてもフォルダの名前を変えられるので要りませんが、
  手順を OS で分けず、Go の単体テストを両方の OS で同じに走らせるためです。mac では後始末でそのまま消せます。
- 移したあとも、動いているプロセスはそのまま動き続けます（実行ファイルを読み直さない）。同じ実行ファイルから
  動いているほかの `vw2026`（別の端末の `status` の繰り返しなど）も、ファイルは 1 つなのでまとめて外れます。
  それらがスプールのファイルを開いている瞬間に当たると付け替えは失敗し、何も変わりません（やり直す）。
- **失敗したら元の場所へ戻します。** 付け替えの失敗とフックの失敗のどちらでも、フォルダを戻したあとで
  CLI を元の場所（`<Plug-Ins>/<name>/` の中の同じ相対パス）へ戻します（動いていても名前の変更はできる）。
- **後始末で消してみて、消せなければ残します。** Windows では、移した CLI は `install` が終わるまで
  動いているので、その `install` の中では消せません。次の `install` / `uninstall` が消します
  （`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*` だけ。[消すコードの歯止め](#消すコードの歯止め)）。
- よけてから付け替えるまでの間に止まる（Ctrl-C・電源断）と、`<Plug-Ins>/cli/` は CLI の無いまま
  残ります。このときは `vw2026` を走らせられないので、[初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)に
  `uninstall cli` を渡してから入れ直します（一時フォルダの CLI はフォルダの外で動くので、よけずに済む）。
- 初回のスクリプトから走らせたときは、動いている CLI は一時フォルダにあるので、よけません。

## CLI とスプールの置き場所

**`cli` の CLI とスプールは、`cli` のフォルダ（`<Plug-Ins>/cli/`）の中に置きます。** CLI は zip の
`bin/` がそのまま置かれたもの（`<Plug-Ins>/cli/bin/vw2026`）を PATH から使い、スプールはプラグインが
`<Plug-Ins>/cli/spool/` に作ります（[名前と識別子「置き場所」](identifiers.md#置き場所)）。

- **ねらいは、`cli` をほかのプラグインと同じ形に閉じ込めることです。** Go の `install` はどの
  プラグインにも「zip の中身をフォルダに置き、フォルダごと付け替える」だけを行います。CLI がフォルダの
  中にあれば、`cli` の CLI もこの付け替えで入れ替わり、フォルダを消せば CLI もスプールも一緒に消えます。
  `cli` のフックが受け持つのは、フォルダの外にしか置けない PATH だけです。
- **CLI を写して置き直す手順を持ちません。** 写しを持たないので、プラグインと CLI が食い違う（写しだけが
  古い・写しだけが消えた）ことが起きません。
- **スプールはどちらの側も自分のファイルの場所から求めます**（環境変数を読まず、探索しない）。
  プラグインは自分のモジュールの場所から、`vw2026` は自分の実行ファイルの場所から、同じ `<Plug-Ins>/cli/spool/`
  にたどり着きます（[通信規則「スプールの場所」](../protocol.md#スプールの場所)）。`--plugins-dir` を
  `call`・`session`・`status` に渡す必要はありません。`install` / `uninstall` は、入れる先の
  `<Plug-Ins>/cli/spool/` のロックで Vectorworks が動いているかを判定します（[流れ](#流れ)の 4）。
- **止まっていると答えるときは、求めたスプールの場所を示します。** フォルダの外で動かした `vw2026`
  （初回のスクリプトの一時フォルダのもの・zip を展開しただけのもの・手でビルドしたもの）は、Vectorworks が
  動いていても止まっていると答えるので、場所が無いと取り違えに気づけないためです（[通信規則「スプールの
  場所」](../protocol.md#スプールの場所)）。
  - `status` は、止まっているときも標準出力の JSON に `spool` を出しています（`{"running":false,"spool":…}`）。
    標準出力を捨てて終了コードだけを見る使い方でも場所が見えるように、標準エラーのメッセージにも載せます。
  - `call` と `session` は、ロックを掴む者が居ないときの標準エラーのメッセージに、実行ファイルの場所から
    求めたスプールの場所を載せます。標準出力と終了コードは変えません。
- **`cli` は利用者ごとの `Plug-Ins` にだけ置きます。** 複数の利用者が読み込む `Plug-Ins`（ワークグループの
  フォルダ・アプリケーションのフォルダの `Plug-Ins`）に置くとスプールも共有され、別の利用者の要求を
  自分の Vectorworks が実行しうるためです（[通信規則「スプールの場所」](../protocol.md#スプールの場所)）。
  `install` はネットワーク共有へは入れられません（`<Work>` と別のボリューム）が、同じボリュームの共有の
  フォルダへは `--plugins-dir` で入りうるので、渡さないのは利用者の責任です（[前提](#前提)の二重のインストールと
  同じく、確かめられない置き方を CLI が見分けない）。
- **フォルダの中のスプールは、付け替えで消えてかまいません。** 付け替えは Vectorworks が止まっている
  間にしか行わず、そのときスプールに要るもの（ロックを掴む者・応答を待つ者）は居ません。占有も
  Vectorworks の終了で消えます（[通信規則「占有」](../protocol.md#占有セッション)）。
  [レジストリ「提供側に求めること」](../registry.md#提供側に求めること)の「残したいものをプラグインの
  フォルダに書かない」でも、Vectorworks が動いている間だけ要るものは置いてよいとしています。
- **持続する `vw2026` の場所は持ちません。** 組み立て・退避・よけた CLI（`staging/`・`old/`）は、
  `cli` のものではなく、どのプラグインを入れるときにも使う `install` の作業の場所です。どれも
  利用者のデータではなく、消えてもレジストリから取り直せるので、利用者ごとの一時フォルダの下（`<Work>`）に
  置きます（[作業の場所](#作業の場所)）。
- **スプールが同期・リダイレクトの対象になる環境には対応しません。** 段 2 まではスプールを
  `%LOCALAPPDATA%` などの利用者のホームの下に置き、同期の対象にならない前提でした（[通信規則「プラグイン側の義務」](../protocol.md#プラグイン側の義務)）。
  段 3a からは Vectorworks の利用者フォルダの中なので、この前提は利用者フォルダの置き場所に依ります。
  - 移動プロファイル（Windows の既定の `<Plug-Ins>` は `%APPDATA%`（Roaming）の下）は、ログオンと
    ログオフのときに写すだけなので、動いている間のロックには関わりません。CLI とスプールも写されますが、
    スプールは Vectorworks が止まると要らないものです。
  - 利用者フォルダを OneDrive・iCloud などで同期するフォルダや、フォルダ リダイレクト・オフライン ファイルの
    対象に置くと、`bridge.lock` が断られ、`vw2026` からは止まっている（not running）ように見えます。
    利用者フォルダをそれらの対象から外して、Vectorworks を起動し直します（[通信規則「スプールの場所」](../protocol.md#スプールの場所)）。
- 受け入れたこと:
  - 通信規則を守るほかのプログラムは、`<Plug-Ins>` を知る必要があります（既定の場所は
    [名前と識別子「置き場所」](identifiers.md#置き場所)の規則で求まる）。

## `cli` のフック

**このプラグインの配置の知識のうち、フォルダの外に置くもの（PATH）は、`cli` のフック（`scripts/hooks/`）の
1 か所に置き、スクリプトのテストで確かめます**（下記「テスト」）。`install` の Go のコードは、どの
プラグインにも同じ手順だけを持ち、`cli` を特別に扱いません（[動いている CLI のよけ方](#動いている-cli-のよけ方)も、
名前ではなく実行ファイルの場所で決まる）。

| ファイル | すること |
| --- | --- |
| `hooks/install.sh` / `hooks/install.ps1` | 下記「PATH」 |
| `hooks/uninstall.sh` / `hooks/uninstall.ps1` | 下記「`uninstall` のフック」 |
| `hooks/lib.sh` / `hooks/lib.ps1` | 両方のフックが読み込む関数（PATH の項目の比べ方・足し方・除き方、リンクの判定）。`install` と `uninstall` が同じ比べ方を使うように 1 か所に置く |

- zip の直下に `hooks/` として入ります（[ビルド「梱包」](build-and-release.md#梱包)）。
- 標準出力に JSON のオブジェクトを 1 つだけ出します（`install` は `{"path":…}`。下記「PATH」。
  `uninstall` は `{"path":…,"left":[…]}`。`left` は消せなかった・確かめられなかったもの）。`install` /
  `uninstall` の出力の `hook` に載ります。
- PATH が指す先は `VW2026_HOOK_INSTALL_DIR`（`<Plug-Ins>/cli/`）の `bin/` です（[レジストリ「フックに渡す環境変数」](../registry.md#フックに渡す環境変数)）。
  `uninstall` のフックはフォルダを `<Work>/old/cli/` へ移したあとで走る（`VW2026_HOOK_PLUGIN_DIR` は移した先）
  ので、取り除く項目は `VW2026_HOOK_INSTALL_DIR` から決めます。

### PATH

**`install` のフックのたびに確かめ、足りなければ通します**（何度走らせても同じ結果になる）。結果は出力の
`path`（`linked` / `exists` / `added` / `not_in_path` / `conflict`）に載せます。PATH の失敗で
フックを失敗にはしません（プラグインは動く）。

| OS | すること | 既にあるとき |
| --- | --- | --- |
| mac | `~/.local/bin/vw2026` → `<Plug-Ins>/cli/bin/vw2026` のシンボリックリンク（`~/.local/bin` が無ければ作る） | **このプラグインの CLI を指すリンクなら何もしない。** それ以外（利用者のファイル・別の場所を指すリンク。別の `<Plug-Ins>` の `cli` を指すリンクを含む）なら触らず `conflict` |
| Windows | 利用者の環境変数 `Path`（`HKCU\Environment`）に `<Plug-Ins>\cli\bin` を追加 | 同じ項目が既にあれば何もしない（`exists`） |

- 行き先は `<Plug-Ins>/cli/bin/` で、フォルダを付け替えてもパスは変わらないので、更新で張り直す必要はありません。
- **シェルの設定ファイル（`.zshrc` 等）は書き換えません。** `~/.local/bin` が PATH に無ければ
  `not_in_path` とし、追加の方法を標準エラーに表示するだけです。
- 新しい値は **新しく開いた端末から**効きます。

#### Windows の `Path` の読み書き

**`HKCU\Environment` の値 `Path` を、.NET の `Microsoft.Win32.RegistryKey` で直接読み書きします。**

- **展開しない値を読み、型を保って書き戻します。** 利用者の `Path` には `%USERPROFILE%\…` の
  ような項目があり、型は REG_EXPAND_SZ です。`GetValue('Path', $null,
  [Microsoft.Win32.RegistryValueOptions]::DoNotExpandEnvironmentNames)` で読み、`GetValueKind` で
  型を得て、`SetValue('Path', <値>, <型>)` で書きます。PowerShell の
  `[Environment]::SetEnvironmentVariable('Path', …, 'User')` は展開した値を読み、REG_SZ で書き
  戻すとされるので、この項目が固定の値に変わるおそれがあり、使いません（[設計のレビュー B2](../design-review.md#b2-windows-の-path-の書き換えが既存の項目を壊しうる)）。
  `setx` も 1024 文字で切り詰めるので使いません。
- 型は読んだものをそのまま使います（REG_SZ なら REG_SZ）。値が無ければ REG_EXPAND_SZ で作ります
  （あとから利用者が `%…%` を含む項目を足しても展開されるように）。REG_SZ・REG_EXPAND_SZ 以外の
  型なら書き換えず、出力の `path` を `conflict` にします。
- 項目は `;` で分け、**`%…%` を展開せずに比べます。** 比べる前に、項目の前後の空白を除き、
  全体を囲む `"` を 1 組だけ除き、末尾の `\` を除いて、大文字と小文字を区別せずに比べます
  （Windows が同じディレクトリとして解決する書き方の違いを、同じ項目とみなすため）。
  `install` の「同じ項目が既にある」と `uninstall` の「一致する項目」は**同じ比べ方の関数**
  （`hooks/lib.ps1`）で判定します（片方だけが一致とみなすと、`install` が `exists` と答えた項目を
  `uninstall` が残すことになるため）。
  - `uninstall` は一致する項目を**すべて**除きます（利用者が書いた ` "C:\…\bin"` のような形も含む）。
    どれも `uninstall` が消すディレクトリを指すので、残すと消えたディレクトリを指したままになるため
    です。
  - 展開しないので、`%APPDATA%\Nemetschek\Vectorworks\2026\Plug-Ins\cli\bin` のように書かれた項目は
    `<Plug-Ins>\cli\bin` と一致しません。`install` はそれとは別に `<Plug-Ins>\cli\bin` を足し、`uninstall` はその
    項目を残します。
- 足すときは、値が空か末尾が `;` なら `<Plug-Ins>\cli\bin` を、そうでなければ `;<Plug-Ins>\cli\bin` を末尾に付けます
  （空の項目を増やさない）。ほかの項目の並び・空の項目・前後の空白は変えません。
- 除くときは、項目とその前の区切りの `;` を除きます（先頭の項目なら後ろの `;`）。元の値の末尾に
  あった `;` は戻りませんが（`C:\a;` に足して除くと `C:\a`）、空の項目は増えません。
- **除いて空になったら値ごと消します**（`DeleteValue`）。フックは値を作ったかを記録しないので、
  `Path` が無かった利用者で元の状態（値が無い）に戻すためです。元から空の値があった利用者では値が無く
  なりますが、どちらも `PATH` に足す項目が無い点で同じです。
- 書いたあと `user32` の `SendMessageTimeoutW(HWND_BROADCAST, WM_SETTINGCHANGE, 0, "Environment",
  SMTO_ABORTIFHUNG, 1000 ms)` で知らせます（`Add-Type` で呼ぶ）。上限はトップレベルのウィンドウ 1 つずつに順にかかる
  ので、全体で待つ時間は決まりません（応えの遅いウィンドウが多いと、その数だけ延びる）。全体の
  上限は持ちません（途中で打ち切ると、Explorer など後ろのウィンドウに知らせが届かず、そこから
  開いた端末に新しい値が効かないため）。知らせの失敗は無視します（値は書けていて、利用者が
  ログインし直せば効くため）。
- レジストリの読み書きは関数に分け、テストでは差し替えます（下記「テスト」）。実物のレジストリでの
  型の扱いは、下記「実物の exe の入れ替えのジョブ」で確かめます。

### `uninstall` のフック

消すもの: リンクと PATH の項目だけです。CLI とスプールはフォルダの中にあるので、フォルダと一緒に
`uninstall`（Go）が消します。

- **外のものを消し始めたら失敗にしません。** 消せなかったもの・確かめられなかったもの（PATH の書き換えに
  失敗した）は `left` に載せ、0 で終わります。フックが失敗にすると CLI がフォルダを `<Plug-Ins>/cli` へ
  戻すので、プラグインは残るのに PATH だけが消えた状態になるためです。失敗にするのは、何も消す前の
  確かめ（環境変数が足りない・PowerShell が使えない）だけです。
- **PATH の後始末**（`VW2026_HOOK_INSTALL_DIR` の `bin/` を指すものだけ）:
  - mac: `~/.local/bin/vw2026` が**シンボリックリンクで、`<Plug-Ins>/cli/bin/` の中を指すときだけ**消す。
    `~/.local/bin` は、`install` のフックが作ったものでも消しません（作ったかを記録しない。ほかの
    道具も使う場所）。
  - Windows: 利用者の `Path` から、`<Plug-Ins>\cli\bin` と**一致する項目だけ**を除く（比べ方と読み書きは
    `install` と同じ。[Windows の `Path` の読み書き](#windows-の-path-の読み書き)）。
- `<Work>` の下には何も置かず、何も消しません。

## アンインストール（`vw2026 uninstall`）

```sh
vw2026 uninstall import-ifc-homeskz
vw2026 uninstall cli                          # CLI そのものも消える
vw2026 uninstall cli --plugins-dir <Plug-Ins> # 既定以外の <Plug-Ins> から
```

1. **Vectorworks が動いていれば何もせずに終わる**（`<Plug-Ins>/cli/spool/` のロックで判定。install と同じ終了コード）。
   `<name>` が `cli` でなければ、`<Plug-Ins>/cli/` に正しい記録が無いときも何も変えずに失敗にする
   （[`cli` と同じ `<Plug-Ins>` に入れる](#流れ)）。
2. **安全弁**: `<Plug-Ins>/<name>/` に記録があり、記録の `name` がフォルダ名と一致し、記録の
   `module` がフォルダの中に実在するときだけ進む。フォルダはあるが記録が無い・一致しないなら、
   何も消さずに失敗にする（`vw2026` が入れたものではない）。
   - `<Plug-Ins>/<name>/` が無く、`<Work>/old/<name>/` に正しい記録（`name` が一致し `module` がある）が
     あり、**`<Work>/old/<name>.uninstalling`（手順 3 の印）もあれば**、前の `uninstall` が手順 3 のあとで
     止まったとみなし、手順 4 から続ける。
   - 印が無ければ、`install` が付け替えの途中で止まった（`old` が入っていた唯一の版かもしれない）のと
     見分けられないので、何も変えずに `old` の場所を `message` に載せて失敗にする（[入れ替えの手順](#入れ替えの手順)の
     1 と同じ。戻すか消すかは利用者が決める）。
   - どちらも無ければ何もせずに成功（`not_installed`）。
3. 印 `<Work>/old/<name>.uninstalling`（空のファイル）を書き、走らせている CLI が `<Plug-Ins>/<name>/` の
   中にあれば `<Work>/old/` へよけて（[動いている CLI のよけ方](#動いている-cli-のよけ方)）から、**先に**
   `<Plug-Ins>/<name>` を `<Work>/old/<name>` へ名前を変える（前回の残りの `old/<name>` の
   扱いは[入れ替えの手順](#入れ替えの手順)の 1 と同じ）。失敗したら（エクスプローラーやウイルス対策が
   フォルダを開いているとき・カレントディレクトリがフォルダの中にあるプロセスが居るとき。
   [入れ替えの手順](#入れ替えの手順)の 3 と同じ）よけた CLI を戻し、印を消して、何も変えずに失敗にする。
4. 記録の `hooks.uninstall` を、移した先（`<Work>/old/<name>/`）で走らせる（`VW2026_HOOK_PLUGIN_DIR` は
   移した先、`VW2026_HOOK_INSTALL_DIR` は `<Plug-Ins>/<name>/`）。失敗したら `<Work>/old/<name>` を
   `<Plug-Ins>/<name>` へ戻し、よけた CLI を戻し、印を消して失敗にする。
   **手順 2 で中断した回から続けたときは、失敗しても `<Plug-Ins>` へ戻しません**（`old/<name>/` と印を
   残し、場所を `message` に載せて失敗にする）。OS の一時フォルダの片付けはファイルを 1 つずつ消すので、
   続きの `old/<name>/` は記録とモジュールだけが残った壊れたフォルダかもしれず、それを `Plug-Ins` に
   戻さないためです。
5. `<Work>/old/<name>` を消し、最後に印 `<Work>/old/<name>.uninstalling` を消す。
6. よけた CLI と前回までの残り（`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`）を消してみる。
   消せなかったもの（Windows で、いま走らせている CLI）は出力の `left` に載せる（失敗にはしない）。
7. `<Work>` に `staging` / `old` の空のディレクトリしか無ければ、`<Work>` も消す。

- フックより先にフォルダを移すのは、フックが外のもの（`cli` なら PATH）を消したあとで
  フォルダの名前の変更が失敗すると、プラグインは残って読み込まれ続けるのに PATH だけが消え、
  利用者が `vw2026` を見つけられなくなるためです。
- 手順 3 と 5 の間で止まった（Ctrl-C・電源断）ときは、もう一度 `uninstall <name>` を走らせれば
  手順 4 から続きます（手順 2）。このとき `install <name>@…` は、`<Work>/old/<name>/` だけがある状態を
  断る（[入れ替えの手順](#入れ替えの手順)の 1）ので、先に `uninstall` を終わらせます。
  - `uninstall cli` が止まったときは、CLI がフォルダと一緒に `<Work>/old/cli/` へ移っているか、
    `<Work>/old/` へよけられていて、PATH からは `vw2026` を走らせられません。そのときは初回のスクリプトに
    `uninstall cli` を渡します（一時フォルダの `latest` の CLI が手順 4 から続ける）。入れ直すなら、
    そのあと初回のスクリプトで入れます。
- フックが失敗してフォルダを戻すとき、フックがすでに外のものを消していると戻せません。そのため
  **`uninstall` のフックは、確かめられることを先に確かめて失敗し、外のものを消し始めたあとは失敗に
  しない**ように書きます（消せなかったものは出力の `left` に載せる。[レジストリ「フック」](../registry.md#フック)）。

- **レジストリを読みません。** 記録だけで決まるので、レジストリから消えたプラグインや、
  ネットワークにつながっていないときでも外せます。
- **`uninstall` の出力の `remaining` には、どの名前でも、残った記録のある `<Plug-Ins>` の直下の
  フォルダの名前を載せます**（Go は `cli` を特別に扱わない）。`uninstall cli` はほかのプラグインが
  残っていても断りません。残ったプラグインは Vectorworks の中で動き続けますが、`vw2026` が無くなる
  ので外せなくなります（先に外したい呼ぶ側はこの一覧を見る）。
- 出力: `{"outcome":"uninstalled","name":…,"hook":{…},"remaining":[…],"left":[…]}`（`left` は手順 6 で
  消せなかったもの。無ければ空の配列）。

### `uninstall cli` のあとに残るもの

| 残るもの | OS | 理由 | 片付け |
| --- | --- | --- | --- |
| `<Work>/old/vw2026.exe.old-<時刻>`（いま走らせている CLI）と、それを含む `<Work>/old/`・`<Work>` | Windows | 動いている実行ファイルは消せない。自分が終わるのを待って消す別のプロセスは残さない（頼まれていないときに動く処理を足さない）。再起動のときに消す指定（`MOVEFILE_DELAY_UNTIL_REBOOT`）は管理者の権限が要る | 出力の `left` に載る。一時フォルダの中なので、OS の片付けで消える（[作業の場所](#作業の場所)）。次に入れたときの `install` も消す |
| `~/.local/bin`（ディレクトリ） | mac | フックが作ったかを記録せず、ほかの道具も使う場所 | 残してよい |
| ほかのプラグインのフォルダ | 両方 | `uninstall cli` はほかのプラグインを外さない（上記 `remaining`） | 先にそれぞれを `uninstall` する |
| Vectorworks が覚えた「有効化」 | 両方 | Vectorworks の設定で、`vw2026` は触らない | 要らない（同じパスに入れ直せば、その間に起動しない限り有効のまま） |

- **すぐに何も残さずに外したいとき**（Windows）は、初回のスクリプトに `uninstall cli` を渡します。走るのは
  スクリプトの一時フォルダの CLI なので、`<Plug-Ins>/cli/` の中の CLI は動いておらず、よけずにフォルダごと消え、
  `<Work>/old/` の前回までの残りも消せます。スクリプトの一時フォルダはスクリプトが消します。
- この表の 1 行目は、CLI を `%LOCALAPPDATA%\vectorworks2026-cli\bin\` に置いていた設計（#61）でも同じでした
  （`uninstall` のフックが動いている `vw2026.exe` を消せずに名前を変えて残した）。CLI をフォルダの中に置き、
  作業の場所を一時フォルダにしたことで、残る場所が持続する場所から一時フォルダに変わり、残したものを
  片付けるのがフックから Go の `uninstall` と OS に移りました。

## 消すコードの歯止め

**利用者のものを消すコードは次の場所だけ**にし、歯止めを緩めません。段 3b でこの表を `CLAUDE.md` に写します。

| 消すコード | 消してよいもの |
| --- | --- |
| `install`（組み立て・後始末・フックの失敗の戻し） | `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip`（どちらも名前をそのまま組み立てたパスだけ。前方一致では消さない）・`<Work>/old/<name>/`（退避した版と前回の残りは、記録の `name` が一致し、記録の `module` があり、`<Plug-Ins>/<name>/` もあるときだけ）・フックが失敗したときの新しい `<Plug-Ins>/<name>/`（自分が置いたもの）・`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`（ファイルだけ。よけた CLI と前回までの残り）・付け替えに成功したあとの印 `<Work>/old/<name>.uninstalling` |
| `uninstall` | 記録の `name` が一致し、記録の `module` がある `<Plug-Ins>/<name>/`（`<Work>/old/<name>/` へ移してから消す）・自分が書いた印 `<Work>/old/<name>.uninstalling`・`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`（ファイルだけ）・空の `<Work>` |
| `cli` の `install` のフック | なし |
| `cli` の `uninstall` のフック | `<Plug-Ins>/cli/bin/` の中を指す `~/.local/bin/vw2026`・`Path` の `<Plug-Ins>\cli\bin` と一致する項目（どちらも `VW2026_HOOK_INSTALL_DIR` から決める） |

- ほかのプラグインのフックがフォルダの外で消すものは、そのプラグインの提供側の責任です
  （[レジストリ「フック」](../registry.md#フック)）。

## テスト

- **`install` / `uninstall`**: Go の単体テスト。配置を行うパッケージの関数には、場所
  （`<Plug-Ins>`・`<Work>`）と既定のレジストリを引数で渡し、偽の HTTP サーバー（`httptest`）と一時
  ディレクトリで確かめます（環境変数は増やさない）。押さえること:
  - レジストリの順と規則の選び方（先に見つかった名前・最初に合った規則・取れなければ次へ進まない・
    `{tag}` のある規則でのタグの照合・知らない版と項目）
  - 新しいかの判定（同じタグとターゲットで zip を取らず、付け替えずにフックだけを走らせる・同じタグでも
    Vectorworks が動いていればフックを走らせない・`--check` で何も変えない）
  - sha256 が合わない・zip の形が正しくない（モジュールが無い・2 つある・シンボリックリンク・`..`・
    `\`）ときに何も変えない
  - 入れる先のフォルダ（記録が無い・`registry` が違うときに断る）
  - ロックが掴まれているときに何も変えない（手順 4 で見たあと、付け替えの直前までに掴まれたときも。
    偽の HTTP サーバーが zip を返すときにロックを掴み、`<Plug-Ins>` が変わらず `vectorworks_running` で
    終わることを確かめる）
  - 付け替えの途中の失敗と、フックの失敗で元に戻る（フックが走る間にロックが掴まれたときは戻さず、新しい版を
    残して失敗で終わる。偽のフックの中でロックを掴む）
  - フックの走らせ方（引数・作業ディレクトリ・環境変数・標準出力が JSON でないときの失敗・
    `uninstall` で記録のフックを走らせる・`sh` / `powershell` の 2 つ目が zip の中に無い・`-` で始まる
    ときに断る）。偽のフックを入れた zip を偽の HTTP サーバーから配る
  - 消すコードの歯止め（記録が無い・名前が違う・モジュールが無いフォルダを消さない）
  - 前回の残りの `<Work>/old/<name>/`（`<Plug-Ins>/<name>/` があり記録が正しければ消す・`<Plug-Ins>/<name>/`
    が無い・記録が読めないなら何も変えずに失敗）
  - `uninstall` の順序（フォルダを移せないときにフックを走らせない・フックが失敗したらフォルダを戻す・
    手順 3 のあとで止まったときに、印があれば手順 4 から続け、印が無ければ断る・続きから走った回で
    フックが失敗したら `<Plug-Ins>` へ戻さない）
  - `cli` 以外を入れる・外すとき、`<Plug-Ins>/cli/` に正しい記録が無ければ何も変えない
  - 付け替えに成功した `install` が、残っていた印 `<Work>/old/<name>.uninstalling` を消す
  - 同じタグでも記録の `module` が無ければ入れ直す・記録の `name` が違う・記録が読めないときに断る
  - 同じタグのとき（記録の `hooks.install` を走らせる・`{tag}` のある規則でターゲットも同じならマニフェストを
    取らない・ターゲットが違えば取って入れ直す）
  - フックの失敗の戻し（新しいフォルダを名前の変更でよけてから前の版を戻す）・`registry` の比べ方（整えた文字列どうし）
  - `uninstall` の出力の `remaining`（どの名前でも出す）
  - 既定のレジストリ（`cli/internal/registry/default.json`）が正しく読めること
  - タグの検査（`.`・`..`・先頭が英数字でないものを断る）とターゲットの決め方（mac は計算機の種類で
    決め、プロセスの種類では決めない。判定の関数を差し替えて確かめる）
  - 動いている CLI のよけ方（走らせている CLI の実行ファイルの場所を関数で差し替え、一時ディレクトリの
    偽の実行ファイルで確かめる。`<Plug-Ins>/<name>/` の中にあればよけ、外にあればよけない・`<Plug-Ins>` を
    実行ファイルと違う書き方（シンボリックリンクを通したパス・末尾の区切り・大文字と小文字の違い）で
    渡しても中にあると判定する。大文字と小文字の違いは、OS ではなく一時ディレクトリのボリュームが大文字と
    小文字を区別しないとき（大文字と小文字を変えた名前を `os.Stat` して確かめる）に走らせる（Windows と、
    mac の既定の APFS の両方で走り、どちらかで文字列の比較に戻ったときに気づける）・付け替えの
    1 つ目と 2 つ目の失敗・フックの失敗・`uninstall` のフォルダの移動とフックの失敗で元の場所へ戻す・
    後始末で消す・消せないものは `install` では残し `uninstall` では `left` に載せる・`<Work>/old/` の
    直下の `vw2026.old-*` / `vw2026.exe.old-*` のほかを消さない）。動いている実物の exe は下記
    「実物の exe の入れ替え」で確かめる
- **コマンドのテストでの場所の差し替え**: コマンド（`cli/cmd/vw2026`）は、上の関数に渡す場所を
  `env` から得ます。`vw2026` のテストはスプールの場所を `env.spool` で差し替えます。
  - スプールは、実行ファイルの場所から求める `spool.Dir()`（`os.Executable()` を `spool.DirOf` に渡す。
    [通信規則「スプールの場所」](../protocol.md#スプールの場所)）で、本番では `main()` だけがこれを
    `env.spool` に入れる（`call`・`session`・`status`・`launch` が使う）。`spool.DirOf` は一時ディレクトリの
    偽の実行ファイルで確かめる。
  - `install` / `uninstall` を足す PR で、次のように改め、`CLAUDE.md`「Go」の記述も同じ PR で直します。
    - `<Work>` を返す `env.workDir`、既定の `<Plug-Ins>` を返す `env.pluginsDir`、走らせている CLI の
      実行ファイルの場所を返す `env.executable` を足す。本番では `main()` だけがそれぞれを求める関数
      （求め方は[名前と識別子「置き場所」](identifiers.md#置き場所)）を入れる。
    - テストの `invoke` は、どれも既定で一時ディレクトリ（`env.executable` はその中の偽のファイル）を返す
      関数を入れる（`env.spool` はすでにそうしている）。テストが場所を渡し忘れても、開発者のマシンの本物の
      `<Plug-Ins>`・`<Work>`・スプールに触れないためです。`--plugins-dir` は、既定以外の場所を渡したときの
      振る舞いを確かめるテストだけが付けます。
    - `install` / `uninstall` は、ロックを入れる先の `<Plug-Ins>/cli/spool` で見る（`env.spool` ではない。
      入れる先の Vectorworks が動いているかを見るため）。
- **`cli` のフック**: CI の `hooks.yml`（[ビルド「CI」](build-and-release.md#ci)）で確かめます。どちらも
  一時ディレクトリを `HOME`・`VW2026_HOOK_*` に渡し、利用者の場所に触れません。
  - mac（`sh`）: `tests/hooks/hooks_test.sh`（`sh` で書いた小さなテスト。外部の枠組みを使わない）。
    `lib.sh` の関数と、`install.sh` / `uninstall.sh` の全体（リンク・別の場所を指すリンクと利用者の
    ファイルに触れない・`uninstall` は `VW2026_HOOK_PLUGIN_DIR` が移した先でも `VW2026_HOOK_INSTALL_DIR`
    を指すリンクを消す・出力・2 回走らせても同じ結果）を確かめる。
  - Windows（`powershell`）: `tests/hooks/Hooks.Tests.ps1`（Pester。版は `scripts/powershell.ps1` で
    固定し、Windows に入っている Pester 3.4 は使わない）。`lib.ps1` の `Path` の文字列の関数（足し方・
    除き方・比べ方。末尾の `;`・空になったとき・前後の空白と `"` を含む項目）と、`install.ps1` /
    `uninstall.ps1` の全体（レジストリの読み書きと知らせは差し替える）を
    確かめる。Windows PowerShell 5.1 で走らせる（フックが走るのと同じもの）。どちらのフックも、
    標準出力が UTF-8 の JSON のオブジェクト 1 つだけであること（日本語を含むパスでも）と、`uninstall` の
    フックが外のものを消し始めたあとは失敗しないことを確かめる。
- **実物の exe の入れ替え**: PR の `build.yml` で、`release`（PR のプレリリースを出す）の
  あとに Windows のジョブで確かめます。**動いている CLI をよけるのが、その PR の Go のコードになる順**に
  します（PR で[動いている CLI のよけ方](#動いている-cli-のよけ方)を壊したら、このジョブが落ちるように）。
  よけるのは走らせている CLI 自身なので、PR の CLI を `<Plug-Ins>\cli\bin\` に入れてから、その CLI に
  付け替え（`uninstall cli` と、版の違う `install`）をさせます。
  1. 利用者の `Path` の値を消しておく（下の 1 のため）。PR の zip から `bin\vw2026.exe` を一時フォルダへ
     取り出し、`install cli@<その PR のタグ>` を走らせる（初回のスクリプトと同じ入り方）。
  2. 実物のレジストリで `Path` の扱いを確かめる（下記）。走らせるのは同じタグの `install` で、付け替えない
     ので CLI はよけない。
  3. 入った `<Plug-Ins>\cli\bin\vw2026.exe` で `uninstall cli` を走らせる。出力が `uninstalled` で、
     `<Plug-Ins>\cli\` が無く、`Path` に `<Plug-Ins>\cli\bin` が無く、`left` に載った
     `<Work>\old\vw2026.exe.old-*` が 1 つだけ残っていることを確かめる。
  4. 手順 1 と同じく一時フォルダの PR の CLI で `install cli@<その PR のタグ>` を走らせ、手順 3 の残りが
     消えたことを確かめる（手順 3 のプロセスは終わっているので消せる）。
  5. 入った `<Plug-Ins>\cli\bin\vw2026.exe` で `install cli@latest` を走らせる。動いているのは PR の
     ビルドで、PR の Go のコードが自分をよけて、フォルダを `latest` のものに付け替える。出力が
     `installed` で、`<Plug-Ins>\cli\bin\vw2026.exe version` の版が `<Plug-Ins>\cli\build.json` の
     `version`（`latest` のビルド）と一致し、手順 4 で入った PR の `version` と違い、
     `<Work>\old\vw2026.exe.old-*` が残り、`<Work>\old\cli\` が無いことを確かめる。比べるのはどちらも
     `build.json` の `version`（同じ zip から入った CLI とプラグインの版）で、タグとは比べない
     （タグの形は版の付け方で変わる。[ビルド「リリースの形」](build-and-release.md#リリースの形)）。
  - **PR の CLI が `latest` を入れられないとき**は、手順 5 を飛ばします。入れられないときとは次のどれかで、
    ジョブが PR のマニフェストと `latest` のマニフェストを比べて決めます。
    - `latest` にマニフェストが無い（段 3b を入れる PR 自身。`latest` がまだ `stable` で `vw2026.json` が無い）。
    - PR の CLI が `latest` の `manifest_version` を読めない。
    手順 3 で、PR のコードが動いている自分をよけることは確かめられます。
  - `main` への push では、版の違う相手が無いので走らせません（PR で確かめてからマージする）。
  - ネットワークと公開済みのリリースに頼るのは、同じ位置にある `verify` ジョブと同じです。
  - 別の `vw2026` を動かしたまま入れ替える形は組めません（ロックが掴まれていると `install` が何もせずに
    終わり、放されると `call` も終わる）。ランナーは使い捨てなので既定の場所（`<Plug-Ins>`・`<Work>`）を
    使いますが、利用者の場所に触れるので `go test` には入れません。
- **実物の exe の入れ替えのジョブ**（`build.yml` の `install-windows`）の条件と、ほかに確かめること:
  - `needs: [meta, release]` で、`release` が公開したあとにだけ走ります。`release` が飛ばされる
    fork の PR・マージキュー・`main` 以外の手動の実行では、ジョブも飛ばされます。`main` への push
    は `if` で除きます。
  - タグは使い回さず、リリースは下書きで資産を上げ終えてから公開するので（[ビルド「リリースの形」](build-and-release.md#リリースの形)）、
    資産が一瞬無いことはありません。ジョブは走らせ直しを持ちません。
  - **実物のレジストリで、`Path` の 3 つの型の扱い**（[Windows の `Path` の読み書き](#windows-の-path-の読み書き)）。
    手順 2 で、利用者の `Path` を置き直して同じタグの `install cli@<その PR のタグ>`（PR の
    フックだけが走る）を走らせ直し、次を確かめます（ランナーは使い捨てなので、元の値は戻さない）。
    1. 手順 1 のあと、REG_EXPAND_SZ で `<Plug-Ins>\cli\bin` だけの値ができている。
    2. REG_SZ の `C:\vw2026-probe-sz` に置き直して走らせる → REG_SZ のまま
       `C:\vw2026-probe-sz;<Plug-Ins>\cli\bin` になる。
    3. REG_EXPAND_SZ の `%USERPROFILE%\vw2026-path-probe;` に置き直して走らせる → REG_EXPAND_SZ の
       まま、項目が展開されずに残り、`%USERPROFILE%\vw2026-path-probe;<Plug-Ins>\cli\bin` になる（末尾の
       `;` に区切りを重ねない）。
    4. 置き直さずにもう一度走らせても同じ値のまま（`exists`）。
    5. 手順 3 の `uninstall cli` のあと、REG_EXPAND_SZ のまま `%USERPROFILE%\vw2026-path-probe` になる。
- **初回のスクリプト**: shellcheck・PSScriptAnalyzer。取ってきて `install` を走らせるだけなので、
  実機の確認（段 3b）で押さえます。
