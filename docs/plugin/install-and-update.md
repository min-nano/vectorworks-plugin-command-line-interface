# インストール・PATH・アンインストール・更新

インストーラとアンインストーラは元:`scripts/vw-install.*` / `vw-uninstall.*` を移し、
**CLI の置き場所・PATH の扱い・殻の ID が同じ更新の入れ方を足します**。**更新は CLI
（`vw2026 update`）が行い**、元の殻の中のアップデータ（元:`src/Updater*`）と同梱スクリプト（元:`vw-update.*` / `vw-token.*`）は移しません。

## 置き場所

**CLI はプラグインのフォルダの外に置きます。** Windows では、開いているファイルを含む
フォルダは名前を変えられません。CLI がプラグインのフォルダの中（`<Plug-Ins>\cli\bin\`）に
あると、MCP などが `vw2026 status` を呼んでいるだけで、また `vw2026 update` や終了を待つ係が
自分自身として動いているだけで、プラグインのフォルダを付け替えられなくなるためです。

| 置くもの | mac | Windows |
| --- | --- | --- |
| プラグイン（`<Plug-Ins>/<name>/`） | `~/Library/Application Support/Vectorworks/2026/Plug-Ins/<name>/` | `%APPDATA%\Nemetschek\Vectorworks\2026\Plug-Ins\<name>\` |
| CLI の場所（`<CLI>`） | `~/Library/Application Support/vectorworks2026-cli/` | `%LOCALAPPDATA%\vectorworks2026-cli\` |
| CLI（安定版） | `<CLI>/bin/vw2026` | `<CLI>\bin\vw2026.exe` |
| CLI（開発版） | `<CLI>/bin-dev/vw2026` | `<CLI>\bin-dev\vw2026.exe` |
| 待機の場所 | `<CLI>/pending/<name>/` | `<CLI>\pending\<name>\` |

- `<VW>` は Vectorworks の利用者フォルダ（mac `~/Library/Application Support/Vectorworks/2026`、
  Windows `%APPDATA%\Nemetschek\Vectorworks\2026`）で、`<Plug-Ins>` はその中にあります。
- 開発版の CLI は PATH に載せません（`vw2026 --channel dev` で開発版の橋へ届くので、コマンドは
  1 つでよい）。開発版の CLI を別に置くのは、開発版のインストールが安定版の CLI を書き換え
  ないようにするためです。
- **配布 zip の形は変えません**（`bin/` は zip の直下にある）。インストーラが `bin/` だけを
  CLI の場所へ置きます。

## インストーラ（`vw-install.sh` / `.ps1`）

- **配置の規則: zip の直下の `bin/` は CLI の場所（`<CLI>/bin/`。開発版は `<CLI>/bin-dev/`）へ、
  それ以外はそのまま `<Plug-Ins>/<name>/` へ置く。** ファイル名を列挙しない。除くのはインストーラ
  自身と `__MACOSX` / `.DS_Store` だけ。
- **プラグインの入れ替えは 2 通り**で、インストーラ自身が選びます（下記「入れ替えの手順」）。
  - **殻の ID が同じ**（入っている `shell-id` と zip の `shell-id` が一致する）: 殻以外のファイルを
    1 つずつ名前の変更で上書きする。Vectorworks が動いていても行える。
  - **殻の ID が違う・読めない・まだ入っていない**: フォルダごと名前の付け替えで入れ替える。
    Vectorworks 2026 のプロセスが 1 つも無いときだけ行う。
- **CLI の入れ替えは、プラグインを入れ終えてから**行う（プラグインの入れ替えが失敗したときに、
  CLI だけが新しくならないように）。下記「CLI の入れ替え」。
- 取り除く古い版は、その版自身のアンインストーラで消す（歯止めは元のまま）。
- mac: 置いたものの隔離属性を外し（`xattr -dr com.apple.quarantine`）、アドホック署名をかけ直す
  （`bin/vw2026` も対象）。Windows: `Unblock-File`。どちらも組み立ての場所で済ませてから置く。
- 機械可読の出力: `installed-shell=<VW_SHELL_ID>`・`mode=files|swap` → `ok` / `error=`。

### 入れ替えの手順

1. **組み立て**: 新しい版を `<VW>/vectorworks2026-cli-staging/<name>/` に丸ごと置く（`bin/` を
   除く。隔離属性の解除・署名・`Unblock-File` もここで済ませる）。`Plug-Ins` の外なので、
   組み立て中に Vectorworks が起動しても読まれない。`<Plug-Ins>` と同じボリュームなので、
   次の段はどれも名前の変更だけで済む。
2. **殻の ID を比べる**: `<Plug-Ins>/<name>/shell-id` と組み立てた `shell-id` を比べ、どちらの
   方式で入れるかを決める（読めなければ「違う」とみなす）。

#### 殻の ID が同じとき（ファイルの上書き）

殻（mac `<name>.vwlibrary/`、Windows `<name>.vlb` と隣の `<name>.vwr` / `.commit` / `.branch` /
`.shell-id`）は Vectorworks が読み込んでいて、Windows ではファイルが開かれたままです。殻の ID が
同じなら殻を置き換える必要は無いので、**殻には触れず、それ以外のファイルだけを置き換えます。**
本体は殻が一時ディレクトリの複製から読み込んでいる（[構成](architecture.md#殻と本体)）ので、
`<Plug-Ins>/<name>/` の本体のファイルは開かれていません。

3. **殻のファイルの一覧はインストーラが持つ**（新しいビルドの側の知識。上の配置の規則の例外は
   この一覧だけ）。組み立てた版のうち、殻のファイル以外のものを 1 つずつ置き換える。
   置き換えは、組み立ての場所から名前の変更で上書きする（同じボリュームなので一瞬で終わる。
   mac `mv -f`、Windows `Move-Item -Force`。中身は `MoveFileEx` の `MOVEFILE_REPLACE_EXISTING`）。
   **本体（`<name>.vwpayload`）を最後に置き換える**（殻は本体のファイルが変わったことで
   読み直すので、そのときにはほかのファイルが揃っているようにする）。
4. 組み立てた版に無く、入っている版にだけあるファイルは、殻のファイルでなければ消す。
   最後に組み立ての場所（中身は殻のファイルだけが残っている）を消す。
5. 置き換えが共有違反で失敗したら（殻がちょうど本体を一時ディレクトリへ複製している間）、
   200 ms おきに 5 回までやり直す。それでも失敗したら `error=busy` で終わる。

- 殻の ID が同じ版どうしは ABI が同じなので、途中で Vectorworks が起動しても、本体が古い版の
  ままか新しい版になるかのどちらかで、殻と本体が食い違うことはありません。
- 殻のファイル（`.commit` / `.branch` / mac の `Info.plist` の刻印）は殻を入れたビルドのまま
  残ります。何が入っているかは `build.json` で判定します（[流れ](#流れ)）。
- 殻が持つリソース（`.vwr`）を殻の ID に含めるのは、この方式で `.vwr` を置き換えないためです
  （[ビルド「殻の ID」](build-and-release.md#殻の-id)）。

#### 殻の ID が違うとき（フォルダの付け替え）

3. **確かめ**: 付け替えの直前に、Vectorworks 2026 のプロセスが無いことを確かめる。居れば
   付け替えずに終わる（`error=running`）。
4. **付け替え**: `<Plug-Ins>/<name>` → `<VW>/vectorworks2026-cli-old/<name>`、続けて
   `<VW>/vectorworks2026-cli-staging/<name>` → `<Plug-Ins>/<name>`。どちらも名前の変更なので
   一瞬で終わる。1 つ目が失敗したら何もせずに終わる（`error=locked`。エクスプローラーや
   ウイルス対策がフォルダの中のファイルを開いているときなど）。2 つ目が失敗したら 1 つ目を戻す。
5. **後始末**: `<VW>/vectorworks2026-cli-old/<name>` を、**古い版のアンインストーラで、
   そのフォルダだけを**消す（`--folder-only`。下記）。フォルダ名と中の殻を確かめる歯止めが
   そのまま効くよう、移した先でもフォルダ名を `<name>` に保つ。

- CLI はプラグインのフォルダの外にあるので、CLI が動いていても付け替えは妨げられません。
- 付け替えの 2 回の名前の変更の間（ミリ秒）に Vectorworks が起動すると、プラグインのフォルダが
  無い状態を読みます。そのときはその起動に限りプラグインが読み込まれない（`vw2026 status` が
  `live:false`）だけで、**半端な版を読むことはありません**。次の起動からは新しい版です。
- mac には 2 つのディレクトリを一度に入れ替える `renamex_np(RENAME_SWAP)` がありますが、
  インストーラ（シェル）からは使えないので、上の 2 回の名前の変更で揃えます。

### CLI の入れ替え

CLI は、`vw2026 update`・終了を待つ係・MCP などの呼び出しとして、**入れ替えの最中にも動いて
いることがあります。** 動いている実行ファイルは、mac では上書きでき（動いているプロセスは古い
inode を使い続ける）、Windows では上書きも削除もできませんが、**名前の変更はできます**。そこで
1 ファイルずつ名前の変更で入れ替えます。

1. 新しい CLI を `<CLI>/bin/` の中へ一時的な名前（`vw2026.new` / `vw2026.exe.new`）で置く
   （隔離属性の解除・署名・`Unblock-File` も済ませる）。
2. mac: `mv -f vw2026.new vw2026`。
   Windows: `vw2026.exe` を `vw2026.exe.old-<時刻>` へ名前を変え、`vw2026.exe.new` を
   `vw2026.exe` へ名前を変える。2 つ目が失敗したら 1 つ目を戻す。
3. 残っている `vw2026.exe.old-*` を消してみる（動いている間は消せないので、失敗は無視して
   次のインストールで消す）。

- 名前を変えられた古い CLI は、動いている間はそのまま動き続けます。次に呼ばれたときから
  新しい CLI です。
- **動いている exe の名前を変えられること**はスクリプトのテスト（Windows の CI）で押さえます
  （`vw2026 wait` を動かしたまま入れ替える）。

### PATH（追加分）

置き終えてから、**安定版のときだけ**行います（開発版はリンクを張らない）。

| OS | すること | 既にあるとき |
| --- | --- | --- |
| mac | `~/.local/bin/vw2026` → `<CLI>/bin/vw2026` のシンボリックリンク（`~/.local/bin` が無ければ作る） | **このプラグインの CLI を指すリンクなら張り直す。** それ以外（利用者のファイル・別の場所を指すリンク）なら触らず、`path=conflict` と出す |
| Windows | 利用者の環境変数 `Path`（`HKCU\Environment`）に `<CLI>\bin` を追加 | 同じ項目が既にあれば何もしない |

- 行き先がプラグインのフォルダの外で版によらず同じなので、**更新でリンクと PATH を張り直す
  必要はありません。**
- **シェルの設定ファイル（`.zshrc` 等）は書き換えません。** `~/.local/bin` が PATH に無ければ、
  追加の方法を表示するだけです（`path=not-in-path`）。
- Windows は `[Environment]::SetEnvironmentVariable('Path', …, 'User')` で書きます（`setx` は
  1024 文字で切り詰めるので使わない）。新しい値は**新しく開いた端末から**効きます。
- 機械可読の出力に `path=linked|added|exists|not-in-path|conflict` を加えます。PATH の失敗で
  インストールを失敗にはしません（プラグインは動く）。

## アンインストーラ（`vw-uninstall.sh` / `.ps1`）

2 つの使い方があります。

| 使い方 | 消すもの | 使う場面 |
| --- | --- | --- |
| `vw-uninstall` | プラグインのフォルダ・その系列の CLI（`<CLI>/bin/` または `bin-dev/`）・その系列の待機の場所（`<CLI>/pending/<name>/`）・リンクと PATH の項目 | 利用者がアンインストールする |
| `vw-uninstall --folder-only <フォルダ>` | 渡されたプラグインのフォルダだけ | インストーラの付け替えの後始末 |

- **安全弁**: プラグインのフォルダは、フォルダ名が `<name>` と一致し、中に殻
  （`<name>.vwlibrary` / `<name>.vlb`）があるときだけ消す。無ければ成功として扱う。
  CLI のフォルダは、名前が `bin` / `bin-dev` で、親が `<CLI>` のときだけ消す。
- 待機の場所を消すのは、アンインストールのあとに終了を待つ係が古い更新を入れ直さないように
  するためです（係は待機の場所が無ければ何もせずに終わる）。
- 動いている CLI（Windows）は消せないので、名前を変えて残し、`bin=busy` と出す（アンインストールは
  失敗にしない）。
- **PATH の後始末（追加分）**:
  - mac: `~/.local/bin/vw2026` が**シンボリックリンクで、`<CLI>/bin/` の中を指すときだけ**消す。
  - Windows: 利用者の `Path` から、`<CLI>\bin` と**完全に一致する項目だけ**を除く。

**利用者のものを消すコードが増えます。** 元のプラグインの規約（消すコードは数か所だけで、
歯止めを緩めない）に倣い、このリポジトリの `CLAUDE.md` に「消すのはアンインストーラの
フォルダ・リンク・PATH の項目だけ」と書き、上の歯止めを回帰テストで押さえます
（元:`tests/vw-uninstall.test.sh` / `.Tests.ps1` に、別の場所を指すリンク・利用者のファイル・
似た名前の PATH 項目を消さないこと、`--folder-only` が CLI・リンク・PATH に触れないことを足す）。

## 更新（`vw2026 update`）

**更新は CLI のコマンドで行います。** プラグインにメニューもアップデータも持たせません。

```sh
vw2026 update                      # 安定版の最新を入れる
vw2026 update --channel dev --branch feature-x   # 開発版のそのブランチの最新を入れる
vw2026 update --check              # 入れずに、新しいビルドがあるかと再起動が要るかだけ返す
vw2026 update --restart            # 再起動が要る更新なら、Vectorworks を終了させて入れ替え、起動し直す
```

### なぜ CLI なのか

- **本体が自分を置き換えられない問題が起きません。** 元のプラグインで更新が殻にあったのは、
  更新する処理が本体の中にあると、実行中の自分を置き換えることになるからでした。CLI は
  Vectorworks の外のプロセスなので、その制約がありません。
- **殻が小さくなります。** 殻にアップデータ・ダイアログ・同梱スクリプトの実行が要らなくなり、
  殻の ID が変わる（＝再起動が要る）変更が減ります。
- **本体が読み込めない状態からも直せます。** ブリッジが動いていなくても CLI は動くので、
  メニューを復旧の経路として残す必要がありません。

### 流れ

```
vw2026 update
  1. 入っているビルドを読む            <プラグインのフォルダ>/build.json
  2. 新しいビルドを探す               GitHub のリリース（stable / dev-<slug>）
  3. 同じなら終わり                    {"outcome":"no_new_build"}
  4. zip を取ってきて一時フォルダへ展開し、zip の build.json と比べる
  5. 振り分け
     ├─ Vectorworks が動いていない            → すぐ入れる（zip の中の vw-install）
     ├─ 動いていて、殻の ID が同じ            → すぐ入れる（インストーラは殻以外のファイルを
     │                                          上書きする）。本体はブリッジの次の受け付けで
     │                                          読み直される（再起動なし）。新しい version が
     │                                          生存の印に出るまで待って確かめる
     └─ 動いていて、殻の ID が違う            → 入れずに置いておき、終了を待つ係を起こす
                                                {"outcome":"scheduled","restart_required":true}
```

- **入れるのは常に zip の中のインストーラ**です（配置の知識は新しいビルドの側にある。元の
  M21・M22 の教訓）。CLI はダウンロード・展開・振り分けだけを持ちます。
- `build.json` はビルドが zip の直下に置くファイルで、配置の規則どおりプラグインのフォルダへ
  入ります。`{"plugin","channel","version","branch","shell_id"}`。CLI はこれで「何が入っているか」
  と「殻が変わるか」を判定します（mac の `Info.plist` を読まずに済む）。
  **読めないときは「殻が変わる」とみなします**（判定できないなら再起動が要る側に倒す。元の
  `NeedsRestartAfterInstall` と同じ）。
- プラグインのフォルダは、既定の `<Plug-Ins>` と系列から決めます（`--channel stable` なら
  `<Plug-Ins>/cli`、`dev` なら `<Plug-Ins>/cli_dev`）。`--plugins-dir` で明示もできます。CLI は
  プラグインのフォルダの外にある（[置き場所](#置き場所)）ので、自分の場所からは求めません。
- 振り分けは「すぐ入れるか、終了を待つか」だけを決めます。どちらの方式で入れ替えるかは
  インストーラが殻の ID を比べて決めます（[入れ替えの手順](#入れ替えの手順)）。
- Vectorworks が動いているかは、生存の印の `pid` で判定します。印が無いのに動いている
  （プラグインが読み込めていない等）こともあるので、プロセス名でも確かめます
  （mac `pgrep -x "Vectorworks 2026"` 相当、Windows `tasklist`）。

### 殻が変わるときは、終了を待って入れ替える

殻は起動時にしか読み込まれず、Windows は読み込み中の `.vlb` を置き換えられません。また、
殻より先に新しい本体だけが入ると、古い殻が新しい本体を読めず（ABI の版が違うと）ブリッジが
止まります。そこで**殻が変わる更新は、Vectorworks の終了を待ってから丸ごと入れます。**

1. 展開したビルドを**待機の場所**（`<CLI>/pending/<name>/`。[置き場所](#置き場所)）へ移す。
   一時ディレクトリは OS に掃除されうるので使わない。系列ごとに分けるのは、安定版と開発版の
   更新が同時に待つことがあるためです。
2. **終了を待つ係**を切り離して起こす: `vw2026 _apply-pending --wait-pid <pid>`
   （CLI 自身。端末を閉じても残る。mac は `setsid`、Windows は `DETACHED_PROCESS`）。
3. 係は Vectorworks のプロセスが終わるのを待ち（mac `kqueue` の `NOTE_EXIT`／`kill(pid,0)` の
   ポーリング、Windows `WaitForSingleObject`）、終わったら待機の場所の zip のインストーラを走らせ、
   結果を `<CLI>/pending/<name>.result.json` に残して待機の場所を消す。待機の場所が無ければ
   （アンインストールされた・新しい `update` が入れ終えた）何もせずに終わる。
   係の実行ファイルは `<CLI>/bin/` にあり、プラグインのフォルダの付け替えを妨げません。
   インストーラが係自身の実行ファイルを入れ替えても、係は名前の変わった古いファイルのまま
   最後まで動きます（[CLI の入れ替え](#cli-の入れ替え)）。
4. CLI は `{"outcome":"scheduled","restart_required":true,"message":"quit Vectorworks to apply the update"}`
   を返す。**再起動が要ることの案内はこれで行います**（ダイアログは出さない）。

- **入れ替えは「Vectorworks が 1 つも動いていないとき」にだけ行います。** 係は待っている
  プロセスが終わったあと、Vectorworks 2026 のプロセスが他に無いことを確かめます。居れば
  入れ替えずに、そのプロセスの終了を待ち直します（[別の手段で再起動されたとき](#別の手段で再起動されたとき)）。
- **待っている更新がある間に `vw2026 update` をもう一度呼ぶと**、待機の場所を新しいビルドで
  置き換え、係が居なければ起こし直します（計算機の再起動で係が消えた場合もここで戻る）。
- `vw2026 status` は、待っている更新（`pending`）と前回の結果（`last_update`）も返します。

### 別の手段で再起動されたとき

利用者が Vectorworks を別の手段で再起動することがあります（Vectorworks 自身の再起動、ほかの
プラグインの再起動の機能、終了してすぐ起動し直す など）。どの場合も入れ替えは安全に行えます。

| 局面 | 起きること | 結果 |
| --- | --- | --- |
| 終了から起動までの間に係が確かめた | 新しい Vectorworks のプロセスが居る | 入れ替えずに、その終了を待ち直す。起動した Vectorworks は**古い版のまま一式**で動く（殻も本体も古い） |
| 確かめたあと、1 つ目の名前の変更の前に起動した | mac: 古い版を読み込み始める／Windows: 読み込み中の殻を含むフォルダは名前を変えられない | mac は入れ替わるが、動いている殻は古い版のまま。**古い殻は新しい本体を読み込まない**（下記）ので、その起動の間は古い本体で動き、次の起動から新しい版。Windows は付け替えが失敗し（`error=locked`）、何も変えずに待ち直す |
| 2 回の名前の変更の間に起動した | プラグインのフォルダが無い | その起動に限りプラグインが読み込まれない。次の起動から新しい版 |
| 付け替えのあとに起動した | 新しい版を読む | 新しい版で動く |

- **どの局面でも、殻と本体の版が食い違った状態で動きません。** 理由は 2 つです。
  - 殻が変わる更新は、フォルダの中を書き換えず、フォルダごと入れ替える。殻のファイルだけを
    上書きすることはしない（殻の ID が同じ更新は殻に触れない）。
  - **殻は、自分と同じ殻の ID のビルドの本体だけを読み直します。** 殻は本体のファイルが
    変わったことに気付いたら（元:`PayloadUse` の刻印の比較）、プラグインのフォルダの
    `shell-id`（ビルドが zip の直下に置く 1 行のファイル）を読み、自分の `VW_SHELL_ID` と
    一致するときだけ本体を降ろして読み直します。一致しない・読めないときは今の本体のまま
    動き続け、見え方と生存の印に `restart_required: true` を出します。殻の ID が同じ更新
    （動いている間に入れる更新）はこの条件を満たすので、これまでどおり再起動なしで効きます。
- 再起動が続いて入れ替えの機会が無い間、更新は待ったままです。`vw2026 status` の `pending` で
  分かり、`vw2026 update --restart` を使えば、終了 → 入れ替え → 起動を 1 回で行えます。
- mac の 2 つ目の局面では、動いている Vectorworks が読み込んだ古い殻のファイルは移されて
  消されますが、読み込み済みのモジュールはファイルが消えても動き続けます（Unix の作法）。
  本体は一時ディレクトリの複製から読み込んでいるので、元のファイルが入れ替わっても影響しません。

### `--restart`

殻が変わる更新で `--restart` を付けると、待つ係を起こしたあとで道具 `quit`（保存の確認を出して
終了させる。[道具](tools.md#quit)）を呼び、**係が入れ替えてから Vectorworks を起動します**。

- Vectorworks 自身の再起動（`CloseAllFilesAndQuitVectorworks` の再起動の指定）は使いません。
  入れ替えより先に起動し直してしまうためです。
- 利用者が保存の確認で取り消したら Vectorworks は終わらないので、係は待ち続けます（次に
  終了したときに入れ替わる。起動はしない）。

### トークン

GitHub の API は認証なしだと IP ごとに 1 時間 60 回までなので、あれば使います（無くても動く）。
環境変数 `VW2026_GITHUB_TOKEN`、無ければ `gh auth token` の出力。キーチェーンは読みません
（CLI に外部の依存を足さないため。要るならラッパー側で環境変数に入れる）。

### 歯止め

- `update` が消すのは、インストーラとアンインストーラが消すもの（上記）と、自分の待機の場所
  （`<CLI>/pending/<name>/`）だけです。
- 入れ替えは**常にインストーラの経路 1 本**です（CLI に配置を書かない）。
- テスト: 振り分け（殻の ID の比較・判定できないとき・動いているかの判定）は Go の単体テストで、
  待つ係はプロセスの終了を偽の子プロセスで確かめます。
