# インストール・更新・アンインストール

**配置は `vw2026 install` / `uninstall` が行います。** このプラグイン（`cli`）も、他の
プラグインも同じ手順で入ります。何を・どこから取るかは[レジストリとマニフェスト](../registry.md)が
決め、プラグインのフォルダの外に置くもの（`cli` なら PATH）はそのプラグインのフックが
置きます。`cli` の CLI とスプールは `cli` のフォルダの中にあり（[CLI とスプールの置き場所](#cli-とスプールの置き場所)）、
外に置くのは PATH だけです。`cli` を入れる最初の 1 回と、`cli` を外すときは、取ってきた CLI で `install` /
`uninstall` を走らせるだけの短いスクリプト（`get-vw2026.sh` / `.ps1`）を使います（入れる前は CLI が無く、外した
後は CLI を使わないため。入っている CLI で外すと、Windows では動いている自分を消せずに残す）。

このページは 2026 の名前で書きます。2025 の `cli`（`vw2025`・`get-vw2025.sh` / `.ps1`・`VW2025_HOOK_*`）も同じ手順で、
名前の読み替えは[版](editions.md)にあります。

| 段 | 手段 | すること |
| --- | --- | --- |
| 初回 | `get-vw2026.sh` / `.ps1`（curl などで取ってパイプで実行） | 一時フォルダに、スクリプトを取ったリリースの CLI を取り出し、`vw2026 install cli@<そのリリースのタグ>` を走らせる |
| インストール・更新 | `vw2026 install <name>@<tag>` | `<Plug-Ins>/<name>/` を付け替え、フックを走らせる。入っているものと同じタグなら、zip を取らず付け替えもせずに、フックだけを走らせる。`cli` の更新も同じ |
| アンインストール | `vw2026 uninstall <name>` | フックを走らせ、`<Plug-Ins>/<name>/` を取り除く |
| `cli` のアンインストール | 入っているタグのリリースの初回のスクリプトに `uninstall` を渡す | そのタグの CLI を一時フォルダに取り出し、`vw2026 uninstall cli` を走らせる（入っている CLI の `uninstall cli` は断り、このコマンドを示す） |

```sh
# mac。latest のリリースを入れる
curl -fsSL https://github.com/min-nano/vectorworks-plugin-command-line-interface/releases/latest/download/get-vw2026.sh | sh
# そのタグを入れる
curl -fsSL …/releases/download/<tag>/get-vw2026.sh | sh
# 既定以外の場所へ入れる
curl -fsSL …/get-vw2026.sh | sh -s -- --plugins-dir <Plug-Ins>
# そのタグの CLI で外す
curl -fsSL …/releases/download/<tag>/get-vw2026.sh | sh -s -- uninstall
```

```powershell
# Windows。latest のリリースを入れる
irm https://github.com/min-nano/vectorworks-plugin-command-line-interface/releases/latest/download/get-vw2026.ps1 | iex
# そのタグを入れる
irm …/releases/download/<tag>/get-vw2026.ps1 | iex
# 既定以外の場所へ入れる
& ([scriptblock]::Create((irm …/get-vw2026.ps1))) --plugins-dir <Plug-Ins>
# そのタグの CLI で外す
& ([scriptblock]::Create((irm …/releases/download/<tag>/get-vw2026.ps1))) uninstall
```

## 前提

- **プラグインのフォルダ（`<Plug-Ins>`）と `vw2026` の作業の場所（`<Work>`。下記「[作業の場所](#作業の場所)」）は
  同じドライブ（ボリューム）にあるものとします。** 既定では同じボリュームにあります。入れ替えは名前の変更だけで
  行い、ボリュームをまたぐ場合の扱い（コピーへの切り替え・その検出）は持ちません。名前の
  変更が失敗したら、何も変えずに失敗で終わります。
- **入れた場所を記録しません。** 入った `vw2026`（`<Plug-Ins>/cli/bin/vw2026` で動き、`<Plug-Ins>/cli/` に
  記録・モジュール・スプールのどれかがあるもの）は、スプールと同じく自分の実行ファイルの場所から求めた
  `<Plug-Ins>` を使います。どれも、あるかだけを見て中身は読みません。`module` が欠けた・記録が壊れた・記録が
  消えた `cli` でも既定の場所に別の `cli` を入れず、自分の入ったフォルダで `install` / `uninstall` が記録を確かめて、
  入れ直すか断ります。それ以外の `vw2026`（初回のスクリプトの一時フォルダのもの・手でビルドしたもの）は既定の
  場所を使います。入れたものの記録は、プラグインのフォルダの中にだけ置きます（[レジストリ「入れたときの記録」](../registry.md#入れたときの記録)）。
- **既定以外の `<Plug-Ins>` は、初回のスクリプトに `--plugins-dir` で渡します。** スクリプトが一時の `vw2026` に
  渡す隠した指定で、help に出さず、環境変数も持たず、入った `vw2026` は使い方の誤りで断ります（入った `vw2026` が
  別の `<Plug-Ins>` を扱うと、動いている `cli` と違う場所のロックを見てしまうため）。
  絶対パスだけを受け付け、相対パスと空の値は使い方の誤りです（相対パスのまま名前の変更や削除へ進まないため。
  `--plugins-dir "$UNSET"` のような取り違えで、黙って既定の場所に入れないため）。
- **隔離属性の解除（mac）・`Unblock-File`（Windows）は行いません。** curl・`Invoke-RestMethod`・
  Go の HTTP で取ったファイルには、隔離属性も Web からの印（Mark of the Web）も付かないためです。
  署名はビルドがかけたアドホック署名で、zip から取り出したファイルにそのまま残ります。
- **同じプラグインを二重に入れないのは利用者の責任です**（[レジストリ「提供側に求めること」](../registry.md#提供側に求めること)）。

場所は[名前と識別子「置き場所」](identifiers.md#置き場所)にあります。

### 作業の場所

**`install` / `uninstall` の作業の場所（`<Work>`）は、利用者ごとの一時フォルダの下の `vectorworks2026-cli-<鍵>/` です
（`<Plug-Ins>` ごとに 1 つ）。**
置くのは、組み立て（`staging/`）・退避（`old/<name>/` と `uninstall` の途中の印）・よけた CLI（`old/` の直下の
`vw2026.old-*` / `vw2026.exe.old-*`）・消さずに脇へ移した前の版（`old/<name>.kept-<時刻>/`。[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)）だけで、
脇へ移した前の版の他は、どれも `install` / `uninstall` の中でしか要らないものです。
持続する `vw2026` の場所（設定・フックが使う場所など）は持ちません。

`<Plug-Ins>` と `<Work>` の片方がもう片方の中にある（同じ場所を含む）なら、`install` / `uninstall` は何も変えずに
失敗にします（初回のスクリプトに `<Work>` の下を `--plugins-dir` で渡したなど。片付けが入れたばかりのプラグインを
消さないため）。パスの書き方（リンクを解いたものも）と、ディレクトリの同一性（Windows のジャンクション・`subst` の
ドライブ・割り当てたドライブも見つける）の両方で比べます。

場所の求め方（環境変数を読まずに、OS の決まった場所から求める）は[名前と識別子「置き場所」](identifiers.md#置き場所)に
あります。

- **`<鍵>` は `<Plug-Ins>` から決め（リンクを解いたパスの sha256 の先頭 12 桁）、`<Plug-Ins>` ごとに `<Work>` を
  分けます。** `<Work>/old/<name>/` は、どの `<Plug-Ins>` から退避したものかを持たないので、同じ利用者が別の
  `<Plug-Ins>` にも入れているとき、分けなければ片方の `install` が、もう片方の付け替えの途中で退避した唯一の版を
  前の版と取り違えて消してしまうためです。同じフォルダの綴りの違いは揃えます（Windows は小文字にし、mac は
  ディスクにある綴りにする。揃え方は `cli/internal/install/places.go` の `WorkDirFor`）。揃えないと、綴りを変えて
  渡したときに `<Work>` が分かれ、付け替えで `old/cli/spool/` へ移ったロックを次の回が見落として、Vectorworks が
  動いていてもフォルダを付け替えてしまうためです。
- **環境変数を読まないのは、**走らせ方（端末・ssh・他のアプリ）で場所が変わると、前の `install` /
  `uninstall` が途中で止まって残した `old/` を、次の回が見つけられなくなるためです。mac で `TMPDIR` が
  無いときに Go の `os.TempDir()` が返す `/tmp` は利用者の間で共有され、他の利用者がシンボリックリンクを
  仕掛けられるので使いません。どちらの場所も利用者だけが書けるフォルダです。
- **OS が片付けて消えてもかまいません**（Windows のディスク クリーンアップ・ストレージ センサー、mac の
  しばらく使われていないファイルの片付け）。どれも利用者のデータではなく、プラグインはレジストリから
  取り直せるためです。
  - よけた CLI の残りは、次の `install` / `uninstall` が消し、この片付けが有効なら、そちらでも消えます（Windows では
    設定しないと走らない。[`uninstall cli` の後に残るもの](#uninstall-cli-の後に残るもの)）。
  - 途中で止まった回の `old/<name>/` が消えたとき、`<Plug-Ins>/<name>/` があれば何も起きません。
    無ければ入っていない状態になり、`install` で入れ直します。
  - **片付けはファイルを 1 つずつ消すので、`old/<name>/` が一部だけ残ることがあります。** そのため、退避した版を
    `<Plug-Ins>` へ戻すのは同じ回の中の失敗のときだけです。前の回が残した `old/<name>/` は、`install` では
    消すか脇へ移すか断るだけ（[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)）、続きから走る `uninstall` では
    消すか断るだけ（[アンインストール](#アンインストールvw2026-uninstall)の 4）で、`<Plug-Ins>` に戻しません。
  - **同じ回の中で戻すときも、その間に片付けが入る危うさは残ります（受け入れる）。** 退避してから戻すまでの
    間にはフックが走り、フックの時間に上限はありません（[レジストリ「書き方」](../registry.md#書き方)）。
    名前の変更ではファイルの時刻が変わらないので、`<Work>` へ移した直後の旧版も、時刻の古さで選ぶ片付けの
    対象になりえます。片付けが走るのは OS が決めた時機だけで、フックが走る間に当たる確率は低いので、歯止めを
    足さずに受け入れます。戻った版が壊れていたときの直し方は、何が消えたかで変わります。
    - 記録の `module` が消えていれば、同じタグの `install` が入れ直します（[流れ](#流れ)）。
    - 記録と `module` が残り、他のファイルだけが消えたとき（`cli` の `bin/vw2026` だけ・mac の `.vwlibrary`
      のバンドルの中身の一部など）は、同じタグの `install` ではフックだけが走るので直りません。`uninstall` してから
      入れ直します。`cli` で `bin/vw2026` が消えていれば、[初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)に
      `uninstall` を渡してから、初回のスクリプトで入れます。
  - 組み立ての途中のファイルが同じように選ばれないよう、zip を展開するときにファイルの時刻を zip の項目の
    ものに戻しません（[レジストリ「zip の形」](../registry.md#zip-の形)）。
  - `old/<name>/` は残り、印 `old/<name>.uninstalling` だけが消えたときは、`install` / `uninstall` が
    `old` の場所を `message` に載せて断るので（[入れ替えの手順](#入れ替えの手順)の 1・[アンインストール](#アンインストールvw2026-uninstall)の 2）、
    利用者が消します。
- **同じボリュームにあること**: Windows の `%LOCALAPPDATA%\Temp` と既定の `<Plug-Ins>`（`%APPDATA%` の下）は
  どちらも利用者のプロファイルの中です。mac の `/var/folders` とホームは、どちらもデータボリュームに
  あります（`/private/var` はデータボリュームへの firmlink）。mac で `/var/folders` から `~/Library/…` へ名前の
  変更で移せることは、実機で確かめました。

## 初回のスクリプト（`get-vw2026.sh` / `.ps1`）

**スクリプトを取ってきたリリースの CLI を取り出して、`install cli@<そのリリースのタグ>`（又は `uninstall cli`）を
走らせるだけ**です。配置の手順・PATH・判断は `install` / `uninstall` と `cli` のフックが持ち、スクリプトは持ちません。

- **入れる・外すタグは、スクリプトを取ってきたリリースのタグに決まっています。** リリースは、雛形（`scripts/get-vw.sh` /
  `.ps1`）の `@VW_TAG@` をそのリリースのタグに、`@VW_YEAR@` を版（2026・2025）に置き換えて、`get-vw2026.*` と
  `get-vw2025.*` を上げます（[ビルド「リリースの形」](build-and-release.md#リリースの形)・[版](editions.md)）。
  `releases/download/<tag>/get-vw2026.sh` を取れば `<tag>` が、`releases/latest/download/get-vw2026.sh` を取れば
  そのとき latest のリリースのタグが入ります。どのタグを入れるかは取る URL だけで決まり、引数でタグを渡す形は
  持ちません（取ったスクリプトと入る CLI の版がいつも揃う）。置き換えていないスクリプト（リポジトリのものを
  そのまま走らせた）は、何もせずに断ります。

1. 引数を見て、走らせるものを決める。位置の引数は `uninstall`（`uninstall cli` とも書ける）だけを受け付け、他の
   位置の引数（`cli@<tag>` など）は、他のタグはそのタグのスクリプトを取ることを示して断る。指定は
   `--plugins-dir`（とその値）だけを受け付け、書いた位置に依らず CLI のコマンドの後ろへそのまま渡す（`vw2026` は
   コマンドの前の指定を受け付けないため）。他の指定は断る。**`--registry` は持たない**（`install` は既定の
   レジストリから先に引き、名前が見つかった時点で止める（[レジストリ「レジストリの順」](../registry.md#レジストリの順)）ので、
   既定のレジストリにある `cli` には、他のレジストリが使われないため。`uninstall` はレジストリを読まない）。
   - **`uninstall` なら** `vw2026 uninstall cli <指定>` を走らせる（`cli` を外すただ 1 つの手段。一時フォルダの
     CLI はフォルダの外で動くので、何も残さずに外せる。止まった `uninstall cli` の続きもこれで走らせる。下記
     「アンインストール」）。入っているタグのスクリプトで外すのは、入れたものと同じ版のスクリプトと CLI が、
     自分の書いた記録を読むため（後の版でスクリプトや記録の扱いが変わっても、外し方が変わらない）。
   - それ以外は `vw2026 install cli@<そのリリースのタグ> <指定>` を走らせる。
2. ターゲットの zip を一時フォルダへ取ってきて、中の `bin/vw2026`（Windows は `bin\vw2026.exe`）だけを取り出す。
   ターゲットは、mac は `sysctl -n hw.optional.arm64` が 1 なら `macos-arm64`、Windows は `windows-x64`
   （[レジストリ「名前・タグ・ターゲット」](../registry.md#名前タグターゲット)）。Intel の mac はリリースが配らない
   （[名前と識別子](identifiers.md)）ので、取りに行く前に分かる文言で止める。zip の場所は既定のレジストリの `cli` の
   規則と同じ形で決める（`releases/download/<そのリリースのタグ>/cli-<target>.zip`）。JSON を読まずに済むように、
   マニフェストは読まない。
3. 取り出した CLI で `install`（又は `uninstall`）を走らせる。
4. 一時フォルダを消し、走らせた `install` / `uninstall` の終了コードで終わる。「Vectorworks が動いている」終了コード
   （番号は `vw2026 --help`）なら「Vectorworks を終了してからもう一度走らせる」と表示する。

- CLI だけの資産は持ちません。zip から取り出します。
- 一時フォルダの CLI は、`install` の中でマニフェストと zip をもう一度取ります（スクリプトが取った
  zip は渡さない。指定を増やさないため。zip は小さい）。`install` は zip を sha256 で照らします。
  `install` にはタグをそのまま渡すので、一時フォルダの CLI と入る CLI はいつも同じビルドです（`latest` の
  URL から取っても、その間に latest が進んで別のビルドが入ることはない）。
- **`get-vw2026.ps1` は `exit` を呼びません。** `iex` で走らせると、`exit` は利用者の PowerShell ごと閉じるためです。
  走らせた `install` / `uninstall` の終了コードは `$LASTEXITCODE` に残り、CLI を走らせる前の失敗（取れない・
  引数が正しくない）は例外で止まります。利用者のセッションに変数を残しません。引数の受け取り方と CLI への
  渡し方（Windows PowerShell 5.1 は空の引数を落とすので、コマンドラインを自分で組み立てる）は `scripts/get-vw.ps1` の
  コメントにあります。ASCII だけで書きます（[ビルド「リリースの形」](build-and-release.md#リリースの形)）。
- PR のプレリリースを試すときは、そのリリースのスクリプト（`releases/download/<そのタグ>/get-vw2026.sh`）を
  取って走らせます。

## インストールと更新（`vw2026 install`）

**初回のインストールも更新も、同じ `install` で行います。**

```sh
# main の最新（同じタグなら zip を取らず、フックだけを走らせる）
vw2026 install cli@latest
# PR のプレリリース
vw2026 install cli@dev-feature-x-61-a1b2c3d
# 入れずに、新しいビルドがあるかだけ返す（Vectorworks が動いていても良い）
vw2026 install cli@latest --check
vw2026 install my-plugin@2026.3.1 --registry https://example.com/plugins.json
# 手元のファイルも URL で書く
vw2026 install my-plugin@2026.3.1 --registry file:///Users/me/plugins.json
```

- **名前とタグは必須です**（`<name>@<tag>`。既定のタグは持たない）。1 回に 1 つだけ入れます
  （途中で失敗したときに、どこまで入ったかを持たないため）。
- `--check` は、新しいビルドがあるか（`available`）と最新か（`up_to_date`）を、終了コードでは
  なく出力の `outcome` で分けます（新しいビルドがあることは失敗ではないため。判定できなかった
  ときだけ失敗）。入っていなければ `available` です。
- **フォルダの中身を入れ直す手段は持ちません。** 入れ直すには `uninstall` してから入れます。
  - 他のプラグイン: `vw2026 uninstall <name>` の後 `vw2026 install <name>@<tag>`。
  - `cli`: 入っている CLI の `uninstall cli` が示すコマンド（入っているタグのリリースの[初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)に
    `uninstall` を渡す）で外し、続けて初回のスクリプトで入れます（入っている CLI の `uninstall cli` は
    断る。下記「アンインストール」）。
    `<Plug-Ins>/cli/bin/vw2026` が消えた（ウイルス対策が隔離した・`install` が付け替えの途中で止まった）
    ときも同じで、`vw2026` を走らせられないので、初回のスクリプトに `uninstall` を渡してから入れ直します。
  - どちらも同じパスに入るので、その間に Vectorworks を起動しなければ「有効化」は残ります（下記
    「入れる先のフォルダ」）。

### 流れ

```
vw2026 install <name>@<tag>
  1. 場所と書き方を確かめる           名前・タグ・--registry の書き方（誤りは使い方の誤り。場所を求める前に見る）。
                                     <Plug-Ins> と <Work> が重ならないこと（作業の場所）。<Plug-Ins>/cli/ に正しい
                                     記録があること（無ければ何も変えずに失敗。下記「cli と同じ <Plug-Ins> に入れる」）
  2. Vectorworks が動いていないか     --check でなければ、<Plug-Ins>/cli/spool/ か <Work>/old/cli/spool/ のロックが
                                     掴まれていれば何もせずに終わる（専用の終了コード。レジストリを取る前に答える）
  3. 名前を引く                       既定のレジストリ → --registry の順（レジストリ「レジストリの順」）
  4. マニフェストを取る               合った規則の path（{tag} を置き換える）。tag を照らし、今のターゲットを選ぶ
                                     （合った規則の path に {tag} があり、@ の後ろが記録の tag と同じで、記録の
                                      target が今のターゲットと同じなら取らない。下記「同じタグのとき」）
  5. 入れる先を確かめる               <Plug-Ins>/<name>/ と中の記録（下記「入れる先のフォルダ」）。
                                     --check なら入れずに、新しいビルドがあるかだけを返して終わる
     （同じタグのとき）              記録の tag と target が同じで、記録の module がフォルダの中に実在するなら、
                                     入っているフォルダで記録の hooks.install だけを
                                     走らせ、<Work>/old/<name>/ を片付けて終わる（zip を取らず、付け替えない）
  6. zip を取って照らす               asset を <Work>/staging/<name>.zip へ。sha256 が合わなければ失敗
  7. 組み立てる                       <Work>/staging/<name>/ へ展開し、モジュールを確かめ、記録を書く
  8. プラグインのフォルダを付け替える  下記「入れ替えの手順」（直前にロックをもう一度見る。動いている CLI が
                                     その中にあれば先によける）
  9. install のフックを走らせる        失敗したら 8 を戻す（レジストリ「フック」）
 10. 後始末                           <Work>/staging/<name>/・<Work>/staging/<name>.zip を消し、<Work>/old/<name>/ を片付け、
                                     よけた CLI を消してみる
```

指定・環境変数・出力（どの段で終わったか・フックの出力）の形・終了コードは `vw2026 help install` が真実です
（`CLAUDE.md`「Go」。ここには写さない）。

- **取得（レジストリ・マニフェスト・zip）に待つ上限を持ちません。** フックと同じく、待つ上限を決めて止める
  のは呼ぶ側です（[レジストリ「書き方」](../registry.md#書き方)・[設計「CLI はプリミティブに保つ」](../design.md#cli-はプリミティブに保つ)）。
  大きな zip を遅い回線で取る時間は CLI には決められず、止まったサーバーやプロキシの待ちは呼ぶ側が
  打ち切ります（Ctrl-C・呼ぶ側の上限）。取得の途中で止めても、変わるのは `<Work>/staging/<name>/`・
  `<Work>/staging/<name>.zip` だけで、次の `install` が消します。
- **zip の取得の進み具合は標準エラーに書きます**（止まっているかを、呼ぶ側と利用者が見分けられるように。
  標準出力は JSON の 1 行のままにする）。始めに URL と大きさ（分かれば）を、終わりに取った量を 1 行ずつ書き、
  その間は、標準エラーが端末なら同じ行を書き直し、端末でなければ（ログ・パイプ）一定の間隔で 1 行ずつ足します
  （間隔と書き直し方は `cli/internal/install/progress.go`）。レジストリとマニフェスト（1 MiB まで）は示しません。
- **新しいかは、タグとターゲットだけで比べます**（タグは使い回さないので、タグが同じならビルドも
  同じ）。マニフェストだけを取り、zip は取りません。
- **記録の `module` がフォルダの中に無いとき**（ウイルス対策が隔離した・手で消した）は、同じタグでも
  同じとみなさず、マニフェストを取って入れ直します（付け替えるので、Vectorworks が止まっている必要が
  ある）。`uninstall` は `module` が無いフォルダを消さない（安全弁）ので、壊れたフォルダは先にこの
  `install` で直してから `uninstall` します。
- **同じタグのとき**は、zip を取らず、フォルダも付け替えずに、`install` のフックだけを走らせます（`up_to_date`。
  `cli` なら PATH を通し直す）。
  - フックは Vectorworks が止まっている間にしか走らせないので、同じタグでも Vectorworks が動いていれば
    `vectorworks_running` で終わります（新しいかだけを知りたいときは `--check`）。
  - 走らせるのは**記録に写した `hooks.install`** です（マニフェストのものは使わない。提供側が同じ場所の
    マニフェストを差し替えても、入れていないフックが走らないため）。`VW2026_HOOK_PREVIOUS_TAG` には同じタグを
    渡します（新しい版を残した `install` を終える回は、`<Work>/old/<name>/` に残った前の版のタグ。
    [レジストリ「フックに渡す環境変数」](../registry.md#フックに渡す環境変数)）。
  - フックが通ったら、記録の `hook_pending` を外し、付け替えの後始末と同じく、`<Work>/old/<name>/`
    （[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)）・よけた CLI・前回の残りの `<Work>/staging/<name>/`・
    `<Work>/staging/<name>.zip` を片付けます。
  - 合った規則の `path` に `{tag}` があり、記録の `target` が今のターゲットと同じなら、マニフェストも取りません
    （ターゲットが違えば、入れ直すのでマニフェストを取る。`latest` のように決まった場所を指す規則では、今のタグを
    知るためにマニフェストを取る）。タグをそのまま指定すれば（`cli@<入っているタグ>`）、ネットワークにつながって
    いなくても、消えた PATH を置き直せます。入っているタグは `install` / `--check` の出力の `tag` と、記録で分かります。
- 初回でも Vectorworks が動いていれば何もせずに終わり、CLI も置きません（何も変えない）。
- **`cli` と同じ `<Plug-Ins>` に入れる**: Vectorworks が動いているかは、入れる先の `<Plug-Ins>/cli/spool/` の
  ロックで判定します。そのため、`cli` 以外のプラグインは、`cli` が入っている `<Plug-Ins>` にだけ入れます。
  `<Plug-Ins>/cli/` に正しい記録（`name` が `cli` で、`module` が実在する）が無ければ、何も変えずに失敗にします
  （`uninstall` も同じ）。`cli` の無い `<Plug-Ins>` では、Vectorworks が動いていても判定できず、付け替えとフックが
  走ってしまうためです。ワークグループのフォルダなど、`cli` の無い `<Plug-Ins>` へは入れられません（対応しない）。
  `cli` の `install` / `uninstall` が途中で止まって `cli` が無いこともあるので、断るときは、Vectorworks を終えて、
  その `install` / `uninstall` を初回のスクリプトで走らせ直すよう添えます（既定でない `<Plug-Ins>` なら
  `--plugins-dir` を付ける。止まった状態は読まず、続け方はその `install cli` / `uninstall cli` が答える）。
- **Vectorworks が動いているかはロックで判定します**（[通信規則「生存の判定」](../protocol.md#生存の判定)）。
  ロックを無い以外の理由で調べられなければ（権限・壊れた場所）、動いているかが分からないので、`install` /
  `uninstall` は始めに何も変えずに失敗にします（「動いていない」とみなして付け替えない。判定そのものは変えない）。
  見るのは `<Plug-Ins>/cli/spool/` と `<Work>/old/cli/spool/`（下記。付け替えで移ったロック）の 2 か所で、`install` /
  `uninstall` のどの確かめも、この同じ 2 か所を見ます（道ごとに見る場所を変えると、見落とす道が残るため）。
  プロセス名は見ません。ロックを掴んでいない Vectorworks（`cli` が入っていない・起動の途中で
  最初の刻みの前・2 つ目の起動）が居るときは、Windows では読み込み中のフォルダの名前を変えられないので
  （[SDK の調査 6](../sdk-research.md#6-プラグインのフォルダの中のモジュール以外のものとモジュールの読み込み元分かった)）
  付け替えが失敗し、何も変わりません。mac では付け替えが成功し、その
  Vectorworks は古い版のまま動き、次の起動から新しい版になります。
- **ロックは手順 2 と付け替えの直前（[入れ替えの手順](#入れ替えの手順)の 2）の 2 度見ます。** 手順 2 は
  レジストリ・zip を取る前に断るため、直前の 2 度目は、zip を取って組み立てる間（ネットワーク次第で長い）に起動した
  Vectorworks を見落とさないためです。mac では付け替えが通るので、その間に起動してロックを掴んだ
  Vectorworks があると、次のことが起きます。
  - プラグインは `bridge.lock` を一度掴むと放さず（[通信規則「ロック」](../protocol.md#ロックbridgelock)）、
    POSIX では開いているファイルはフォルダの名前の変更に付いて動くので、掴まれたロックは付け替えで
    `<Work>/old/cli/spool/bridge.lock` へ移ります。プラグインは他のファイルをスプールの場所の文字列から
    開き直すので、要求は付け替えた後の `<Plug-Ins>/cli/spool/` で探します。
  - 新しい CLI は `<Plug-Ins>/cli/spool/` でロックを掴む者を見つけられず、Vectorworks が動いていても
    止まっていると判定し、`call` も断ります。
  - そのため `install` / `uninstall` は `<Work>/old/cli/spool/` のロックも見ます。この Vectorworks を動いていると
    みなし（`vectorworks_running`。付け替えの後の後始末なら知らせるだけ）、`<Work>/old/cli/` を消しも移しもしません
    （[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)）。見ないと、後始末が掴まれたままのロックごと
    `<Work>/old/cli/` を消し、それ以降の `install` / `uninstall` が、Vectorworks が動いているのに通ります。
- **フックが失敗して戻す前にも、ロックを見ます**（[入れ替えの手順](#入れ替えの手順)の 4）。フックの時間には
  上限が無く、その間に起動した Vectorworks が新しい版を読み込み、ロックを掴むことがあります。そのまま戻すと、
  mac では動いているプラグインのロックごと新しい版が消え、`<Plug-Ins>` には古い版が戻り、上と同じく止まって
  いると判定されます。Windows では読み込まれた新しい版の名前を変えられず、戻しの途中で止まります。
- 2 度目と戻しの前の確かめの後も見落とすのは、確かめてから名前を変えるまでのごく短い間に起動した
  Vectorworks と、起動の途中でまだ最初の刻みが来ていない Vectorworks だけで、どちらも上と同じくロックを
  掴んでいない Vectorworks です。
- **終了させるのは呼ぶ側です。** `install` は終了を頼まず、待ちもしません（[設計「CLI は
  プリミティブに保つ」](../design.md#cli-はプリミティブに保つ)）。終了から起動し直すまでを 1 度に
  行いたい呼ぶ側は、`session start` → `call quit` → 止まるのを待つ → `install` → `launch` →
  動き出すのを待つ、を組み合わせます。CLI は動き出す・止まるのを待つコマンドを持たないので、
  `vw2026 status` を繰り返し、終了コードで分けます。
  sh の見本と、見本が守る決めごと（どの終了コードで抜けるか）は `vw2026 --help` にあります（CLI の使い方の
  真実は help。PowerShell の書き方は `vw2026 help status`）。決めごとの内次の 2 つは、他の組み合わせでも守ります。
  - `quit` は占有の中でだけ呼べ、図面を 1 枚も開いていないときだけ受け付けます。呼ぶ側が先に図面を
    保存して閉じます（[道具](tools.md#quit)）。
  - **失敗したら占有を解いてから抜けます。** 占有は Vectorworks を起動し直すまで残り、他の呼ぶ側は
    全て `occupied` で断られるためです。Vectorworks が終われば占有も消えるので、起動し直した後に使うなら
    占有を取り直します。
- 失敗したら（取れない・照らせない・展開できない・付け替えられない・フックが失敗した）、
  `<Plug-Ins>` を元のままにして理由を `message` に載せ、失敗の終了コードで終わります
  （フックがフォルダの外で変えたものは除く。よけた CLI も元の場所へ戻す）。同じ理由を標準エラーにも書きます
  （`uninstall` も同じ）。名前やタグの形が正しくないときは、使い方の誤りの終了コードで終わります。

### 入れる先のフォルダ

**フォルダ名はレジストリの名前です**（`<Plug-Ins>/<name>/`。`cli` は `<Plug-Ins>/cli/`）。見れば何の
プラグインか分かり、名前からフォルダが直接決まります。

| `<Plug-Ins>/<name>/` | 振る舞い |
| --- | --- |
| 無い | 作って入れる |
| あり、記録の `name` が一致し、記録の `registry` が今回使ったレジストリと同じ | 更新として付け替える |
| あるが、記録が無い（手で入れたもの・他のインストーラで入れたもの） | **何も変えずに失敗にする。** `message` に場所を載せる（利用者のものを上書きしない） |
| あるが、記録の `name` がフォルダ名と違う（手で写したものなど）・記録が読めない（壊れている・知らない `record_version`） | **何も変えずに失敗にする。** `message` に場所を載せる（どう直すかは利用者が決める） |
| あるが、フォルダでない（ファイル・シンボリックリンク・Windows のジャンクション。リンクの先が記録のあるフォルダでも） | **何も変えずに失敗にする。** リンクの先の作業用のコピーなどに触れないため（`uninstall` も同じ） |
| あるが、記録の `registry` が違う（後から既定のレジストリに同じ名前が載り、そちらが勝つようになったときなど） | **何も変えずに失敗にする。** 別のプラグインを黙って入れ替えないため。利用者が `uninstall` してから入れ直す（`cli` は既定のレジストリが先頭にあるので、この場合にならない） |

- **更新ではフォルダのパスが変わりません。** Vectorworks は署名の無いプラグインの「有効化」を
  モジュールのフルパスで覚えるので、モジュールのファイル名が変わらない限り、更新の後も有効の
  まま読み込まれます（[Findings「Plug-in Modules」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)の「開発元不明のプラグイン」のダイアログ。SDK リファレンス #258）。
  `uninstall` してから入れ直しても同じパスなので、その間に Vectorworks を起動しなければ有効のままです
  （プラグインが居ない起動でダイアログを閉じると、有効化は消える）。
- `<Plug-Ins>` そのものが無ければ作ります（Vectorworks を一度も起動していない利用者・CI のランナー）。
- 同じ名前のフォルダに記録が無ければ断るので、**同じ名前のフォルダへの上書きだけは CLI が防ぎます**。
  別の名前で同じプラグインが入っているか（手で入れたもの・別のレジストリの名前）は見ません。

### 入れ替えの手順

1. **組み立て**: zip を `<Work>/staging/<name>/` に展開し、直下のモジュールとフック（スクリプトが zip の中にあり、
   インタプリタがこの OS で走ること。インタプリタを通さないものは、mac では実行の権限があること、Windows では拡張子が
   `.exe`・`.com`・`.cmd`・`.bat` であること）を確かめて、記録（`vw2026-install.json`）を書く。フックが走らないことに
   付け替えの後で気付くと、その間に起動した Vectorworks の下に入れ終えられない版が残るため、付け替えの前に
   確かめる。その前に、次の順で前回の残りを片付ける。
   1. **前回の残りの `<Work>/old/<name>/` があれば**（前の `install` / `uninstall` が付け替えの途中で
      止まった・新しい版を残した）、下記「[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)」の規則で
      片付ける。片付けられなければ（`<Plug-Ins>/<name>/` が無い）、何も変えずに失敗にする。
   2. 前回の残りの `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip` を消す。消せなければ何も変えずに
      失敗にする。1 で消すものは組み立ての場所を通るので、この順にすると、1 で消しきれなかったもの
      （Windows でウイルス対策が開いているファイルなど）があれば 2 が失敗し、前の版のファイルを新しい版に
      混ぜて組み立てない。
2. **ロックをもう一度見て、動いている CLI をよける**: `<Plug-Ins>/cli/spool/` のロックが掴まれていれば、
   何も変えずに `vectorworks_running` で終わる（[流れ](#流れ)の 2 と同じ。2 度見る理由は[流れ](#流れ)の
   「ロックは手順 2 と付け替えの直前の 2 度見ます」）。このとき組み立てた `<Work>/staging/<name>/`・
   `<Work>/staging/<name>.zip` は消す。続けて、走らせている CLI の実行ファイルが `<Plug-Ins>/<name>/` の中にあれば、
   `<Work>/old/` へ名前の変更で移す（下記「[動いている CLI のよけ方](#動いている-cli-のよけ方)」）。
   失敗したら何もせずに終わる。
3. **付け替え**: `<Plug-Ins>/<name>` → `<Work>/old/<name>`、続けて `<Work>/staging/<name>` →
   `<Plug-Ins>/<name>`。まだ入っていなければ 1 つ目は飛ばす。1 つ目が失敗したら、2 でよけた CLI を戻して終わる。
   2 つ目が失敗したら 1 つ目を戻し、よけた CLI を戻す。1 つ目が失敗するのは、Windows で次のどれかがフォルダの
   中のものを開いているとき。
   - エクスプローラーやウイルス対策がフォルダの中のファイルを開いている
   - Vectorworks が読み込んでいる
   - **端末などのプロセスのカレントディレクトリがフォルダの中にある**（`Path` は新しく開いた端末から効くので、
     開いたままの端末で `cd <Plug-Ins>\cli\bin` してから `.\vw2026.exe` を走らせたときなど。走らせた
     `vw2026` 自身もカレントディレクトリを受け継ぐので、CLI をよけても通らない）

   どれかを `vw2026` から見分けることはできないので、失敗の `message` には、名前を変えられなかった場所と
   ともに、これらを閉じる・カレントディレクトリをフォルダの外へ移すことを示す。
4. **フック**: `install` のフックを走らせる。失敗したら、まずロックを見る（[流れ](#流れ)の「フックが失敗して
   戻す前にも、ロックを見ます」。他の確かめと同じ 2 か所）。
   - **掴まれていれば戻さない。** 戻しの 1 の名前の変更が失敗したとき（Windows で、ロックを掴む前の Vectorworks が
     新しい版を読み込んでいる）も、その先へ進まない。どちらも次のようにして、フックの失敗として失敗で終わる。
     - 新しい版を `<Plug-Ins>/<name>` に残し、`<Work>/old/<name>` も残す（同じタグで走らせ直した `install` が、
       フックが通った後で片付ける。[流れ](#流れ)の「同じタグのとき」）。残した版の記録には、組み立てるときに
       書いた `hook_pending` が残る（[レジストリ「入れたときの記録」](../registry.md#入れたときの記録)）。
     - よけた CLI は、前の版のフォルダ（`<Work>/old/<name>/`）の元の場所へ戻す（利用者が前の版を手で戻しても
       CLI が欠けず、後始末がよけた名前のまま消さないように。戻せなければ、その場所を `message` に載せる）。
     - 取った `<Work>/staging/<name>.zip` は消す（同じタグの `install` は zip を取らない）。
     - `message` には、フックが失敗したことと、Vectorworks が起動したので新しい版を残したこと、Vectorworks を
       終了してから同じタグで `install` を走らせ直す（フックだけが走る）ことを載せる。
   - 掴まれていなければ、次の順に戻す。
     1. 新しい `<Plug-Ins>/<name>` を、名前の変更で `<Work>/staging/<name>` へよける（1 回で済み、元に
        戻せる。消すのは後にする。ウイルス対策が新しいファイルを調べていると削除が途中で止まり、
        半分消えたプラグインが `<Plug-Ins>` に残るため）。
     2. `<Work>/old/<name>` を `<Plug-Ins>/<name>` へ戻す（最初に入れたときは無い）。
     3. 2 でよけた CLI を、戻したフォルダの元の場所へ戻す。
     4. よけた `<Work>/staging/<name>` を消す。
5. **後始末**: `<Work>/staging/<name>.zip` を消し、退避した版を「[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)」の
   規則で片付け（片付けられなくても入れたことは変わらないので、標準エラーに示すだけにする）、中断した `uninstall` の印
   `<Work>/old/<name>.uninstalling` が残っていれば消し、2 でよけた CLI と前回までの残り
   （`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`）を消してみる。動いていて消せない
   ものは残し、次の `install` / `uninstall` で消す。

- **記録に `hook_pending` がある版**（フックがまだ通っていない。[レジストリ「入れたときの記録」](../registry.md#入れたときの記録)）は、
  同じタグでも入れ終えていないものとして扱います。
  - `--check` は同じタグでも `available` を返します。
  - **前の版が `<Work>/old/<name>/` にある間は、付け替えません**（付け替えの前の片付けが前の版を消してから
    新しい版のフックが失敗すると、通っていない版だけが残るため）。別のタグなら、同じタグで入れ終えるよう示します
    （諦めるなら、残した版を消して前の版を戻す手順も示す）。同じタグでも入れ直しになる（`module` が欠けた）なら、
    前の版を戻すか消すかを示します。断るのは Vectorworks が動いていないと分かった後（動いていれば
    `vectorworks_running`）で、`--check` は断らずに `available` を返します（新しいビルドがあるかだけを答える）。
  - フックが通ったのに `hook_pending` を外せなかったときは、退避した版も片付けません（次の同じタグの `install` が
    外して片付ける）。
- **中断した `uninstall` の印は、`<Plug-Ins>/<name>/` があれば付け替えの前（同じタグのときも）に消し、付け替えに
  成功した後（5）にも消します。** `uninstall` はフォルダを移してから止まるので、`<Plug-Ins>/<name>/` があるときの
  印は前の回の残りです（`uninstall` のフックが失敗して戻すことにも失敗し、利用者が手で戻したときなど）。残すと、
  その後の `install` が付け替えの途中で止まったときに、次の `uninstall` がそれを中断した `uninstall` とみなし、
  唯一残った `old/<name>/` を消してしまいます。後始末だけで消すと、同じタグの `install` や付け替えの前に失敗した
  `install` の後に印が残るので、付け替えの前にも消します。
- 付け替えを名前の変更で行うのは、途中で失敗したときに元へ戻せるようにするためです（ファイル
  ごとに置き換えると、半端な版が残る）。
- 組み立てと退避の場所を `<Work>` に置くのは、`<Plug-Ins>` の外（Vectorworks に読まれない）で、
  前提により `<Plug-Ins>` と同じドライブにあるためです。
- **`install` と `uninstall` を同時に走らせないのは、呼ぶ側の責任です。** 同じ名前の 2 つの `install`
  は同じ `<Work>/staging/<name>/`・`<Work>/old/<name>/` を使い、片方の「前回の残りを消す」がもう片方の
  組み立ての途中のフォルダを消しうるので、「失敗したら `<Plug-Ins>` を変えない」が保てません。CLI は
  排他を持ちません（[設計「CLI はプリミティブに保つ」](../design.md#cli-はプリミティブに保つ)。
  排他はプラグインの占有だけで、`install` は Vectorworks が止まっている間に走るので占有も無い）。
  **名前が違っても同時に走らせません。** どの回も後始末で共通の `<Work>/old/vw2026.old-*` /
  `vw2026.exe.old-*` を消すので、mac では、`install cli@…` がよけた CLI を、同時に走る別の名前の
  `install` が消しえます（動いているファイルも消せる）。その後 `cli` の付け替えかフックが失敗すると
  CLI を戻せず、`bin/vw2026` の無い `cli/` が残ります。
- フックが失敗して元に戻したとき、フックがフォルダの外で変えたもの（`cli` なら PATH）は
  戻りません。フックは何度走っても同じ結果になるように書くので、もう一度 `install` を走らせます。

### `<Work>/old/<name>/` の片付け

**`install` のどの道（[入れ替えの手順](#入れ替えの手順)の 1 と 5・[同じタグのとき](#流れ)のフックの後）も、
`<Work>/old/<name>/` をこの 1 つの規則で片付けます。** 道ごとに規則を変えると、ある道が残したものを
他の道が片付けられず、その名前の `install` / `uninstall` が通らなくなるためです。

- 無ければ何もしない。
- **`<Plug-Ins>/<name>/` が無ければ**、`old` が入っていた唯一の版かもしれないので、何も変えずに `old` の場所を
  `message` に載せて失敗にする（戻すか消すかは利用者が決める）。印 `<Work>/old/<name>.uninstalling` も
  あれば、止まった `uninstall` なので、`uninstall <name>` を走らせ直して終わらせることを示す。
- **Vectorworks が動いていれば**（`<Plug-Ins>/cli/spool/` と `<Work>/old/cli/spool/` のロック。[流れ](#流れ)）、
  動いている Vectorworks が使っているかもしれないので、消しも移しもしない。付け替えの前なら `vectorworks_running` で
  何も変えずに終わり、付け替えやフックの後（フックの間に起動した）なら知らせるだけにする（終了してから同じタグの
  `install` を走らせ直すと片付ける）。
- `<Plug-Ins>/<name>/` があり、`old` の記録の `name` が一致し記録の `module` があれば、退避した版・退避の残りと
  して消す（[消すコードの歯止め](#消すコードの歯止め)）。
- `<Plug-Ins>/<name>/` があり、`old` の記録が無い・読めない・`module` が無いとき（`module` の無いフォルダを
  入れ直したときの前の版・OS の片付けで一部が消えた残り）は、利用者のファイルが入っているかもしれないので
  消さずに、`<Work>/old/<name>.kept-<時刻>/` へ名前の変更で移し、その場所を標準エラーに示す。付け替えで動いている
  CLI をよけていれば、それもその版の元の場所へ戻す（利用者が戻すかもしれない版から `vw2026` を欠かさない。戻せなければ、
  よけた場所を示して消さない）。
  - `old/<name>/` に置いたままにしないのは、`uninstall` が `old/<name>/` を消さずに断る（[アンインストール](#アンインストールvw2026-uninstall)の 3）
    ので、利用者が見つけて消すまでその名前を外せなくなるためです。
  - `<name>.kept-<時刻>` は `vw2026` のどの道も消しません（利用者が消す）。`<Work>` の下なので、OS の片付けで
    消えることもあります（[作業の場所](#作業の場所)）。名前は `.` を含むので、`<Work>/old/<name>/` と重なりません。
- **消すときは、まず `<Work>/staging/<name>/` へ名前の変更で移してから消す**（`uninstall` の手順 5 も同じ。
  消すのが途中で止まっても（Windows でウイルス対策が中のファイルを開いているなど）、記録だけが先に消えた
  半分のフォルダを `old/<name>/` に残さないため。残すと、次の回が唯一の版と見分けられない）。半分の残りは
  組み立ての場所にあり、次の `install` の手順 1 と `uninstall` が名前のパスとして消す。移せなければ
  何も変えずに失敗にする。

### 動いている CLI のよけ方

**Windows では、開いているファイルを含むフォルダの名前を変えられません。** 動いている実行ファイルも
開いているファイルなので、`install cli@…` を走らせている CLI（`<Plug-Ins>/cli/bin/vw2026.exe`）が
`<Plug-Ins>/cli/` の中にある限り、付け替えの 1 つ目が失敗します。一方で、**動いている実行ファイルそのものの
名前は変えられ、同じボリュームの別のフォルダへも移せます**（移すことも名前の変更）。そこで、
付け替えの前に CLI 自身をフォルダの外へ移します（[入れ替えの手順](#入れ替えの手順)の 2）。

- **条件は「走らせている CLI の実行ファイル（リンクを解いたもの）が、付け替える `<Plug-Ins>/<name>/` の中に
  あること」だけ**です。Go のコードは名前で `cli` を見分けません（他の名前のフォルダに CLI が入ることはないので、
  実際に当たるのは `cli` だけ）。
- **中にあるかは、パスの文字列ではなくディレクトリの同一性で決めます。** `<Plug-Ins>` は入った場所・初回の
  スクリプトの `--plugins-dir`・既定の場所のどれからでも来て、実行ファイルのパスと書き方（大文字と小文字・8.3 形式・
  ジャンクション・末尾の区切り）が揃うとは限らないためです。文字列で比べると外と判定してよけず、付け替えの
  1 つ目が失敗します（入っている CLI では `install cli` が通らなくなる）。`uninstall` も同じ判定で、走らせている
  CLI が外すフォルダの中にあれば断ります（下記「アンインストール」）。比べ方は `cli/internal/install/sidestep.go` の
  `within` にあります。
- 移す先は `<Work>/old/vw2026.old-<時刻>`（Windows は `vw2026.exe.old-<時刻>`）です。名前は実行ファイルの名前に
  依らず決めます（大文字の `VW2026.EXE` や別の名前の写しで動かしても、後始末が同じ頭で見つけて消せるように）。
  `<Work>` は前提により `<Plug-Ins>` と同じドライブにあるので、名前の変更で移せます。
- **mac でも同じ手順を踏みます。** mac は中で何が動いていてもフォルダの名前を変えられるので要りませんが、
  手順を OS で分けず、Go の単体テストを両方の OS で同じに走らせるためです。mac では後始末でそのまま消せます。
- 移した後も、動いているプロセスはそのまま動き続けます（実行ファイルを読み直さない）。同じ実行ファイルから
  動いている他の `vw2026`（別の端末の `status` の繰り返しなど）も、ファイルは 1 つなのでまとめて外れます。
  それらがスプールのファイルを開いている瞬間に当たると付け替えは失敗し、何も変わりません（やり直す）。
- **失敗したら元の場所へ戻します。** 付け替えの失敗とフックの失敗のどちらでも、フォルダを戻した後で
  CLI を元の場所（`<Plug-Ins>/<name>/` の中の同じ相対パス）へ戻します（動いていても名前の変更はできる）。
- **よけるのは `install` だけです。** `uninstall` は、走らせている CLI が外すフォルダの中にあれば何もせずに断る
  ので、よけません（下記「アンインストール」）。
- **後始末で消してみて、消せなければ残します。** Windows では、移した CLI は `install` が終わるまで
  動いているので、その `install` の中では消せません。次の `install` / `uninstall` が消します
  （`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*` だけ。[消すコードの歯止め](#消すコードの歯止め)）。
- よけてから付け替えるまでの間に止まる（Ctrl-C・電源断）と、`<Plug-Ins>/cli/` は CLI の無いまま
  残ります。このときは `vw2026` を走らせられないので、[初回のスクリプト](#初回のスクリプトget-vw2026sh--ps1)に
  `uninstall` を渡してから入れ直します（一時フォルダの CLI はフォルダの外で動くので、よけずに済む）。
- 初回のスクリプトから走らせたときは、動いている CLI は一時フォルダにあるので、よけません。

## CLI とスプールの置き場所

**`cli` の CLI とスプールは、`cli` のフォルダ（`<Plug-Ins>/cli/`）の中に置きます。** CLI は zip の
`bin/` がそのまま置かれたもの（`<Plug-Ins>/cli/bin/vw2026`）を PATH から使い、スプールはプラグインが
`<Plug-Ins>/cli/spool/` に作ります（[名前と識別子「置き場所」](identifiers.md#置き場所)）。

- **ねらいは、`cli` を他のプラグインと同じ形に閉じ込めることです。** Go の `install` はどの
  プラグインにも「zip の中身をフォルダに置き、フォルダごと付け替える」だけを行います。CLI がフォルダの
  中にあれば、`cli` の CLI もこの付け替えで入れ替わり、フォルダを消せば CLI もスプールも一緒に消えます。
  `cli` のフックが受け持つのは、フォルダの外にしか置けない PATH だけです。
- **CLI を写して置き直す手順を持ちません。** 写しを持たないので、プラグインと CLI が食い違う（写しだけが
  古い・写しだけが消えた）ことが起きません。
- **スプールの場所の求め方は[通信規則「スプールの場所」](../protocol.md#スプールの場所)が真実です**（どちらの側も自分の
  ファイルの場所から求める。フォルダの外で動かした `vw2026` は入っている `cli` のスプールを見ない）。`install` /
  `uninstall` も、入った `vw2026` は自分の実行ファイルの場所から `<Plug-Ins>` を求め（[前提](#前提)）、入れる先の
  `<Plug-Ins>/cli/spool/` のロックで Vectorworks が動いているかを判定します（[流れ](#流れ)の 2）。
- **`cli` は利用者ごとの `Plug-Ins` にだけ置きます**（複数の利用者が読み込む `Plug-Ins` に置くとスプールも共有される。
  [通信規則「スプールの場所」](../protocol.md#スプールの場所)）。`install` はネットワーク共有へは入れられません
  （`<Work>` と別のボリューム）が、同じボリュームの共有のフォルダへは初回のスクリプトの `--plugins-dir` で入りうるので、
  渡さないのは利用者の責任です（[前提](#前提)の二重のインストールと同じく、確かめられない置き方を CLI が見分けない）。
- **フォルダの中のスプールは、付け替えで消えてかまいません。** 付け替えは Vectorworks が止まっている
  間にしか行わず、そのときスプールに要るもの（ロックを掴む者・応答を待つ者）は居ません。占有も
  Vectorworks の終了で消えます（[通信規則「占有」](../protocol.md#占有セッション)）。
  [レジストリ「提供側に求めること」](../registry.md#提供側に求めること)の「残したいものをプラグインの
  フォルダに書かない」でも、Vectorworks が動いている間だけ要るものは置いて良いとしています。
- **スプールが同期・リダイレクトの対象になる環境には対応しません**（Vectorworks の利用者フォルダを OneDrive・iCloud
  などの同期・フォルダ リダイレクト・オフライン ファイルの対象に置いた環境。症状と直し方は
  [通信規則「プラグイン側の義務」](../protocol.md#プラグイン側の義務)）。Windows の既定の `<Plug-Ins>` は移動プロファイル
  （`%APPDATA%`）の下で、CLI とスプールも写されますが、写すのはログオンとログオフのときだけです。
- 通信規則を守る他のプログラムは、`<Plug-Ins>` を知る必要があります（受け入れたこと。既定の場所は
  [名前と識別子「置き場所」](identifiers.md#置き場所)の規則で求まる）。

## `cli` のフック

**このプラグインの配置の知識の内、フォルダの外に置くもの（PATH）は、`cli` のフック（`scripts/hooks/`）の
1 か所に置き、スクリプトのテストで確かめます**（下記「テスト」）。`install` の Go のコードは、どの
プラグインにも同じ手順だけを持ち、`cli` を特別に扱いません（[動いている CLI のよけ方](#動いている-cli-のよけ方)も、
名前ではなく実行ファイルの場所で決まる）。

| ファイル | すること |
| --- | --- |
| `hooks/install.sh` / `hooks/install.ps1` | 下記「PATH」 |
| `hooks/uninstall.sh` / `hooks/uninstall.ps1` | 下記「`uninstall` のフック」 |
| `hooks/lib.sh` / `hooks/lib.ps1` | 両方のフックが読み込む関数（PATH の項目の比べ方・足し方・除き方、リンクの判定）。`install` と `uninstall` が同じ比べ方を使うように 1 か所に置く |

- zip の直下に `hooks/` として入ります（[ビルド「梱包」](build-and-release.md#梱包)）。
- 標準出力に JSON のオブジェクトを 1 つだけ出します（`install` は `{"path":…}`。下記「PATH」。
  `uninstall` は `{"path":…,"left":[…]}`。`left` は消せなかった・確かめられなかったもの）。`install` /
  `uninstall` の出力の `hook` に載ります。
- 同じフックを 2026 と 2025 の zip に入れます。フックは、渡された変数の名前で版と CLI の名前（mac のリンクの名前と、
  `bin/` にあるかを確かめる CLI）を決めます（[版「決めたこと」](editions.md#決めたこと)の「フック」）。
- PATH が指す先は `VW2026_HOOK_INSTALL_DIR`（`<Plug-Ins>/cli/`）の `bin/` です（[レジストリ「フックに渡す環境変数」](../registry.md#フックに渡す環境変数)）。
  `uninstall` のフックはフォルダを `<Work>/old/cli/` へ移した後で走る（`VW2026_HOOK_PLUGIN_DIR` は移した先）
  ので、取り除く項目は `VW2026_HOOK_INSTALL_DIR` から決めます。
- **同じ場所かは、パスの文字列ではなくディレクトリの同一性で決めます**（[動いている CLI のよけ方](#動いている-cli-のよけ方)と
  同じ考え方）。在るいちばん近いフォルダどうしを比べ、その下の在らない部分は名前で比べます（`uninstall` のフックが
  走るときは `<Plug-Ins>/cli/` が無いため、在る `<Plug-Ins>` までさかのぼる）。`--plugins-dir` の書き方・リンク・
  大文字と小文字の違う書き方で入れたものも、同じ `<Plug-Ins>` なら同じとみなします。`install` の「既にある」と
  `uninstall` の「一致する」は同じ関数で決めます（片方だけが一致とみなすと、`install` が `exists` と答えたものを
  `uninstall` が残すため）。比べ方は `hooks/lib.sh` の `same_place`・`hooks/lib.ps1` の `Test-PathEntryTarget` に
  あります。

### PATH

**`install` のフックの度に確かめ、足りなければ通します**（何度走らせても同じ結果になる）。結果は出力の
`path` に載せます。PATH の失敗でフックを失敗にはしません（プラグインは動く）。フックを失敗にするのは、
何も変える前の確かめ（`VW2026_HOOK_INSTALL_DIR` と `HOME` が絶対パスであること・`bin/` に CLI があること）だけです。

| `path` | OS | 意味 |
| --- | --- | --- |
| `linked` | mac | リンクを作った（`~/.local/bin` は PATH にある） |
| `added` | Windows | `Path` の末尾に足した |
| `exists` | 両方 | 既にあった（mac はこのプラグインの CLI を指すリンクがあり、`~/.local/bin` は PATH にある） |
| `not_in_path` | mac | リンクはある（作った・既にあった）が、`~/.local/bin` が PATH に無い |
| `conflict` | 両方 | 触らなかった（mac は `~/.local/bin/vw2026` か `~/.local/bin` に別のものがある。Windows は `Path` の型が REG_SZ・REG_EXPAND_SZ のどちらでもない） |
| `failed` | 両方 | 作れなかった・読み書きできなかった（理由は標準エラー） |

- mac の `not_in_path` はリンクの状態より先に伝えます（`linked` / `exists` と重なるときは `not_in_path`）。
  利用者が手を動かす必要があるのは PATH のほうだからです。

| OS | すること | 既にあるとき |
| --- | --- | --- |
| mac | `~/.local/bin/vw2026` → `<Plug-Ins>/cli/bin/vw2026` のシンボリックリンク（`~/.local/bin` が無ければ作る） | **このプラグインの CLI を指すリンクなら何もしない。** それ以外（利用者のファイル・別の場所を指すリンク。別の `<Plug-Ins>` の `cli` を指すリンクを含む）なら触らず `conflict` |
| Windows | 利用者の環境変数 `Path`（`HKCU\Environment`）に `<Plug-Ins>\cli\bin` を追加 | 同じ項目が既にあれば何もしない（`exists`） |

- 行き先は `<Plug-Ins>/cli/bin/` で、フォルダを付け替えてもパスは変わらないので、更新で張り直す必要はありません。
- **シェルの設定ファイル（`.zshrc` など）は書き換えません。** `~/.local/bin` が PATH に無ければ
  `not_in_path` とし、追加の方法を標準エラーに表示するだけです。PATH の項目は末尾の `/` の違いを
  同じとみなして比べ、`~` や `$HOME` を含む項目は展開しません（`install` を走らせた環境の `PATH` を見る）。
- 新しい値は **新しく開いた端末から**効きます。

#### Windows の `Path` の読み書き

**`HKCU\Environment` の値 `Path` を、.NET の `Microsoft.Win32.RegistryKey` で直接読み書きします。**
関数ごとの細かな扱いは `hooks/lib.ps1` のコメントにあります。

- **展開しない値を読み、型を保って書き戻します。** 利用者の `Path` には `%USERPROFILE%\…` のような項目があり、
  型は REG_EXPAND_SZ です。`[Environment]::SetEnvironmentVariable` は展開した値を REG_SZ で書き戻すとされるので
  この項目が固定の値に変わる恐れがあり、`setx` は 1024 文字で切り詰めるので、どちらも使いません。
- 型は読んだものをそのまま使います（REG_SZ なら REG_SZ）。値が無ければ REG_EXPAND_SZ で作ります
  （後から利用者が `%…%` を含む項目を足しても展開されるように）。REG_SZ・REG_EXPAND_SZ 以外の
  型なら書き換えず、出力の `path` を `conflict` にします。
- 項目は `;` で分け、**`%…%` を展開せずに比べます。** 前後の空白・全体を囲む `"`・`/` と `\` の違い・末尾の `\`・
  大文字と小文字の違いを除いて比べ、それで違えば実際の場所で比べます（上記「同じ場所かは」）。`%…%` を含む項目・
  絶対でない項目（`C:`・`C:x`・`\x` のように、フックの今のディレクトリやドライブで解かれるもの）・解けない項目は、
  一致とみなしません。そのため `%APPDATA%\…\Plug-Ins\cli\bin` のように書かれた項目は `<Plug-Ins>\cli\bin` と一致せず、
  `install` はそれとは別に `<Plug-Ins>\cli\bin` を足し、`uninstall` はその項目を残します。
- **`<Plug-Ins>\cli\bin` がこの計算機の固定ドライブにあるときは、根（`C:` や `\\server\share`）の違う項目を開かずに
  違うとみなします。** 開くと、届かない共有の項目ごとに SMB の待ちで止まり、時間の上限を持たないフックが長く
  止まるためです（`subst` のドライブ・`\\localhost\c$` のような別の根からの書き方は同じとみなさない）。共有や
  ネットワークドライブにあるとき（AppData をリダイレクトしたときなど）は、どの項目も実際の場所で比べます。
- 足すときは末尾に足し、空の項目を増やしません。他の項目の並び・空の項目・前後の空白は変えません。
- `uninstall` は一致する項目を**全て**除きます（利用者が書いた ` "C:\…\bin"` のような形も含む）。どれも
  `uninstall` が消すフォルダを指すので、残すと消えたフォルダを指したままになるためです。
- **除いて空になっても値は消さず、空の文字列を元の型で書きます。** 消して良いのは一致する項目だけで、値そのもの
  （型と、利用者の空の項目を含む）は利用者のものだからです（[消すコードの歯止め](#消すコードの歯止め)）。
- 書いた後 `WM_SETTINGCHANGE` を知らせます。全体の上限は持ちません（途中で打ち切ると、Explorer など後ろの
  ウィンドウに知らせが届かず、そこから開いた端末に新しい値が効かないため）。知らせの失敗は無視します（値は
  書けていて、利用者がログインし直せば効くため）。
- **`powershell` のフックの標準出力は ASCII だけにします**（JSON の文字列の中の ASCII の外の文字は `\uXXXX`）。
  `[Console]::OutputEncoding` を UTF-8 にする（[レジストリ「書き方」](../registry.md#書き方)）のはコンソールの無い
  プロセスで例外になることがあり、そのときも OEM のコードページで日本語のパスが読み崩れないようにするためです。

### `uninstall` のフック

消すもの: リンクと PATH の項目だけです。CLI とスプールはフォルダの中にあるので、フォルダと一緒に
`uninstall`（Go）が消します。

- **外のものを消し始めたら失敗にしません。** 消せなかったもの・確かめられなかったもの（PATH の書き換えに
  失敗した）は `left` に載せ、0 で終わります。フックが失敗にすると CLI がフォルダを `<Plug-Ins>/cli` へ
  戻すので、プラグインは残るのに PATH だけが消えた状態になるためです。失敗にするのは、何も消す前の
  確かめ（環境変数が足りない・PowerShell が使えない）だけです。
- **PATH の後始末**（`VW2026_HOOK_INSTALL_DIR` の `bin/` を指すものだけ。同じ場所かは[`cli` のフック](#cli-のフック)の
  「同じ場所かは」）:
  - mac: `~/.local/bin/vw2026` が**シンボリックリンクで、`<Plug-Ins>/cli/bin/vw2026` を指すときだけ**消す。
    `~/.local/bin` は、`install` のフックが作ったものでも消さない（作ったかを記録しない。他のプログラムも
    使う場所）。
  - Windows: 利用者の `Path` から、`<Plug-Ins>\cli\bin` と**一致する項目だけ**を除く（比べ方と読み書きは
    `install` と同じ。[Windows の `Path` の読み書き](#windows-の-path-の読み書き)）。
- `<Work>` の下には何も置かず、何も消しません。
- 出力の `path` と `left`:

  | `path` | OS | 意味 |
  | --- | --- | --- |
  | `removed` | 両方 | リンクを消した・`Path` から項目を除いた |
  | `none` | 両方 | このプラグインの CLI を指すものが無かった（利用者のファイル・別の場所を指すリンク・型が文字列でない `Path` には触れない） |
  | `failed` | 両方 | 消せなかった・`Path` を読み書きできなかった。`left` に、mac はリンクのパス、Windows は `HKCU\Environment\Path: <Plug-Ins>\cli\bin` を載せる |

## アンインストール（`vw2026 uninstall`）

```sh
vw2026 uninstall my-plugin
# cli（CLI そのもの）は、入っているタグの初回のスクリプトで外す
curl -fsSL …/download/<tag>/get-vw2026.sh | sh -s -- uninstall
```

**走らせている CLI が外すフォルダの中にあれば、何も変えずに使い方の誤りで終わり、入っているタグ（記録の `tag`）の
初回のスクリプトに `uninstall` を渡すコマンドを標準エラーと出力の `command` に示します**
（入った `<Plug-Ins>` が既定の場所でなければ、初回のスクリプトに渡す `--plugins-dir` も載せる）。PR のプレリリースは
PR を閉じると消えるので、標準エラーには `latest` の初回のスクリプトに `uninstall` を渡すコマンドも添えます。
実際に当たるのは、PATH から使う入った `cli` の `vw2026` で `uninstall cli` を走らせたときだけです（Go は名前で
`cli` を見分けず、[動いている CLI のよけ方](#動いている-cli-のよけ方)と同じく実行ファイルの場所で決める）。

- `cli` を外せば CLI は使わなくなるので、入っている CLI が自分を外す必然はありません。フォルダの外で動く
  一時フォルダの CLI で外せば、動いている自分を消せずに残すこと（Windows）も、自分をよけることも要りません。
- 指定・出力の形・終了コードは `vw2026 help uninstall` が真実です（`CLAUDE.md`「Go」。ここには写さない）。

1. `<name>` が `cli` でなければ、`<Plug-Ins>/cli/` に正しい記録が無いときは
   何も変えずに失敗にする（[`cli` と同じ `<Plug-Ins>` に入れる](#流れ)）。
   **次に、Vectorworks が動いていれば何もせずに終わる**（`<Plug-Ins>/cli/spool/` と
   `<Work>/old/cli/spool/` のロックで判定。`install` と同じ 2 か所・同じ終了コード）。
   確かめる順は `install`（[流れ](#流れ)の 1・2）と同じ（`cli` の記録の誤りは、
   Vectorworks を終えて走らせ直しても通らないので、先に確かめる）。
2. **安全弁**: `<Plug-Ins>/<name>/` に記録があり、記録の `name` がフォルダ名と一致し、記録の
   `module` がフォルダの中に実在するときだけ進む。フォルダはあるが記録が無い・一致しないなら、
   何も消さずに失敗にする（`vw2026` が入れたものではない）。
   - `<Plug-Ins>/<name>/` が無く、`<Work>/old/<name>/` に正しい記録（`name` が一致し `module` がある）が
     あり、**`<Work>/old/<name>.uninstalling`（手順 3 の印）もあれば**、前の `uninstall` が手順 3 の後で
     止まったとみなし、手順 4 から続ける（`cli` の移した先のロックは、手順 1 が `<Work>/old/cli/spool/` で見ている）。
   - 印が無ければ、`install` が付け替えの途中で止まった（`old` が入っていた唯一の版かもしれない）のと
     見分けられないので、何も変えずに `old` の場所を `message` に載せて失敗にする（[入れ替えの手順](#入れ替えの手順)の
     1 と同じ。戻すか消すかは利用者が決める）。
   - どちらも無ければ何もせずに成功（`not_installed`）。前の回が消しきれなかった `<Work>/staging/<name>/`・
     `<Work>/staging/<name>.zip` と、続ける先の無い印 `<Work>/old/<name>.uninstalling`（前の回の残り）があれば消す。
3. 走らせている CLI が `<Plug-Ins>/<name>/` の中にあれば、何も変えずに断る（上記）。
   **前回の残りの `<Work>/old/<name>/` があれば、消さずに、何も変えずに場所を `message` に載せて失敗にする**
   （`uninstall` が消して良いものに入らない。[消すコードの歯止め](#消すコードの歯止め)。`install` のフックが失敗して
   Vectorworks が起動したときに残した前の版かもしれず、黙って消すと戻せない）。`message` には、記録の `registry` と
   `<Plug-Ins>` で、入っている版のタグの `install <name>@<tag>` を走らせ直す（その `install` を終えて片付ける。別の
   レジストリや `<Plug-Ins>` では[入れる先のフォルダ](#入れる先のフォルダ)の確かめで断られる。[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)）か、
   消してから走らせ直すことを示す。
   それから印 `<Work>/old/<name>.uninstalling`（空のファイル）を書き、**先に** `<Plug-Ins>/<name>` を
   `<Work>/old/<name>` へ名前を変える。失敗したら（エクスプローラーやウイルス対策がフォルダを開いているとき・
   カレントディレクトリがフォルダの中にあるプロセスが居るとき。[入れ替えの手順](#入れ替えの手順)の 3 と同じ）印を消して、
   何も変えずに失敗にする（`uninstall` は CLI をよけない）。
4. 記録の `hooks.uninstall` を、移した先（`<Work>/old/<name>/`）で走らせる（`VW2026_HOOK_PLUGIN_DIR` は
   移した先、`VW2026_HOOK_INSTALL_DIR` は `<Plug-Ins>/<name>/`）。失敗したら、まずロックを見る（手順 1 と同じ 2 か所。
   `install` のフックの失敗と同じ。[入れ替えの手順](#入れ替えの手順)の 4）。`cli` は、ロックのある
   `<Plug-Ins>/cli/spool/` ごと移しているので、移した先の `<Work>/old/cli/spool/` で見つかる（mac では、移す直前に
   読み込んだプラグインが掴んだロックが、フォルダと一緒に移る）。掴まれていれば戻さず、
   `old/<name>/` と印を残して失敗にする（Vectorworks を終了してから走らせ直すと、手順 4 から続く）。掴まれて
   いなければ `<Work>/old/<name>` を `<Plug-Ins>/<name>` へ戻し、印を消して失敗にする。
   **手順 2 で中断した回から続けたときは、失敗しても `<Plug-Ins>` へ戻さない**（`old/<name>/` と印を
   残し、場所を `message` に載せて失敗にする）。OS の一時フォルダの片付けはファイルを 1 つずつ消すので、
   続きの `old/<name>/` は記録とモジュールだけが残った壊れたフォルダかもしれず、それを `<Plug-Ins>` に
   戻さないため。
5. フックが通った後にもロックを見る（手順 1 と同じ 2 か所）。掴まれていれば消さずに、印を
   残して失敗にする（フォルダを移してフックも走らせたので、「何もしなかった」の `vectorworks_running` にはしない。
   終了してから走らせ直すと手順 4 から続く）。`<Work>/old/<name>` を
   `<Work>/staging/<name>/` へ名前の変更で移してから消し（[`<Work>/old/<name>/` の片付け](#workoldname-の片付け)と
   同じ。前回の残りの `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip` は先に消す）、印 `<Work>/old/<name>.uninstalling` を
   消す。移せなければ（Windows でウイルス対策が中のファイルを開いているなど）何も消さずに印を残して失敗にし、
   走らせ直すと手順 4 から続く（フックは走らせ直しても同じ結果になるように書く。[レジストリ「フック」](../registry.md#フック)）。
   移した後で消しきれなかったものは標準エラーに示し、外したことは変えない（次の `install` / `uninstall` が消す）。
6. よけた CLI と前回までの残り（`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`）を消してみる。
   消せなかったもの（Windows で、今走らせている CLI）は出力の `left` に載せる（失敗にはしない）。
7. `<Work>` に `staging` / `old` の空のフォルダしか無ければ、`<Work>` も消す。

- フックより先にフォルダを移すのは、フックが外のもの（`cli` なら PATH）を消した後で
  フォルダの名前の変更が失敗すると、プラグインは残って読み込まれ続けるのに PATH だけが消え、
  利用者が `vw2026` を見つけられなくなるためです。
- 手順 3 と 5 の間で止まった（Ctrl-C・電源断）ときは、もう一度 `uninstall <name>` を走らせれば
  手順 4 から続きます（手順 2）。このとき `install <name>@…` は、`<Work>/old/<name>/` だけがある状態を
  断る（[入れ替えの手順](#入れ替えの手順)の 1）ので、先に `uninstall` を終わらせます。
  `uninstall cli` が止まったときも、同じ初回のスクリプトに `uninstall` をもう一度渡します（一時フォルダの
  そのタグの CLI が手順 4 から続ける）。入れ直すなら、その後初回のスクリプトで入れます。
- フックが失敗してフォルダを戻しても、フックがすでに消した外のものは戻りません（そうならないための `uninstall` の
  フックの書き方は[レジストリ「いつ走るか」](../registry.md#いつ走るか)）。
- **レジストリを読みません。** 記録だけで決まるので、レジストリから消えたプラグインや、
  ネットワークにつながっていないときでも外せます。
- **`uninstall` の出力の `remaining` には、どの名前でも、残った記録のある `<Plug-Ins>` の直下の
  フォルダの名前を載せます**（Go は `cli` を特別に扱わない）。`uninstall cli` は他のプラグインが
  残っていても断りません。残ったプラグインは Vectorworks の中で動き続けますが、`vw2026` が無くなる
  ので外せなくなります（先に外したい呼ぶ側はこの一覧を見る）。
- 出力の `left` には、手順 6 で消せなかったものを載せます。

### `uninstall cli` の後に残るもの

| 残るもの | OS | 理由 | 片付け |
| --- | --- | --- | --- |
| `<Work>/old/vw2026.exe.old-<時刻>` の内消せなかったもの（動いている CLI。入っている CLI で更新したときに残ったものは、そのプロセスが終わっていれば消える） | Windows | 動いている実行ファイルは消せない | 出力の `left` に載る。次の `install` / `uninstall` が消す。一時フォルダの中なので、Windows の一時ファイルの掃除（ストレージ センサー・ディスク クリーンアップ）が有効なら、そちらでも消える（[作業の場所](#作業の場所)） |
| `~/.local/bin`（フォルダ） | mac | フックが作ったかを記録せず、他のプログラムも使う場所 | 残して良い |
| 他のプラグインのフォルダ | 両方 | `uninstall cli` は他のプラグインを外さない（上記 `remaining`） | 先にそれぞれを `uninstall` する |
| Vectorworks が覚えた「有効化」 | 両方 | Vectorworks の設定で、`vw2026` は触らない | 要らない（同じパスに入れ直せば、その間に起動しない限り有効のまま） |

- `uninstall cli` は初回のスクリプトの一時フォルダの CLI が走らせるので、`<Plug-Ins>/cli/` の中の CLI は動いておらず、
  フォルダごと消え、`<Work>/old/` の前回までの残りも消せます。スクリプトの一時フォルダはスクリプトが消します。

## 消すコードの歯止め

**利用者のものを消すコードは次の場所だけ**にし、歯止めを緩めません。同じ表を `CLAUDE.md` の 9 に置いています
（変えるときは両方を直す）。

| 消すコード | 消して良いもの |
| --- | --- |
| `install`（組み立て・後始末・フックの失敗の戻し） | `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip`（どちらも名前をそのまま組み立てたパスだけ。前方一致では消さない）・`<Work>/old/<name>/`（退避した版と前回の残りは、記録の `name` が一致し、記録の `module` があり、`<Plug-Ins>/<name>/` もあるときだけ。`<Work>/staging/<name>/` へ移してから消す。条件に合わないものは消さずに `<Work>/old/<name>.kept-<時刻>/` へ移す）・フックが失敗したときの新しい `<Plug-Ins>/<name>/`（自分が置いたもの）・`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`（ファイルだけ。よけた CLI と前回までの残り）・中断した `uninstall` の印 `<Work>/old/<name>.uninstalling`（付け替えに成功した後と、`<Plug-Ins>/<name>/` があるとき。どちらも前の回の残り） |
| `uninstall` | 記録の `name` が一致し、記録の `module` がある `<Plug-Ins>/<name>/`（`<Work>/old/<name>/` へ移し、フックの後で `<Work>/staging/<name>/` へ移してから消す）・`<Work>/staging/<name>/`・`<Work>/staging/<name>.zip`（どちらも名前をそのまま組み立てたパスだけ）・自分が書いた印 `<Work>/old/<name>.uninstalling`・`<Plug-Ins>/<name>/` も `<Work>/old/<name>/` も無いときの前の回の印 `<Work>/old/<name>.uninstalling`・`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`（ファイルだけ）・空の `<Work>/staging`・`<Work>/old`・`<Work>`（中身のあるものは消さない） |
| `cli` の `install` のフック | なし |
| `cli` の `uninstall` のフック | `<Plug-Ins>/cli/bin/vw2026` を指す `~/.local/bin/vw2026`・`Path` の `<Plug-Ins>\cli\bin` と一致する項目（どちらも `VW2026_HOOK_INSTALL_DIR` から決め、同じ場所かはディレクトリの同一性で決める） |

- 他のプラグインのフックがフォルダの外で消すものは、そのプラグインの提供側の責任です
  （[レジストリ「フック」](../registry.md#フック)）。

## テスト

- **`install` / `uninstall`**: Go の単体テスト（`cli/internal/install`）。場所（`<Plug-Ins>`・`<Work>`）と既定の
  レジストリを `install.Options` で渡し、偽の HTTPS サーバーと一時ディレクトリで確かめます（環境変数は増やさない）。
  偽のフックはテストの実行ファイルそのものを `sh` の代わりに走らせます（`sh` の無い Windows でも同じテストを
  走らせるため。仕組みは `cli/internal/install/harness_test.go` のコメント）。付け替えと後始末の失敗は、実際に起こせる
  ものはそのまま起こし、OS の失敗（権限・ディスクの誤り）でしか起きないものは、パッケージの中のファイルの操作を
  差し替えて起こします。**`install` / `uninstall` のコードは、どの分岐もテストで通します。** テストから通せないのは、
  `main()` と、走らせる OS でしか通らない分岐（`places_*.go`・`powershell` のフック）だけで、後者は mac と Windows の
  `go.yml` で通ります。何を確かめるかはテストの名前とコメントにあり、ここには写しません。
- **コマンドのテストでの場所の差し替え**: コマンド（`cli/cmd/vw2026`）のテストは、スプール・`<Work>`・既定の
  `<Plug-Ins>`・走らせている CLI の場所を、どれも既定で一時ディレクトリにします（`CLAUDE.md`「Go」。テストが場所を
  渡し忘れても、開発者の計算機の本物の `<Plug-Ins>`・`<Work>`・スプールに触れないため）。
- **`cli` のフック**: CI の `hooks.yml`（[ビルド「CI」](build-and-release.md#ci)）で、フックが走るのと同じもの
  （mac の `/bin/sh`・Windows PowerShell 5.1）で確かめます。どちらも一時ディレクトリを `HOME`・`VW2026_HOOK_*` に
  渡し（Windows は利用者の `Path` を偽の置き場所に替える）、利用者の場所に触れません。版ごと（`VW2026_HOOK_*` と
  `VW2025_HOOK_*`）に全てを走らせます。
  - mac（`sh`）: `tests/hooks/hooks_test.sh`（外部の枠組みを使わない）。
  - Windows（`powershell`）: `tests/hooks/Hooks.Tests.ps1`（Pester。版は `scripts/powershell.ps1` で固定し、
    Windows に入っている Pester 3.4 は使わない）。
  - どちらのフックも、標準出力が UTF-8 の JSON のオブジェクト 1 つだけであること（日本語を含むパスでも）と、
    `uninstall` のフックが外のものを消し始めた後は失敗しないことを確かめます。
- **実物の exe の入れ替え**: PR の `build.yml` の `install-windows`（版ごとのジョブ `install-windows-editions`）で、
  `release` が PR のプレリリースを公開した後に確かめます。手順は `build.yml` の各手順のコメントにあります。
  - **動いている CLI をよけるのが、その PR の Go のコードになる順にします**（PR で[動いている CLI のよけ方](#動いている-cli-のよけ方)を
    壊したら、このジョブが落ちるように）。PR の CLI を `<Plug-Ins>\cli\bin\` に入れてから、その CLI に付け替え
    （記録のタグを違うものにしてからの `install` と、`install cli@latest`）をさせます。
  - あわせて、入った CLI の `uninstall cli` が断ること、初回のスクリプトで外すと何も残らないこと、実物のレジストリで
    利用者の `Path` の型（REG_SZ・REG_EXPAND_SZ）と既存の項目（展開しない `%…%`）が保たれることを確かめます。
  - `latest` にマニフェストが無い・`manifest_version` が PR のものと違うときは、`latest` を入れる手順を飛ばします
    （PR のコードが動いている自分をよけることは、その前の手順で確かめられる）。
  - `main` への push では、版の違う相手が無いので走らせません（PR で確かめてからマージする）。
  - 別の `vw2026` を動かしたまま入れ替える形は組めません（ロックが掴まれていると `install` が何もせずに
    終わり、放されると `call` も終わる）。ランナーは使い捨てなので既定の場所（`<Plug-Ins>`・`<Work>`）を
    使いますが、利用者の場所に触れるので `go test` には入れません。
- **初回のスクリプト**: shellcheck・PSScriptAnalyzer。取ってきて `install` を走らせるだけなので、公開した
  スクリプトで入れて外すことを CI（mac は `build.yml` の `verify`、Windows は上の `install-windows`）と実機の確認で
  押さえます。
