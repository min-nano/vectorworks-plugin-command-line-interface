# インストール・更新・アンインストール

**配置は `vw2026 install` / `uninstall` が行います。** このプラグイン（`cli`）も、他の
プラグインも同一の手順でインストールされます。何を・どこから取得するかは[レジストリとマニフェスト](../registry.md)が
定め、プラグインのフォルダの外に配置するもの（`cli` なら PATH）はそのプラグインのフックが
配置します。`cli` の CLI とスプールは `cli` のフォルダの中にあり（[CLI とスプールの配置場所](#cli-とスプールの配置場所)）、
外に配置するのは PATH のみです。`cli` をインストールする最初の 1 回と、`cli` をアンインストールする場合は、取得した CLI で
`install` / `uninstall` を実行するのみの短いスクリプト（`get-vw2026.sh` / `.ps1`）を使用します（インストール前は CLI が
存在せず、アンインストール後は CLI を使用しないため。インストール済みの CLI でアンインストールすると、Windows では実行中の
自身を削除できずに残置する）。

このページは 2026 の名前で記述します。2025 の `cli`（`vw2025`・`get-vw2025.sh` / `.ps1`・`VW2025_HOOK_*`）も同一の手順で、
名前の読み替えは[版](editions.md)にあります。

| 段階 | 手段 | 処理内容 |
| --- | --- | --- |
| 初回 | `get-vw2026.sh` / `.ps1`（curl などで取得してパイプで実行） | 一時フォルダに、スクリプトを取得したリリースの CLI を展開し、`vw2026 install cli@<そのリリースのタグ>` を実行する |
| インストール・更新 | `vw2026 install <name>@<tag>` | `<Plug-Ins>/<name>/` を置換し、フックを実行する。インストール済みのものと同一のタグなら、zip を取得せず置換もせずに、フックのみを実行する。`cli` の更新も同様 |
| アンインストール | `vw2026 uninstall <name>` | フックを実行し、`<Plug-Ins>/<name>/` を除去する |
| `cli` のアンインストール | インストール済みのタグのリリースの初回スクリプトに `uninstall` を渡す | そのタグの CLI を一時フォルダに展開し、`vw2026 uninstall cli` を実行する（インストール済みの CLI の `uninstall cli` は拒否し、このコマンドを提示する） |

```sh
# mac。latest のリリースを入れる
curl -fsSL https://github.com/min-nano/vectorworks-plugin-command-line-interface/releases/latest/download/get-vw2026.sh | sh
# そのタグを入れる
curl -fsSL …/releases/download/<tag>/get-vw2026.sh | sh
# 既定以外の場所へ入れる
curl -fsSL …/get-vw2026.sh | sh -s -- --plugins-dir <Plug-Ins>
# そのタグの CLI で外す
curl -fsSL …/releases/download/<tag>/get-vw2026.sh | sh -s -- uninstall
```

```powershell
# Windows。latest のリリースを入れる
irm https://github.com/min-nano/vectorworks-plugin-command-line-interface/releases/latest/download/get-vw2026.ps1 | iex
# そのタグを入れる
irm …/releases/download/<tag>/get-vw2026.ps1 | iex
# 既定以外の場所へ入れる
& ([scriptblock]::Create((irm …/get-vw2026.ps1))) --plugins-dir <Plug-Ins>
# そのタグの CLI で外す
& ([scriptblock]::Create((irm …/releases/download/<tag>/get-vw2026.ps1))) uninstall
```

## 前提

- **プラグインのフォルダ（`<Plug-Ins>`）と `vw2026` の作業領域（`<Work>`。下記「[作業領域](#作業領域)」）は
  同一のドライブ（ボリューム）にあるものとします。** 既定では同一のボリュームにあります。置換は名前の変更のみで
  行い、ボリュームをまたぐ場合の処理（コピーへの切り替え・その検出）は有しません。名前の
  変更が失敗した場合は、何も変更せずに失敗で終了します。
- **インストール先を記録しません。** インストール済みの `vw2026`（`<Plug-Ins>/cli/bin/vw2026` で実行され、`<Plug-Ins>/cli/` に
  記録・モジュール・スプールのいずれかがあるもの）は、スプールと同様に自身の実行ファイルの場所から導出した
  `<Plug-Ins>` を使用します。いずれも、存在のみを確認して内容は読み取りません。`module` が欠けた・記録が破損した・記録が
  削除された `cli` でも既定の場所に別の `cli` をインストールせず、自身のインストール先のフォルダで `install` / `uninstall` が
  記録を確認して、再インストールするか拒否します。それ以外の `vw2026`（初回スクリプトの一時フォルダのもの・手動でビルドしたもの）は
  既定の場所を使用します。インストールしたものの記録は、プラグインのフォルダの中にのみ配置します（[レジストリ「インストールの記録」](../registry.md#インストールの記録)）。
- **既定以外の `<Plug-Ins>` は、初回スクリプトに `--plugins-dir` で渡します。** スクリプトが一時の `vw2026` に
  渡す隠した指定で、help に表示せず、環境変数も持たず、インストール済みの `vw2026` は使用方法の誤りとして拒否します
  （インストール済みの `vw2026` が別の `<Plug-Ins>` を扱うと、実行中の `cli` と異なる場所のロックを参照してしまうため）。
  絶対パスのみを受け付け、相対パスと空の値は使用方法の誤りです（相対パスのまま名前の変更や削除へ進まないため。
  `--plugins-dir "$UNSET"` のような取り違えで、暗黙に既定の場所へインストールしないため）。
- **隔離属性の解除（mac）・`Unblock-File`（Windows）は行いません。** curl・`Invoke-RestMethod`・
  Go の HTTP で取得したファイルには、隔離属性も Web からの標識（Mark of the Web）も付与されないためです。
  署名はビルドが付与したアドホック署名で、zip から展開したファイルにそのまま残ります。
- **同一のプラグインを二重にインストールしないのは利用者の責任です**（[レジストリ「提供側への要件」](../registry.md#提供側への要件)）。

場所は[名前と識別子「配置場所」](identifiers.md#配置場所)にあります。

### 作業領域

**`install` / `uninstall` の作業領域（`<Work>`）は、利用者ごとの一時フォルダの下の `vectorworks2026-cli-<鍵>/` です
（`<Plug-Ins>` ごとに 1 つ）。**
配置するのは、構築（`staging/`）・退避（`old/<name>/` と `uninstall` の途中の標識）・退避した CLI（`old/` の直下の
`vw2026.old-*` / `vw2026.exe.old-*`）・削除せずに別の場所へ移動した前の版（`old/<name>.kept-<時刻>/`。[`<Work>/old/<name>/` の整理](#workoldname-の整理)）のみで、
別の場所へ移動した前の版の他は、いずれも `install` / `uninstall` の中でのみ必要なものです。
`vw2026` の永続領域（設定・フックが使用する場所など）は有しません。

`<Plug-Ins>` と `<Work>` の一方がもう一方の中にある（同一の場所を含む）なら、`install` / `uninstall` は何も変更せずに
失敗とします（初回スクリプトに `<Work>` の下を `--plugins-dir` で渡した場合など。後処理がインストールした直後のプラグインを
削除しないため）。パスの表記（リンクを解決したものも）と、ディレクトリの同一性（Windows のジャンクション・`subst` の
ドライブ・割り当てたドライブも検出する）の両方で比較します。

削除・移動の可否を判定する前の検証は、いずれも失敗を安全側に倒します（[削除処理の制約](#削除処理の制約)）。

- **`<Work>`・`<Work>/staging`・`<Work>/old` は、存在しないか通常のフォルダでなければなりません。** リンク（Windows の
  ジャンクションを含む）・ファイルであれば、`install` / `uninstall` は何も変更せずに失敗とします。名前をそのまま組み立てた
  `staging/<name>/`・`old/<name>/` を削除・移動する際に、途中のリンクを経由してリンク先のフォルダに触れないためです。
  `<Work>` の親（mac の `/var` など）は検証しません。
- **`<Work>/old/<name>/`・`<Plug-Ins>/<name>/`・標識 `<Work>/old/<name>.uninstalling` の有無を、存在しない以外の理由で
  確認できなければ**（権限・到達できない共有）、存在しないとみなさずに、何も変更せずに失敗とします。存在しないとみなすと、
  唯一の版である可能性のある `old/<name>/` を見落とすか、中断した `uninstall` の続きと取り違えるためです。
- **`<Plug-Ins>/<name>/` が存在するときに前回の標識 `<Work>/old/<name>.uninstalling` を削除できなければ**（ウイルス対策
  ソフトが開いている場合など）、`install` は何も変更せずに失敗とします。標識を残したまま置換へ進み、その途中で停止すると、
  次回の `uninstall` がそれを中断した `uninstall` とみなし、唯一残った `old/<name>/` を削除するためです。

場所の導出方法（環境変数を読み取らずに、OS の定まった場所から導出する）は[名前と識別子「配置場所」](identifiers.md#配置場所)に
あります。

- **`<鍵>` は `<Plug-Ins>` から決定し（リンクを解決したパスの sha256 の先頭 12 桁）、`<Plug-Ins>` ごとに `<Work>` を
  分割します。** `<Work>/old/<name>/` は、どの `<Plug-Ins>` から退避したものかを保持しないので、同一の利用者が別の
  `<Plug-Ins>` にもインストールしている場合、分割しなければ一方の `install` が、もう一方の置換の途中で退避した唯一の版を
  前の版と取り違えて削除してしまうためです。同一のフォルダの綴りの違いは統一します（Windows は小文字にし、mac は
  ディスク上の綴りにする。統一の方法は `cli/internal/install/places.go` の `WorkDirFor`）。統一しないと、綴りを変えて
  渡した場合に `<Work>` が分かれ、置換で `old/cli/spool/` へ移動したロックを次の回が見落として、Vectorworks が
  実行中でもフォルダを置換してしまうためです。
- **環境変数を読み取らないのは、**実行方法（端末・ssh・他のアプリ）で場所が変わると、前の `install` /
  `uninstall` が途中で停止して残置した `old/` を、次の回が検出できなくなるためです。mac で `TMPDIR` が
  存在しない場合に Go の `os.TempDir()` が返す `/tmp` は利用者の間で共有され、他の利用者がシンボリックリンクを
  仕掛けられるので使用しません。いずれの場所も利用者のみが書き込めるフォルダです。
- **OS の後処理で削除されても差し支えありません**（Windows のディスク クリーンアップ・ストレージ センサー、mac の
  一定期間使用されていないファイルの整理）。いずれも利用者のデータではなく、プラグインはレジストリから
  再取得できるためです。
  - 退避した CLI の残りは、次の `install` / `uninstall` が削除し、この後処理が有効なら、そちらでも削除されます（Windows では
    設定しないと実行されない。[`uninstall cli` の後に残存するもの](#uninstall-cli-の後に残存するもの)）。
  - 途中で停止した回の `old/<name>/` が削除された場合、`<Plug-Ins>/<name>/` があれば何も起きません。
    無ければ未インストールの状態になり、`install` で再インストールします。
  - **後処理はファイルを 1 つずつ削除するので、`old/<name>/` が一部のみ残ることがあります。** そのため、退避した版を
    `<Plug-Ins>` へ戻すのは同一の回の中の失敗の場合のみです。前の回が残置した `old/<name>/` は、`install` では
    削除するか別の場所へ移動するか拒否するのみ（[`<Work>/old/<name>/` の整理](#workoldname-の整理)）、途中から再開する
    `uninstall` では削除するか拒否するのみ（[アンインストール](#アンインストールvw2026-uninstall)の 4）で、`<Plug-Ins>` に戻しません。
  - **同一の回の中で戻す場合も、その間に後処理が介入する危険は残ります（許容する）。** 退避してから戻すまでの
    間にはフックが実行され、フックの時間に上限はありません（[レジストリ「記法」](../registry.md#記法)）。
    名前の変更ではファイルの時刻が変わらないので、`<Work>` へ移動した直後の旧版も、時刻の古さで選択する後処理の
    対象になりえます。後処理が実行されるのは OS が定めた時機のみで、フックの実行中に当たる確率は低いので、制約を
    追加せずに許容します。戻した版が破損していた場合の修復方法は、何が削除されたかで異なります。
    - 記録の `module` が削除されていれば、同一のタグの `install` が再インストールします（[処理の流れ](#処理の流れ)）。
    - 記録と `module` が残り、他のファイルのみが削除された場合（`cli` の `bin/vw2026` のみ・mac の `.vwlibrary`
      のバンドルの内容の一部など）は、同一のタグの `install` ではフックのみが実行されるので修復されません。`uninstall` してから
      再インストールします。`cli` で `bin/vw2026` が削除されていれば、[初回スクリプト](#初回スクリプトget-vw2026sh--ps1)に
      `uninstall` を渡してから、初回スクリプトでインストールします。
  - 構築の途中のファイルが同様に選択されないよう、zip を展開する際にファイルの時刻を zip の項目の
    ものに戻しません（[レジストリ「zip の構成」](../registry.md#zip-の構成)）。
  - `old/<name>/` は残り、標識 `old/<name>.uninstalling` のみが削除された場合は、`install` / `uninstall` が
    `old` の場所を `message` に載せて拒否するので（[置換の手順](#置換の手順)の 1・[アンインストール](#アンインストールvw2026-uninstall)の 2）、
    利用者が削除します。
- **同一のボリュームにあること**: Windows の `%LOCALAPPDATA%\Temp` と既定の `<Plug-Ins>`（`%APPDATA%` の下）は
  いずれも利用者のプロファイルの中です。mac の `/var/folders` とホームは、いずれもデータボリュームに
  あります（`/private/var` はデータボリュームへの firmlink）。mac で `/var/folders` から `~/Library/…` へ名前の
  変更で移動できることは、実機で確認しました。

## 初回スクリプト（`get-vw2026.sh` / `.ps1`）

**スクリプトを取得したリリースの CLI を展開して、`install cli@<そのリリースのタグ>`（又は `uninstall cli`）を
実行するのみ**です。配置の手順・PATH・判断は `install` / `uninstall` と `cli` のフックが保持し、スクリプトは保持しません。

- **インストール・アンインストールするタグは、スクリプトを取得したリリースのタグに定まっています。** リリースは、雛形（`scripts/get-vw.sh` /
  `.ps1`）の `@VW_TAG@` をそのリリースのタグに、`@VW_YEAR@` を版（2026・2025）に置換して、`get-vw2026.*` と
  `get-vw2025.*` を公開します（[ビルド「リリースの構成」](build-and-release.md#リリースの構成)・[版](editions.md)）。
  `releases/download/<tag>/get-vw2026.sh` を取得すれば `<tag>` が、`releases/latest/download/get-vw2026.sh` を取得すれば
  その時点の latest のリリースのタグがインストールされます。どのタグをインストールするかは取得する URL のみで決まり、引数でタグを渡す形式は
  有しません（取得したスクリプトとインストールされる CLI の版が常に一致する）。置換していないスクリプト（リポジトリのものを
  そのまま実行した場合）は、何もせずに拒否します。

1. 引数を確認して、実行するものを決定する。位置の引数は `uninstall`（`uninstall cli` とも記述できる）のみを受け付け、他の
   位置の引数（`cli@<tag>` など）は、他のタグはそのタグのスクリプトを取得することを示して拒否する。指定は
   `--plugins-dir`（とその値）のみを受け付け、記述した位置に依らず CLI のコマンドの後ろへそのまま渡す（`vw2026` は
   コマンドの前の指定を受け付けないため）。他の指定は拒否する。**`--registry` は有しない**（`install` は既定の
   レジストリから先に検索し、名前が見つかった時点で停止する（[レジストリ「レジストリの優先順位」](../registry.md#レジストリの優先順位)）ので、
   既定のレジストリにある `cli` には、他のレジストリが使用されないため。`uninstall` はレジストリを読み取らない）。
   - **`uninstall` なら** `vw2026 uninstall cli <指定>` を実行する（`cli` をアンインストールする唯一の手段。一時フォルダの
     CLI はフォルダの外で実行されるので、何も残置せずにアンインストールできる。停止した `uninstall cli` の続きもこれで実行する。下記
     「アンインストール」）。インストール済みのタグのスクリプトでアンインストールするのは、インストールしたものと同一の版のスクリプトと CLI が、
     自身の書き込んだ記録を読み取るため（後の版でスクリプトや記録の扱いが変わっても、アンインストールの方法が変わらない）。
   - それ以外は `vw2026 install cli@<そのリリースのタグ> <指定>` を実行する。
2. ターゲットの zip を一時フォルダへ取得して、中の `bin/vw2026`（Windows は `bin\vw2026.exe`）のみを展開する。
   ターゲットは、mac は `sysctl -n hw.optional.arm64` が 1 なら `macos-arm64`、Windows は `windows-x64`
   （[レジストリ「名前・タグ・ターゲット」](../registry.md#名前タグターゲット)）。Intel の mac はリリースが配布しない
   （[名前と識別子](identifiers.md)）ので、取得する前に理解できる文言で停止する。zip の場所は既定のレジストリの `cli` の
   規則と同一の形式で決定する（`releases/download/<そのリリースのタグ>/cli-<target>.zip`）。JSON の読み取りが不要になるように、
   マニフェストは読み取らない。
3. 展開した CLI で `install`（又は `uninstall`）を実行する。
4. 一時フォルダを削除し、実行した `install` / `uninstall` の終了コードで終了する。「Vectorworks が実行中」の終了コード
   （番号は `vw2026 --help`）なら「Vectorworks を終了してから再度実行する」と表示する。

- CLI のみの資産は有しません。zip から展開します。
- 一時フォルダの CLI は、`install` の中でマニフェストと zip を再度取得します（スクリプトが取得した
  zip は渡さない。指定を増やさないため。zip は小さい）。`install` は zip を sha256 で照合します。
  `install` にはタグをそのまま渡すので、一時フォルダの CLI とインストールされる CLI は常に同一のビルドです（`latest` の
  URL から取得しても、その間に latest が進んで別のビルドがインストールされることはない）。
- **`get-vw2026.ps1` は `exit` を呼び出しません。** `iex` で実行すると、`exit` は利用者の PowerShell ごと閉じるためです。
  実行した `install` / `uninstall` の終了コードは `$LASTEXITCODE` に残り、CLI を実行する前の失敗（取得できない・
  引数が正しくない）は例外で停止します。利用者のセッションに変数を残置しません。引数の受け取り方と CLI への
  渡し方（Windows PowerShell 5.1 は空の引数を落とすので、コマンドラインを自身で構築する）は `scripts/get-vw.ps1` の
  コメントにあります。ASCII のみで記述します（[ビルド「リリースの構成」](build-and-release.md#リリースの構成)）。
- PR のプレリリースを試す場合は、そのリリースのスクリプト（`releases/download/<そのタグ>/get-vw2026.sh`）を
  取得して実行します。

## インストールと更新（`vw2026 install`）

**初回のインストールも更新も、同一の `install` で行います。**

```sh
# main の最新（同一のタグなら zip を取得せず、フックのみを実行する）
vw2026 install cli@latest
# PR のプレリリース
vw2026 install cli@dev-feature-x-61-a1b2c3d
# インストールせずに、新しいビルドがあるかのみを返す（Vectorworks が実行中でもよい）
vw2026 install cli@latest --check
vw2026 install my-plugin@2026.3.1 --registry https://example.com/plugins.json
# ローカル環境のファイルも URL で記述する
vw2026 install my-plugin@2026.3.1 --registry file:///Users/me/plugins.json
```

- **名前とタグは必須です**（`<name>@<tag>`。既定のタグは有しない）。1 回に 1 つのみインストールします
  （途中で失敗した場合に、どこまでインストールされたかを保持しないため）。
- `--check` は、新しいビルドがあるか（`available`）と最新か（`up_to_date`）を、終了コードでは
  なく出力の `outcome` で区別します（新しいビルドがあることは失敗ではないため。判定できなかった
  場合のみ失敗）。インストールされていなければ `available` です。
- **フォルダの内容を再インストールする手段は有しません。** 再インストールするには `uninstall` してからインストールします。
  - 他のプラグイン: `vw2026 uninstall <name>` の後 `vw2026 install <name>@<tag>`。
  - `cli`: インストール済みの CLI の `uninstall cli` が提示するコマンド（インストール済みのタグのリリースの[初回スクリプト](#初回スクリプトget-vw2026sh--ps1)に
    `uninstall` を渡す）でアンインストールし、続けて初回スクリプトでインストールします（インストール済みの CLI の `uninstall cli` は
    拒否する。下記「アンインストール」）。
    `<Plug-Ins>/cli/bin/vw2026` が削除された（ウイルス対策が隔離した・`install` が置換の途中で停止した）
    場合も同様で、`vw2026` を実行できないので、初回スクリプトに `uninstall` を渡してから再インストールします。
  - いずれも同一のパスにインストールされるので、その間に Vectorworks を起動しなければ「有効化」は残ります（下記
    「インストール先のフォルダ」）。

### 処理の流れ

```
vw2026 install <name>@<tag>
  1. 場所と記法の確認                名前・タグ・--registry の記法（誤りは使用方法の誤り。場所を導出する前に確認する）。
                                     <Plug-Ins> と <Work> が重複しないこと（作業領域）。<Plug-Ins>/cli/ に正しい
                                     記録が存在すること（無ければ何も変更せずに失敗。下記「cli と同一の <Plug-Ins> にインストールする」）
  2. Vectorworks の停止の確認        --check でなければ、<Plug-Ins>/cli/spool/ か <Work>/old/cli/spool/ のロックが
                                     取得されていれば何もせずに終了する（専用の終了コード。レジストリを取得する前に応答する）
  3. 名前の参照                      既定のレジストリ → --registry の順（レジストリ「レジストリの優先順位」）
  4. マニフェストの取得              合致した規則の path（{tag} を置換する）。tag を照合し、現在のターゲットを選択する
                                     （合致した規則の path に {tag} があり、@ の後ろが記録の tag と同一で、記録の
                                      target が現在のターゲットと同一であれば取得しない。下記「同一のタグの場合」）
  5. インストール先の確認            <Plug-Ins>/<name>/ と内部の記録（下記「インストール先のフォルダ」）。
                                     --check であればインストールせずに、新しいビルドの有無のみを返して終了する
     （同一のタグの場合）            記録の tag と target が同一で、記録の module がフォルダの中に実在すれば、
                                     インストール済みのフォルダで記録の hooks.install のみを
                                     実行し、<Work>/old/<name>/ を整理して終了する（zip を取得せず、置換しない）
  6. zip の取得と照合                asset を <Work>/staging/<name>.zip へ。sha256 が一致しなければ失敗
  7. 構築                            <Work>/staging/<name>/ へ展開し、モジュールを確認し、記録を書き込む
  8. プラグインのフォルダの置換      下記「置換の手順」（直前にロックを再度確認する。実行中の CLI が
                                     その中にあれば先に退避する）
  9. install のフックの実行          失敗したら 8 を巻き戻す（レジストリ「フック」）
 10. 後処理                          <Work>/staging/<name>/・<Work>/staging/<name>.zip を削除し、<Work>/old/<name>/ を整理し、
                                     退避した CLI の削除を試みる
```

指定・環境変数・出力（どの段階で終了したか・フックの出力）の形式・終了コードは `vw2026 help install` が真実です
（`CLAUDE.md`「Go」。ここには複製しない）。

- **取得（レジストリ・マニフェスト・zip）に待機の上限を設けません。** フックと同様に、待機の上限を決定して停止する
  のは呼び出し元です（[レジストリ「記法」](../registry.md#記法)・[設計「CLI のプリミティブ性の維持」](../design.md#cli-のプリミティブ性の維持)）。
  大きな zip を低速な回線で取得する時間は CLI には決定できず、停止したサーバーやプロキシの待機は呼び出し元が
  打ち切ります（Ctrl-C・呼び出し元の上限）。取得の途中で停止しても、変更されるのは `<Work>/staging/<name>/`・
  `<Work>/staging/<name>.zip` のみで、次の `install` が削除します。
- **zip の取得の進捗は標準エラーに書き込みます**（停止しているかを、呼び出し元と利用者が判別できるように。
  標準出力は JSON の 1 行のままにする）。開始時に URL と大きさ（判明していれば）を、終了時に取得した量を 1 行ずつ書き込み、
  その間は、標準エラーが端末なら同一の行を書き直し、端末でなければ（ログ・パイプ）一定の間隔で 1 行ずつ追加します
  （間隔と書き直しの方法は `cli/internal/install/progress.go`）。レジストリとマニフェスト（1 MiB まで）は表示しません。
- **新しいかは、タグとターゲットのみで比較します**（タグは再利用しないので、タグが同一ならビルドも
  同一）。マニフェストのみを取得し、zip は取得しません。
- **記録の `module` がフォルダの中に無い場合**（ウイルス対策が隔離した・手動で削除した）は、同一のタグでも
  同一とみなさず、マニフェストを取得して再インストールします（置換するので、Vectorworks が停止している必要が
  ある）。`uninstall` は `module` が無いフォルダを削除しない（安全弁）ので、破損したフォルダは先にこの
  `install` で修復してから `uninstall` します。
- **同一のタグの場合**は、zip を取得せず、フォルダも置換せずに、`install` のフックのみを実行します（`up_to_date`。
  `cli` なら PATH を再設定する）。
  - フックは Vectorworks の停止中にのみ実行するので、同一のタグでも Vectorworks が実行中であれば
    `vectorworks_running` で終了します（新しいかのみを知りたい場合は `--check`）。
  - 実行するのは**記録に複製した `hooks.install`** です（マニフェストのものは使用しない。提供側が同一の場所の
    マニフェストを差し替えても、インストールしていないフックが実行されないため）。`VW2026_HOOK_PREVIOUS_TAG` には同一のタグを
    渡します（新しい版を残置した `install` を完了させる回は、`<Work>/old/<name>/` に残った前の版のタグ。
    [レジストリ「フックに渡す環境変数」](../registry.md#フックに渡す環境変数)）。
  - フックが成功したら、記録の `hook_pending` を除去し、置換の後処理と同様に、`<Work>/old/<name>/`
    （[`<Work>/old/<name>/` の整理](#workoldname-の整理)）・退避した CLI・前回の残りの `<Work>/staging/<name>/`・
    `<Work>/staging/<name>.zip` を整理します。
  - 合致した規則の `path` に `{tag}` があり、記録の `target` が現在のターゲットと同一なら、マニフェストも取得しません
    （ターゲットが異なれば、再インストールするのでマニフェストを取得する。`latest` のように定まった場所を指す規則では、現在のタグを
    知るためにマニフェストを取得する）。タグをそのまま指定すれば（`cli@<入っているタグ>`）、ネットワークに接続して
    いなくても、削除された PATH を再設定できます。インストール済みのタグは `install` / `--check` の出力の `tag` と、記録で判明します。
- 初回でも Vectorworks が実行中であれば何もせずに終了し、CLI も配置しません（何も変更しない）。
- **`cli` と同一の `<Plug-Ins>` にインストールする**: Vectorworks が実行中かは、インストール先の `<Plug-Ins>/cli/spool/` の
  ロックで判定します。そのため、`cli` 以外のプラグインは、`cli` がインストールされている `<Plug-Ins>` にのみインストールします。
  `<Plug-Ins>/cli/` に正しい記録（`name` が `cli` で、`module` が実在する）が無ければ、何も変更せずに失敗とします
  （`uninstall` も同様）。`cli` の無い `<Plug-Ins>` では、Vectorworks が実行中でも判定できず、置換とフックが
  実行されてしまうためです。ワークグループのフォルダなど、`cli` の無い `<Plug-Ins>` へはインストールできません（対応しない）。
  `cli` の `install` / `uninstall` が途中で停止して `cli` が無いこともあるので、拒否する際は、Vectorworks を終了して、
  その `install` / `uninstall` を初回スクリプトで再実行するよう付記します（既定でない `<Plug-Ins>` なら
  `--plugins-dir` を付ける。停止した状態は読み取らず、続行の方法はその `install cli` / `uninstall cli` が応答する）。
- **Vectorworks が実行中かはロックで判定します**（[通信規則「生存の判定」](../protocol.md#生存の判定)）。
  ロックを不在以外の理由で調査できなければ（権限・破損した場所）、実行中かが不明なので、`install` /
  `uninstall` は最初に何も変更せずに失敗とします（「実行中でない」とみなして置換しない。判定そのものは変更しない）。
  参照するのは `<Plug-Ins>/cli/spool/` と `<Work>/old/cli/spool/`（下記。置換で移動したロック）の 2 か所で、`install` /
  `uninstall` のいずれの確認も、この同一の 2 か所を参照します（経路ごとに参照する場所を変えると、見落とす経路が残るため）。
  プロセス名は参照しません。ロックを取得していない Vectorworks（`cli` がインストールされていない・起動の途中で
  最初の周期処理の前・2 つ目の起動）が存在する場合は、Windows では読み込み中のフォルダの名前を変更できないので
  （[SDK の調査 6](../sdk-research.md#6-プラグインのフォルダ内のモジュール以外のファイルとモジュールの読み込み元判明)）
  置換が失敗し、何も変更されません。mac では置換が成功し、その
  Vectorworks は古い版のまま実行され、次の起動から新しい版になります。
- **ロックは手順 2 と置換の直前（[置換の手順](#置換の手順)の 2）の 2 度参照します。** 手順 2 は
  レジストリ・zip を取得する前に拒否するため、直前の 2 度目は、zip を取得して構築する間（ネットワーク次第で長い）に起動した
  Vectorworks を見落とさないためです。mac では置換が成功するので、その間に起動してロックを取得した
  Vectorworks があると、次の事象が起きます。
  - プラグインは `bridge.lock` を一度取得すると解放せず（[通信規則「ロック」](../protocol.md#ロックbridgelock)）、
    POSIX では開いているファイルはフォルダの名前の変更に追随して移動するので、取得されたロックは置換で
    `<Work>/old/cli/spool/bridge.lock` へ移動します。プラグインは他のファイルをスプールの場所の文字列から
    開き直すので、要求は置換した後の `<Plug-Ins>/cli/spool/` で探索します。
  - 新しい CLI は `<Plug-Ins>/cli/spool/` でロックを保持する者を検出できず、Vectorworks が実行中でも
    停止していると判定し、`call` も拒否します。
  - そのため `install` / `uninstall` は `<Work>/old/cli/spool/` のロックも参照します。この Vectorworks を実行中と
    みなし（`vectorworks_running`。置換の後の後処理なら通知するのみ）、`<Work>/old/cli/` を削除も移動もしません
    （[`<Work>/old/<name>/` の整理](#workoldname-の整理)）。参照しないと、後処理が取得されたままのロックごと
    `<Work>/old/cli/` を削除し、それ以降の `install` / `uninstall` が、Vectorworks が実行中であるにもかかわらず成功します。
- **フックが失敗して戻す前にも、ロックを参照します**（[置換の手順](#置換の手順)の 4）。フックの時間には
  上限が無く、その間に起動した Vectorworks が新しい版を読み込み、ロックを取得することがあります。そのまま戻すと、
  mac では実行中のプラグインのロックごと新しい版が削除され、`<Plug-Ins>` には古い版が戻り、上記と同様に停止して
  いると判定されます。Windows では読み込まれた新しい版の名前を変更できず、戻す処理の途中で停止します。
- 2 度目と戻す前の確認の後も見落とすのは、確認してから名前を変更するまでのごく短い間に起動した
  Vectorworks と、起動の途中でまだ最初の周期処理が来ていない Vectorworks のみで、いずれも上記と同様にロックを
  取得していない Vectorworks です。
- **終了させるのは呼び出し元です。** `install` は終了を要求せず、待機もしません（[設計「CLI の
  プリミティブ性の維持」](../design.md#cli-のプリミティブ性の維持)）。終了から再起動までを 1 度に
  行いたい呼び出し元は、`session start` → `call quit` → 停止を待機する → `install` → `launch` →
  起動を待機する、を組み合わせます。CLI は起動・停止を待機するコマンドを有しないので、
  `vw2026 status` を繰り返し、終了コードで区別します。
  sh の例と、例が守る規則（どの終了コードで抜けるか）は `vw2026 --help` にあります（CLI の使用方法の
  真実は help。PowerShell の記法は `vw2026 help status`）。規則の内次の 2 つは、他の組み合わせでも守ります。
  - `quit` は占有の中でのみ呼び出せ、図面を 1 枚も開いていない場合のみ受け付けます。呼び出し元が先に図面を
    保存して閉じます（[ツール](tools.md#quit)）。
  - **失敗したら占有を解除してから抜けます。** 占有は Vectorworks を再起動するまで残り、他の呼び出し元は
    全て `occupied` で拒否されるためです。Vectorworks が終了すれば占有も消滅するので、再起動した後に使用するなら
    占有を再取得します。
- 失敗した場合（取得できない・照合できない・展開できない・置換できない・フックが失敗した）、
  `<Plug-Ins>` を元のままにして理由を `message` に載せ、失敗の終了コードで終了します
  （フックがフォルダの外で変更したものは除く。退避した CLI も元の場所へ戻す）。同一の理由を標準エラーにも書き込みます
  （`uninstall` も同様）。名前やタグの形式が正しくない場合は、使用方法の誤りの終了コードで終了します。

### インストール先のフォルダ

**フォルダ名はレジストリの名前です**（`<Plug-Ins>/<name>/`。`cli` は `<Plug-Ins>/cli/`）。参照すれば何の
プラグインか判別でき、名前からフォルダが直接決まります。

| `<Plug-Ins>/<name>/` | 振る舞い |
| --- | --- |
| 無い | 作成してインストールする |
| あり、記録の `name` が一致し、記録の `registry` が今回使用したレジストリと同一 | 更新として置換する |
| あるが、記録が無い（手動でインストールしたもの・他のインストーラでインストールしたもの） | **何も変更せずに失敗とする。** `message` に場所を載せる（利用者のものを上書きしない） |
| あるが、記録の `name` がフォルダ名と異なる（手動で複製したものなど）・記録が読み取れない（破損している・未知の `record_version`） | **何も変更せずに失敗とする。** `message` に場所を載せる（修復の方法は利用者が決定する） |
| あるが、フォルダでない（ファイル・シンボリックリンク・Windows のジャンクション。リンクの先が記録のあるフォルダでも） | **何も変更せずに失敗とする。** リンクの先の作業用のコピーなどに触れないため（`uninstall` も同様） |
| あるが、記録の `registry` が異なる（後から既定のレジストリに同一の名前が掲載され、そちらが優先されるようになった場合など） | **何も変更せずに失敗とする。** 別のプラグインを暗黙に置換しないため。利用者が `uninstall` してから再インストールする（`cli` は既定のレジストリが先頭にあるので、この場合に該当しない） |

- **更新ではフォルダのパスが変わりません。** Vectorworks は署名の無いプラグインの「有効化」を
  モジュールのフルパスで記憶するので、モジュールのファイル名が変わらない限り、更新の後も有効の
  まま読み込まれます（[Findings「Plug-in Modules」](https://github.com/min-nano/vectorworks-developer-sdk-reference/blob/main/Findings/Plug-in%20Modules.md)の「開発元不明のプラグイン」のダイアログ。SDK リファレンス #258）。
  `uninstall` してから再インストールしても同一のパスなので、その間に Vectorworks を起動しなければ有効のままです
  （プラグインが存在しない起動でダイアログを閉じると、有効化は消滅する）。
- `<Plug-Ins>` そのものが無ければ作成します（Vectorworks を一度も起動していない利用者・CI のランナー）。
- 同一の名前のフォルダに記録が無ければ拒否するので、**同一の名前のフォルダへの上書きのみは CLI が防止します**。
  別の名前で同一のプラグインがインストールされているか（手動でインストールしたもの・別のレジストリの名前）は確認しません。

### 置換の手順

1. **構築**: zip を `<Work>/staging/<name>/` に展開し、直下のモジュールとフック（スクリプトが zip の中にあり、
   インタプリタがこの OS で実行できること。インタプリタを経由しないものは、mac では実行の権限があること、Windows では拡張子が
   `.exe`・`.com`・`.cmd`・`.bat` であること）を確認して、記録（`vw2026-install.json`）を書き込む。フックが実行されないことに
   置換の後で気付くと、その間に起動した Vectorworks の下にインストールを完了できない版が残るため、置換の前に
   確認する。その前に、次の順で前回の残りを整理する。
   1. **前回の残りの `<Work>/old/<name>/` があれば**（前の `install` / `uninstall` が置換の途中で
      停止した・新しい版を残置した）、下記「[`<Work>/old/<name>/` の整理](#workoldname-の整理)」の規則で
      整理する。整理できなければ（`<Plug-Ins>/<name>/` が無い）、何も変更せずに失敗とする。
   2. 前回の残りの `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip` を削除する。削除できなければ何も変更せずに
      失敗とする。1 で削除するものは構築の場所を経由するので、この順にすると、1 で削除しきれなかったもの
      （Windows でウイルス対策が開いているファイルなど）があれば 2 が失敗し、前の版のファイルを新しい版に
      混入させて構築しない。
2. **ロックを再度参照して、実行中の CLI を退避する**: `<Plug-Ins>/cli/spool/` のロックが取得されていれば、
   何も変更せずに `vectorworks_running` で終了する（[処理の流れ](#処理の流れ)の 2 と同様。2 度参照する理由は[処理の流れ](#処理の流れ)の
   「ロックは手順 2 と置換の直前の 2 度参照します」）。この場合、構築した `<Work>/staging/<name>/`・
   `<Work>/staging/<name>.zip` は削除する。続けて、実行している CLI の実行ファイルが `<Plug-Ins>/<name>/` の中にあれば、
   `<Work>/old/` へ名前の変更で移動する（下記「[実行中の CLI の退避](#実行中の-cli-の退避)」）。
   失敗したら何もせずに終了する。
3. **置換**: `<Plug-Ins>/<name>` → `<Work>/old/<name>`、続けて `<Work>/staging/<name>` →
   `<Plug-Ins>/<name>`。未インストールであれば 1 つ目は省略する。1 つ目が失敗したら、2 で退避した CLI を戻して終了する。
   2 つ目が失敗したら 1 つ目を戻し、退避した CLI を戻す。1 つ目が失敗するのは、Windows で次のいずれかがフォルダの
   中のものを開いている場合。
   - エクスプローラーやウイルス対策がフォルダの中のファイルを開いている
   - Vectorworks が読み込んでいる
   - **端末などのプロセスのカレントディレクトリがフォルダの中にある**（`Path` は新しく開いた端末から有効になるので、
     開いたままの端末で `cd <Plug-Ins>\cli\bin` してから `.\vw2026.exe` を実行した場合など。実行した
     `vw2026` 自身もカレントディレクトリを継承するので、CLI を退避しても成功しない）

   いずれであるかを `vw2026` から判別することはできないので、失敗の `message` には、名前を変更できなかった場所と
   ともに、これらを閉じる・カレントディレクトリをフォルダの外へ移動することを示す。
4. **フック**: `install` のフックを実行する。失敗したら、まずロックを参照する（[処理の流れ](#処理の流れ)の「フックが失敗して
   戻す前にも、ロックを参照します」。他の確認と同一の 2 か所）。
   - **取得されていれば戻さない。** 戻す処理の 1 の名前の変更が失敗した場合（Windows で、ロックを取得する前の Vectorworks が
     新しい版を読み込んでいる）も、その先へ進まない。いずれも次のようにして、フックの失敗として失敗で終了する。
     - 新しい版を `<Plug-Ins>/<name>` に残置し、`<Work>/old/<name>` も残置する（同一のタグで再実行した `install` が、
       フックが成功した後で整理する。[処理の流れ](#処理の流れ)の「同一のタグの場合」）。残置した版の記録には、構築する際に
       書き込んだ `hook_pending` が残る（[レジストリ「インストールの記録」](../registry.md#インストールの記録)）。
     - 退避した CLI は、前の版のフォルダ（`<Work>/old/<name>/`）の元の場所へ戻す（利用者が前の版を手動で戻しても
       CLI が欠けず、後処理が退避した名前のまま削除しないように。戻せなければ、その場所を `message` に載せる）。
     - 取得した `<Work>/staging/<name>.zip` は削除する（同一のタグの `install` は zip を取得しない）。
     - `message` には、フックが失敗したことと、Vectorworks が起動したので新しい版を残置したこと、Vectorworks を
       終了してから同一のタグで `install` を再実行する（フックのみが実行される）ことを載せる。
   - 取得されていなければ、次の順に戻す。
     1. 新しい `<Plug-Ins>/<name>` を、名前の変更で `<Work>/staging/<name>` へ退避する（1 回で足り、元に
        戻せる。削除は後に行う。ウイルス対策が新しいファイルを調査していると削除が途中で停止し、
        半分削除されたプラグインが `<Plug-Ins>` に残るため）。
     2. `<Work>/old/<name>` を `<Plug-Ins>/<name>` へ戻す（最初のインストールでは存在しない）。
     3. 2 で退避した CLI を、戻したフォルダの元の場所へ戻す。
     4. 退避した `<Work>/staging/<name>` を削除する。
5. **後処理**: `<Work>/staging/<name>.zip` を削除し、退避した版を「[`<Work>/old/<name>/` の整理](#workoldname-の整理)」の
   規則で整理し（整理できなくてもインストールしたことは変わらないので、標準エラーに表示するのみとする）、中断した `uninstall` の標識
   `<Work>/old/<name>.uninstalling` が残っていれば削除し、2 で退避した CLI と前回までの残り
   （`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`）の削除を試みる。実行中で削除できない
   ものは残置し、次の `install` / `uninstall` で削除する。

- **記録に `hook_pending` がある版**（フックがまだ成功していない。[レジストリ「インストールの記録」](../registry.md#インストールの記録)）は、
  同一のタグでもインストールを完了していないものとして扱います。
  - `--check` は同一のタグでも `available` を返します。
  - **前の版が `<Work>/old/<name>/` にある間は、置換しません**（置換の前の整理が前の版を削除してから
    新しい版のフックが失敗すると、成功していない版のみが残るため）。別のタグなら、同一のタグでインストールを完了するよう示します
    （断念するなら、残置した版を削除して前の版を戻す手順も示す）。同一のタグでも再インストールになる（`module` が欠けた）なら、
    前の版を戻すか削除するかを示します。拒否するのは Vectorworks が実行中でないと判明した後（実行中であれば
    `vectorworks_running`）で、`--check` は拒否せずに `available` を返します（新しいビルドがあるかのみを応答する）。
  - フックが成功したのに `hook_pending` を除去できなかった場合は、退避した版も整理しません（次の同一のタグの `install` が
    除去して整理する）。
- **中断した `uninstall` の標識は、`<Plug-Ins>/<name>/` があれば置換の前（同一のタグの場合も）に削除し、置換に
  成功した後（5）にも削除します。** `uninstall` はフォルダを移動してから停止するので、`<Plug-Ins>/<name>/` がある場合の
  標識は前の回の残りです（`uninstall` のフックが失敗して戻す処理にも失敗し、利用者が手動で戻した場合など）。残置すると、
  その後の `install` が置換の途中で停止した場合に、次の `uninstall` がそれを中断した `uninstall` とみなし、
  唯一残った `old/<name>/` を削除してしまいます。後処理のみで削除すると、同一のタグの `install` や置換の前に失敗した
  `install` の後に標識が残るので、置換の前にも削除します。
- 置換を名前の変更で行うのは、途中で失敗した場合に元へ戻せるようにするためです（ファイル
  ごとに置換すると、不完全な版が残る）。
- 構築と退避の場所を `<Work>` に置くのは、`<Plug-Ins>` の外（Vectorworks に読み込まれない）で、
  前提により `<Plug-Ins>` と同一のドライブにあるためです。
- **`install` と `uninstall` を同時に実行しないのは、呼び出し元の責任です。** 同一の名前の 2 つの `install`
  は同一の `<Work>/staging/<name>/`・`<Work>/old/<name>/` を使用し、一方の「前回の残りを削除する」がもう一方の
  構築の途中のフォルダを削除しうるので、「失敗したら `<Plug-Ins>` を変更しない」が保てません。CLI は
  排他を有しません（[設計「CLI のプリミティブ性の維持」](../design.md#cli-のプリミティブ性の維持)。
  排他はプラグインの占有のみで、`install` は Vectorworks の停止中に実行されるので占有も無い）。
  **名前が異なっても同時に実行しません。** いずれの回も後処理で共通の `<Work>/old/vw2026.old-*` /
  `vw2026.exe.old-*` を削除するので、mac では、`install cli@…` が退避した CLI を、同時に実行される別の名前の
  `install` が削除しえます（実行中のファイルも削除できる）。その後 `cli` の置換かフックが失敗すると
  CLI を戻せず、`bin/vw2026` の無い `cli/` が残ります。
- フックが失敗して元に戻した場合、フックがフォルダの外で変更したもの（`cli` なら PATH）は
  戻りません。フックは何度実行しても同一の結果になるように記述するので、再度 `install` を実行します。

### `<Work>/old/<name>/` の整理

**`install` のいずれの経路（[置換の手順](#置換の手順)の 1 と 5・[同一のタグの場合](#処理の流れ)のフックの後）も、
`<Work>/old/<name>/` をこの 1 つの規則で整理します。** 経路ごとに規則を変えると、ある経路が残置したものを
他の経路が整理できず、その名前の `install` / `uninstall` が成功しなくなるためです。

- 無ければ何もしない。
- **`<Plug-Ins>/<name>/` が無ければ**、`old` がインストールされていた唯一の版である可能性があるので、何も変更せずに `old` の場所を
  `message` に載せて失敗とする（戻すか削除するかは利用者が決定する）。標識 `<Work>/old/<name>.uninstalling` も
  あれば、停止した `uninstall` なので、`uninstall <name>` を再実行して完了させることを示す。
- **Vectorworks が実行中であれば**（`<Plug-Ins>/cli/spool/` と `<Work>/old/cli/spool/` のロック。[処理の流れ](#処理の流れ)）、
  実行中の Vectorworks が使用している可能性があるので、削除も移動もしない。置換の前なら `vectorworks_running` で
  何も変更せずに終了し、置換やフックの後（フックの実行中に起動した）なら通知するのみとする（終了してから同一のタグの
  `install` を再実行すると整理する）。
- `<Plug-Ins>/<name>/` があり、`old` の記録の `name` が一致し記録の `module` があれば、退避した版・退避の残りと
  して削除する（[削除処理の制約](#削除処理の制約)）。
- `<Plug-Ins>/<name>/` があり、`old` の記録が無い・読み取れない・`module` が無い場合（`module` の無いフォルダを
  再インストールした際の前の版・OS の後処理で一部が削除された残り）は、利用者のファイルが含まれている可能性があるので
  削除せずに、`<Work>/old/<name>.kept-<時刻>/` へ名前の変更で移動し、その場所を標準エラーに表示する。置換で実行中の
  CLI を退避していれば、それもその版の元の場所へ戻す（利用者が戻す可能性のある版から `vw2026` を欠かさない。戻せなければ、
  退避した場所を示して削除しない）。
  - `old/<name>/` に配置したままにしないのは、`uninstall` が `old/<name>/` を削除せずに拒否する（[アンインストール](#アンインストールvw2026-uninstall)の 3）
    ので、利用者が発見して削除するまでその名前をアンインストールできなくなるためです。
  - `<name>.kept-<時刻>` は `vw2026` のいずれの経路も削除しません（利用者が削除する）。`<Work>` の下なので、OS の後処理で
    削除されることもあります（[作業領域](#作業領域)）。名前は `.` を含むので、`<Work>/old/<name>/` と重複しません。
- **削除する際は、まず `<Work>/staging/<name>/` へ名前の変更で移動してから削除する**（`uninstall` の手順 5 も同様。
  削除が途中で停止しても（Windows でウイルス対策が中のファイルを開いているなど）、記録のみが先に削除された
  不完全なフォルダを `old/<name>/` に残置しないため。残置すると、次の回が唯一の版と判別できない）。不完全な残りは
  構築の場所にあり、次の `install` の手順 1 と `uninstall` が名前のパスとして削除する。移動できなければ
  何も変更せずに失敗とする。

### 実行中の CLI の退避

**Windows では、開いているファイルを含むフォルダの名前を変更できません。** 実行中の実行ファイルも
開いているファイルなので、`install cli@…` を実行している CLI（`<Plug-Ins>/cli/bin/vw2026.exe`）が
`<Plug-Ins>/cli/` の中にある限り、置換の 1 つ目が失敗します。一方で、**実行中の実行ファイルそのものの
名前は変更でき、同一のボリュームの別のフォルダへも移動できます**（移動も名前の変更）。そこで、
置換の前に CLI 自身をフォルダの外へ移動します（[置換の手順](#置換の手順)の 2）。

- **条件は「実行している CLI の実行ファイル（リンクを解決したもの）が、置換する `<Plug-Ins>/<name>/` の中に
  あること」のみ**です。Go のコードは名前で `cli` を判別しません（他の名前のフォルダに CLI がインストールされることはないので、
  実際に該当するのは `cli` のみ）。
- **中にあるかは、パスの文字列ではなくディレクトリの同一性で決定します。** `<Plug-Ins>` はインストール先・初回
  スクリプトの `--plugins-dir`・既定の場所のいずれからでも与えられ、実行ファイルのパスと表記（大文字と小文字・8.3 形式・
  ジャンクション・末尾の区切り）が一致するとは限らないためです。文字列で比較すると外と判定して退避せず、置換の
  1 つ目が失敗します（インストール済みの CLI では `install cli` が成功しなくなる）。`uninstall` も同一の判定で、実行している
  CLI がアンインストールするフォルダの中にあれば拒否します（下記「アンインストール」）。比較の方法は `cli/internal/install/sidestep.go` の
  `within` にあります。
- 移動先は `<Work>/old/vw2026.old-<時刻>`（Windows は `vw2026.exe.old-<時刻>`）です。名前は実行ファイルの名前に
  依らず決定します（大文字の `VW2026.EXE` や別の名前の複製で実行しても、後処理が同一の接頭辞で検出して削除できるように）。
  `<Work>` は前提により `<Plug-Ins>` と同一のドライブにあるので、名前の変更で移動できます。
- **mac でも同一の手順を踏みます。** mac は中で何が実行されていてもフォルダの名前を変更できるので不要ですが、
  手順を OS で分割せず、Go の単体テストを両方の OS で同様に実行するためです。mac では後処理でそのまま削除できます。
- 移動した後も、実行中のプロセスはそのまま実行され続けます（実行ファイルを読み直さない）。同一の実行ファイルから
  実行されている他の `vw2026`（別の端末の `status` の繰り返しなど）も、ファイルは 1 つなので一括して外れます。
  それらがスプールのファイルを開いている瞬間に当たると置換は失敗し、何も変更されません（再試行する）。
- **失敗したら元の場所へ戻します。** 置換の失敗とフックの失敗のいずれでも、フォルダを戻した後で
  CLI を元の場所（`<Plug-Ins>/<name>/` の中の同一の相対パス）へ戻します（実行中でも名前の変更はできる）。
- **退避するのは `install` のみです。** `uninstall` は、実行している CLI がアンインストールするフォルダの中にあれば何もせずに拒否する
  ので、退避しません（下記「アンインストール」）。
- **後処理で削除を試み、削除できなければ残置します。** Windows では、移動した CLI は `install` が終了するまで
  実行中なので、その `install` の中では削除できません。次の `install` / `uninstall` が削除します
  （`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*` のみ。[削除処理の制約](#削除処理の制約)）。
- 退避してから置換するまでの間に停止する（Ctrl-C・電源断）と、`<Plug-Ins>/cli/` は CLI の無いまま
  残ります。この場合は `vw2026` を実行できないので、[初回スクリプト](#初回スクリプトget-vw2026sh--ps1)に
  `uninstall` を渡してから再インストールします（一時フォルダの CLI はフォルダの外で実行されるので、退避が不要になる）。
- 初回スクリプトから実行した場合は、実行中の CLI は一時フォルダにあるので、退避しません。

## CLI とスプールの配置場所

**`cli` の CLI とスプールは、`cli` のフォルダ（`<Plug-Ins>/cli/`）の中に配置します。** CLI は zip の
`bin/` がそのまま配置されたもの（`<Plug-Ins>/cli/bin/vw2026`）を PATH から使用し、スプールはプラグインが
`<Plug-Ins>/cli/spool/` に作成します（[名前と識別子「配置場所」](identifiers.md#配置場所)）。

- **目的は、`cli` を他のプラグインと同一の形式に閉じ込めることです。** Go の `install` はいずれの
  プラグインにも「zip の内容をフォルダに配置し、フォルダごと置換する」のみを行います。CLI がフォルダの
  中にあれば、`cli` の CLI もこの置換で入れ替わり、フォルダを削除すれば CLI もスプールも一緒に削除されます。
  `cli` のフックが担当するのは、フォルダの外にしか配置できない PATH のみです。
- **CLI を複製して再配置する手順を有しません。** 複製を持たないので、プラグインと CLI が食い違う（複製のみが
  古い・複製のみが削除された）ことが起きません。
- **スプールの場所の導出方法は[通信規則「スプールの場所」](../protocol.md#スプールの場所)が真実です**（いずれの側も自身の
  ファイルの場所から導出する。フォルダの外で実行した `vw2026` はインストール済みの `cli` のスプールを参照しない）。`install` /
  `uninstall` も、インストール済みの `vw2026` は自身の実行ファイルの場所から `<Plug-Ins>` を導出し（[前提](#前提)）、インストール先の
  `<Plug-Ins>/cli/spool/` のロックで Vectorworks が実行中かを判定します（[処理の流れ](#処理の流れ)の 2）。
- **`cli` は利用者ごとの `Plug-Ins` にのみ配置します**（複数の利用者が読み込む `Plug-Ins` に配置するとスプールも共有される。
  [通信規則「スプールの場所」](../protocol.md#スプールの場所)）。`install` はネットワーク共有へはインストールできません
  （`<Work>` と別のボリューム）が、同一のボリュームの共有のフォルダへは初回スクリプトの `--plugins-dir` でインストールされうるので、
  渡さないのは利用者の責任です（[前提](#前提)の二重のインストールと同様に、確認できない配置を CLI が判別しない）。
- **フォルダの中のスプールは、置換で削除されても差し支えありません。** 置換は Vectorworks の停止中
  にのみ行い、その時点でスプールに必要なもの（ロックを保持する者・応答を待機する者）は存在しません。占有も
  Vectorworks の終了で消滅します（[通信規則「占有」](../protocol.md#占有セッション)）。
  [レジストリ「提供側への要件」](../registry.md#提供側への要件)の「残置したいものをプラグインの
  フォルダに書き込まない」でも、Vectorworks の実行中のみ必要なものは配置してよいとしています。
- **スプールが同期・リダイレクトの対象になる環境には対応しません**（Vectorworks の利用者フォルダを OneDrive・iCloud
  などの同期・フォルダ リダイレクト・オフライン ファイルの対象に配置した環境。症状と修正方法は
  [通信規則「プラグイン側の義務」](../protocol.md#プラグイン側の義務)）。Windows の既定の `<Plug-Ins>` は移動プロファイル
  （`%APPDATA%`）の下で、CLI とスプールも複製されますが、複製されるのはログオンとログオフの時点のみです。
- 通信規則を守る他のプログラムは、`<Plug-Ins>` を知る必要があります（許容したこと。既定の場所は
  [名前と識別子「配置場所」](identifiers.md#配置場所)の規則で導出できる）。

## `cli` のフック

**このプラグインの配置の知識の内、フォルダの外に配置するもの（PATH）は、`cli` のフック（`scripts/hooks/`）の
1 か所に集約し、スクリプトのテストで検証します**（下記「テスト」）。`install` の Go のコードは、いずれの
プラグインにも同一の手順のみを有し、`cli` を特別に扱いません（[実行中の CLI の退避](#実行中の-cli-の退避)も、
名前ではなく実行ファイルの場所で決まる）。

| ファイル | 処理内容 |
| --- | --- |
| `hooks/install.sh` / `hooks/install.ps1` | 下記「PATH」 |
| `hooks/uninstall.sh` / `hooks/uninstall.ps1` | 下記「`uninstall` のフック」 |
| `hooks/lib.sh` / `hooks/lib.ps1` | 両方のフックが読み込む関数（PATH の項目の比較・追加・除去の方法、リンクの判定）。`install` と `uninstall` が同一の比較方法を使用するように 1 か所に集約する |

- zip の直下に `hooks/` として格納されます（[ビルド「梱包」](build-and-release.md#梱包)）。
- 標準出力に JSON のオブジェクトを 1 つのみ出力します（`install` は `{"path":…}`。下記「PATH」。
  `uninstall` は `{"path":…,"left":[…]}`。`left` は削除できなかった・確認できなかったもの）。`install` /
  `uninstall` の出力の `hook` に載ります。
- 同一のフックを 2026 と 2025 の zip に格納します。フックは、渡された変数の名前で版と CLI の名前（mac のリンクの名前と、
  `bin/` にあるかを確認する CLI）を決定します（[版「決定事項」](editions.md#決定事項)の「フック」）。
- PATH が指す先は `VW2026_HOOK_INSTALL_DIR`（`<Plug-Ins>/cli/`）の `bin/` です（[レジストリ「フックに渡す環境変数」](../registry.md#フックに渡す環境変数)）。
  `uninstall` のフックはフォルダを `<Work>/old/cli/` へ移動した後で実行される（`VW2026_HOOK_PLUGIN_DIR` は移動先）
  ので、除去する項目は `VW2026_HOOK_INSTALL_DIR` から決定します。
- **同一の場所かは、パスの文字列ではなくディレクトリの同一性で決定します**（[実行中の CLI の退避](#実行中の-cli-の退避)と
  同一の考え方）。存在する最も近いフォルダ同士を比較し、その下の存在しない部分は名前で比較します（`uninstall` のフックが
  実行される時点では `<Plug-Ins>/cli/` が無いため、存在する `<Plug-Ins>` まで遡る）。`--plugins-dir` の表記・リンク・
  大文字と小文字の異なる表記でインストールしたものも、同一の `<Plug-Ins>` なら同一とみなします。`install` の「既にある」と
  `uninstall` の「一致する」は同一の関数で決定します（一方のみが一致とみなすと、`install` が `exists` と応答したものを
  `uninstall` が残置するため）。比較の方法は `hooks/lib.sh` の `same_place`・`hooks/lib.ps1` の `Test-PathEntryTarget` に
  あります。

### PATH

**`install` のフックの度に確認し、不足していれば設定します**（何度実行しても同一の結果になる）。結果は出力の
`path` に載せます。PATH の失敗でフックを失敗とはしません（プラグインは動作する）。フックを失敗とするのは、
何も変更する前の確認（`VW2026_HOOK_INSTALL_DIR` と `HOME` が絶対パスであること・`bin/` に CLI があること）のみです。

| `path` | OS | 意味 |
| --- | --- | --- |
| `linked` | mac | リンクを作成した（`~/.local/bin` は PATH にある） |
| `added` | Windows | `Path` の末尾に追加した |
| `exists` | 両方 | 既にあった（mac はこのプラグインの CLI を指すリンクがあり、`~/.local/bin` は PATH にある） |
| `not_in_path` | mac | リンクはある（作成した・既にあった）が、`~/.local/bin` が PATH に無い |
| `conflict` | 両方 | 変更しなかった（mac は `~/.local/bin/vw2026` か `~/.local/bin` に別のものがある。Windows は `Path` の型が REG_SZ・REG_EXPAND_SZ のいずれでもない） |
| `failed` | 両方 | 作成できなかった・読み書きできなかった（理由は標準エラー） |

- mac の `not_in_path` はリンクの状態より優先して伝えます（`linked` / `exists` と重なる場合は `not_in_path`）。
  利用者が対処する必要があるのは PATH の方だからです。

| OS | 処理内容 | 既にある場合 |
| --- | --- | --- |
| mac | `~/.local/bin/vw2026` → `<Plug-Ins>/cli/bin/vw2026` のシンボリックリンク（`~/.local/bin` が無ければ作成する） | **このプラグインの CLI を指すリンクなら何もしない。** それ以外（利用者のファイル・別の場所を指すリンク。別の `<Plug-Ins>` の `cli` を指すリンクを含む）なら変更せず `conflict` |
| Windows | 利用者の環境変数 `Path`（`HKCU\Environment`）に `<Plug-Ins>\cli\bin` を追加 | 同一の項目が既にあれば何もしない（`exists`） |

- リンク先は `<Plug-Ins>/cli/bin/` で、フォルダを置換してもパスは変わらないので、更新で再作成する必要はありません。
- **シェルの設定ファイル（`.zshrc` など）は書き換えません。** `~/.local/bin` が PATH に無ければ
  `not_in_path` とし、追加の方法を標準エラーに表示するのみです。PATH の項目は末尾の `/` の違いを
  同一とみなして比較し、`~` や `$HOME` を含む項目は展開しません（`install` を実行した環境の `PATH` を参照する）。
- 新しい値は **新しく開いた端末から**有効になります。

#### Windows の `Path` の読み取りと書き込み

**`HKCU\Environment` の値 `Path` を、.NET の `Microsoft.Win32.RegistryKey` で直接読み書きします。**
関数ごとの詳細な扱いは `hooks/lib.ps1` のコメントにあります。

- **展開しない値を読み取り、型を保持して書き戻します。** 利用者の `Path` には `%USERPROFILE%\…` のような項目があり、
  型は REG_EXPAND_SZ です。`[Environment]::SetEnvironmentVariable` は展開した値を REG_SZ で書き戻すとされるので
  この項目が固定の値に変わる恐れがあり、`setx` は 1024 文字で切り詰めるので、いずれも使用しません。
- 型は読み取ったものをそのまま使用します（REG_SZ なら REG_SZ）。値が無ければ REG_EXPAND_SZ で作成します
  （後から利用者が `%…%` を含む項目を追加しても展開されるように）。REG_SZ・REG_EXPAND_SZ 以外の
  型なら書き換えず、出力の `path` を `conflict` にします。
- 項目は `;` で分割し、**`%…%` を展開せずに比較します。** 前後の空白・全体を囲む `"`・`/` と `\` の違い・末尾の `\`・
  大文字と小文字の違いを除いて比較し、それで異なれば実際の場所で比較します（上記「同一の場所かは」）。`%…%` を含む項目・
  絶対でない項目（`C:`・`C:x`・`\x` のように、フックの現在のディレクトリやドライブで解決されるもの）・解決できない項目は、
  一致とみなしません。そのため `%APPDATA%\…\Plug-Ins\cli\bin` のように記述された項目は `<Plug-Ins>\cli\bin` と一致せず、
  `install` はそれとは別に `<Plug-Ins>\cli\bin` を追加し、`uninstall` はその項目を残置します。
- **`<Plug-Ins>\cli\bin` がこの計算機の固定ドライブにある場合は、ルート（`C:` や `\\server\share`）の異なる項目を開かずに
  異なるとみなします。** 開くと、到達できない共有の項目ごとに SMB の待機で停止し、時間の上限を持たないフックが長く
  停止するためです（`subst` のドライブ・`\\localhost\c$` のような別のルートからの表記は同一とみなさない）。共有や
  ネットワークドライブにある場合（AppData をリダイレクトした場合など）は、全ての項目を実際の場所で比較します。
- 追加する際は末尾に追加し、空の項目を増やしません。他の項目の順序・空の項目・前後の空白は変更しません。
- `uninstall` は一致する項目を**全て**除去します（利用者が記述した ` "C:\…\bin"` のような形式も含む）。いずれも
  `uninstall` が削除するフォルダを指すので、残置すると削除されたフォルダを指したままになるためです。
- **除去して空になっても値は削除せず、空の文字列を元の型で書き込みます。** 削除してよいのは一致する項目のみで、値そのもの
  （型と、利用者の空の項目を含む）は利用者のものだからです（[削除処理の制約](#削除処理の制約)）。
- 書き込んだ後 `WM_SETTINGCHANGE` を通知します。全体の上限は設けません（途中で打ち切ると、Explorer など後方の
  ウィンドウに通知が届かず、そこから開いた端末で新しい値が有効にならないため）。通知の失敗は無視します（値は
  書き込めており、利用者が再ログインすれば有効になるため）。
- **`powershell` のフックの標準出力は ASCII のみにします**（JSON の文字列の中の ASCII 以外の文字は `\uXXXX`）。
  `[Console]::OutputEncoding` を UTF-8 にする（[レジストリ「記法」](../registry.md#記法)）のはコンソールの無い
  プロセスで例外になることがあり、その場合も OEM のコードページで日本語のパスが文字化けしないようにするためです。

### `uninstall` のフック

削除するもの: リンクと PATH の項目のみです。CLI とスプールはフォルダの中にあるので、フォルダと一緒に
`uninstall`（Go）が削除します。

- **外のものを削除し始めたら失敗としません。** 削除できなかったもの・確認できなかったもの（PATH の書き換えに
  失敗した）は `left` に載せ、0 で終了します。フックが失敗とすると CLI がフォルダを `<Plug-Ins>/cli` へ
  戻すので、プラグインは残るのに PATH のみが削除された状態になるためです。失敗とするのは、何も削除する前の
  確認（環境変数が不足している・PowerShell が使用できない）のみです。
- **PATH の後処理**（`VW2026_HOOK_INSTALL_DIR` の `bin/` を指すもののみ。同一の場所かは[`cli` のフック](#cli-のフック)の
  「同一の場所かは」）:
  - mac: `~/.local/bin/vw2026` が**シンボリックリンクで、`<Plug-Ins>/cli/bin/vw2026` を指す場合のみ**削除する。
    `~/.local/bin` は、`install` のフックが作成したものでも削除しない（作成したかを記録しない。他のプログラムも
    使用する場所）。
  - Windows: 利用者の `Path` から、`<Plug-Ins>\cli\bin` と**一致する項目のみ**を除去する（比較の方法と読み書きは
    `install` と同一。[Windows の `Path` の読み取りと書き込み](#windows-の-path-の読み取りと書き込み)）。
- `<Work>` の下には何も配置せず、何も削除しません。
- 出力の `path` と `left`:

  | `path` | OS | 意味 |
  | --- | --- | --- |
  | `removed` | 両方 | リンクを削除した・`Path` から項目を除去した |
  | `none` | 両方 | このプラグインの CLI を指すものが無かった（利用者のファイル・別の場所を指すリンク・型が文字列でない `Path` には触れない） |
  | `failed` | 両方 | 削除できなかった・`Path` を読み書きできなかった。`left` に、mac はリンクのパス、Windows は `HKCU\Environment\Path: <Plug-Ins>\cli\bin` を載せる |

## アンインストール（`vw2026 uninstall`）

```sh
vw2026 uninstall my-plugin
# cli（CLI そのもの）は、インストール済みのタグの初回スクリプトでアンインストールする
curl -fsSL …/download/<tag>/get-vw2026.sh | sh -s -- uninstall
```

**実行している CLI がアンインストールするフォルダの中にあれば、何も変更せずに使用方法の誤りで終了し、インストール済みのタグ（記録の `tag`）の
初回スクリプトに `uninstall` を渡すコマンドを標準エラーと出力の `command` に示します**
（インストール先の `<Plug-Ins>` が既定の場所でなければ、初回スクリプトに渡す `--plugins-dir` も載せる）。PR のプレリリースは
PR を閉じると削除されるので、標準エラーには `latest` の初回スクリプトに `uninstall` を渡すコマンドも付記します。
実際に該当するのは、PATH から使用するインストール済みの `cli` の `vw2026` で `uninstall cli` を実行した場合のみです（Go は名前で
`cli` を判別せず、[実行中の CLI の退避](#実行中の-cli-の退避)と同様に実行ファイルの場所で決定する）。

- `cli` をアンインストールすれば CLI は使用しなくなるので、インストール済みの CLI が自身をアンインストールする必然性はありません。フォルダの外で実行される
  一時フォルダの CLI でアンインストールすれば、実行中の自身を削除できずに残置すること（Windows）も、自身を退避することも不要です。
- 指定・出力の形式・終了コードは `vw2026 help uninstall` が真実です（`CLAUDE.md`「Go」。ここには複製しない）。

1. `<name>` が `cli` でなければ、`<Plug-Ins>/cli/` に正しい記録が無い場合は
   何も変更せずに失敗とする（[`cli` と同一の `<Plug-Ins>` にインストールする](#処理の流れ)）。
   **次に、Vectorworks が実行中であれば何もせずに終了する**（`<Plug-Ins>/cli/spool/` と
   `<Work>/old/cli/spool/` のロックで判定。`install` と同一の 2 か所・同一の終了コード）。
   確認の順序は `install`（[処理の流れ](#処理の流れ)の 1・2）と同一（`cli` の記録の誤りは、
   Vectorworks を終了して再実行しても成功しないので、先に確認する）。
2. **安全弁**: `<Plug-Ins>/<name>/` に記録があり、記録の `name` がフォルダ名と一致し、記録の
   `module` がフォルダの中に実在する場合のみ進む。フォルダはあるが記録が無い・一致しないなら、
   何も削除せずに失敗とする（`vw2026` がインストールしたものではない）。
   - `<Plug-Ins>/<name>/` が無く、`<Work>/old/<name>/` に正しい記録（`name` が一致し `module` がある）が
     あり、**`<Work>/old/<name>.uninstalling`（手順 3 の標識）もあれば**、前の `uninstall` が手順 3 の後で
     停止したとみなし、手順 4 から続行する（`cli` の移動先のロックは、手順 1 が `<Work>/old/cli/spool/` で参照している）。
   - 標識が無ければ、`install` が置換の途中で停止した（`old` がインストールされていた唯一の版である可能性がある）場合と
     判別できないので、何も変更せずに `old` の場所を `message` に載せて失敗とする（[置換の手順](#置換の手順)の
     1 と同様。戻すか削除するかは利用者が決定する）。
   - いずれも無ければ何もせずに成功（`not_installed`）。前の回が削除しきれなかった `<Work>/staging/<name>/`・
     `<Work>/staging/<name>.zip` と、続行先の無い標識 `<Work>/old/<name>.uninstalling`（前の回の残り）があれば削除する。
3. 実行している CLI が `<Plug-Ins>/<name>/` の中にあれば、何も変更せずに拒否する（上記）。
   **前回の残りの `<Work>/old/<name>/` があれば、削除せずに、何も変更せずに場所を `message` に載せて失敗とする**
   （`uninstall` が削除してよいものに含まれない。[削除処理の制約](#削除処理の制約)。`install` のフックが失敗して
   Vectorworks が起動した際に残置した前の版である可能性があり、暗黙に削除すると戻せない）。`message` には、記録の `registry` と
   `<Plug-Ins>` で、インストール済みの版のタグの `install <name>@<tag>` を再実行する（その `install` を完了させて整理する。別の
   レジストリや `<Plug-Ins>` では[インストール先のフォルダ](#インストール先のフォルダ)の確認で拒否される。[`<Work>/old/<name>/` の整理](#workoldname-の整理)）か、
   削除してから再実行することを示す。
   それから標識 `<Work>/old/<name>.uninstalling`（空のファイル）を書き込み、**先に** `<Plug-Ins>/<name>` を
   `<Work>/old/<name>` へ名前を変更する。失敗したら（エクスプローラーやウイルス対策がフォルダを開いている場合・
   カレントディレクトリがフォルダの中にあるプロセスが存在する場合。[置換の手順](#置換の手順)の 3 と同様）標識を削除して、
   何も変更せずに失敗とする（`uninstall` は CLI を退避しない）。
4. 記録の `hooks.uninstall` を、移動先（`<Work>/old/<name>/`）で実行する（`VW2026_HOOK_PLUGIN_DIR` は
   移動先、`VW2026_HOOK_INSTALL_DIR` は `<Plug-Ins>/<name>/`）。失敗したら、まずロックを参照する（手順 1 と同一の 2 か所。
   `install` のフックの失敗と同様。[置換の手順](#置換の手順)の 4）。`cli` は、ロックのある
   `<Plug-Ins>/cli/spool/` ごと移動しているので、移動先の `<Work>/old/cli/spool/` で検出される（mac では、移動する直前に
   読み込んだプラグインが取得したロックが、フォルダと一緒に移動する）。取得されていれば戻さず、
   `old/<name>/` と標識を残置して失敗とする（Vectorworks を終了してから再実行すると、手順 4 から続行する）。取得されて
   いなければ `<Work>/old/<name>` を `<Plug-Ins>/<name>` へ戻し、標識を削除して失敗とする。
   **手順 2 で中断した回から続行した場合は、失敗しても `<Plug-Ins>` へ戻さない**（`old/<name>/` と標識を
   残置し、場所を `message` に載せて失敗とする）。OS の一時フォルダの後処理はファイルを 1 つずつ削除するので、
   続行する `old/<name>/` は記録とモジュールのみが残った破損したフォルダである可能性があり、それを `<Plug-Ins>` に
   戻さないため。
5. フックが成功した後にもロックを参照する（手順 1 と同一の 2 か所）。取得されていれば削除せずに、標識を
   残置して失敗とする（フォルダを移動してフックも実行したので、「何もしなかった」の `vectorworks_running` にはしない。
   終了してから再実行すると手順 4 から続行する）。`<Work>/old/<name>` を
   `<Work>/staging/<name>/` へ名前の変更で移動してから削除し（[`<Work>/old/<name>/` の整理](#workoldname-の整理)と
   同様。前回の残りの `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip` は先に削除する）、標識 `<Work>/old/<name>.uninstalling` を
   削除する。移動できなければ（Windows でウイルス対策が中のファイルを開いているなど）何も削除せずに標識を残置して失敗とし、
   再実行すると手順 4 から続行する（フックは再実行しても同一の結果になるように記述する。[レジストリ「フック」](../registry.md#フック)）。
   移動した後で削除しきれなかったものは標準エラーに表示し、アンインストールしたことは変えない（次の `install` / `uninstall` が削除する）。
6. 退避した CLI と前回までの残り（`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`）の削除を試みる。
   削除できなかったもの（Windows で、現在実行している CLI）は出力の `left` に載せる（失敗とはしない）。
7. `<Work>` に `staging` / `old` の空のフォルダしか無ければ、`<Work>` も削除する。

- フックより先にフォルダを移動するのは、フックが外のもの（`cli` なら PATH）を削除した後で
  フォルダの名前の変更が失敗すると、プラグインは残って読み込まれ続けるのに PATH のみが削除され、
  利用者が `vw2026` を発見できなくなるためです。
- 手順 3 と 5 の間で停止した（Ctrl-C・電源断）場合は、再度 `uninstall <name>` を実行すれば
  手順 4 から続行します（手順 2）。この場合 `install <name>@…` は、`<Work>/old/<name>/` のみがある状態を
  拒否する（[置換の手順](#置換の手順)の 1）ので、先に `uninstall` を完了させます。
  `uninstall cli` が停止した場合も、同一の初回スクリプトに `uninstall` を再度渡します（一時フォルダの
  そのタグの CLI が手順 4 から続行する）。再インストールするなら、その後初回スクリプトでインストールします。
- フックが失敗してフォルダを戻しても、フックが既に削除した外のものは戻りません（そうならないための `uninstall` の
  フックの記述方法は[レジストリ「実行の時機」](../registry.md#実行の時機)）。
- **レジストリを読み取りません。** 記録のみで決まるので、レジストリから削除されたプラグインや、
  ネットワークに接続していない場合でもアンインストールできます。
- **`uninstall` の出力の `remaining` には、どの名前でも、残った記録のある `<Plug-Ins>` の直下の
  フォルダの名前を載せます**（Go は `cli` を特別に扱わない）。`uninstall cli` は他のプラグインが
  残っていても拒否しません。残ったプラグインは Vectorworks の中で動作し続けますが、`vw2026` が無くなる
  のでアンインストールできなくなります（先にアンインストールしたい呼び出し元はこの一覧を参照する）。
- 出力の `left` には、手順 6 で削除できなかったものを載せます。

### `uninstall cli` の後に残存するもの

| 残存するもの | OS | 理由 | 整理 |
| --- | --- | --- | --- |
| `<Work>/old/vw2026.exe.old-<時刻>` の内削除できなかったもの（実行中の CLI。インストール済みの CLI で更新した際に残ったものは、そのプロセスが終了していれば削除される） | Windows | 実行中の実行ファイルは削除できない | 出力の `left` に載る。次の `install` / `uninstall` が削除する。一時フォルダの中なので、Windows の一時ファイルの整理（ストレージ センサー・ディスク クリーンアップ）が有効なら、そちらでも削除される（[作業領域](#作業領域)） |
| `~/.local/bin`（フォルダ） | mac | フックが作成したかを記録せず、他のプログラムも使用する場所 | 残置してよい |
| 他のプラグインのフォルダ | 両方 | `uninstall cli` は他のプラグインをアンインストールしない（上記 `remaining`） | 先にそれぞれを `uninstall` する |
| Vectorworks が記憶した「有効化」 | 両方 | Vectorworks の設定で、`vw2026` は変更しない | 不要（同一のパスに再インストールすれば、その間に起動しない限り有効のまま） |

- `uninstall cli` は初回スクリプトの一時フォルダの CLI が実行するので、`<Plug-Ins>/cli/` の中の CLI は実行されておらず、
  フォルダごと削除され、`<Work>/old/` の前回までの残りも削除できます。スクリプトの一時フォルダはスクリプトが削除します。

## 削除処理の制約

**利用者のものを削除するコードは次の場所のみ**とし、制約を緩めません。同一の表を `CLAUDE.md` の 9 に記載しています
（変更する際は両方を修正する）。

| 削除するコード | 削除してよいもの |
| --- | --- |
| `install`（構築・後処理・フックの失敗時の巻き戻し） | `<Work>/staging/<name>/`・`<Work>/staging/<name>.zip`（いずれも名前をそのまま用いて構築したパスのみ。前方一致では削除しない）・`<Work>/old/<name>/`（退避した版と前回の残存物は、記録の `name` が一致し、記録の `module` が存在し、`<Plug-Ins>/<name>/` も存在する場合のみ。`<Work>/staging/<name>/` へ移動してから削除する。条件に合致しないものは削除せずに `<Work>/old/<name>.kept-<時刻>/` へ移動する）・フックが失敗した場合の新しい `<Plug-Ins>/<name>/`（自身が配置したもの）・`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`（ファイルのみ。退避した CLI と前回までの残存物）・中断した `uninstall` の標識 `<Work>/old/<name>.uninstalling`（差し替えに成功した後と、`<Plug-Ins>/<name>/` が存在する場合。いずれも以前の回の残存物） |
| `uninstall` | 記録の `name` が一致し、記録の `module` が存在する `<Plug-Ins>/<name>/`（`<Work>/old/<name>/` へ移動し、フックの後で `<Work>/staging/<name>/` へ移動してから削除する）・`<Work>/staging/<name>/`・`<Work>/staging/<name>.zip`（いずれも名前をそのまま用いて構築したパスのみ）・自身が書き込んだ標識 `<Work>/old/<name>.uninstalling`・`<Plug-Ins>/<name>/` も `<Work>/old/<name>/` も存在しない場合の以前の回の標識 `<Work>/old/<name>.uninstalling`・`<Work>/old/` の直下の `vw2026.old-*` / `vw2026.exe.old-*`（ファイルのみ）・空の `<Work>/staging`・`<Work>/old`・`<Work>`（内容のあるものは削除しない） |
| `cli` の `install` のフック | なし |
| `cli` の `uninstall` のフック | `<Plug-Ins>/cli/bin/vw2026` を指す `~/.local/bin/vw2026`・`Path` の `<Plug-Ins>\cli\bin` と一致する項目（いずれも `VW2026_HOOK_INSTALL_DIR` から決定し、同一の場所か否かはディレクトリの同一性で判定する） |

- 他のプラグインのフックがフォルダの外で削除するものは、そのプラグインの提供側の責任です
  （[レジストリ「フック」](../registry.md#フック)）。

## テスト

- **`install` / `uninstall`**: Go の単体テスト（`cli/internal/install`）。場所（`<Plug-Ins>`・`<Work>`）と既定の
  レジストリを `install.Options` で渡し、擬似 HTTPS サーバーと一時ディレクトリで検証します（環境変数は増やさない）。
  擬似フックはテストの実行ファイルそのものを `sh` の代わりに実行します（`sh` の無い Windows でも同一のテストを
  実行するため。仕組みは `cli/internal/install/harness_test.go` のコメント）。置換と後処理の失敗は、実際に起こせる
  ものはそのまま起こし、OS の失敗（権限・ディスクの誤り）でしか起きないものは、パッケージの中のファイルの操作を
  差し替えて起こします。**`install` / `uninstall` のコードは、全ての分岐をテストで通します。** テストから通せないのは、
  `main()` と、実行する OS でしか通らない分岐（`places_*.go`・`powershell` のフック）のみで、後者は mac と Windows の
  `go.yml` で通ります。何を検証するかはテストの名前とコメントにあり、ここには複製しません。
- **コマンドのテストでの場所の差し替え**: コマンド（`cli/cmd/vw2026`）のテストは、スプール・`<Work>`・既定の
  `<Plug-Ins>`・実行している CLI の場所を、いずれも既定で一時ディレクトリにします（`CLAUDE.md`「Go」。テストが場所を
  渡し忘れても、開発者の計算機の本物の `<Plug-Ins>`・`<Work>`・スプールに触れないため）。
- **`cli` のフック**: CI の `hooks.yml`（[ビルド「CI」](build-and-release.md#ci)）で、フックが実行されるのと同一のもの
  （mac の `/bin/sh`・Windows PowerShell 5.1）で検証します。いずれも一時ディレクトリを `HOME`・`VW2026_HOOK_*` に
  渡し（Windows は利用者の `Path` を擬似の配置場所に替える）、利用者の場所に触れません。版ごと（`VW2026_HOOK_*` と
  `VW2025_HOOK_*`）に全てを実行します。
  - mac（`sh`）: `tests/hooks/hooks_test.sh`（外部の枠組みを使用しない）。
  - Windows（`powershell`）: `tests/hooks/Hooks.Tests.ps1`（Pester。版は `scripts/powershell.ps1` で固定し、
    Windows に同梱の Pester 3.4 は使用しない）。
  - いずれのフックも、標準出力が UTF-8 の JSON のオブジェクト 1 つのみであること（日本語を含むパスでも）と、
    `uninstall` のフックが外のものを削除し始めた後は失敗しないことを検証します。
- **実物の exe の置換**: PR の `build.yml` の `install-windows`（版ごとのジョブ `install-windows-editions`）で、
  `release` が PR のプレリリースを公開した後に検証します。手順は `build.yml` の各手順のコメントにあります。
  - **実行中の CLI を退避するのが、その PR の Go のコードになる順序にします**（PR で[実行中の CLI の退避](#実行中の-cli-の退避)を
    破損させたら、このジョブが失敗するように）。PR の CLI を `<Plug-Ins>\cli\bin\` に格納してから、その CLI に置換
    （記録のタグを異なるものにしてからの `install` と、`install cli@latest`）を行わせます。
  - 併せて、インストール済みの CLI の `uninstall cli` が拒否すること、初回スクリプトでアンインストールすると何も残らないこと、実物のレジストリで
    利用者の `Path` の型（REG_SZ・REG_EXPAND_SZ）と既存の項目（展開しない `%…%`）が保持されることを検証します。
  - `latest` にマニフェストが無い・`manifest_version` が PR のものと異なる場合は、`latest` をインストールする手順を省略します
    （PR のコードが実行中の自身を退避することは、その前の手順で検証できる）。
  - `main` への push では、版の異なる相手が無いので実行しません（PR で検証してからマージする）。
  - 別の `vw2026` を実行したまま置換する形式は構成できません（ロックが取得されていると `install` が何もせずに
    終了し、解放されると `call` も終了する）。ランナーは使い捨てなので既定の場所（`<Plug-Ins>`・`<Work>`）を
    使用しますが、利用者の場所に触れるので `go test` には含めません。
- **初回スクリプト**: shellcheck・PSScriptAnalyzer。取得して `install` を実行するのみなので、公開した
  スクリプトでインストールしてアンインストールすることを CI（mac は `build.yml` の `verify`、Windows は上記の `install-windows`）と実機の確認で
  押さえます。
