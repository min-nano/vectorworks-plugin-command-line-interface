# 受け渡しの作法（protocol 1）

ブリッジ（プラグイン）と呼ぶ側（`vw2026` や、作法を守る任意のプログラム）は、**ローカルの
ディレクトリ 1 つ（スプール）に置くファイル**でやり取りします。この文書が作法の真実で、
プラグイン側（C++）と CLI 側（`cli/internal/spool`）はその対になる実装です。**どちらかを
変えたら、この文書と両方を直してください。** 形を変えたら版（`protocol`）を上げます。

作法は、構造設計支援プラグイン（`vectorworks-plugin-import-ifc-homeskz`）の開発版の MCP
ブリッジ（M24〜M42）で実機で確かめた作り（`src/core/Bridge.h`）を引き継いでいます。違いは
末尾の「元の作法との違い」にまとめています。

## スプールの場所

```
<CLI>/spool/
```

`<CLI>` は CLI の場所で、mac `~/Library/Application Support/vectorworks2026-cli/`、Windows
`%LOCALAPPDATA%\vectorworks2026-cli\` です（[インストールと更新「置き場所」](plugin/install-and-update.md#置き場所)）。

- **プラグインと呼ぶ側は、同じ規則で同じ場所を求めます**（探索しない）。mac はホーム
  ディレクトリ、Windows は `%LOCALAPPDATA%`（プラグインは `SHGetKnownFolderPath(FOLDERID_LocalAppData)`）
  から決まるので、GUI アプリの Vectorworks と、ssh や別のアプリから起動されたプロセスとで
  食い違いません。一時ディレクトリは環境変数で決まり食い違いうるので使いません。
- **名前に Vectorworks の版を入れます。** 版ごとにプラグインを入れるので、2026 と 2027 を
  同時に起動しても、2 つの橋が同じ要求を取り合わない（コマンド `vw2026` と対になる）。
- 場所は環境変数 `VW2026_SPOOL` で明示できます（両側で同じ値にする。テストにも使う）。

### 持ち主と権限

- プラグイン側は**自分の所有・0700** で作り、既にあるものは持ち主と権限を確かめてから
  使います（POSIX）。他の利用者のもの・他から書けるものは使いません。
- 呼ぶ側も同じ基準で判定し、合わない場所は使いません。理由: 他から書ける場所に偽の印を
  置かれると、要求（引数）が漏れ、偽の応答を受け取ります。
- Windows の `%LOCALAPPDATA%` は利用者ごとなので、存在だけを確かめます。

## ファイル

| ファイル | 書く側 | 中身 |
| --- | --- | --- |
| `bridge.lock` | プラグイン | ロック（受け付けている間ずっと掴む。中身は空） |
| `bridge.json` | プラグイン | 生存の印 |
| `<id>.req.json` | 呼ぶ側 | 要求 1 件 |
| `<id>.res.json` | プラグイン | 応答 1 件 |
| `*.tmp` | 両方 | 書きかけ（下記） |

**`bridge.lock` 以外のどのファイルも、同じディレクトリへ `<名前>.tmp` として書いてから
rename で公開します。** 読み手に書きかけの内容を読ませないためです。読み手は、読めない・
JSON として壊れているファイルを「まだ無い」とみなして読み直します。

### id

- 綴りは `[0-9A-Za-z_-]{1,64}`。**プラグイン側はこれを満たさない id を受け付けません**
  （ファイル名に使うので、`../` を混ぜてスプールの外へ書かせないための関門）。
- id はファイル名だけが持ちます（要求と応答の本文には入れない）。
- プラグイン側は要求を**ファイル名の昇順**で処理します。呼ぶ側は、名前の昇順が送った順に
  なる id を付けます。`vw2026` は `<UnixNano を 19 桁>-<乱数 8 桁の 16 進>` で、別々の
  プロセスからの要求も送った順に並びます。

## ロック（`bridge.lock`）

**スプールを受け付ける橋は、`bridge.lock` を掴んでいる 1 つだけです。** プラグインは
ロックを取れたときから Vectorworks の終了まで、ロックを放しません。

| | 掴む（プラグイン） | 掴まれているかを見る（呼ぶ側） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT, 0600)` のあと `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY)` のあと `flock(LOCK_SH\|LOCK_NB)`。`EWOULDBLOCK` なら掴まれている。取れたらすぐ放す |
| Windows | 共有なし（share mode 0）・`OPEN_ALWAYS` で開いたハンドルを持ち続ける | 開いて共有違反（`ERROR_SHARING_VIOLATION`）なら掴まれている。開けたらすぐ閉じる |

- ロックはプロセスが終われば（異常終了を含む）OS が放します。止まったかどうかを
  `pid` やプロセス名で推し量る必要はありません。
- **ロックを取れなかった回は何もしません**（要求を取り出さない・印を書かない）。次の回に
  取り直します。取れないのは、同じスプールを別の Vectorworks が受け付けているとき（Windows では
  Vectorworks 2026 を 2 つ起動できる）か、呼ぶ側がちょうど確かめているときです。前者は相手が
  終われば引き継ぎ、後者は次の回に取れます。
- **ロックを取れたら、前の回の残骸（要求・応答・書きかけ）を消してから**受け付けを始めます。
  ロックを取れたことは、ほかに受け付けている橋が居ないことを意味するので、消してよい。
- 呼ぶ側はロックを掴み続けません（確かめたらすぐ放す）。
- `bridge.lock` は消しません（消すと、掴んだままのファイルと新しく作られたファイルが別物になる）。
- 受け付けていない Vectorworks の図面は CLI から操作できません。どちらが受け付けているかは
  印の `pid` で分かります。

## 生存の印（`bridge.json`）

```json
{"version":"abcdef0","branch":"main","protocol":1,"beat":1760000000,"pid":4242}
```

| フィールド | 意味 |
| --- | --- |
| `version` | プラグインの版（短い sha。更新が効いたかを確かめる手掛かり） |
| `branch` | プラグインを作ったブランチ（PR のプレリリースを入れているかが分かる） |
| `protocol` | この作法の版。呼ぶ側は一致しなければ要求を置かない |
| `beat` | 最後に書き直した時刻（epoch 秒）。プラグイン側は数秒ごとに書き直す |
| `pid` | 受け付けている Vectorworks のプロセス ID（表示のため。判定には使わない） |

- プラグイン側は、ロックを掴んでいるときだけ印を書きます。印を消しません。

### 生存の判定

呼ぶ側はロックと印から次の 3 つの状態を判定します。

| 状態 | 条件 | 意味 |
| --- | --- | --- |
| `live`（動いている） | ロックが掴まれていて、`beat` が 15 秒以内 | 要求に応える |
| `unresponsive`（応えない） | ロックが掴まれているが、`beat` が 15 秒より古い（または印が読めない） | 受け付けが見送られている。置いた要求は受け付けが戻れば処理される |
| `down`（止まっている） | ロックが掴まれていない（場所が無い・持ち主や権限が合わないときも） | 要求を置いても応えない |

- **印が古いことだけで「止まっている」とはみなしません。** プラグイン側は、undo の記録が
  開いている間・モーダルダイアログの最中は受け付けを見送り、その間は印を書き直せません
  （mac ではモーダルの最中にタイマー自体が刻まない。
  [構成「受け付けを止めない・処理中は見送る」](plugin/architecture.md#受け付けを止めない処理中は見送る)）。
  これを「止まっている」と判定すると、`quit` の保存の確認を開いている間に終了したと誤り、
  利用者がダイアログを開いている間の呼び出しを「起動していない」と誤ります。
- 印が新しくてもロックが掴まれていなければ `down` です（異常終了で残った印）。
- ロックを取ってから最初の印を書くまでの間は、印が無くても `unresponsive` です。このとき
  `protocol` は分からないので、呼ぶ側は版の検査を省いて要求を置きます。
- `unresponsive` に時間の上限は設けません。ダイアログは利用者が閉じるまで開いています。

## 要求（`<id>.req.json`）

```json
{"tool":"layers","args":{"include_sheets":false}}
```

- `args` はオブジェクト。省略・オブジェクト以外は `{}` として扱います。
- 1 件の上限は **1 MiB**。超えるものは「読めない要求」としてエラーで応答されます。

## 応答（`<id>.res.json`）

```json
{"ok":true,"result":{…}}
{"ok":false,"error":"知らない道具です: nope"}
```

- 呼ぶ側は応答を読んだら消します。
- 待つのを諦めた呼ぶ側は、置いた要求を消して取り下げます（あとで読み取られて、誰も待たない
  応答が残らないように）。既にプラグインが読んだ要求は取り下げられず、応答が残ることがあります。
  残った応答は、次にロックを取ったときに消えます。

## プラグイン側の義務

- **要求は読んでから消し、消せたものだけを実行します。** 読めなかった（無くなっていた）・
  消せなかった要求は黙って飛ばします（応答しない）。無くなっていたのは呼ぶ側が取り下げた
  とき、消せなかったのはウイルス対策ソフトなどが一時的に掴んでいるときで、後者は次の回に
  やり直せば済みます（消さずに実行すると、次の回にまた実行してしまう）。
- 読めたが JSON として壊れている要求には、ファイル名の id が正しければエラーで応答します
  （呼ぶ側を待たせ切らない）。
- 1 回の受け付けで処理する件数に上限を設けます（溜まっていても Vectorworks を占有し続けない）。
- 道具 1 つの失敗（例外を含む）で橋を止めません。

## 予約された道具

| 道具 | 結果 |
| --- | --- |
| `tools` | `{"protocol":1,"tools":[{"name":…,"description":…,"inputSchema":{…},"kind":…}]}`。`inputSchema` は JSON Schema。`kind` は `read` / `write` / `app`（`app` は Vectorworks そのものに働く道具。図面を変えるか・Vectorworks を終わらせるかを呼ぶ側が判定できるように） |

道具の名前は `[a-z0-9_]+(\.[a-z0-9_]+)*`。プラグインが自分で持つ道具は接頭辞なし
（`ping` / `layers` …）、ほかのプラグインの機能を呼ぶ道具は `<提供者>.<名前>` にする予定です
（[設計「他のプラグインの道具」](design.md#他のプラグインの道具)。呼び出しの手段は SDK の調査待ち）。

長く走る道具（受け付け 1 回の中で数秒を超える道具）は今は持ちません。足すときは、その間も
呼ぶ側が待ち続けられる手段（印に処理中の要求と締切を載せる、など）を決め、版を上げます。

## 元の作法との違い

構造設計支援プラグインの MCP ブリッジ（protocol 1）からの変更点です。この作法は新しい
プラグインのもので、元のものとは**別の版の系列**です（スプールの場所も違うので混ざりません）。

| 項目 | 元 | ここ |
| --- | --- | --- |
| スプールの場所 | `<一時ディレクトリ>/<プラグイン名>-mcp` | `<CLI>/spool/` |
| 場所の明示 | `VW_MCP_SPOOL` | `VW2026_SPOOL` |
| 道具の一覧 | `vw_tools` | `tools` |
| 道具の名前 | `vw_` 接頭辞 | 接頭辞なし・提供者は `.` で区切る |
| 生存の印 | `commit` / `branch` / `served` / `failed` | `version` / `branch` / `pid`（数は印に載せない） |
| 生存の判定 | 印が古ければ動いていない | ロックで生死を、印の新しさで応えるかを分ける |
| 同じスプールの橋 | 取り決めなし | ロックを掴んだ 1 つだけが受け付ける |
| 長く走る道具 | `busy` / `busy_until` | 持たない |
| id | 連番＋乱数（1 プロセス内の順）。本文にも入れる | 時刻＋乱数（プロセスをまたいで送った順）。ファイル名だけ |
| 印を消す | 止まるときに消す | 消さない（ロックで `down` と判定する） |
