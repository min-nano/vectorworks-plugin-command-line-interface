# 受け渡しの作法（protocol 1）

ブリッジ（プラグイン）と呼ぶ側（`vw2026` や、作法を守る任意のプログラム）は、**ローカルの
ディレクトリ 1 つ（スプール）に置くファイル**でやり取りします。この文書が作法の真実で、
プラグイン側（C++）と CLI 側（`cli/internal/spool`）はその対になる実装です。**どちらかを
変えたら、この文書と両方を直してください。** 形を変えたら版（`protocol`）を上げます。

作法は、構造設計支援プラグイン（`vectorworks-plugin-import-ifc-homeskz`）の開発版の MCP
ブリッジ（M24〜M42）で実機で確かめた作り（`src/core/Bridge.h`）を引き継いでいます。違いは
末尾の「元の作法との違い」にまとめています。

## スプールの場所

```
<一時ディレクトリ>/vectorworks2026-cli-bridge/       … 安定版
<一時ディレクトリ>/vectorworks2026-cli-bridge-dev/   … 開発版
```

- **名前に Vectorworks の版を入れます。** 版ごとにプラグインを入れるので、2026 と 2027 を
  同時に起動しても、2 つの橋が同じ要求を取り合わない（コマンド `vw2026` と対になる）。
- 安定版と開発版のプラグインが同居しても取り違えないよう、開発版は別の名前にします。
  呼ぶ側は系列（`stable` / `dev`）で選びます。
- **プラグイン側は自分の一時ディレクトリへそのまま置きます**（探索しない）。macOS では
  利用者ごとの `/var/folders/…/T/`、Windows では `%TEMP%`。
- **探すのは呼ぶ側の役割です。** 一時ディレクトリは環境変数で決まるので、GUI アプリの
  Vectorworks と、ssh や別のアプリから起動されたプロセスとで食い違いえます。呼ぶ側は次の順に
  候補を調べ、**有効な生存の印があるところ**を使います。
  1. 利用者ごとの一時ディレクトリ（macOS の `getconf DARWIN_USER_TEMP_DIR`）
  2. 自分の一時ディレクトリ・`TMPDIR`・`TMP`・`TEMP`
  3. ただし macOS で 1 が取得できたなら `/tmp` は調べない
- **推測による候補は持ちません**（`/tmp` への退避や `/var/folders` の総当たりはしない）。
  場所が分かっているなら環境変数 `VW2026_SPOOL` で明示します（両側で同じ値にする）。

### 持ち主と権限

- プラグイン側は**自分の所有・0700** で作り、既にあるものは持ち主と権限を確かめてから
  使います（POSIX）。他の利用者のもの・他から書けるものは使いません。
- 呼ぶ側も同じ基準で判定し、合わない場所は使いません。理由: `/tmp` のような誰でも書ける
  場所に偽の印を置かれると、要求（引数）が漏れ、偽の応答を受け取ります。
- Windows の `%TEMP%` は利用者ごとなので、存在だけを確かめます。

## ファイル

| ファイル | 書く側 | 中身 |
| --- | --- | --- |
| `bridge.json` | プラグイン（本体） | 生存の印 |
| `shell.json` | プラグイン（殻） | 殻の診断。本体を動かせない間だけ（下記） |
| `<id>.req.json` | 呼ぶ側 | 要求 1 件 |
| `<id>.work` | プラグイン | 取り出した要求（確保の印。下記「プラグイン側の義務」） |
| `<id>.res.json` | プラグイン | 応答 1 件 |
| `*.tmp` | 両方 | 書きかけ（下記） |

**どのファイルも、同じディレクトリへ `<名前>.tmp` として書いてから rename で公開します。**
読み手に書きかけの内容を読ませないためです。読み手は、読めない・JSON として壊れている
ファイルを「まだ無い」とみなして読み直します。

### id

- 綴りは `[0-9A-Za-z_-]{1,64}`。**プラグイン側はこれを満たさない id を受け付けません**
  （ファイル名に使うので、`../` を混ぜてスプールの外へ書かせないための関門）。
- プラグイン側は要求を**ファイル名の昇順**で処理します。呼ぶ側は、名前の昇順が送った順に
  なる id を付けます。`vw2026` は `<UnixNano を 19 桁>-<乱数 8 桁の 16 進>` で、別々の
  プロセスからの要求も送った順に並びます。

## 生存の印（`bridge.json`）

```json
{"plugin":"cli","channel":"stable","version":"abcdef0","branch":"main","protocol":1,"beat":1760000000,"pid":4242}
```

| フィールド | 意味 |
| --- | --- |
| `plugin` | プラグイン名（`cli` / `cli_dev`） |
| `channel` | 配布の系列（`stable` / `dev`） |
| `version` | 受け答えをしている本体の版（短い sha。殻と本体の入れ替えを確かめる手掛かり） |
| `branch` | 本体を作ったブランチ |
| `protocol` | この作法の版。呼ぶ側は一致しなければ要求を置かない |
| `beat` | 最後に書き直した時刻（epoch 秒）。プラグイン側は数秒ごとに書き直す |
| `pid` | Vectorworks のプロセス ID。印が古いときに、Vectorworks が動いているかを呼ぶ側が確かめる（下記） |
| `busy` / `busy_id` / `busy_until` | 長く走る道具の最中だけ。道具の名前・処理中の要求の id・いつまでかかりうるか（epoch 秒） |
| `restart_required` | 真なら、殻の変わる版が入っていて Vectorworks を再起動するまで効かない（省略＝偽） |

- 呼ぶ側は、待つ上限を過ぎても `busy_id` が自分の要求で `busy_until` が未来なら待ち続けます。
- プラグイン側は止まるときに印を消します。異常終了すると印は残りますが、古びて pid の
  プロセスも無くなるので「止まっている」と判定されます。**消すのは `pid` が自分の印だけです**
  （[1 つのスプールに橋は 1 つ](#1-つのスプールに橋は-1-つ)）。

### 生存の判定

呼ぶ側は印から次の 3 つの状態を判定します。

| 状態 | 条件 | 意味 |
| --- | --- | --- |
| `live`（動いている） | `beat` が 15 秒以内、または `busy_until` が未来 | 要求に応える |
| `unresponsive`（応えない） | `beat` が 15 秒より古いが、`pid` のプロセスが Vectorworks として動いている | 受け付けが見送られている。置いた要求は受け付けが戻れば処理される |
| `down`（止まっている） | 印が無い・読めない、または古くて `pid` のプロセスが無い | 要求を置いても応えない |

- **印が古いことだけで「止まっている」とはみなしません。** プラグイン側は、undo の記録が
  開いている間・モーダルダイアログの最中・長く走る道具の最中は受け付けを見送り、その間は
  印を書き直せません（mac ではモーダルの最中にタイマー自体が刻まない。
  [構成「受け付けを止めない・処理中は見送る」](plugin/architecture.md#受け付けを止めない処理中は見送る)）。
  これを「止まっている」と判定すると、`quit` の保存の確認を開いている間に終了したと誤り、
  利用者がダイアログを開いている間の呼び出しを「起動していない」と誤ります。
- `pid` のプロセスは、あるか（POSIX は `kill(pid, 0)`、Windows は `OpenProcess` と終了コード）と、
  実行ファイルの名前に `vectorworks` を含むか（大文字小文字を区別しない）で確かめます。名前も
  見るのは、異常終了で残った印の `pid` が別のプロセスに再利用されたとき、いつまでも
  `unresponsive` と判定し続けないためです。名前が取れないとき（権限など）は、プロセスが
  あることだけで動いているとみなします。
- `unresponsive` に時間の上限は設けません。ダイアログは利用者が閉じるまで開いています。
- 候補が複数あるときは `live` のところを優先し、無ければ最初の `unresponsive` のところを使います。
- 判定は印の形を変えないので、版（`protocol`）は上げていません（`pid` は初めから印にある）。

### 1 つのスプールに橋は 1 つ

Windows では Vectorworks 2026 を 2 つ起動できます。どちらのプラグインも同じスプールを使うので、
何もしなければ 2 つの橋が同じ要求を取り合い、印を交互に書き換えます。そこで、**スプールを
受け付ける橋は 1 つだけ**にします。

- プラグイン側は、印を書く前に印を読みます。**別の `pid` の印が `down` でなければ（[生存の判定](#生存の判定)
  で `live` か `unresponsive`）、印を書かず、要求も取り出しません**（待機）。見え方には待機と
  相手の `pid` を出します。
- `unresponsive` でも引き継ぎません。相手はダイアログの最中などで見送っているだけで、終われば
  受け付けに戻ります。引き継ぐと、戻った相手が待機に回り、受け付ける側が入れ替わり続けます。
- 待機中も毎回この判定を続け、相手の印が `down`（印が消えた、または古くて `pid` のプロセスが
  無い）になったら受け付けを引き継ぎます。引き継ぎでは残骸を消しません（相手が受け付けていた
  間に置かれた要求を処理するため）。
- 読んでから書くまでは不可分ではないので、2 つが同時に起動すると両方が印を書くことがあります。
  印は rename で置き換わる（後に書いた方が残る）ので、次の書き直しの前に読んだとき、先に書いた方は
  相手の `pid` を見て待機に回り、1 つに収まります。その間の要求の取り合いは、次の「確保」で防ぎます。
- 呼ぶ側は何もしません（見えるのは受け付けている橋の印だけ）。待機している Vectorworks の
  図面は CLI から操作できません。どちらの Vectorworks が受け付けているかは印の `pid` で分かります。

## 殻の診断（`shell.json`）

プラグインは殻（Vectorworks が起動時に読み込む部分）と本体（受け付けを行う部分）に分かれて
います。殻は本体を読み込めない・動かせない間だけ、このファイルを書きます。生存の印が無い
ときに、「Vectorworks が動いていない」と「プラグインは読み込まれたが受け付けられない」を
呼ぶ側が区別できるようにするためです。

```json
{"plugin":"cli","channel":"stable","shell_id":"0123abc","protocol":1,"beat":1760000000,"pid":4242,"restart_required":false,"error":{"code":"abi_mismatch","message":"payload abi 2, shell abi 1"}}
```

| フィールド | 意味 |
| --- | --- |
| `plugin` / `channel` / `protocol` / `beat` / `pid` | 生存の印と同じ |
| `shell_id` | 殻の ID |
| `restart_required` | 生存の印と同じ（省略＝偽） |
| `error.code` | `copy_failed` / `load_failed` / `symbol_missing` / `abi_mismatch` / `init_failed` / `serve_failed`（[ABI「殻の診断」](plugin/abi.md#殻の診断shelljson)） |
| `error.message` | 英語の詳細（OS の理由など） |

- **これは生存の印ではありません。** 要求を置いても誰も受け付けません。呼ぶ側は[状態](#生存の判定)が
  `live` でないときにだけ読み、要求を置く判断には使いません。`down` なら、Vectorworks は動いて
  いてプラグインの本体が読み込めていないことを示します。`unresponsive` なら、見送り（ダイアログ等）
  ではなく本体が動かなくなった（`serve_failed` 等）ことを示します。
- `beat` が 15 秒より古ければ無視します（Vectorworks が終わると書き直されない）。
- プラグイン側は、本体が受け付けを 1 回行えたら消します。本体はこのファイルを消しません
  （前の回の残骸の掃除の対象外）。
- このファイルの追加は、知らない呼ぶ側が無視しても受け渡しが壊れないので、版（`protocol`）を
  上げません。

## 要求（`<id>.req.json`）

```json
{"id":"1760000000123456789-0a1b2c3d","tool":"layers","args":{"include_sheets":false}}
```

- `id` はファイル名の `<id>` と一致させます。食い違う要求はエラーで応答されます。
- `args` はオブジェクト。省略・オブジェクト以外は `{}` として扱います。
- 1 件の上限は **1 MiB**。超えるものは「読めない要求」としてエラーで応答されます。

## 応答（`<id>.res.json`）

```json
{"id":"…","ok":true,"result":{…}}
{"id":"…","ok":false,"error":"知らない道具です: nope"}
```

- 呼ぶ側は応答を読んだら消します。
- 待つのを諦めた呼ぶ側は、置いた要求を消して取り下げます（あとで読み取られて、誰も待たない
  応答が残らないように）。既に確保された（`<id>.work` になった）要求は取り下げられず、応答が
  残ることがあります。残った応答はプラグインの開始時に消えます。

## プラグイン側の義務

- **要求は `<id>.req.json` → `<id>.work` への rename で確保してから読みます。rename に
  失敗したら、その要求は黙って飛ばします**（応答しない・消さない）。失敗するのは、別の橋が
  先に確保した・呼ぶ側が取り下げた・ウイルス対策ソフトなどが一時的にファイルを掴んでいる
  ときで、どれも自分が応える要求ではないか、次の回に確保し直せば済みます。読んでから消す
  作りだと、相手が消した要求を「読めなかった要求」と取り違えて偽の失敗を返します。
  - **確保は排他でなければなりません。** POSIX の `rename(2)` は不可分で、元の名前が消えた
    あとの rename は失敗するので、そのまま使えます。
  - **Windows の `MoveFileEx`（`std::filesystem::rename`）は排他になりません。** 元の名前で
    開いたハンドルを通して rename するので、開いてから rename するまでの間に相手が rename
    すると、ハンドルは移ったファイルを指したままで、同じ名前への rename も成功します（2 つの
    橋が同じ要求を確保する）。Windows では**共有なし（share mode 0）・`DELETE` で開いた
    ハンドルで rename します**（`SetFileInformationByHandle` の `FileRenameInfo`、既にあれば
    失敗させる）。相手は共有違反か「無い」で開けないので、飛ばします。
- **確保した要求は、読めても読めなくても消します**（残すと毎回取り出し直す）。確保した
  あとで読めなかった要求には、ファイル名から取り出した id が正しければエラーで応答します
  （呼ぶ側を待たせ切らない）。
- 1 回の受け付けで処理する件数に上限を設けます（溜まっていても Vectorworks を占有し続けない）。
- **開始時に、前の回の残骸（要求・確保した要求・応答・書きかけ）を消します。** ただし有効な生存の印が
  あるとき（本体を入れ替えただけで、橋は続いている）は消しません——入れ替えの直前に
  書いた応答や、置かれたばかりの要求まで消すことになります。
- 道具 1 つの失敗（例外を含む）で橋を止めません。

## 予約された道具

| 道具 | 結果 |
| --- | --- |
| `tools` | `{"protocol":1,"tools":[{"name":…,"description":…,"inputSchema":{…},"kind":…,"timeoutSeconds":…}]}`。`inputSchema` は JSON Schema。`kind` は `read` / `write` / `long` / `shell`（図面を変えるか・殻が処理するかを呼ぶ側が判定できるように）。`timeoutSeconds` は既定より長くかかりうる道具だけ |

道具の名前は `[a-z0-9_]+(\.[a-z0-9_]+)*`。プラグインが自分で持つ道具は接頭辞なし
（`ping` / `layers` …）、ほかのプラグインの機能を呼ぶ道具は `<提供者>.<名前>` にする予定です
（[設計「他のプラグインの道具」](design.md#他のプラグインの道具)。呼び出しの手段は SDK の調査待ち）。

## 元の作法との違い

構造設計支援プラグインの MCP ブリッジ（protocol 1）からの変更点です。この作法は新しい
プラグインのもので、元のものとは**別の版の系列**です（スプールの名前も違うので混ざりません）。

| 項目 | 元 | ここ |
| --- | --- | --- |
| スプールの名前 | `<プラグイン名>-mcp` | `vectorworks2026-cli-bridge`（`-dev`）（MCP 専用ではない） |
| 場所の明示 | `VW_MCP_SPOOL` | `VW2026_SPOOL` |
| 道具の一覧 | `vw_tools` | `tools` |
| 道具の名前 | `vw_` 接頭辞 | 接頭辞なし・提供者は `.` で区切る |
| 生存の印 | `commit` / `branch` / `served` / `failed` | `channel` / `version` / `branch` / `pid`（数は印に載せない） |
| 長く走る道具 | `busy` / `busy_until` | それに `busy_id` を加える（呼ぶ側が自分の要求か判定できる） |
| 生存の判定 | 印が古ければ動いていない | 古くても `pid` の Vectorworks が動いていれば `unresponsive`（見送りの間を止まったと誤らない） |
| id | 連番＋乱数（1 プロセス内の順） | 時刻＋乱数（プロセスをまたいで送った順） |
| 要求の取り出し | 読んでから消す | `<id>.work` への rename で確保してから読む。失敗したら飛ばす |
| 同じスプールの橋 | 取り決めなし | 別の `pid` の印が `down` でなければ待機する |
