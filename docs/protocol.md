# 通信規則（protocol 7）

ブリッジ（プラグイン）と呼び出し元（`vw2026` や、通信規則に準拠する任意のプログラム）は、**ローカルの
フォルダ 1 つ（スプール）に配置するファイル**で通信します。この文書が通信規則の真実であり、
プラグイン側（C++）と CLI 側（`cli/internal/spool`）はその対になる実装です。**いずれかを
変更した場合は、この文書と両方を修正します。** 版（`protocol`）を上げるかは[互換性](#互換性)の
規則に従います。

## スプールの場所

```
<Plug-Ins>/cli/spool/
```

`<Plug-Ins>/cli/` は `cli` のプラグインがインストールされているフォルダです（[名前と識別子「配置場所」](plugin/identifiers.md#配置場所)。
[インストール「CLI とスプールの配置場所」](plugin/install-and-update.md#cli-とスプールの配置場所)）。

- **両側とも、自身のファイルの場所から導出します**（探索しない・環境変数を読み取らない）。
  - プラグイン: 自身のモジュールが存在するフォルダの下の `spool/` です。Windows は `cli.vlb` が存在するフォルダ、
    mac は `cli.vwlibrary` バンドルが存在するフォルダ（モジュールのパスが
    `<X>.vwlibrary/Contents/MacOS/<実行ファイル>` の形式なら、`<X>.vwlibrary` が存在するフォルダ）です。
    リンクは解決しません。
  - `vw2026`: 自身の実行ファイル（`<Plug-Ins>/cli/bin/vw2026`）のパスのリンクを解決し（mac の
    `~/.local/bin/vw2026` はリンク）、`bin/` の親の下の `spool/` です。解決できなければ（Windows の subst の
    ドライブ・割り当てたネットワークドライブなど）、解決前のパスから導出します。
  - 通信規則に準拠する他のプログラムは、`<Plug-Ins>` が既知であれば `<Plug-Ins>/cli/spool/` として導出できます。
  - いずれもパスの綴りから決定し、そこにフォルダが存在するかは確認しません。GUI アプリの Vectorworks と、ssh や
    別のアプリから起動されたプロセスとで不一致が生じないよう、環境変数（`HOME`・`LOCALAPPDATA`・`TMPDIR`
    など）は使用しません。
- **`cli` のフォルダ内をリンクにする場合は、`cli` のフォルダ単位で行います。** プラグインはリンクを解決せずに
  モジュールが存在するフォルダから、`vw2026` は実行ファイルのリンクを解決してから導出するので、`bin/vw2026` のみを
  他の場所へのリンクにすると、両側の場所が一致しなくなります（`vw2026` は Vectorworks が動作していても停止して
  いると応答する）。バンドル（`cli.vwlibrary`）のみをリンクにしても、プラグインはバンドルが存在するフォルダを
  指しますが、Vectorworks がリンクを解決した場所からモジュールを読み込むかは確認していません。
- **名前に Vectorworks の版を含めません。** `<Plug-Ins>` が Vectorworks の版ごとの利用者フォルダ内に
  存在するので、2026 と 2027 を同時に起動しても、2 つのブリッジが同一の要求を奪い合いません。
- プラグイン側は存在しなければ 0700 で作成します（親も存在しなければ作成する。Windows は親のフォルダの権限を継承する）。所有者と権限は確認しません。
  プラグインのフォルダへ他の利用者が書き込めるなら、モジュールを置換できるので、スプールに限らず
  保護できないためです。
- **いずれの側も、場所を変更する指定（引数・環境変数）を有しません。** 片側のみを変更できても
  要求が届かず、GUI アプリの Vectorworks は環境変数を継承しないので、プラグイン側では指定が
  本番で効かないためです。
- **`cli` は利用者ごとの `Plug-Ins` にのみ配置します。** スプールはモジュールの場所に付随するので、
  複数の利用者が読み込む `Plug-Ins`（ネットワーク共有のワークグループのフォルダ・mac の
  `/Applications/Vectorworks 2026/Plug-Ins` など）に `cli` を配置すると、スプールとロックも共有されます。
  Windows の共有モードはネットワーク共有の先でも有効なので、利用者 B の `vw2026` は、別の計算機で
  利用者 A の Vectorworks が取得したロックを「動作中」と判定し、B の要求を A の Vectorworks が A の図面に
  対して実行します（[本番環境で常駐させる前提](design.md#本番環境で常駐させる前提安全性)の「相手は同一の計算機の
  同一の利用者のプロセスのみ」が成り立たなくなる）。mac のローカルのボリュームでは、スプールを先に 0700 で作成した
  利用者の他は開けないので、他の利用者が使用できないだけになります。0700 で防止できるのはローカルのボリュームのみです。
  mac が SMB の共有をマウントすると、ファイルの所有者と権限はマウントした利用者のものとして見え、実際に
  誰が開けるかはサーバーの ACL が決定するので、別の計算機の利用者から開けることがあり、SMB のロックが有効なら
  Windows と同じ事態が起こりえます（ネットワーク共有での振る舞いは確認していない）。`vw2026 install` は
  `<Work>` と別のボリュームへはインストールできないのでネットワーク共有へはインストールされません。手作業での複製は
  防止できないので、対応しない配置方法として文書に示すのみとします（プラグインは場所を確認しない。[設計「決定事項」](design.md#決定事項)）。
- フォルダの外で実行した `vw2026`（手作業でビルドしたもの・初回スクリプトの一時フォルダのもの・zip を
  展開しただけのもの）は、インストールされている `cli` のスプールを発見できません。導出した場所でロックを取得する者が
  存在しないので、Vectorworks が動作していても停止していると判定します。停止していると応答する場合、`status`・
  `call`・`tools`・`session` は標準エラーのメッセージに、`status` は標準出力の JSON の `spool` にも、導出した
  スプールの場所を示します（場所の取り違えと区別できるように）。
  `install` / `uninstall` はスプールに要求を配置せず、インストール先の `<Plug-Ins>/cli/spool/` のロックのみを
  確認するので、一時フォルダの CLI でも動作します。
- **スプールは Vectorworks の利用者フォルダ内に存在し、利用者フォルダは設定で移動できます。** 利用者フォルダを
  同期・フォルダ リダイレクト・オフライン ファイル・HSM の対象に置いた環境には対応しません（[プラグイン側の義務](#プラグイン側の義務)）。
  移動プロファイル（Windows の既定の `%APPDATA%`）はログオンとログオフの時点で複製するのみなので、動作している
  間のロックには関係しません。
- 版 5 までは、スプールを利用者のホームの下の `vectorworks2026-cli/spool/`（mac は
  `~/Library/Application Support/`、Windows は `%LOCALAPPDATA%\` の下）に配置していました。版 6 で
  `cli` のフォルダ内に移動しました（[版の履歴](#版の履歴)）。

## ファイル

| ファイル | 書き込む側 | 内容 |
| --- | --- | --- |
| `bridge.lock` | プラグイン | ロック（受付処理を行う間は常に取得する。内容は空） |
| `<id>.req.json` | 呼び出し元 | 要求 1 件 |
| `<id>.res.json` | プラグイン | 応答 1 件 |
| `<id>.wait` | 呼び出し元 | 待機標識（応答を待機する間は常に取得する。内容は空。必須。[下記](#待機標識idwait)） |
| `*.tmp` | 両方 | 書き込み途中のファイル（下記） |

**要求と応答は、同一のフォルダへ `<名前>.tmp` として書き込んでから rename で公開します。**
読み手に書き込み途中の内容を読み取らせないためです。**書き込み途中のファイルは、存在すれば削除してから新規に
作成します**（POSIX は `O_CREAT|O_EXCL`、Windows は `CREATE_NEW`。両側とも）。既存のものを開いて切り詰めると、
配置されたリンク（シンボリックリンクでも hard link でも）の先、つまりスプールの外のファイルを
破損させるためです。

- 読み手は、読み取れない（存在しない・開けない）ファイルを「未作成」とみなして再度読み取ります。
- rename で公開するので、読み取れたファイルは書き込みを終えたものです。応答として解釈できない（JSON として
  破損している・形式が合わない）のは書き手が通信規則に違反した場合のみで、待機しても解消しません。呼び出し元は、
  応答のファイルが応答として解釈できなければ再度読み取らず、そのファイルを削除し、期限を待たずに破損した
  応答として扱います。

### id

- 綴りは `[0-9A-Za-z_-]{1,64}`。**プラグイン側はこれを満たさない id を受け付けません**
  （ファイル名に使用するので、`../` を混入させてスプールの外へ書き込ませないための関門）。そうした要求は
  読み取らず・削除せず・応答もしません（応答の名前にも同一の id を使用するため）。
- id はファイル名のみが保持します（要求と応答の本文には含めない）。
- プラグイン側は要求を**ファイル名の昇順**で処理します。呼び出し元は、名前の昇順が送信順に
  なる id を付けます。`vw2026` は `<UnixNano を 19 桁>-<乱数 8 桁の 16 進>` です。
- **順序を保証するのは、応答を受け取ってから次を送信した要求のみです。** 応答を待たずに連続して
  配置した要求と、別々のプロセスからの要求の順序は保証しません。時計の分解能は粗く（Windows では
  数 ms〜15.6 ms）同一の時刻の id は乱数の部分で並び、時計の調整で時刻は前後し、id を付けた時刻と
  rename で公開した時刻もずれる（遅れて公開された要求は次の回に回る）ためです。順序が必要なら
  呼び出し元が応答を待機して順序を保証します（[占有](#占有セッション)・[設計「CLI のプリミティブ性の維持」](design.md#cli-のプリミティブ性の維持)）。
- Windows の予約デバイス名（`CON`・`NUL`・`AUX`・`COM1` など）も、綴りを満たせば id です。
  プラグイン側はスプールのファイルを `\\?\` を付けて開くので、こうした名前の要求もデバイスでは
  なくファイルとして扱います（付けずに開くと、Windows 10 までは拡張子があってもデバイスを指す）。
  フィクスチャの id（[通信規則のフィクスチャ](fixtures.md)の `ids.json`）にも含めます。

## ロック（`bridge.lock`）

**スプールの受付処理を行うブリッジは、`bridge.lock` を取得している 1 つのみです。** プラグインは
ロックを取得した時点から Vectorworks の終了まで、ロックを解放しません。

| | 取得する（プラグイン） | 取得されているかを確認する（呼び出し元） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT\|O_CLOEXEC, 0600)` の後 `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY)` の後 `flock(LOCK_SH\|LOCK_NB)`。`EWOULDBLOCK` なら取得されている。取得できたら直ちに解放する |
| Windows | `CreateFile` を共有なし（share mode 0）・`OPEN_ALWAYS`・`lpSecurityAttributes` に null で開いたハンドルを保持し続ける | 開いて共有違反（`ERROR_SHARING_VIOLATION`）なら取得されている。開けたら直ちに閉じる |

- **ロックを子プロセスに継承させません**（POSIX は `O_CLOEXEC`、Windows は継承できない
  ハンドル）。`flock` は開いたファイルの記述に付随するので、Vectorworks が起動した子プロセスが
  記述子を継承すると、Vectorworks が終了してもロックが解放されず、停止したと判定されなくなります。

- ロックはプロセスが終了すれば（異常終了を含む）OS が解放します。停止したかどうかを
  `pid` やプロセス名で推測する必要はありません。
- **ロックを取得できなかった回は何もしません**（要求を取り出さない）。次の回に再度取得を試みます。
  取得できないのは、同一のスプールを別の Vectorworks が受付処理している場合（Windows では
  Vectorworks 2026 を 2 つ起動できる）か、呼び出し元が丁度確認している場合です。前者は相手が
  終了すれば引き継ぎ、後者は次の回に取得できます。
- **ロックを取得したら、前回の残骸を削除してから**受付処理を開始します。削除するのは、
  [待機標識](#待機標識idwait)を取得できる・存在しない id のファイル（要求・応答・待機標識・書き込み途中のファイル）のみです。
  待機標識を確認できない id のファイルは削除しません（待機している呼び出し元のものである可能性があるため。
  確認できるようになった後の回に削除されます）。
  - 待機している呼び出し元（待機標識が取得されている）のファイルは残置します。要求は引き継いだブリッジがそのまま
    処理し、前のブリッジが書き込んだ応答は呼び出し元が読み取れます。前のブリッジが終了したことで、待機している
    呼び出し元に「実行されたかもしれない」という終了コードを返させないためです。ロックを取得した直後に配置された
    要求を削除してしまうこともありません。
  - 呼び出し元を区別できないので、どの Vectorworks が要求を処理するかは呼び出し元には選択できません。前のブリッジに
    向けて配置された要求も、引き継いだブリッジが処理します（引き継ぎの直後に配置された要求と同じ扱い）。
  - 待機標識を作成してから取得するまでのごく短い間（POSIX）に掃除が待機標識を削除すると、その要求は待機標識の
    存在しない要求として `no_wait` で拒否されます。実行はされず、呼び出し元はタイムアウトと同じ「実行されない」終了コードを受け取ります。
- 呼び出し元はロックを保持し続けません（確認したら直ちに解放する）。
- `bridge.lock` は削除しません（削除すると、保持したままのファイルと新たに作成されたファイルが別物になる）。
  例外として、プラグインが通常のファイルでない・内容がローカルにないとして拒否した `bridge.lock` は、
  1 つの Vectorworks につき 1 度のみ、削除して再作成します（[プラグイン側の義務](#プラグイン側の義務)。
  受付処理の度に繰り返さない）。拒否できたのは、他の Vectorworks が取得していない場合のみです
  （Windows は共有なしで開けた、POSIX はリンクや FIFO で取得できない）。フォルダ（Windows は
  ジャンクションも）は開けないので、拒否したことにならず、再作成しません。
- 受付処理を行っていない Vectorworks の図面は CLI から操作できません。いずれが受付処理を行っているかは
  `ping` の `pid` で判明します。

### 生存の判定

**生死はロックのみで判定します。** 呼び出し元は次の 2 つの状態を判定します。

| 状態 | 条件 | 意味 |
| --- | --- | --- |
| 動作中（`running`） | ロックが取得されている | 要求を配置すれば、次の回の受付処理で処理される |
| 停止中 | ロックが取得されていない（スプールが存在しない場合も） | 要求を配置しても応答しない |

**動作中でも、直ちに応答するとは限りません。** プラグイン側は OS のタイマーの周期処理の中で受付処理を
行うので、Vectorworks が周期処理を配送しない間（重い処理・一部のダイアログの最中。[長時間を要するツール](#予約ツール)の
呼び出しの最中を含む）は応答しません
（[構成「受付処理の流れ」](plugin/architecture.md#受付処理の流れ)）。応答するかどうかは、要求を配置して
待機することでしか判明しません。その間もロックは取得されたままなので、呼び出し元は次のように扱えます
（他の文書はここを参照します）。

- 要求は配置したままにしておけば、周期処理が再開したときに処理されます。
- 終了の依頼の最中と、ツール内のダイアログで受付処理が入れ子になった場合（Windows）は、要求を
  配置したままにせず、`busy` で直ちに拒否します（[Vectorworks が処理中](#vectorworks-が処理中)）。
- ツールの長い呼び出しの最中（イベントを処理しない）と、mac でツール内のダイアログの最中は、周期処理が
  来ないので `busy` も返りません。要求は配置したままになり、呼び出しが戻ってから処理されます
  （[予約ツール](#予約ツール)の「長時間を要するツール」）。
- `quit` は図面が開いていれば終了を依頼せずに失敗するので、通常は保存の確認を開きません（確認してから依頼するまでの間に
  利用者が図面を開く競合の場合のみ開きうる）。その間も「停止した」とは判定されません。終了を確認するには
  ロックが解放されるのを待機します（`vw2026 status` が停止していると応答するまで繰り返す）。利用者が取り消せば
  Vectorworks は動作し続け、待機する側は上限を過ぎて終了します。

## 待機標識（`<id>.wait`）

呼び出し元が応答を待機しているかを、`bridge.lock` と同じ仕組みを要求 1 件ごとに逆向きに使用して
示します。呼び出し元が強制終了（Ctrl-C・kill・異常終了）された後に、誰も待機していない要求が実行される
のを防止するためです（書き込みツールでは、利用者の知らない操作が図面に加わる）。

| | 取得する（呼び出し元） | 取得できるかを試行する（プラグイン） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT\|O_EXCL\|O_CLOEXEC, 0600)` の後 `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY\|O_CLOEXEC)` の後 `flock(LOCK_EX\|LOCK_NB)`。`EWOULDBLOCK` なら取得されている |
| Windows | `CreateFile` を共有なし・`CREATE_NEW`・`lpSecurityAttributes` に null で開いたハンドルを保持し続ける | 共有なし・`OPEN_EXISTING` で開いて、共有違反なら取得されている。開けたら閉じる |

呼び出し元:

1. `<id>.wait` を作成して取得する。
2. **その後で** `<id>.req.json` を公開する（公開した時点で、プラグインが生死を判定できるように）。
3. 応答を受け取ったか、待機を中止する場合は、`<id>.wait` を解放して削除する。待機を中止する場合は、
   **その後で**要求を削除する（[待機の中止](#待機の中止)）。

プラグイン: 要求を削除した直後、実行する前に `<id>.wait` を取得できるか試行します。

| `<id>.wait` | 意味 | 扱い |
| --- | --- | --- |
| 取得できた | 呼び出し元が解放した・終了した（異常終了でも OS が解放する） | `<id>.wait` を削除し、**実行も応答もしない** |
| 取得できない | 呼び出し元が待機している | 実行して応答する |
| 存在しない | 呼び出し元が待機を中止して削除した・待機標識を配置し忘れた | **実行せず**、`no_wait` で応答する |
| 確認できない | 存在しない以外の理由（権限・記述子の枯渇など）で開けない・取得を試行できない | **実行せず**、`no_wait` で応答する（待機しているか否かが不明であるため、実行しない側に倒す） |

- 「存在しない」には、通常のファイルでない待機標識と、名前が長すぎて配置できない待機標識（ファイル名の上限を超える）も
  含めます。いずれも呼び出し元が取得していることはないためです（Windows では、フォルダも開けずに拒否されますが、
  存在しないものとします）。

- **`<id>.wait` は必須です。** 待機標識の存在しない要求を実行しないので、想定外の理由（スプールの整理など）で
  待機標識が消えても、実行しない側に倒れます。配置し忘れた呼び出し元に理由が伝わるよう、存在しない場合は
  応答します（待機する者が存在しなければ誰も読み取らない応答が残りますが、次にロックを取得したときに削除されます）。
- シェルのスクリプトなど、ロックを保持し続けにくい呼び出し元は `vw2026 call` を使用します。
- 生死を `pid` で推測しないのは `bridge.lock` と同じ理由です（`pid` は再利用される）。要求に
  期限を含めないのは、長い待機時間で、生存して待機している呼び出し元の要求まで破棄してしまうためです。
- 呼び出し元が強制終了されても、OS が `<id>.wait` を解放するので、待機を中止したときと同じになります。
  シグナルを受けて後処理を行う必要はありません。

## 占有（セッション）

呼び出し元の 1 つがブリッジを**占有**し、図面か Vectorworks を変更するツール（種類 `write` と `app`）を
その呼び出し元にのみ実行させます。複数の呼び出し元（別々のエージェントなど）の操作が、同一の Vectorworks の
中で混在しないようにするためです。**種類 `write` と `app` のツールは占有の中でのみ呼び出せます**（誰も
占有していない場合も拒否する。書き込みを占有した 1 つの呼び出し元からのみとし、Vectorworks を終了させる `quit` を
他の呼び出し元の作業の最中に呼び出させないため）。読み取りのみのツール（種類 `read`）は図面を変更しないので、
占有している呼び出し元の作業と混在せず、占有と照合せずに誰に対しても実行します。

- **占有のセッション ID はプラグインが発行します。** 発行するのは 1 つの Vectorworks に
  つき同時に 1 つのみで、メモリにのみ保持します（ファイルに書き込まない）。セッション ID の綴りは [id](#id) と同じで、
  推測されにくい乱数を含みます。
- 呼び出し元は `@session_start` でセッション ID を受け取り、以後の要求に `session` として含め、`@session_end` で
  終了します（[予約ツール](#予約ツール)）。

プラグインは、要求を読み取り、待機標識を確認し、解析した後、実行する前に占有と照合します。

| ツール | 占有されていない | 占有されている |
| --- | --- | --- |
| `@tools`・種類 `read`（`ping` を含む） | 実行する（`session` は参照しない） | 実行する（`session` は参照しない） |
| 一覧に無いツール | `unknown_tool`（占有と照合しない） | `unknown_tool`（占有と照合しない） |
| `@session_start` | セッション ID を発行する（要求に `session` があれば `no_session`） | `occupied` |
| `@session_end`・種類 `write`・`app` | `no_session` | セッション ID が同一なら実行する。異なる・存在しないなら `occupied` |

- **この表は Vectorworks が処理中でない場合のものです。** 終了の依頼の最中は、一覧のツール（種類 `read`・`ping` を
  含む全て）を、占有と照合して実行してよい場合も `busy` で拒否します。応答するのは SDK を呼び出さない 3 つのツール
  （`@tools`・`@session_start`・`@session_end`）と、一覧に無いツールの `unknown_tool` のみです
  （[Vectorworks が処理中](#vectorworks-が処理中)）。占有との照合が先です（他の呼び出し元が
  占有していれば、処理中でも種類 `write`・`app` は `occupied`）。
- 終了した占有のセッション ID を含む種類 `read` の要求も実行します（`session` を参照しない）。セッション ID が
  古いことは、次に種類 `write`・`app` か `@session_end` を呼び出したときに `no_session` で判明します。

- **プラグインは、セッション ID の発行（`@session_start`）・占有の終了（`@session_end`）・`quit` による
  終了を、その応答を書き込めた場合にのみ行います。** 応答を書き込めない（ディスクの容量不足など）と、呼び出し元は
  結果を受け取れないのに、占有のみが残る・消える、Vectorworks が終了する、という事態になるためです。書き込めな
  かった要求は、呼び出し元からは「実行されたかもしれない」に見えます（占有は変わらず、Vectorworks も
  終了していない）。
- **占有を解除するのは `@session_end` と Vectorworks の終了のみです。** 期限やタイマーでは解除しません
  （長時間使用している占有を奪わないため）。終了し忘れた占有は、Vectorworks を再起動するまで継続します。
- `@session_start` の応答が呼び出し元に届かなかった場合（[待機の中止](#待機の中止)で「実行されたかもしれない」になった、応答を待機する間に強制終了された）は、
  誰も知らないセッション ID が発行されたままになり、これも再起動するまで継続します。発行した相手を識別できない
  ので、プラグインは区別しません。
- 占有が残って塞がった場合（種類 `write`・`app` のツールを誰も呼び出せない）は、利用者が GUI で Vectorworks を終了します。
- Vectorworks を再起動すると、占有は消滅します。古いセッション ID を含む要求は `no_session` で拒否されるので、
  呼び出し元は再起動されたことを検知できます。更新の手順（`quit`・`install`・`launch`）の後は、
  占有を再取得します。
- 同一のスプールを 2 つの Vectorworks が参照している場合（[ロック](#ロックbridgelock)）、セッション ID は受付処理を
  行っている側が発行したものです。引き継いだ側は発行していないので、前の側のセッション ID は `no_session` で拒否されます。
- `ping` は占有されているかを返します（[ツール「ping」](plugin/tools.md#ping)）。

- 占有が防止するのは呼び出し元同士の混在のみです。利用者が GUI で図面を操作することは防止しません
  （CLI を使用している間は GUI を操作しない前提）。どの図面に書き込むかは、`call` で呼び出すプラグインの
  ツールが決定します（[設計「決定事項」](design.md#決定事項)）。

### Vectorworks が処理中

次の間は、要求を配置したままにせず `busy` で拒否します（実行しない）。呼び出し元を待たせ続けずに理由を
伝え、再度呼び出すかを呼び出し元に委ねるためです（[設計「CLI のプリミティブ性の維持」](design.md#cli-のプリミティブ性の維持)）。
理由は `error` に記述します。

| 場面 | 拒否する要求 | 理由 |
| --- | --- | --- |
| 終了の依頼の最中（`quit` の保存の確認を開いている） | 一覧のツール全て（種類 `read`・`ping` も）。SDK を呼び出さない `@tools`・`@session_start`・`@session_end` は応答し、一覧に無いツールは `unknown_tool` | 終了の呼び出しの途中でツールが SDK を呼び出さない（保存しようとしている図面を読み書きしない）。終了の依頼を重複させない |
| 受付処理の入れ子（ツール内で Vectorworks がイベントを処理し、周期処理が再度届いた） | 全て（`@tools`・`ping` も） | 受付処理の途中の状態（セッション ID など）を奪い合わない。ツールの SDK 呼び出しの途中で SDK を呼び出さない |

- 受付処理の入れ子では、要求を解析せずに拒否します。外側の回が既に並べていた要求も拒否します（外側の回は、
  取り出せなかった要求を飛ばす）。
- ツールの一覧（`@tools`）と占有の開始と終了（`@session_start`・`@session_end`）は、終了の依頼の最中も応答します
  （SDK を呼び出さず、図面にも Vectorworks にも作用しない）。呼び出し元は、保存の確認が開いたまま待機しきれなかった
  場合も占有を解除できます。
- 終了の依頼の最中に拒否する範囲を受付処理の入れ子と同じ「全て」にしないのは、入れ子の回は要求を解析せずに拒否するので
  `@session_end` も拒否され、占有が Vectorworks を再起動するまで残るためです。
- undo の記録が開いているかは確認しません。種類 `write` のツールは自身で記録を開いて閉じるので、他の
  記録に混在しません（[ブリッジ「ツールの一覧」](plugin/bridge.md#ツールの一覧)）。
- 判定の配置場所と根拠は[構成「Vectorworks が処理中」](plugin/architecture.md#vectorworks-が処理中)にあります。

## 要求（`<id>.req.json`）

```json
{"tool":"layers","args":{"include_sheets":false}}
{"tool":"layers","args":{},"session":"1760000000000000000-0a1b2c3d"}
```

- `tool` は空でない文字列で、必須です（`null`・空の文字列は存在しないのと同じで `invalid_request`）。
- `args` はオブジェクト。省略可能なフィールドで、省略・`null` は既定値の `{}` として扱います。
  オブジェクト以外（配列・文字列など）は「解釈できない要求」として `invalid_request` で応答されます
  （[互換性](#互換性)の「未知の値」）。
- `session` は[占有](#占有セッション)のセッション ID（文字列）。占有していない呼び出し元は省略します。`null` と
  空の文字列は省略と同じに扱います。
- 1 件の上限は **1 MiB**。超過するものは「解釈できない要求」として `invalid_request` で応答されます。
- 入れ子（オブジェクトと配列）の深さの上限は **64**（要求の外側のオブジェクトを 1 と数える）。
  超過するものも `invalid_request` で応答されます。深い入れ子で解析がスタックを溢れさせ、
  Vectorworks ごと異常終了して利用者の未保存の作業が失われることを防止するための関門で、プラグインは深さが
  上限を超えた時点で解析を中止します。
- 未知のトップレベルのキーは無視されます（[互換性](#互換性)）。キーは大文字と小文字を区別して
  照合します（`ARGS` は `args` ではなく、未知のキーとして無視される）。
- 要求は UTF-8 の JSON です。解釈の仕方は Go の `encoding/json` に合わせます（`vw2026` が送信する要求を
  プラグインが同じ範囲で受け付けるように）。
  - 文字列の中の不正な UTF-8 と、対にならないサロゲートの `\u` エスケープは、U+FFFD に置換して
    解釈します（解釈できない要求とはしない）。
  - オブジェクトに同一のキーが重複すれば、後のものを使用します。
  - BOM・コメント・末尾のカンマ・`NaN` など、JSON の文法に無いものは解釈できない要求です。
- 受け付ける要求と拒否する要求のフィクスチャは[通信規則のフィクスチャ](fixtures.md)にあります。

## 応答（`<id>.res.json`）

```json
{"ok":true,"result":{…}}
{"ok":false,"code":"unknown_tool","error":"知らない道具です: nope"}
```

- **成功の応答は必ず `result` を有し、`result` は JSON のオブジェクトです。** 返す値の無いツールは
  `{}` を返します。プラグインは、ツールが値を返さなければ `{}` とし、オブジェクトでない値を返せば
  ツールの不具合として `internal` で応答します。呼び出し元は、`result` が存在しない・オブジェクトでない成功の
  応答を破損した応答として扱います（`vw2026 call` は汎用の失敗の終了コード）。どのツールの結果も同じ形式
  なので、呼び出し元はツールごとに形式を区別せずに読み取れます。
- 失敗の応答は、機械が読み取る種別 `code` と、人向けの理由 `error` を有します。`code` の綴りは
  次に固定します（値を追加するのは版を上げる変更）。呼び出し元は `code` で分岐し、`error` の文言で
  分岐しません。

  | `code` | 意味 |
  | --- | --- |
  | `invalid_request` | 要求を解釈できない（JSON として破損している・大きさか入れ子の深さが上限を超える・`tool` が存在しない・`tool`・`args`・`session` の型が異なる） |
  | `unknown_tool` | 未知のツール |
  | `invalid_args` | ツールの引数が誤っている（未知の引数・型や値の誤り・必須の引数の欠落） |
  | `no_wait` | 待機標識（`<id>.wait`）が存在しないので実行しなかった |
  | `busy` | Vectorworks かプラグインが処理中（終了の依頼の最中・ツール内のダイアログで受付処理が入れ子になった）なので実行しなかった（[Vectorworks が処理中](#vectorworks-が処理中)。処理中でも周期処理が来ない間は `busy` も返らない。[生存の判定](#生存の判定)） |
  | `occupied` | 他の呼び出し元が[占有](#占有セッション)しているので実行しなかった |
  | `no_session` | 要求の `session` が現在の占有のセッション ID ではない（その占有は終了した・Vectorworks を再起動した）、又は占有の中でのみ呼び出せるツール（`@session_end`・種類 `write`・`app`）を占有せずに呼び出したので実行しなかった |
  | `internal` | その他（ツール内の例外・図面が開かれていないなど） |

- 失敗の応答は、ツールが詳細を返す場合のみ `detail`（JSON のオブジェクト）を有します。呼び出し元が
  失敗の原因を機械的に読み取るための、ツールごとの内容です（例: `quit` が開いている図面の一覧を返す。
  [ツール「quit」](plugin/tools.md#quit)）。`detail` を有するのはツールが返した失敗（`invalid_args`・`internal`）
  のみで、通信規則が付ける失敗（`busy` など）は有しません。**省略可能なフィールドを追加する互換の変更**なので
  版は上げません（[互換性](#互換性)。対応していない読み手は無視する）。形式はツールごとに定め、通信規則は内容を
  解釈しません。プラグインは、ツールがオブジェクトでない詳細を返せばツールの不具合として `internal` で
  応答し（`detail` を付けない）、成功の応答には `detail` を付けません。呼び出し元は、`detail` を有しえない
  応答（成功と、`invalid_args`・`internal` 以外の失敗）に `detail` があるもの、`detail` がオブジェクトで
  ない（`null` を含む）ものを破損した応答として扱います。

  `code` は通信規則として共通に定まる種別のみに限ります。図面が開かれていないことのように、ツールに
  よって失敗になるかが異なる理由は `internal` とし、`error` で説明します（ツールごとの解釈を通信規則に
  持ち込まない）。呼び出し元が理由を機械的に区別できるよう、ツールは `detail` に理由を含められます（形式は
  ツールごとに定める。例: [ツール](plugin/tools.md)の `{"reason":"no_document"}`）。

  呼び出し元が[待機標識](#待機標識idwait)を解放していて実行しなかった要求には、応答しません。
- 呼び出し元は応答を読み取ったら削除します。

### 待機の中止

待機を断念した呼び出し元は、**`<id>.wait` を解放して削除してから**、要求を削除します。削除できたかどうかで、
要求が実行されうるかが分かれます。

| 要求を削除できたか | 意味 | `vw2026 call` |
| --- | --- | --- |
| 削除できた | 取り出されていないので、実行されない。誰も待機していない要求も応答も残らない | 「実行されない」タイムアウトの終了コード（Vectorworks が停止していれば「ブリッジが動作していない」） |
| 削除できない（存在しない・Windows でプラグインが開いている） | プラグインが受け取った。中止する前に受け取っていれば実行される | 短い猶予（`vw2026` は 5 秒）の間のみ応答を待機し、届けば受け取る。届かなければ「実行されたかもしれない」の終了コード |

- 待機標識を先に解放するのは、要求を先に削除しようとすると、削除する前にプラグインが要求を取り出して
  待機標識を試行し、実行してしまうことがあるためです。待機標識を先に解放すれば、要求を削除する前に取り出され
  ても実行されません。
- 待機標識のみでも実行は防止できますが、要求を削除することで「実行されない」を確認し、誰も読み取らない
  `no_wait` の応答も残しません。
- 猶予は、待機を中止する直前にプラグインが受け取った要求の応答を取得するためのものです。応答は同一の回の
  受付処理の中で書き込まれるので、短時間のツールならこの間に届きます。ツールの同期の呼び出しが猶予より長く掛かれば
  （[予約ツール](#予約ツール)の「長時間を要するツール」）、呼び出し元は「実行されたかもしれない」で終了し、
  ツールは処理を継続します。結果は呼び出し元がツールで確認します。
- 回の始めに並べられ、前の要求（長時間を要するツール）の後ろでまだ取り出されていない要求は、待機を
  中止すれば削除できるので「実行されない」で終わります。中止する直前に取り出されていれば、上の表の
  「削除できない」に該当し、実行されえます（取り出した後に待機標識を試行するので、待機標識を解放する前に
  取り出された要求のみが実行される）。呼び出し元の待機時間には、前の要求の後ろで待機する時間も含まれます。
- `busy`・`occupied`・`no_session` も「実行しなかった」を意味します（ツールの失敗ではない）。
- **`no_wait` の応答は「実行しなかった」を意味します。** 猶予の間（中止した後にプラグインが
  受け取った）や、待機標識が想定外に消えた場合に届きます。`vw2026 call` はツールの失敗ではなく、
  タイムアウトと同じ「実行されない」終了コードで扱います（終了コードの番号は `vw2026 --help`）。
- 呼び出し元が強制終了された場合に残った要求は、プラグインが取り出したとき（実行せずに破棄する）か、
  次にロックを取得したときに削除されます。待機標識を削除できなかった場合（Windows でプラグインが丁度開いている）も、
  解放してあるので実行されず、プラグインかロックを取得したときの掃除が削除します。猶予の後に残った応答も、次に
  ロックを取得したときに削除されます。長時間を要するツールでは呼び出し元の上限を過ぎることが通常起こるので、
  そうした応答は Vectorworks が動作している間スプールに蓄積し、削除されるのは次にロックを取得したとき
  （通常は次回の起動）です。受付処理の中では整理しません（猶予の間に読み取られる応答と区別する基準が
  必要になるため）。

## プラグイン側の義務

- **要求は読み取ってから削除し、削除できたものの内[呼び出し元が待機している](#待機標識idwait)ものだけを実行します。** 読み取れなかった（消失していた）・
  削除できなかった要求は黙って飛ばします（応答しない）。消失していたのはスプールが整理された
  場合など、削除できなかったのはウイルス対策ソフトなどが一時的に保持している場合で、後者は次の回に
  再試行すれば足ります（削除せずに実行すると、次の回に再度実行してしまう）。
- 読み取れたが JSON として破損している要求には、ファイル名の id が正しければ `invalid_request` で
  応答します（呼び出し元を待たせ続けない）。
- 1 回の受付処理で処理するのは、**回の始めに並べた要求のみ**です。その後に配置された要求は次の回に
  回します（配置され続けても 1 回が終了するように）。件数と時間の上限は設けません（CLI を使用している
  間は GUI を操作しない前提で、蓄積した要求を早く処理する方を採る）。長時間を要するツール（[予約ツール](#予約ツール)）が
  幾つも並べば、1 回の受付処理はその合計の間メインスレッドを塞ぎますが、回を分割しても合間に GUI へ渡るのは
  周期処理 1 回分のみで、どのツールが長いかもプラグインには分からない（他のプラグインの機能を含む）ためです。
  取り出した要求には同一の回の中で応答します（応答を後の回へ持ち越さない。[待機の中止](#待機の中止)）。受付処理の
  入れ子が起きた場合は、回の始めに並べた要求も入れ子の回が `busy` で拒否します（[Vectorworks が処理中](#vectorworks-が処理中)）。
- `@session_start`・`@session_end` と種類 `write`・`app` の要求は、実行する前に[占有](#占有セッション)と
  照合し、[Vectorworks が処理中](#vectorworks-が処理中)なら拒否します。
- 1 つのツールの失敗（例外を含む）でブリッジを停止させません。例外は `internal` で応答します。ツールの外
  （セッション ID を生成するときなど）で、要求 1 件の処理の中で起きた例外も同様です（要求は削除してあるので、
  応答しなければ呼び出し元は「実行されたかもしれない」で終了する）。
- 開くファイル（`bridge.lock`・`<id>.wait`・要求・応答）を子プロセスに継承させません
  （[ロック](#ロックbridgelock)）。
- **スプールのファイルを開く際に待機しません。** 通常のファイルでないもの（FIFO・デバイス・名前付き
  パイプなど）を配置されても受付処理が停止しないよう、開くのは通常のファイルのみで、リンクは
  たどりません（POSIX は `O_NONBLOCK` と `O_NOFOLLOW`、Windows は `FILE_FLAG_OPEN_REPARSE_POINT` で
  開き、reparse point（リンク・AF_UNIX のソケット・WSL の FIFO とデバイスの他、OneDrive などの
  クラウドのファイルも）とディスクのファイルでないものを拒否する。開いてから拒否するのでは、リンクの先の
  デバイスやパイプを開いてしまう。内容がローカルにないもの（読み取るとダウンロードされる）も、ダウンロードを
  待機して停止しないように拒否する）。Windows は `\\?\` を付けて開きます（[id](#id)）。
  - 通常のファイルでない・内容がローカルにない要求は読み取れない要求（黙って飛ばす）、待機標識は存在しない
    待機標識（`no_wait`）として扱います。`bridge.lock` は 1 度のみ削除して再作成し（クラウドの
    ファイルなら、削除するときに同期のサービスを待機することがある）、それでも拒否されたらロックを取得できない
    （受付処理の状態は `error`）とします。
  - スプールは Vectorworks の利用者フォルダ内（[スプールの場所](#スプールの場所)）に配置するので、利用者
    フォルダを同期（OneDrive・iCloud など）・フォルダ リダイレクト・WOF の圧縮・重複除去・オフライン
    ファイル・HSM の対象に置いた環境には対応しません。そうなると、再作成した `bridge.lock` も拒否される
    ので、呼び出し元からは停止している（`vw2026` は not running）と見えます。利用者フォルダをそれらの
    対象から外し、Vectorworks を再起動すれば解消します。

## 予約ツール

| ツール | 結果 |
| --- | --- |
| `@tools` | `{"protocol":7,"tools":[{"name":…,"description":…,"inputSchema":{…},"kind":…}]}`。`inputSchema` は JSON Schema。`kind` は `read` / `write` / `app` の 3 つに限る（`write` は図面の内容を変更するツール、`app` は Vectorworks・図面のファイルやウィンドウに作用し、図面の内容は変更しないツール。呼び出し元が図面を変更するかと、占有が必要かを判定できるように。Vectorworks を終了させるかは種類では決まらない）。図面を変更するかが不明なツールは `write` とする |
| `@session_start` | `{"session":"<セッション ID>"}`。[占有](#占有セッション)を開始する |
| `@session_end` | `{"ended":true}`。占有を終了する（要求に `session` が必要） |
| `ping` | `{"version":…,"branch":…,"protocol":7,"pid":…,"session":…,…}`。プラグインの版（短い sha）・ビルドしたブランチ・通信規則の版・受付処理を行っている Vectorworks のプロセス ID。他のフィールドは[ツール「ping」](plugin/tools.md#ping) |

`@tools` の結果に含まれるのはツールの一覧のツールです。予約ツールの内 `ping` は一覧に含まれるので結果にも含まれ、
`@tools`・`@session_start`・`@session_end` は通信規則そのものが担うツールなので含まれません。

ツール名は `[a-z0-9_]+(\.[a-z0-9_]+)*`。プラグインが自身で有するツールは接頭辞なし
（`ping` / `layers` …）、他のプラグインの機能を呼び出すツールは `<提供者>.<名前>` とします
（[設計「他のプラグインのツール」](design.md#他のプラグインのツール)）。

**通信規則そのものが担うツール（`@tools`・`@session_start`・`@session_end`）は `@` で始めます。**
ツール名の綴りでは記述できない名前にして、ツール名（このプラグインのツールと他のプラグインの
提供者の名前）に予約語を作らないためです。`@` の無い `tools`・`session_start`・`session_end` は
ツール名として使用可能であり、一覧に無ければ `unknown_tool` です。`vw2026` は予約ツールを
それぞれのコマンド（`vw2026 tools`・`vw2026 session start`・`vw2026 session end`）から呼び出し、
`vw2026 call` はツール名をそのまま渡します。

**ツールは、受付処理の中で非同期の処理の完了を待機しません。** 後から完了する処理（Vectorworks の
イベントループが回って進行するもの。`quit` の終了・開いた図面の最初の描画など）は依頼するのみで戻り、
完了したかは呼び出し元が別の要求（`vw2026 status` やツール）で確認します。受付処理の中で待機すると、待機する間
ループでメインスレッドを塞ぎ、待機の対象がイベントループを必要とすれば完了しないためです。

**長時間を要するツール（同期の呼び出しが戻るまでに時間を要するツール）は設けます。** 大きな図面の `save`・
`close`、他のプラグインの機能が多数の図形を作成・編集するもの、人が応答するまで戻らないダイアログを
表示しうるもの（保存先のフォルダに `VW Backup` を作成できない場合の `save`、他のプラグインの機能がダイアログを表示するもの）がこれに該当します。長さに上限は設けません。呼び出しの間の
振る舞いは、Vectorworks がその間にイベントを処理するかで 2 つに分かれ、いずれも許容します。

| 呼び出し | 例 | 利用者 | 他の要求 |
| --- | --- | --- | --- |
| イベントを処理しない | 大きな図面の `save`・`close`（ダイアログが表示されない場合）、他のプラグインの機能が多数の図形を作成・編集するもの | 図面を操作できない。Vectorworks は応答しない状態になる（Windows は数秒を超えると「応答なし」と表示する） | 周期処理が来ないので何も応答しない（`busy` も返らない。要求は配置したまま） |
| 人が応答するまで戻らないダイアログを表示する | 保存先のフォルダに `VW Backup` を作成できない場合の `save`（保存は成功し、OK のみの警告が表示される）、他のプラグインの機能がダイアログを表示するもの | ダイアログには応答できる（他の操作はできない） | Windows は周期処理が再度入って受付処理が入れ子になり、全て `busy` で拒否する（[Vectorworks が処理中](#vectorworks-が処理中)）。mac は周期処理が来ないので何も応答しない |

- いずれも、呼び出し元が依頼した処理を Vectorworks が行っている間なので、利用者が Vectorworks で同じ操作を
  したときと同様に扱います。
- ロックは取得したままなので、呼び出し元からは動作中と見えます（[生存の判定](#生存の判定)）。処理の最中か、
  人の応答を待機しているか、応答不能になったかは、呼び出し元からは区別できません。
- **呼び出し元の待機の上限を過ぎても、ツールは処理を継続します。** 呼び出し元は「実行されたかもしれない」で終了し
  （[待機の中止](#待機の中止)）、結果をツールで確認します。どれだけ待機するかは呼び出し元が決定します
  （`vw2026 call` の `--timeout`）。

## 版

**通信規則の版は実行時に照合しません。** 版はこの文書と `@tools` / `ping` の結果に含まれる表示のみです。

- CLI とプラグインは同一の zip から同時にインストールされ、更新は Vectorworks の終了後にしか行わない
  （[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)）ので、動作しているプラグインと
  インストールされている CLI は同一のビルドです。
- 不一致が生じるのは、手作業でビルドした CLI を使用した場合などに限られます（CLI はプラグインと
  同一のフォルダにあり、フォルダ単位で置換されるので、CLI のみが置換に失敗することはない）。気づく手掛かりは
  `vw2026 version` と `call ping` の `protocol` で、照合のための標識や終了コードは有しません。
- 通信規則に準拠する任意のプログラムも、合わせたい版があれば `@tools` か `ping` の `protocol` を参照します。

### 互換性

通信規則は `vw2026` の他、通信規則に準拠する任意のプログラムや将来の他のプラグインにも公開します。
変更の度に版を上げる必要が無いよう、読み手と書き手は次に従います。

- **読み手は、要求と応答の未知のフィールドを無視します**（must-ignore）。プラグインが要求の
  未知のトップレベルのキーを受け取った場合も無視します。
- **省略可能なフィールドを追加することは互換の変更**とし、版を上げません。
- **省略可能なものには既定値を設けます。** 通信規則のフィールド（例: `args` は `{}`）もツールの
  引数（[ツール](plugin/tools.md)の表の「既定」）も同様です。追加するフィールドの既定値は、追加する前の
  振る舞いと同一にします（省略した読み手・書き手の振る舞いが変わらないように）。
- 次の場合にのみ版を上げます: フィールドの意味を変更する・必須のフィールドを追加する・定まった綴りの
  値（`code`・`kind` など）を追加する・ファイルの名前や配置方法を変更する。
- **例外として、まだどの実装もリリースしていない振る舞いの変更は版を上げず、現在の版に含めて
  [版の履歴](#版の履歴)に記述します。** 版は、リリースした実装同士が不一致を起こさないための表示で、
  リリースしていない振る舞いには合わせる相手が存在しないためです（例: 版 5 の `args` の扱い。プラグインは
  未実装で、`vw2026` はオブジェクト以外を送信しない）。
- 無視するのは**通信規則の封筒（要求の `tool`・`args`・`session` と応答の `ok`・`code`・`error`・`result` の並び）
  の未知のフィールド**のみです。**既知のフィールドの未知の値**（例: 未知の `code`・
  `kind`、型の異なる `args`）と、**ツールの未知の引数**（`args` の中）はエラーとして扱い、
  既定値に読み替えません。`args` の中はツールごとの取り決めで、
  未知の引数を黙って無視すると、呼び出し元の綴りの誤りが気づかれないまま図面に作用するためです。
- `vw2026 call` は、失敗の応答の `code` が存在しない・未知の値なら、ツールの失敗では
  なく破損した応答として、汎用の失敗の終了コードで終了します。

## 版の履歴

| 版 | 変更 |
| --- | --- |
| 1 | 初版 |
| 2 | 標識から `beat` を除き、ロックを取得したときに 1 度のみ書き込む。状態を「動作中／停止中」の 2 つにする（「応答しない」を除く）。スプールの所有者と権限を確認しない |
| 3 | 標識（`bridge.json`）を除く。版・ブランチ・`pid` は `ping` が返す。通信規則の版を実行時に照合しない |
| 4 | 待機標識（`<id>.wait`）を必須にし、待機する者の存在しない要求を実行しない。掃除は待機標識を取得できる・存在しない id のファイルのみを削除する。待機を中止する場合は待機標識を解放して削除してから要求を削除し、削除できたかで「実行されない」と「実行されたかもしれない」を区別する。開くファイルを子プロセスに継承させない。失敗の応答に `code` を追加する。互換性の規則を設ける |
| 5 | [占有](#占有セッション)を追加する（予約ツール `session_start` / `session_end`、要求の `session`、応答の `code` の `busy` / `no_session`、`ping` の `session`）。`quit` は占有の中でのみ呼び出せる。要求の入れ子の深さに上限（64）を設ける。破損した応答を再度読み取らない。後から、版を上げずに次を改めた（[互換性](#互換性)の例外。括弧の中はその理由）: `vw2026` の破損した応答への 1 秒の猶予を除く（応答は rename で公開されるので待機しても解消せず、通信規則に従う書き手には影響しない）。`args` のオブジェクト以外（配列・文字列など）を `{}` への読み替えから `invalid_request` に改める（意味の変更だが、プラグインが未実装で、`vw2026` もオブジェクト以外を送信しない）。要求の JSON の解釈の仕方（文字列の不正な UTF-8 と対にならないサロゲートは U+FFFD、同一のキーは後のもの、`session` の空の文字列は省略と同じ）を定め、`tools` の結果に `tools`・`session_start`・`session_end` を含めないことを明記する（擬似プラグインは `encoding/json` で既にそのように解釈し、プラグインは未実装）。種類 `write` も占有の中でのみ呼び出せるようにし、種類 `read` と一覧に無いツールを占有と照合せず、他の呼び出し元の占有で拒否する `code` を `busy` から `occupied` に分離し、`busy` を「Vectorworks が処理中」（終了の依頼・受付処理の入れ子）に充て、処理中の要求を配置したままにせずに拒否する（意味の変更と `code` の追加だが、プラグインも `vw2026` もまだリリースしていない）。成功の応答の `result` を必ずオブジェクトとする（リリースしたプラグインのツールは既にオブジェクトのみを返す） |
| 6 | スプールを `cli` のプラグインのフォルダ内（`<Plug-Ins>/cli/spool/`）に移動する。プラグインは自身のモジュールの場所から、呼び出し元の `vw2026` は自身の実行ファイルの場所から導出する（[スプールの場所](#スプールの場所)）。後から、版を上げずに次を改めた（[互換性](#互換性)の例外。括弧の中はその理由）: 長時間実行されるツールを設けない規則を「受付処理の中で非同期の処理の完了を待機しない。同期の呼び出しが長時間を要するツールは設ける」に改める（受け渡しの形式も `vw2026` の振る舞い（上限を過ぎれば「実行されない」か「実行されたかもしれない」）も変わらず、リリースしたツールは `ping` のみ）。終了の依頼の最中に拒否する要求を、種類 `write`・`app` から一覧のツール全て（`tools`・`session_start`・`session_end` と一覧に無いツールを除く）に拡大する（`quit` をリリースする前で、終了の依頼の最中を生じさせる実装をまだリリースしていない） |
| 7 | 通信規則そのものが担う予約ツールの名前を `tools`・`session_start`・`session_end` から `@tools`・`@session_start`・`@session_end` に改める（ツール名の綴りで記述できない名前にし、ツール名に予約語を作らない）。`@` の無い名前は一覧に無いツールとして `unknown_tool` になる |
