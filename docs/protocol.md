# 受け渡しの作法（protocol 4）

ブリッジ（プラグイン）と呼ぶ側（`vw2026` や、作法を守る任意のプログラム）は、**ローカルの
ディレクトリ 1 つ（スプール）に置くファイル**でやり取りします。この文書が作法の真実で、
プラグイン側（C++）と CLI 側（`cli/internal/spool`）はその対になる実装です。**どちらかを
変えたら、この文書と両方を直してください。** 版（`protocol`）を上げるかは[互換性](#互換性)の
決まりに従います。

作法は、構造設計支援プラグイン（`vectorworks-plugin-import-ifc-homeskz`）の開発版の MCP
ブリッジ（M24〜M42。`src/core/Bridge.h`）で実機で確かめた作りを引き継いでいます。元の作法
（protocol 1 の系列）とは別の系列で、スプールの場所も違うので混ざりません。

## スプールの場所

```
<CLI>/spool/
```

`<CLI>` は CLI の場所です（[名前と識別子](plugin/identifiers.md#置き場所)）。

- **プラグインと呼ぶ側は、同じ規則で同じ場所を求めます**（探索しない）。mac はホーム
  ディレクトリ、Windows は `%LOCALAPPDATA%`（プラグインは `SHGetKnownFolderPath(FOLDERID_LocalAppData)`）
  から決まるので、GUI アプリの Vectorworks と、ssh や別のアプリから起動されたプロセスとで
  食い違いません。一時ディレクトリは環境変数で決まり食い違いうるので使いません。
- **名前に Vectorworks の版を入れます。** 版ごとにプラグインを入れるので、2026 と 2027 を
  同時に起動しても、2 つの橋が同じ要求を取り合わない（コマンド `vw2026` と対になる）。
- プラグイン側は無ければ 0700 で作ります（親も無ければ作る）。持ち主と権限は確かめません。
  場所は利用者のホーム（Windows は `%LOCALAPPDATA%`）の下で、そこへほかの利用者が書けるなら、
  スプールに限らず利用者のファイルはどのみち守れないためです。
- 呼ぶ側は `VW2026_SPOOL`（`vw2026` では `--spool` も）で別の場所を指せます。テストのため
  で、プラグイン側は読みません（GUI アプリの Vectorworks は環境変数を受け継がず、本番では
  効かない）。

## ファイル

| ファイル | 書く側 | 中身 |
| --- | --- | --- |
| `bridge.lock` | プラグイン | ロック（受け付けている間ずっと掴む。中身は空） |
| `<id>.req.json` | 呼ぶ側 | 要求 1 件 |
| `<id>.res.json` | プラグイン | 応答 1 件 |
| `<id>.wait` | 呼ぶ側 | 待つ印（応答を待つ間ずっと掴む。中身は空。必須。[下記](#待つ印idwait)） |
| `*.tmp` | 両方 | 書きかけ（下記） |

**要求と応答は、同じディレクトリへ `<名前>.tmp` として書いてから rename で公開します。**
読み手に書きかけの内容を読ませないためです。読み手は、読めない・JSON として壊れている
ファイルを「まだ無い」とみなして読み直します。

### id

- 綴りは `[0-9A-Za-z_-]{1,64}`。**プラグイン側はこれを満たさない id を受け付けません**
  （ファイル名に使うので、`../` を混ぜてスプールの外へ書かせないための関門）。
- id はファイル名だけが持ちます（要求と応答の本文には入れない）。
- プラグイン側は要求を**ファイル名の昇順**で処理します。呼ぶ側は、名前の昇順が送った順に
  なる id を付けます。`vw2026` は `<UnixNano を 19 桁>-<乱数 8 桁の 16 進>` で、別々の
  プロセスからの要求も送った順に並びます。

## ロック（`bridge.lock`）

**スプールを受け付ける橋は、`bridge.lock` を掴んでいる 1 つだけです。** プラグインは
ロックを取れたときから Vectorworks の終了まで、ロックを放しません。

| | 掴む（プラグイン） | 掴まれているかを見る（呼ぶ側） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT\|O_CLOEXEC, 0600)` のあと `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY)` のあと `flock(LOCK_SH\|LOCK_NB)`。`EWOULDBLOCK` なら掴まれている。取れたらすぐ放す |
| Windows | `CreateFile` を共有なし（share mode 0）・`OPEN_ALWAYS`・`lpSecurityAttributes` に null で開いたハンドルを持ち続ける | 開いて共有違反（`ERROR_SHARING_VIOLATION`）なら掴まれている。開けたらすぐ閉じる |

- **ロックを子プロセスに受け継がせません**（POSIX は `O_CLOEXEC`、Windows は継承できない
  ハンドル）。`flock` は開いたファイルの記述に付くので、Vectorworks が起動した子プロセスが
  記述子を受け継ぐと、Vectorworks が終わってもロックが放されず、止まったと判定されなくなります。

- ロックはプロセスが終われば（異常終了を含む）OS が放します。止まったかどうかを
  `pid` やプロセス名で推し量る必要はありません。
- **ロックを取れなかった回は何もしません**（要求を取り出さない）。次の回に取り直します。
  取れないのは、同じスプールを別の Vectorworks が受け付けているとき（Windows では
  Vectorworks 2026 を 2 つ起動できる）か、呼ぶ側がちょうど確かめているときです。前者は相手が
  終われば引き継ぎ、後者は次の回に取れます。
- **ロックを取れたら、前の回の残骸（要求・応答・待つ印・書きかけ）を消してから**受け付けを始めます。
  ロックを取れたことは、ほかに受け付けている橋が居ないことを意味するので、消してよい。
- 呼ぶ側はロックを掴み続けません（確かめたらすぐ放す）。
- `bridge.lock` は消しません（消すと、掴んだままのファイルと新しく作られたファイルが別物になる）。
- 受け付けていない Vectorworks の図面は CLI から操作できません。どちらが受け付けているかは
  `ping` の `pid` で分かります。

### 生存の判定

**生死はロックだけで決めます。** 呼ぶ側は次の 2 つの状態を判定します。

| 状態 | 条件 | 意味 |
| --- | --- | --- |
| 動いている（`running`） | ロックが掴まれている | 要求を置けば、受け付けの次の回に処理される |
| 止まっている | ロックが掴まれていない（スプールが無いときも） | 要求を置いても応えない |

**動いていても、すぐに応えるとは限りません。** プラグイン側は undo の記録が開いている間・
モーダルダイアログの最中は受け付けを見送ります（[構成「受け付けを止めない・処理中は見送る」](plugin/architecture.md#受け付けを止めない処理中は見送る)）。
応えるかどうかは、要求を置いて待つことでしか分かりません。見送りの間もロックは掴まれたままなので、
呼ぶ側は次のように扱えます（ほかの文書はここを参照します）。

- 要求は置いたままにしておけば、見送りが終わったときに処理されます。
- `quit` の保存の確認を開いている間も「止まった」とは判定されません。終了を見届けるには
  ロックが放されるのを待ちます（`vw2026 wait --down`）。利用者が取り消せば Vectorworks は
  動き続け、待つ側は上限を過ぎて終わります。

## 待つ印（`<id>.wait`）

呼ぶ側が応答を待っているかを、`bridge.lock` と同じ仕組みを要求 1 件ごとに逆向きに使って
示します。呼ぶ側が強制終了（Ctrl-C・kill・異常終了）されたあとに、誰も待たない要求が実行される
のを防ぐためです（書く道具では、利用者の知らない操作が図面に入る）。

| | 掴む（呼ぶ側） | 掴めるかを試す（プラグイン） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT\|O_EXCL\|O_CLOEXEC, 0600)` のあと `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY\|O_CLOEXEC)` のあと `flock(LOCK_EX\|LOCK_NB)`。`EWOULDBLOCK` なら掴まれている |
| Windows | `CreateFile` を共有なし・`CREATE_NEW`・`lpSecurityAttributes` に null で開いたハンドルを持ち続ける | 共有なし・`OPEN_EXISTING` で開いて、共有違反なら掴まれている。開けたら閉じる |

呼ぶ側:

1. `<id>.wait` を作って掴む。
2. **そのあとで** `<id>.req.json` を公開する（公開した時点で、プラグインが生死を判定できるように）。
3. 応答を受け取ったか、待つのをやめるときは、`<id>.wait` を放して消す。待つのをやめるときも
   **要求は消しません**（[待つのをやめる](#待つのをやめる)）。

プラグイン: 要求を消した直後、実行する前に `<id>.wait` を掴めるか試します。

| `<id>.wait` | 意味 | 扱い |
| --- | --- | --- |
| 掴めた | 呼ぶ側が放した・死んだ（異常終了でも OS が放す） | `<id>.wait` を消し、**実行も応答もしない** |
| 掴めない | 呼ぶ側が待っている | 実行して応答する |
| 無い | 呼ぶ側が待つのをやめて消した・待つ印を置き忘れた | **実行せず**、`no_wait` で応答する |

- **`<id>.wait` は必須です。** 無い要求を実行しないので、想定外の理由（スプールの片付けなど）で
  待つ印が消えても、実行ではなく見送りに倒れます。置き忘れた呼ぶ側に理由が伝わるよう、無いときは
  応答します（待つ者が居なければ誰も読まない応答が残りますが、次にロックを取ったときに消えます）。
- シェルのスクリプトなど、ロックを掴み続けにくい呼ぶ側は `vw2026 call` を使います。
- 生死を `pid` で推し量らないのは `bridge.lock` と同じ理由です（`pid` は再利用される）。要求に
  期限を載せないのは、長い待ち時間で生きて待っている呼ぶ側の要求まで捨ててしまうためです。
- 呼ぶ側が強制終了されても、OS が `<id>.wait` を放すので、待つのをやめたときと同じになります。
  シグナルを受けて後始末をする必要はありません。

## 要求（`<id>.req.json`）

```json
{"tool":"layers","args":{"include_sheets":false}}
```

- `args` はオブジェクト。省略・オブジェクト以外は `{}` として扱います。
- 1 件の上限は **1 MiB**。超えるものは「読めない要求」として `invalid_request` で応答されます。
- 知らないトップレベルのキーは無視されます（[互換性](#互換性)）。

## 応答（`<id>.res.json`）

```json
{"ok":true,"result":{…}}
{"ok":false,"code":"unknown_tool","error":"知らない道具です: nope"}
```

- 失敗の応答は、機械が読む種別 `code` と、人向けの理由 `error` を持ちます。`code` の綴りは
  次に固定します（値を足すのは版を上げる変更）。呼ぶ側は `code` で分岐し、`error` の文言で
  分岐しません。

  | `code` | 意味 |
  | --- | --- |
  | `invalid_request` | 要求が読めない（JSON として壊れている・上限を超える・`tool` が無い） |
  | `unknown_tool` | 知らない道具 |
  | `invalid_args` | 道具の引数が誤っている（知らない引数・型や値の誤り・必須の欠け） |
  | `no_wait` | 待つ印（`<id>.wait`）が無いので実行しなかった |
  | `internal` | そのほか（道具の中の例外・図面が開かれていないなど） |

  `code` は作法として共通に決まる種別だけに限ります。図面が開かれていないことのように、道具に
  よって失敗になるかが違う理由は `internal` とし、`error` で説明します（道具ごとの解釈を作法に
  持ち込まない）。

  呼ぶ側が[待つ印](#待つ印idwait)を放していて実行しなかった要求には、応答しません。
- 呼ぶ側は応答を読んだら消します。

### 待つのをやめる

待つのを諦めた呼ぶ側は、**`<id>.wait` を放して消してから**、要求が残っているかを見ます。
要求は消しません（取り下げは待つ印を放して消すことで足りる）。

| やめたあとの要求 | 意味 | `vw2026 call` |
| --- | --- | --- |
| 残っている | まだ取り出されていない。以後に取り出されても、待つ印を掴める・無いので実行されない | 終了コード 4（Vectorworks が止まっていれば 3） |
| 無い | プラグインが受け取った。やめる前に受け取っていれば実行される | 短い猶予（`vw2026` は 5 秒）だけ応答を待ち、届けば受け取る。届かなければ終了コード 8 |

- やめてから見るのは、見てからやめると、その間にプラグインが要求を取り出して待つ印を試し、実行
  してしまうことがあるためです。
- 応答は受け付けの同じ回の中で書かれ、受け付け 1 回の中で数秒を超える道具は持たない
  （[予約された道具](#予約された道具)）ので、猶予は短くて足ります。
- 猶予の間に `no_wait` の応答が届くことがあります（やめたあとにプラグインが受け取った）。実行は
  されていません。
- 残った要求は、プラグインが取り出したとき（実行せずに断る）か、次にロックを取ったときに
  消えます。待つ印を消せなかったとき（Windows でプラグインがちょうど開いている）も、放してあるので
  実行されず、プラグインかロックを取ったときの掃除が消します。猶予のあとに残った応答も、次に
  ロックを取ったときに消えます。

## プラグイン側の義務

- **要求は読んでから消し、消せたもののうち[呼ぶ側が待っている](#待つ印idwait)ものだけを実行します。** 読めなかった（無くなっていた）・
  消せなかった要求は黙って飛ばします（応答しない）。無くなっていたのはスプールが片付けられた
  ときなど、消せなかったのはウイルス対策ソフトなどが一時的に掴んでいるときで、後者は次の回に
  やり直せば済みます（消さずに実行すると、次の回にまた実行してしまう）。
- 読めたが JSON として壊れている要求には、ファイル名の id が正しければ `invalid_request` で
  応答します（呼ぶ側を待たせ切らない）。
- 1 回の受け付けで処理する件数に上限を設けます（溜まっていても Vectorworks を占有し続けない）。
- 道具 1 つの失敗（例外を含む）で橋を止めません。例外は `internal` で応答します。
- 開くファイル（`bridge.lock`・`<id>.wait`・要求・応答）を子プロセスに受け継がせません
  （[ロック](#ロックbridgelock)）。

## 予約された道具

| 道具 | 結果 |
| --- | --- |
| `tools` | `{"protocol":4,"tools":[{"name":…,"description":…,"inputSchema":{…},"kind":…}]}`。`inputSchema` は JSON Schema。`kind` は `read` / `write` / `app`（`app` は Vectorworks そのものに働く道具。図面を変えるか・Vectorworks を終わらせるかを呼ぶ側が判定できるように） |
| `ping` | `{"version":…,"branch":…,"protocol":4,"pid":…,…}`。プラグインの版（短い sha）・作ったブランチ・作法の版・受け付けている Vectorworks のプロセス ID。ほかのフィールドは[道具「ping」](plugin/tools.md#ping) |

道具の名前は `[a-z0-9_]+(\.[a-z0-9_]+)*`。プラグインが自分で持つ道具は接頭辞なし
（`ping` / `layers` …）、ほかのプラグインの機能を呼ぶ道具は `<提供者>.<名前>` にする予定です
（[設計「他のプラグインの道具」](design.md#他のプラグインの道具)。呼び出しの手段は SDK の調査待ち）。

長く走る道具（受け付け 1 回の中で数秒を超える道具）は今は持ちません。足すときは、その間も
呼ぶ側が待ち続けられる手段を決め、版を上げます。

## 版

**作法の版は実行時に照合しません。** 版はこの文書と `tools` / `ping` の結果に載る表示だけです。

- CLI とプラグインは同じ zip から同時に入り、更新は Vectorworks の終了後にしか行わない
  （[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)）ので、動いているプラグインと
  入っている CLI は同じビルドです。
- 食い違うのは、手でビルドした CLI を使ったとき・`install` が CLI の入れ替えだけに
  失敗したときなどに限られます。気づく手掛かりは `vw2026 version` と `call ping` の
  `protocol` で、照合のための印や終了コードは持ちません。
- 作法を守る任意のプログラムも、合わせたい版があれば `tools` か `ping` の `protocol` を見ます。

### 互換性

作法は `vw2026` のほか、作法を守る任意のプログラムや将来のほかのプラグインにも公開します。
変更のたびに版を上げずに済むよう、読み手と書き手は次に従います。

- **読み手は、要求と応答の知らないフィールドを無視します**（must-ignore）。プラグインが要求の
  知らないトップレベルのキーを受け取ったときも無視します。
- **省略できるフィールドを足すことは互換の変更**とし、版を上げません。
- 次のときだけ版を上げます: フィールドの意味を変える・必須のフィールドを足す・決まった綴りの
  値（`code`・`kind` など）を足す・ファイルの名前や置き方を変える。
- 無視するのは**作法の封筒（要求の `tool`・`args` と応答の `ok`・`code`・`error`・`result` の並び）
  の知らないフィールド**だけです。**知っているフィールドの未知の値**（例: 知らない `code`）と、
  **道具の知らない引数**（`args` の中）はエラーとして扱います。`args` の中は道具ごとの約束で、
  知らない引数を黙って無視すると、呼ぶ側の綴りの誤りが気づかれないまま図面に効くためです。

| 版 | 変更 |

| 1 | 最初の版 |
