# 通信規則（protocol 5）

ブリッジ（プラグイン）と呼ぶ側（`vw2026` や、通信規則を守る任意のプログラム）は、**ローカルの
ディレクトリ 1 つ（スプール）に置くファイル**でやり取りします。この文書が通信規則の真実で、
プラグイン側（C++）と CLI 側（`cli/internal/spool`）はその対になる実装です。**どちらかを
変えたら、この文書と両方を直してください。** 版（`protocol`）を上げるかは[互換性](#互換性)の
決まりに従います。

通信規則はこのリポジトリで決めたものです。構造設計支援プラグイン（`vectorworks-plugin-import-ifc-homeskz`）
の開発版のブリッジの通信規則（protocol 1 の系列）とは別のもので、スプールの場所も違うので混ざりません。

## スプールの場所

```
<CLI>/spool/
```

`<CLI>` は CLI の場所です（[名前と識別子](plugin/identifiers.md#置き場所)）。

- **プラグインと呼ぶ側は、同じ規則で同じ場所を求めます**（探索しない）。GUI アプリの
  Vectorworks と、ssh や別のアプリから起動されたプロセスとで食い違わないためです。一時
  ディレクトリは環境変数で決まり食い違いうるので使いません。
  - Windows: `%LOCALAPPDATA%` の指す場所を、**両側とも `SHGetKnownFolderPath(FOLDERID_LocalAppData)`
    で求めます**（環境変数 `LOCALAPPDATA` は読まない。`vw2026` は `syscall` 経由で呼ぶ）。
  - mac: ホームディレクトリの `Library/Application Support`。ホームは**両側とも利用者の passwd の
    項目（`getpwuid_r(getuid())` の `pw_dir`）から求めます**（環境変数 `HOME` は読まない。launchd の
    ジョブで無い・ツールの実行環境で上書きされることがあるため。`vw2026` は `os/user` で、cgo なしでも
    libSystem を呼ぶ）。
- **名前に Vectorworks の版を入れます。** 版ごとにプラグインを入れるので、2026 と 2027 を
  同時に起動しても、2 つの橋が同じ要求を取り合わない（コマンド `vw2026` と対になる）。
- プラグイン側は無ければ 0700 で作ります（親も無ければ作る）。持ち主と権限は確かめません。
  場所は利用者のホーム（Windows は `%LOCALAPPDATA%`）の下で、そこへほかの利用者が書けるなら、
  スプールに限らず利用者のファイルはどのみち守れないためです。
- **どちらの側も、場所を変える指定（引数・環境変数）を持ちません。** 片側だけを変えられても
  要求が届かず、GUI アプリの Vectorworks は環境変数を受け継がないので、プラグイン側では指定が
  本番で効かないためです。`vw2026` のテストは、場所を求める関数をコードの中で差し替えます。

## ファイル

| ファイル | 書く側 | 中身 |
| --- | --- | --- |
| `bridge.lock` | プラグイン | ロック（受け付けている間ずっと掴む。中身は空） |
| `<id>.req.json` | 呼ぶ側 | 要求 1 件 |
| `<id>.res.json` | プラグイン | 応答 1 件 |
| `<id>.wait` | 呼ぶ側 | 待つ印（応答を待つ間ずっと掴む。中身は空。必須。[下記](#待つ印idwait)） |
| `*.tmp` | 両方 | 書きかけ（下記） |

**要求と応答は、同じディレクトリへ `<名前>.tmp` として書いてから rename で公開します。**
読み手に書きかけの内容を読ませないためです。**書きかけは、あれば消してから新しく作ります**
（POSIX は `O_CREAT|O_EXCL`、Windows は `CREATE_NEW`。両側とも）。あるものを開いて切り詰めると、
置かれたリンク（シンボリックリンクでも hard link でも）の先、つまりスプールの外のファイルを
壊すためです。

- 読み手は、読めない（無い・開けない）ファイルを「まだ無い」とみなして読み直します。
- rename で公開するので、読めたファイルは書き終えたものです。応答として読めない（JSON として
  壊れている・形が合わない）のは書き手が通信規則に反したときだけで、待っても直りません。呼ぶ側は、
  応答のファイルが応答として読めなければ読み直さず、そのファイルを消し、締切を待たずに壊れた
  応答として扱います。

### id

- 綴りは `[0-9A-Za-z_-]{1,64}`。**プラグイン側はこれを満たさない id を受け付けません**
  （ファイル名に使うので、`../` を混ぜてスプールの外へ書かせないための関門）。そうした要求は
  読まず・消さず・応答もしません（応答の名前にも同じ id を使うため）。
- id はファイル名だけが持ちます（要求と応答の本文には入れない）。
- プラグイン側は要求を**ファイル名の昇順**で処理します。呼ぶ側は、名前の昇順が送った順に
  なる id を付けます。`vw2026` は `<UnixNano を 19 桁>-<乱数 8 桁の 16 進>` です。
- **順序を保証するのは、応答を受け取ってから次を送った要求だけです。** 応答を待たずに続けて
  置いた要求と、別々のプロセスからの要求の順序は保証しません。時計の刻みは粗く（Windows では
  数 ms〜15.6 ms）同じ刻みの id は乱数の部分で並び、時計の調整で時刻は前後し、id を付けた時刻と
  rename で公開した時刻もずれる（遅れて公開された要求は次の回に回る）ためです。順序が要るなら
  呼ぶ側が応答を待って揃えます（[占有](#占有セッション)・[設計「CLI はプリミティブに保つ」](design.md#cli-はプリミティブに保つ)）。
- Windows の予約されたデバイス名（`CON`・`NUL`・`AUX`・`COM1` など）も、綴りを満たせば id です。
  プラグイン側はスプールのファイルを `\\?\` を付けて開くので、こうした名前の要求もデバイスでは
  なくファイルとして扱います（付けずに開くと、Windows 10 までは拡張子があってもデバイスを指す）。
  見本の id（[通信規則の見本](fixtures.md)の `ids.json`）にも含めます。

## ロック（`bridge.lock`）

**スプールを受け付ける橋は、`bridge.lock` を掴んでいる 1 つだけです。** プラグインは
ロックを取れたときから Vectorworks の終了まで、ロックを放しません。

| | 掴む（プラグイン） | 掴まれているかを見る（呼ぶ側） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT\|O_CLOEXEC, 0600)` のあと `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY)` のあと `flock(LOCK_SH\|LOCK_NB)`。`EWOULDBLOCK` なら掴まれている。取れたらすぐ放す |
| Windows | `CreateFile` を共有なし（share mode 0）・`OPEN_ALWAYS`・`lpSecurityAttributes` に null で開いたハンドルを持ち続ける | 開いて共有違反（`ERROR_SHARING_VIOLATION`）なら掴まれている。開けたらすぐ閉じる |

- **ロックを子プロセスに受け継がせません**（POSIX は `O_CLOEXEC`、Windows は継承できない
  ハンドル）。`flock` は開いたファイルの記述に付くので、Vectorworks が起動した子プロセスが
  記述子を受け継ぐと、Vectorworks が終わってもロックが放されず、止まったと判定されなくなります。

- ロックはプロセスが終われば（異常終了を含む）OS が放します。止まったかどうかを
  `pid` やプロセス名で推し量る必要はありません。
- **ロックを取れなかった回は何もしません**（要求を取り出さない）。次の回に取り直します。
  取れないのは、同じスプールを別の Vectorworks が受け付けているとき（Windows では
  Vectorworks 2026 を 2 つ起動できる）か、呼ぶ側がちょうど確かめているときです。前者は相手が
  終われば引き継ぎ、後者は次の回に取れます。
- **ロックを取れたら、前の回の残骸を消してから**受け付けを始めます。消すのは、
  [待つ印](#待つ印idwait)を掴める・無い id のファイル（要求・応答・待つ印・書きかけ）だけです。
  - 待っている呼ぶ側（待つ印が掴まれている）のファイルは残します。要求は引き継いだ橋がそのまま
    処理し、前の橋が書いた応答は呼ぶ側が読めます。前の橋が終わったことで、待っている呼ぶ側に
    「実行されたかもしれない」という終了コードを返させないためです。ロックを取った直後に置かれた
    要求を消してしまうこともありません。
  - 呼ぶ側を区別できないので、どの Vectorworks が要求を処理するかは呼ぶ側には選べません。前の橋に
    向けて置かれた要求も、引き継いだ橋が処理します（引き継ぎの直後に置かれた要求と同じ扱い）。
  - 待つ印を作ってから掴むまでのごく短い間（POSIX）に掃除が待つ印を消すと、その要求は待つ印の
    無い要求として `no_wait` で断られます。実行はされず、呼ぶ側はタイムアウトと同じ「実行されない」終了コードを受け取ります。
- 呼ぶ側はロックを掴み続けません（確かめたらすぐ放す）。
- `bridge.lock` は消しません（消すと、掴んだままのファイルと新しく作られたファイルが別物になる）。
  例外として、プラグインが通常のファイルでない・中身がローカルにないとして断った `bridge.lock` は、
  1 つの Vectorworks につき 1 度だけ、消して作り直します（[プラグイン側の義務](#プラグイン側の義務)。
  受け付けのたびに繰り返さない）。断れたのは、ほかの Vectorworks が掴んでいないときだけです
  （Windows は共有なしで開けた、POSIX はリンクや FIFO で掴めない）。ディレクトリ（Windows は
  ジャンクションも）は開けないので、断ったことにならず、作り直しません。
- 受け付けていない Vectorworks の図面は CLI から操作できません。どちらが受け付けているかは
  `ping` の `pid` で分かります。

### 生存の判定

**生死はロックだけで決めます。** 呼ぶ側は次の 2 つの状態を判定します。

| 状態 | 条件 | 意味 |
| --- | --- | --- |
| 動いている（`running`） | ロックが掴まれている | 要求を置けば、受け付けの次の回に処理される |
| 止まっている | ロックが掴まれていない（スプールが無いときも） | 要求を置いても応えない |

**動いていても、すぐに応えるとは限りません。** プラグイン側は OS のタイマーの刻みの中で受け付ける
ので、Vectorworks が刻みを配らない間（重い処理・一部のダイアログの最中）は応えません
（[構成「受け付けの流れ」](plugin/architecture.md#受け付けの流れ)）。応えるかどうかは、要求を置いて
待つことでしか分かりません。その間もロックは掴まれたままなので、呼ぶ側は次のように扱えます
（ほかの文書はここを参照します）。

- 要求は置いたままにしておけば、刻みが戻ったときに処理されます。
- Vectorworks かプラグインが処理中（終了の依頼の最中・ほかの要求を処理している最中）のときは、
  要求を置いたままにせず、`busy` ですぐに断ります（[Vectorworks が処理中](#vectorworks-が処理中)）。
- `quit` は図面が開いていれば終了を頼まずに失敗するので、通常は保存の確認を開きません（確かめてから頼むまでの間に
  利用者が図面を開く競合のときだけ開きうる）。その間も「止まった」とは判定されません。終了を見届けるには
  ロックが放されるのを待ちます（`vw2026 status` が止まっていると答えるまで繰り返す）。利用者が取り消せば Vectorworks は
  動き続け、待つ側は上限を過ぎて終わります。

## 待つ印（`<id>.wait`）

呼ぶ側が応答を待っているかを、`bridge.lock` と同じ仕組みを要求 1 件ごとに逆向きに使って
示します。呼ぶ側が強制終了（Ctrl-C・kill・異常終了）されたあとに、誰も待たない要求が実行される
のを防ぐためです（書く道具では、利用者の知らない操作が図面に入る）。

| | 掴む（呼ぶ側） | 掴めるかを試す（プラグイン） |
| --- | --- | --- |
| POSIX | `open(O_RDWR\|O_CREAT\|O_EXCL\|O_CLOEXEC, 0600)` のあと `flock(LOCK_EX\|LOCK_NB)` | `open(O_RDONLY\|O_CLOEXEC)` のあと `flock(LOCK_EX\|LOCK_NB)`。`EWOULDBLOCK` なら掴まれている |
| Windows | `CreateFile` を共有なし・`CREATE_NEW`・`lpSecurityAttributes` に null で開いたハンドルを持ち続ける | 共有なし・`OPEN_EXISTING` で開いて、共有違反なら掴まれている。開けたら閉じる |

呼ぶ側:

1. `<id>.wait` を作って掴む。
2. **そのあとで** `<id>.req.json` を公開する（公開した時点で、プラグインが生死を判定できるように）。
3. 応答を受け取ったか、待つのをやめるときは、`<id>.wait` を放して消す。待つのをやめるときは、
   **そのあとで**要求を消す（[待つのをやめる](#待つのをやめる)）。

プラグイン: 要求を消した直後、実行する前に `<id>.wait` を掴めるか試します。

| `<id>.wait` | 意味 | 扱い |
| --- | --- | --- |
| 掴めた | 呼ぶ側が放した・死んだ（異常終了でも OS が放す） | `<id>.wait` を消し、**実行も応答もしない** |
| 掴めない | 呼ぶ側が待っている | 実行して応答する |
| 無い | 呼ぶ側が待つのをやめて消した・待つ印を置き忘れた | **実行せず**、`no_wait` で応答する |

- **`<id>.wait` は必須です。** 無い要求を実行しないので、想定外の理由（スプールの片付けなど）で
  待つ印が消えても、実行しない側に倒れます。置き忘れた呼ぶ側に理由が伝わるよう、無いときは
  応答します（待つ者が居なければ誰も読まない応答が残りますが、次にロックを取ったときに消えます）。
- シェルのスクリプトなど、ロックを掴み続けにくい呼ぶ側は `vw2026 call` を使います。
- 生死を `pid` で推し量らないのは `bridge.lock` と同じ理由です（`pid` は再利用される）。要求に
  期限を載せないのは、長い待ち時間で生きて待っている呼ぶ側の要求まで捨ててしまうためです。
- 呼ぶ側が強制終了されても、OS が `<id>.wait` を放すので、待つのをやめたときと同じになります。
  シグナルを受けて後始末をする必要はありません。

## 占有（セッション）

呼ぶ側の 1 つがブリッジを**占有**し、図面か Vectorworks を変える道具（種類 `write` と `app`）を
その呼ぶ側だけに実行させます。複数の呼ぶ側（別々のエージェントなど）の操作が、同じ Vectorworks の
中で混ざらないようにするためです。**種類 `write` と `app` の道具は占有の中でだけ呼べます**（誰も
占有していないときも断る）。読むだけの道具（種類 `read`）は図面を変えないので、占有している呼ぶ側の
作業と混ざらず、占有に照らさずに誰にでも実行します。

- **占有の印（セッション ID）はプラグインが発行します。** 発行するのは 1 つの Vectorworks に
  つき同時に 1 つだけで、メモリだけに持ちます（ファイルに書かない）。印の綴りは [id](#id) と同じで、
  推測されにくい乱数を含みます。
- 呼ぶ側は `session_start` で印を受け取り、以後の要求に `session` として載せ、`session_end` で
  終えます（[予約された道具](#予約された道具)）。

プラグインは、要求を読み、待つ印を確かめ、解析したあと、実行する前に占有に照らします。

| 道具 | 占有されていない | 占有されている |
| --- | --- | --- |
| `tools`・種類 `read`（`ping` を含む） | 実行する（`session` は見ない） | 実行する（`session` は見ない） |
| 表に無い道具 | `unknown_tool`（占有に照らさない） | `unknown_tool`（占有に照らさない） |
| `session_start` | 印を発行する（要求に `session` があれば `no_session`） | `occupied` |
| `session_end`・種類 `write`・`app` | `no_session` | 印が同じなら実行する。違う・無いなら `occupied` |

- 種類 `write` と `app` は、占有に照らして実行してよいときも、終了の依頼の最中なら `busy` で
  断ります（[Vectorworks が処理中](#vectorworks-が処理中)）。占有に照らすのが先です（ほかの呼ぶ側が
  占有していれば、処理中でも `occupied`）。
- 終わった占有の印を載せた種類 `read` の要求も実行します（`session` を見ない）。印が古いことは、
  次に種類 `write`・`app` か `session_end` を呼んだときに `no_session` で分かります。

- **プラグインは、占有の印の発行（`session_start`）・占有の終了（`session_end`）・`quit` による
  終了を、その応答を書けたときだけ行います。** 応答を書けない（ディスクが一杯など）と、呼ぶ側は
  結果を受け取れないのに、占有だけが残る・消える、Vectorworks が終わる、となるためです。書けな
  かった要求は、呼ぶ側からは「実行されたかもしれない」に見えます（占有は変わらず、Vectorworks も
  終了していない）。
- **占有を解くのは `session_end` と Vectorworks の終了だけです。** 期限やタイマーでは解きません
  （長く使っている占有を奪わないため）。終え忘れた占有は、Vectorworks を起動し直すまで続きます。
- `session_start` の応答が呼ぶ側に届かなかったとき（[待つのをやめる](#待つのをやめる)で「実行されたかもしれない」になった、応答を待つ間に強制終了された）は、
  誰も知らない印が発行されたままになり、これも起動し直すまで続きます。発行した相手を見分けられない
  ので、プラグインは区別しません。
- **図面を変える道具と `quit` は占有している呼ぶ側だけが呼べます**（誰も占有していないときも断る）。
  書き込みを占有した 1 つの呼ぶ側からだけにし、Vectorworks を終わらせる道具をほかの呼ぶ側の作業の
  最中に呼ばせないためです。占有が残って塞がったときは、利用者が GUI で Vectorworks を終了します。
- Vectorworks を起動し直すと、占有は消えます。古い印を載せた要求は `no_session` で断られるので、
  呼ぶ側は起動し直したことに気づけます。更新の手順（`quit`・`install`・`launch`）のあとは、
  占有を取り直します。
- 同じスプールを 2 つの Vectorworks が見ているとき（[ロック](#ロックbridgelock)）、印は受け付けている
  側が発行したものです。引き継いだ側は発行していないので、前の側の印は `no_session` で断られます。
- `ping` は占有されているかを返します（[道具「ping」](plugin/tools.md#ping)）。

- 占有が守るのは呼ぶ側どうしの混ざりだけです。利用者が GUI で図面を操作することは防ぎません
  （CLI を使っている間は GUI を操作しない前提）。どの図面に書くかは、`call` で呼ぶプラグインの
  道具が決めます（[設計「決めたこと」](design.md#決めたこと)）。

### Vectorworks が処理中

次の間は、要求を置いたままにせず `busy` で断ります（実行しない）。呼ぶ側を待たせ切らずに理由を
伝え、呼び直すかを呼ぶ側に任せるためです（[設計「CLI はプリミティブに保つ」](design.md#cli-はプリミティブに保つ)）。
理由は `error` に書きます。

| 場面 | 断る要求 | 理由 |
| --- | --- | --- |
| 終了の依頼の最中（`quit` の保存の確認を開いている） | 種類 `write`・`app` | 保存しようとしている図面を書き換えない。終了の依頼を重ねない（この判定を残すかは段 6 の前に決める。[構成「Vectorworks が処理中」](plugin/architecture.md#vectorworks-が処理中)） |
| 受け付けの入れ子（道具の中で Vectorworks がイベントを回し、刻みがまた届いた） | すべて（`tools`・`ping` も） | 受け付けの途中の状態（占有の印など）を取り合わない。道具の SDK 呼び出しの途中で SDK を呼ばない |

- 受け付けの入れ子では、要求を解析せずに断ります。外の回がすでに並べていた要求も断ります（外の回は、
  取り出せなかった要求を飛ばす）。
- 占有の始めと終わり（`session_start`・`session_end`）は、終了の依頼の最中も応えます（図面にも
  Vectorworks にも働かない）。
- undo の記録が開いているかは見ません。種類 `write` の道具は自分で記録を開いて閉じるので、ほかの
  記録に混ざりません（[ブリッジ「道具の表」](plugin/bridge.md#道具の表)）。
- 判定の置き場所と根拠は[構成「Vectorworks が処理中」](plugin/architecture.md#vectorworks-が処理中)にあります。

## 要求（`<id>.req.json`）

```json
{"tool":"layers","args":{"include_sheets":false}}
{"tool":"layers","args":{},"session":"1760000000000000000-0a1b2c3d"}
```

- `tool` は空でない文字列で、必須です（`null`・空の文字列は無いのと同じで `invalid_request`）。
- `args` はオブジェクト。省略できるフィールドで、省略・`null` は既定値の `{}` として扱います。
  オブジェクト以外（配列・文字列など）は「読めない要求」として `invalid_request` で応答されます
  （[互換性](#互換性)の「未知の値」）。
- `session` は[占有](#占有セッション)の印（文字列）。占有していない呼ぶ側は省きます。`null` と
  空の文字列は省略と同じに扱います。
- 1 件の上限は **1 MiB**。超えるものは「読めない要求」として `invalid_request` で応答されます。
- 入れ子（オブジェクトと配列）の深さの上限は **64**（要求の外側のオブジェクトを 1 と数える）。
  超えるものも `invalid_request` で応答されます。深い入れ子で解析がスタックを溢れさせ、
  Vectorworks ごと落ちて利用者の未保存の作業が失われないための関門で、プラグインは深さが上限を
  超えた時点で解析をやめます。
- 知らないトップレベルのキーは無視されます（[互換性](#互換性)）。キーは大文字と小文字を区別して
  照合します（`ARGS` は `args` ではなく、知らないキーとして無視される）。
- 要求は UTF-8 の JSON です。読み方は Go の `encoding/json` に合わせます（`vw2026` が送る要求を
  プラグインが同じ範囲で受け付けるように）。
  - 文字列の中の不正な UTF-8 と、対にならないサロゲートの `\u` エスケープは、U+FFFD に置き換えて
    読みます（読めない要求とはしない）。
  - オブジェクトに同じキーが重なれば、後のものを使います。
  - BOM・コメント・末尾のカンマ・`NaN` など、JSON の文法に無いものは読めない要求です。
- 受け付ける要求と断る要求の見本は[通信規則の見本](fixtures.md)にあります。

## 応答（`<id>.res.json`）

```json
{"ok":true,"result":{…}}
{"ok":false,"code":"unknown_tool","error":"知らない道具です: nope"}
```

- 失敗の応答は、機械が読む種別 `code` と、人向けの理由 `error` を持ちます。`code` の綴りは
  次に固定します（値を足すのは版を上げる変更）。呼ぶ側は `code` で分岐し、`error` の文言で
  分岐しません。

  | `code` | 意味 |
  | --- | --- |
  | `invalid_request` | 要求が読めない（JSON として壊れている・大きさか入れ子の深さが上限を超える・`tool` が無い・`tool`・`args`・`session` の型が違う） |
  | `unknown_tool` | 知らない道具 |
  | `invalid_args` | 道具の引数が誤っている（知らない引数・型や値の誤り・必須の欠け） |
  | `no_wait` | 待つ印（`<id>.wait`）が無いので実行しなかった |
  | `busy` | Vectorworks かプラグインが処理中（終了の依頼の最中・ほかの要求を処理している最中）なので実行しなかった（[Vectorworks が処理中](#vectorworks-が処理中)） |
  | `occupied` | ほかの呼ぶ側が[占有](#占有セッション)しているので実行しなかった |
  | `no_session` | 要求の `session` がいまの占有の印ではない（その占有は終わった・Vectorworks を起動し直した）、または占有の中でしか呼べない道具（`session_end`・種類 `write`・`app`）を占有せずに呼んだので実行しなかった |
  | `internal` | そのほか（道具の中の例外・図面が開かれていないなど） |

- 失敗の応答は、道具が詳細を返すときだけ `detail`（JSON のオブジェクト）を持ちます。呼ぶ側が
  失敗の原因を機械的に読むための、道具ごとの内容です（例: `quit` が開いている図面の一覧を返す。
  [道具「quit」](plugin/tools.md#quit)）。`detail` を持つのは道具が返した失敗（`invalid_args`・`internal`）だけで、
  通信規則が付ける失敗（`busy` など）は持ちません。**省略できるフィールドを足す互換の変更**なので版は
  上げません（[互換性](#互換性)。知らない読み手は無視する。実装は[実装の順序](plugin/plan.md)の段 4 の共通部の変更で、`src/core`・`spool`・見本と同時に入れる）。形は道具ごとに決め、通信規則は中身を
  解釈しません。

  `code` は通信規則として共通に決まる種別だけに限ります。図面が開かれていないことのように、道具に
  よって失敗になるかが違う理由は `internal` とし、`error` で説明します（道具ごとの解釈を通信規則に
  持ち込まない）。

  呼ぶ側が[待つ印](#待つ印idwait)を放していて実行しなかった要求には、応答しません。
- 呼ぶ側は応答を読んだら消します。

### 待つのをやめる

待つのを諦めた呼ぶ側は、**`<id>.wait` を放して消してから**、要求を消します。消せたかどうかで、
要求が実行されうるかが分かれます。

| 要求を消せたか | 意味 | `vw2026 call` |
| --- | --- | --- |
| 消せた | 取り出されていないので、実行されない。誰も待たない要求も応答も残らない | 「実行されない」タイムアウトの終了コード（Vectorworks が止まっていれば「ブリッジが動いていない」） |
| 消せない（無い・Windows でプラグインが開いている） | プラグインが受け取った。やめる前に受け取っていれば実行される | 短い猶予（`vw2026` は 5 秒）だけ応答を待ち、届けば受け取る。届かなければ「実行されたかもしれない」の終了コード |

- 待つ印を先にやめるのは、要求を先に消そうとすると、消す前にプラグインが要求を取り出して
  待つ印を試し、実行してしまうことがあるためです。待つ印を先にやめれば、要求を消す前に取り出され
  ても実行されません。
- 待つ印だけでも実行は防げますが、要求を消すことで「実行されない」を確かめ、誰も読まない
  `no_wait` の応答も残しません。
- 応答は受け付けの同じ回の中で書かれ、受け付け 1 回の中で数秒を超える道具は持たない
  （[予約された道具](#予約された道具)）ので、猶予は短くて足ります。
- `busy`・`occupied`・`no_session` も「実行しなかった」を意味します（道具の失敗ではない）。
- **`no_wait` の応答は「実行しなかった」を意味します。** 猶予の間（やめたあとにプラグインが
  受け取った）や、待つ印が想定外に消えたときに届きます。`vw2026 call` は道具の失敗ではなく、
  タイムアウトと同じ「実行されない」終了コードで扱います（終了コードの番号は `vw2026 --help`）。
- 呼ぶ側が強制終了されたときに残った要求は、プラグインが取り出したとき（実行せずに捨てる）か、
  次にロックを取ったときに消えます。待つ印を消せなかったとき（Windows でプラグインがちょうど開いている）も、放してあるので
  実行されず、プラグインかロックを取ったときの掃除が消します。猶予のあとに残った応答も、次に
  ロックを取ったときに消えます。

## プラグイン側の義務

- **要求は読んでから消し、消せたもののうち[呼ぶ側が待っている](#待つ印idwait)ものだけを実行します。** 読めなかった（無くなっていた）・
  消せなかった要求は黙って飛ばします（応答しない）。無くなっていたのはスプールが片付けられた
  ときなど、消せなかったのはウイルス対策ソフトなどが一時的に掴んでいるときで、後者は次の回に
  やり直せば済みます（消さずに実行すると、次の回にまた実行してしまう）。
- 読めたが JSON として壊れている要求には、ファイル名の id が正しければ `invalid_request` で
  応答します（呼ぶ側を待たせ切らない）。
- 1 回の受け付けで処理するのは、**回の始めに並べた要求だけ**です。その後に置かれた要求は次の回に
  回します（置かれ続けても 1 回が終わるように）。件数と時間の上限は設けません（CLI を使っている
  間は GUI を操作しない前提で、溜まった要求は早く片付ける方を採る）。取り出した要求には同じ回の
  中で応えます（[待つのをやめる](#待つのをやめる)の猶予が短くて足りるように）。受け付けの入れ子が
  起きたときは、回の始めに並べた要求も入れ子の回が `busy` で断ります（[Vectorworks が処理中](#vectorworks-が処理中)）。
- `session_start`・`session_end` と種類 `write`・`app` の要求は、実行する前に[占有](#占有セッション)に
  照らし、[Vectorworks が処理中](#vectorworks-が処理中)なら断ります。
- 道具 1 つの失敗（例外を含む）で橋を止めません。例外は `internal` で応答します。道具の外
  （占有の印を作るときなど）で、要求 1 件の処理の中で起きた例外も同じです（要求は消してあるので、
  応えなければ呼ぶ側は「実行されたかもしれない」で終わる）。
- 開くファイル（`bridge.lock`・`<id>.wait`・要求・応答）を子プロセスに受け継がせません
  （[ロック](#ロックbridgelock)）。
- **スプールのファイルを開いて待ちません。** 通常のファイルでないもの（FIFO・デバイス・名前付き
  パイプなど）を置かれても受け付けが止まらないよう、開くのは通常のファイルだけで、リンクは
  たどりません（POSIX は `O_NONBLOCK` と `O_NOFOLLOW`、Windows は `FILE_FLAG_OPEN_REPARSE_POINT` で
  開き、reparse point（リンク・AF_UNIX のソケット・WSL の FIFO とデバイスのほか、OneDrive などの
  クラウドのファイルも）とディスクのファイルでないものを断る。開いてから断るのでは、リンクの先の
  デバイスやパイプを開いてしまう。中身がローカルにないもの（読むと取り寄せる）も、取り寄せを
  待って止まらないように断る）。Windows は `\\?\` を付けて開きます（[id](#id)）。
  - 通常のファイルでない・中身がローカルにない要求は読めない要求（黙って飛ばす）、待つ印は無い
    待つ印（`no_wait`）として扱います。`bridge.lock` は 1 度だけ消して作り直し（クラウドの
    ファイルなら、消すときに同期のサービスを待つことがある）、それでも断られたらロックを取れない
    （受け付けの状態は `error`）とします。
  - スプールは利用者のホーム（Windows は `%LOCALAPPDATA%`）の下に置くので、同期・WOF の圧縮・
    重複除去・オフラインファイル・HSM の対象になることは想定しません。そうなると、作り直した
    `bridge.lock` も断られるので、呼ぶ側からは止まっている（`vw2026` は not running）と
    見えます。スプールをそれらの対象から外し、Vectorworks を起動し直せば直ります。

## 予約された道具

| 道具 | 結果 |
| --- | --- |
| `tools` | `{"protocol":5,"tools":[{"name":…,"description":…,"inputSchema":{…},"kind":…}]}`。`inputSchema` は JSON Schema。`kind` は `read` / `write` / `app` の 3 つに限る（`app` は Vectorworks そのものに働く道具。図面を変えるか・Vectorworks を終わらせるかを呼ぶ側が判定できるように）。図面を変えるかが分からない道具は `write` とする |
| `session_start` | `{"session":"<印>"}`。[占有](#占有セッション)を始める |
| `session_end` | `{"ended":true}`。占有を終える（要求に `session` が要る） |
| `ping` | `{"version":…,"branch":…,"protocol":5,"pid":…,"session":…,…}`。プラグインの版（短い sha）・作ったブランチ・通信規則の版・受け付けている Vectorworks のプロセス ID。ほかのフィールドは[道具「ping」](plugin/tools.md#ping) |

`tools` の結果に載るのは道具の表の道具です。予約された道具のうち `ping` は表に載るので含まれ、
`tools`・`session_start`・`session_end` は通信規則そのものが受け持つ道具なので含まれません。

道具の名前は `[a-z0-9_]+(\.[a-z0-9_]+)*`。プラグインが自分で持つ道具は接頭辞なし
（`ping` / `layers` …）、ほかのプラグインの機能を呼ぶ道具は `<提供者>.<名前>` にする予定です
（[設計「他のプラグインの道具」](design.md#他のプラグインの道具)。呼び出しの形は未決）。

長く走る道具（受け付け 1 回の中で数秒を超える道具）は今は持ちません。足すときは、その間も
呼ぶ側が待ち続けられる手段を決め、版を上げます。

## 版

**通信規則の版は実行時に照合しません。** 版はこの文書と `tools` / `ping` の結果に載る表示だけです。

- CLI とプラグインは同じ zip から同時に入り、更新は Vectorworks の終了後にしか行わない
  （[インストール](plugin/install-and-update.md#インストールと更新vw2026-install)）ので、動いているプラグインと
  入っている CLI は同じビルドです。
- 食い違うのは、手でビルドした CLI を使ったとき・`install` が CLI の入れ替えだけに
  失敗したときなどに限られます。気づく手掛かりは `vw2026 version` と `call ping` の
  `protocol` で、照合のための印や終了コードは持ちません。
- 通信規則を守る任意のプログラムも、合わせたい版があれば `tools` か `ping` の `protocol` を見ます。

### 互換性

通信規則は `vw2026` のほか、通信規則を守る任意のプログラムや将来のほかのプラグインにも公開します。
変更のたびに版を上げずに済むよう、読み手と書き手は次に従います。

- **読み手は、要求と応答の知らないフィールドを無視します**（must-ignore）。プラグインが要求の
  知らないトップレベルのキーを受け取ったときも無視します。
- **省略できるフィールドを足すことは互換の変更**とし、版を上げません。
- **省略できるものには既定値を設けます。** 通信規則のフィールド（例: `args` は `{}`）も道具の
  引数（[道具](plugin/tools.md)の表の「既定」）も同じです。足すフィールドの既定値は、足す前の
  振る舞いと同じにします（省いた読み手・書き手の振る舞いが変わらないように）。
- 次のときだけ版を上げます: フィールドの意味を変える・必須のフィールドを足す・決まった綴りの
  値（`code`・`kind` など）を足す・ファイルの名前や置き方を変える。
- **例外として、まだどの実装も出していない振る舞いの変更は版を上げず、いまの版に含めて
  [版の履歴](#版の履歴)に書きます。** 版は、出した実装どうしが食い違わないための表示で、
  出していない振る舞いには合わせる相手が居ないためです（例: 版 5 の `args` の扱い。プラグインは
  未実装で、`vw2026` はオブジェクト以外を送らない）。
- 無視するのは**通信規則の封筒（要求の `tool`・`args`・`session` と応答の `ok`・`code`・`error`・`result` の並び）
  の知らないフィールド**だけです。**知っているフィールドの未知の値**（例: 知らない `code`・
  `kind`、型の違う `args`）と、**道具の知らない引数**（`args` の中）はエラーとして扱い、
  既定値に読み替えません。`args` の中は道具ごとの約束で、
  知らない引数を黙って無視すると、呼ぶ側の綴りの誤りが気づかれないまま図面に効くためです。
- `vw2026 call` は、失敗の応答の `code` が無い・知らない値なら、道具の失敗では
  なく壊れた応答として、汎用の失敗の終了コードで終わります。
