# SDK の調査（待っているもの）

**SDK の挙動が分からないまま実装に入らない**のがこのリポジトリの決めごとです。調べるのは
[SDK リファレンス](https://github.com/min-nano/vectorworks-developer-sdk-reference)の側で、
issue を立てて `Findings/` に反映されてから、それを根拠に実装します。待つ間は SDK に依らない
作業（作法・CLI・殻と本体の移植）を進めます。

## 1. プラグイン間で道具を登録する仕組み

[設計「他のプラグインの道具」](design.md#他のプラグインの道具)のため。ほかのプラグイン
（構造設計支援など）が、このプラグインへ道具（名前・説明・引数の形・実行する関数）を
実行時に登録し、このプラグインがブリッジの要求をその関数へ取り次ぐ。

SDK リファレンスに立てる issue の文案:

> **プラグインモジュール間の呼び出し・登録の手段**
>
> 別々の `.vwlibrary` / `.vlb` 間で、一方が他方へ関数（コールバック）を登録し、のちに
> 呼び出してもらう手段を知りたい。
>
> - SDK に、ほかのプラグインモジュールを見つけて呼び出す API はあるか
>   （例: `CallPluginLibrary` 系、VectorScript のライブラリ関数の登録、拡張機能の
>   インタフェースを GUID で問い合わせる仕組み など）。それぞれの宣言と、実機での挙動。
> - プラグインモジュールの読み込み順は決まっているか。登録する側が先に読み込まれたとき、
>   受ける側が後から現れたことを知る手段はあるか。
> - 受ける側・登録する側のどちらかがアンロードされうるか（コンパイル済みプラグインは
>   起動時にしか読み込まれないが、ホットリロードで本体だけを差し替える作りの場合、
>   登録した関数のアドレスが無効になる時機をどう知るか）。
> - 上が無い場合、同じプロセス内の C の ABI（`dlsym` / `GetProcAddress` で互いの殻の
>   公開関数を引く）で済ませてよいか。macOS のバンドル・署名・Windows の DLL 探索で
>   困ることはあるか。

## 2. 汎用の実行口（のちの検討）

[設計「進め方」](design.md#進め方)の 6（書く道具）を汎用にするかの判断材料。

- プラグインから Vectorworks 内蔵の Python／VectorScript を、文字列で渡して実行できるか。
  結果や出力を受け取れるか。
- メニューコマンドを名前（ユニバーサル名）で起動できるか。
- Vectorworks 自身の外部からの受け口（macOS の Apple Events、起動引数でのスクリプト実行など）が
  あるか。
